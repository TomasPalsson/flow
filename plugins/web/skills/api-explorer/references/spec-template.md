## Tier 2: Endpoint Details

### Authentication Flow

**CRITICAL — Must complete before any authenticated calls.**

1. `POST /api/auth/login`
   ```
   Content-Type: application/json
   Body: {"email": "...", "password": "..."}
   Response: {"access_token": "eyJ...", "refresh_token": "...", "expires_in": 3600}
   ```

2. Use token in all subsequent requests:
   ```
   Authorization: Bearer {access_token}
   ```

3. Token refresh (when you receive 401):
   ```
   POST /api/auth/refresh
   Body: {"refresh_token": "..."}
   Response: {"access_token": "eyJ...", "expires_in": 3600}
   ```

**Do NOT retry on 403** — this indicates insufficient permissions, not token expiry.

### Pagination Pattern

```
Request: GET /api/v2/users?limit=20&cursor={next_cursor}
  - limit: int, max 100, default 20
  - cursor: string, omit for first page

Response:
{
  "data": [...],
  "pagination": {
    "has_more": true,
    "next_cursor": "abc123"
  }
}

Iteration: repeat until has_more is false or next_cursor is null.
Boundary: requesting beyond last page returns {"data": [], "pagination": {"has_more": false}}.
```

### Error Response Envelope

```json
{
  "error": {
    "code": "validation_error",
    "message": "Human-readable description",
    "details": [{"field": "email", "message": "is required"}]
  }
}
```

| HTTP Status | Meaning | Agent Action |
|-------------|---------|-------------|
| 400 | Validation error | Check details[].field for specific errors |
| 401 | Token expired or missing | Refresh token, retry once |
| 403 | Insufficient permissions | Do NOT refresh token; escalate |
| 404 | Resource not found | Check ID validity |
| 429 | Rate limited | Wait for Retry-After header seconds |
| 500 | Server error | Retry with exponential backoff, max 3 |

### [Endpoint Name]: GET /api/v2/users

**Request:**
```
GET /api/v2/users?limit=20&status=active&sort=created_at
Authorization: Bearer {token}
```

| Param | Type | Required | Description |
|-------|------|----------|-------------|
| limit | int | No | Max 100, default 20 |
| cursor | string | No | Omit for first page |
| status | enum | No | `active`, `inactive`, `archived` |
| sort | string | No | `created_at`, `name`, `-created_at` (prefix `-` for desc) |

**Response (200):**
```json
{
  "data": [
    {
      "id": "f47ac10b-...",
      "email": "user@example.com",
      "name": "Full Name",
      "status": "active",
      "created_at": "2024-01-15T10:30:00Z",
      "org_id": "org_abc123"
    }
  ],
  "pagination": {"has_more": true, "next_cursor": "..."}

## Tier 3: Procedural Workflows

### Initialization Sequence (MUST complete from cold start)

```
1. GET /api/config → returns {api_base, feature_flags}
2. POST /api/auth/login → returns {access_token, refresh_token}
3. GET /api/me → returns user profile + permissions (cached for session)
```

All subsequent requests depend on this sequence. Skipping step 3 may cause endpoints to return guest-mode data silently (no error, just incomplete data).

### [Workflow Name]: Create and Configure a Project

```
1. POST /api/v2/projects — Body: {name, org_id}
   Returns: {id, name, status: "draft"}

2. PUT /api/v2/projects/:id/settings — Body: {visibility, default_branch}
   Returns: updated project

3. POST /api/v2/projects/:id/activate — Body: {}
   Returns: {status: "active"}
   NOTE: Cannot activate without completing step 2 first (returns 422)
```

## Template Usage Notes

- **Delete sections that don't apply** — if the API has no WebSocket endpoints, remove WebSocket sections
- **Tier 1 should be self-contained** — a consuming agent reading only Tier 1 should know every endpoint name, method, and whether it needs auth
- **Auth flow is always Tier 2** — it's critical detail but not needed in the discovery index
- **One curl example per endpoint** — worth more than verbose schema descriptions
- **Mark inferred vs confirmed** — if you couldn't verify something, note it: "(inferred from single observation, not verified)"
