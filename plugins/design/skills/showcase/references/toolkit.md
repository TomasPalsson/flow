# Showcase Toolkit — HTML Mockup Patterns

Complete reference for building in-context component mockups. **Read this before writing any HTML.**

---

## CDN Libraries

| Library | CDN URL | When to use |
|---------|---------|-------------|
| Google Fonts | `https://fonts.googleapis.com/css2?family=...` | Always — match the project's font |
| Prism.js | `https://cdnjs.cloudflare.com/ajax/libs/prism/1.29.0/prism.min.js` | Only if the component shows code |
| Prism Tomorrow | `https://cdnjs.cloudflare.com/ajax/libs/prism/1.29.0/themes/prism-tomorrow.min.css` | Dark code theme |

**Skip Tailwind CDN** — it compiles in-browser, causes FOUC, and adds a large script. 150-200 lines of hand-written CSS with custom properties is smaller, faster, and readable in devtools.

**Skip animation libraries** — CSS `transition` and `@keyframes` handle everything a mockup needs.

**Never base64-encode fonts** — 10-32x slower CSS parsing on mobile. CDN requests are faster and cacheable.

        <div class="existing-content">
          <!-- 2-3 representative cards/rows from the current page -->
        </div>

        <!-- NEW COMPONENT (full opacity, spotlighted) -->
        <div class="new-component" data-state="default">
          <!-- The proposed component goes here -->
        </div>

        <!-- More existing content (reduced opacity) -->
        <div class="existing-content">
          <!-- More context below -->
        </div>
      </main>
    </div>
  </div>

  <!-- ANNOTATION OVERLAY (hidden by default) -->
  <div class="annotations hidden">
    <!-- Annotation badges and callouts outside the page shell -->
  </div>

  <footer class="mockup-footer">
    <p>Mockup preview — Generated by Claude · <time>[Date]</time></p>
  </footer>

  <script>/* All scripts inline — see JS section below */</script>
</body>
</html>

## JavaScript Patterns

```javascript
// State switcher
document.querySelectorAll('.state-btn').forEach(btn => {
  btn.addEventListener('click', () => {
    document.querySelectorAll('.state-btn').forEach(b => b.classList.remove('active'));
    btn.classList.add('active');
    document.querySelector('.new-component').setAttribute('data-state', btn.dataset.state);
  });
});

// Theme toggle (only include if project has dark mode)
document.getElementById('theme-toggle')?.addEventListener('click', () => {
  const html = document.documentElement;
  const next = html.getAttribute('data-theme') === 'dark' ? 'light' : 'dark';
  html.setAttribute('data-theme', next);
});

// Annotations toggle
document.getElementById('annotations-toggle')?.addEventListener('click', () => {
  document.querySelector('.annotations')?.classList.toggle('hidden');
});
```

## Variation Switcher (default pattern — 2-4 design options)

Render each variation as a sibling in the same component slot. Show one at a time via a `data-variation-active` attribute on the wrapper.

```html
<!-- Switcher control (place above the component, inside main but outside shell chrome) -->
<div class="variation-switcher" role="tablist" aria-label="Design variations">
  <button class="variation-btn active" data-variation="minimal" role="tab">
    <span class="variation-name">Minimal</span>
    <span class="variation-desc">Flat, bordered, low density</span>
  </button>
  <button class="variation-btn" data-variation="structured" role="tab">
    <span class="variation-name">Structured</span>
    <span class="variation-desc">Grouped sections, clear hierarchy</span>
  </button>
  <button class="variation-btn" data-variation="dense" role="tab">
    <span class="variation-name">Dense</span>
    <span class="variation-desc">Inline fields, compact layout</span>
  </button>
</div>

<!-- Component slot with all variations -->
<div class="new-component" data-variation-active="minimal">
  <div class="variation" data-variation="minimal">
    <!-- Minimal variation HTML -->
  </div>
  <div class="variation" data-variation="structured">
    <!-- Structured variation HTML -->
  </div>
  <div class="variation" data-variation="dense">
    <!-- Dense variation HTML -->
  </div>
</div>
```

```javascript
// Variation switcher
document.querySelectorAll('.variation-btn').forEach(btn => {
  btn.addEventListener('click', () => {
    document.querySelectorAll('.variation-btn').forEach(b => b.classList.remove('active'));
    btn.classList.add('active');
    document.querySelector('.new-component').setAttribute('data-variation-active', btn.dataset.variation);
  });
});

// Keyboard navigation (arrow keys cycle through variations — reviewers compare faster this way)
document.querySelector('.variation-switcher')?.addEventListener('keydown', (e) => {
  if (e.key !== 'ArrowLeft' && e.key !== 'ArrowRight') return;
  const buttons = [...document.querySelectorAll('.variation-btn')];
  const currentIndex = buttons.findIndex(b => b.classList.contains('active'));
  const direction = e.key === 'ArrowRight' ? 1 : -1;
  const nextIndex = (currentIndex + direction + buttons.length) % buttons.length;
  buttons[nextIndex].click();
  buttons[nextIndex].focus();
});
```

**Do NOT scroll-animate between variations.** The mental A/B comparison happens in the instant of switching — any fade or slide breaks that perception and makes differences harder to see.

**Do NOT use stars or "recommended" badges on any variation.** Every variation should be presented as equally considered. The user chooses.

## Before/After Toggle (for redesigns only)

Only include when the mockup replaces an existing component.

```html
<div class="before-after-toggle">
  <button class="ba-btn active" data-view="after">Proposed</button>
  <button class="ba-btn" data-view="before">Current</button>
</div>

<div class="new-component">
  <div class="view-after"><!-- New component --></div>
  <div class="view-before" style="display:none"><!-- Old component or screenshot --></div>
</div>
```

```javascript
document.querySelectorAll('.ba-btn').forEach(btn => {
  btn.addEventListener('click', () => {
    document.querySelectorAll('.ba-btn').forEach(b => b.classList.remove('active'));
    btn.classList.add('active');
    const showAfter = btn.dataset.view === 'after';
    document.querySelector('.view-after').style.display = showAfter ? 'block' : 'none';
    document.querySelector('.view-before').style.display = showAfter ? 'none' : 'block';
  });
});
```

## Responsive Preview Controls (optional)

Include only when responsive behavior is a design question.

```html
<div class="viewport-toggle" style="display:flex;gap:4px;margin-bottom:8px;">
  <button class="vp-btn" data-width="375px">Mobile</button>
  <button class="vp-btn" data-width="768px">Tablet</button>
  <button class="vp-btn active" data-width="100%">Desktop</button>
</div>
```

```javascript
document.querySelectorAll('.vp-btn').forEach(btn => {
  btn.addEventListener('click', () => {
    document.querySelectorAll('.vp-btn').forEach(b => b.classList.remove('active'));
    btn.classList.add('active');
    document.querySelector('.app-main').style.maxWidth = btn.dataset.width;
  });
});
```

**Note:** This uses `max-width`, not an iframe. CSS `@media` queries respond to the outer viewport, not this inner width. For accurate responsive preview, use CSS container queries on the component:

```css
.new-component { container-type: inline-size; }
@container (max-width: 480px) {
  /* mobile layout rules */
}
```

## Shell Variants

### No Sidebar (content-first apps)

Remove `.app-sidebar` and change the grid:
```css
.app-layout {
  display: block; /* No grid needed */
}
.app-main {
  max-width: var(--max-width);
  margin: 0 auto;
  padding: calc(var(--spacing-base) * 2);
}
```

### No Nav (embedded widget or component library)

Remove `.app-nav` and use a minimal header:
```html
<div class="context-header">
  <span class="context-label">Preview: [Component Name]</span>
</div>
```

## Edge Cases

### Component IS the full page
When the proposed feature is an entire page, skip `.existing-content` wrappers. Use before/after toggle to show current page vs proposed page. The shell (nav + sidebar) still provides context.

### Project has no design system
Extract the rough palette and typeface from the most polished existing component. Replicate the "feel" rather than exact tokens. A 70% match is sufficient — the goal is recognizable context, not pixel parity.

### Component renders inside a modal/drawer
Wrap the component in a modal/drawer overlay and show the underlying page dimmed. The modal's relationship to the page IS the design question.

### Dark mode where project uses `prefers-color-scheme` only
Support both automatic and manual: use `@media (prefers-color-scheme: dark)` for the default, and `[data-theme="dark"]` for the toggle override.

### Monorepo / multi-app project
When the codebase contains multiple apps with different design systems (common in Nx, Turborepo, or pnpm workspace setups), identify which app the component belongs to before extracting. Extract tokens only from that app's directory tree (`apps/admin/`, `packages/dashboard/`, etc.). Do not aggregate tokens across apps — this produces chimera mockups that match no real page.
