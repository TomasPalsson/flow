# Managed platforms (Bedrock-anchored)

All figures **2026-08-13**, read off AWS docs that day. Prices and quotas move; the *shapes* below do not. Anything not traced to a doc page that day is marked **unverified** — do not paste an unverified parameter name, quota, or price into code.

## The fork that decides everything: Managed vs Customer-managed KB

AWS recommends Managed. The consequence nobody reads is one Note box on the `RetrieveAndGenerate` API page: *"This API cannot be used with managed knowledge bases. Use AgenticRetrieveStream or Retrieve with managed knowledge bases."* **Every RAG tutorial, AWS sample, and Terraform module on the internet calls `RetrieveAndGenerate`.** Adopt AWS's own default and all of it stops applying — you lose `textPromptTemplate`, `inferenceConfig.textInferenceConfig`, `orchestrationConfiguration.queryTransformationConfiguration` (QUERY_DECOMPOSITION), service-managed `sessionId` memory, and the span-anchored `citations[].generatedResponsePart.textResponsePart.span` model. Managed KB = `Retrieve` + your own generation, or `AgenticRetrieveStream`. Nothing between.

| Dimension | **Managed KB** | **Customer-managed KB** |
|---|---|---|
| Generation API | `RetrieveAndGenerate` **unavailable**; `Retrieve` or `AgenticRetrieveStream` | `Retrieve`, `RetrieveAndGenerate`, `RetrieveAndGenerateStream` |
| Retrieval config object | `managedSearchConfiguration` (has `filter`, `numberOfResults`, `rerankingConfiguration`, `rerankingModelType` ∈ `MANAGED\|CUSTOM\|NONE`) | `vectorSearchConfiguration` (adds `overrideSearchType`, `implicitFilterConfiguration`) |
| Chunking | `DEFAULT` / `FIXED_SIZE` / `NONE`. `SEMANTIC` explicitly *"not supported"*; `HIERARCHICAL` absent from the managed page (**unverified** whether it works) | `FIXED_SIZE` / `NONE` / `HIERARCHICAL` / `SEMANTIC` |
| Parsing | `SMART_PARSING` only — auto-selects per doc type incl. audio/video/scans, **$0** | default text / `BEDROCK_FOUNDATION_MODEL` / `BEDROCK_DATA_AUTOMATION`, your prompts |
| Embeddings | Managed model is **undisclosed** — no name, dims, or version. Custom = Titan Text V2, Cohere Embed English/Multilingual v3, **Cohere Embed v4**, Nova Multimodal, at **1024 dims, float32, both fields required** | Any Bedrock embedding model, any supported dims (Titan G1 1536, Titan V2 256/512/1024, binary vectors) |
| Custom embedding side-effect | **Silently disables the managed reranker, permanently** | n/a |
| Metadata operators | No `startsWith`, no `stringContains`; reserved prefix `_` (`_source_uri`, `_data_source_id`) | Full set (per-store caveats); reserved prefix `x-amz-bedrock` |
| Doc-level ACLs, 7 connectors, AgentCore Gateway/MCP | **Yes** | **No** (S3 + Custom only) |
| Storage / data sources / KBs | 10 TB raw per KB; 200 DS/KB; 10,000 KBs (adjustable) | your store's limits; **5 DS/KB**; **100 KBs**, non-adjustable |
| Query length | 10,000 chars | **1,000 chars** |
| Direct index access | None | Yes |

**The reversal:** choosing *control* costs you agentic retrieval, 5 of 7 connectors, document-level ACLs, and MCP/Gateway. The split is not managed-vs-control — it is **connectors + ACLs + agentic** vs **retrieval-quality knobs + debuggability**. No configuration gives both, and there is no migration: embedding model *type* is immutable, chunking strategy is immutable once the data source is connected, and KB type is immutable. Price all three as create-time bets. **Sleeper:** 5 data sources per customer-managed KB, non-adjustable — multi-corpus designs that assumed one data source per team hit a wall at team #6, and the only fix is more KBs (100/account, also non-adjustable). Design data-source granularity around 5, not your org chart.

## Chunking parameters, and the pre-chunk escape hatch

`ChunkingConfiguration.chunkingStrategy` (Required) ∈ `FIXED_SIZE | NONE | HIERARCHICAL | SEMANTIC` — note `DEFAULT` is **not in the API enum** but is accepted on managed KBs.

| Strategy | Fields and exact ranges |
|---|---|
| `FIXED_SIZE` | `maxTokens` **1–8192**; `overlapPercentage` **1–99** (a percentage) |
| `HIERARCHICAL` | `levelConfigurations` **exactly 2 items**; `overlapTokens` min 1 (max undocumented) — note this is an **absolute count**, different unit, same concept |
| `SEMANTIC` | `maxTokens` **1–8192**; `bufferSize` **0–1** (1 = current+prev+next sentence — you cannot widen it); `breakpointPercentileThreshold` **50–99**. Bills a foundation model at ingest |
| `NONE` | omit `fixedSizeChunkingConfiguration`; one file = one chunk |

Managed `DEFAULT` is documented precisely: **fixed-size, 300 tokens, 20% overlap** — small by 2026 standards and a plausible first thing to change (see `ingestion.md` for what the chunking evidence actually supports; the 8–9-point spread bounds your upside here). Customer-managed "default chunking" is ~300 tokens honoring sentence boundaries, overlap unstated.

Three semantics that break code: **advanced parsers silently override `maxTokens`** (*"may chunk content to optimize for best results… does not merge content across"* page/section boundaries — measure your actual chunk-size distribution after ingest, never assume the config was honored); **hierarchical retrieval returns fewer results than requested** because `numberOfResults` counts *child* chunks that get replaced by parents, so `len(results) == numberOfResults` assertions fail; **Nova multimodal ignores text chunking entirely** and chunks audio/video by duration, 1–30 s, default 5 s.

**Structure-aware chunking is not offered on either KB type.** Two escape hatches. **(a) `NONE` + one file per chunk** — costs you page-number citations (`x-amz-bedrock-kb-document-page-number` is unavailable under no-chunking) and inflates file counts against ingestion quotas.
- **(b) Custom transformation Lambda — the real one.** `vectorIngestionConfiguration.customTransformationConfiguration` with `intermediateStorage.s3Location.uri`, `transformations[].transformationFunction.transformationLambdaConfiguration.lambdaArn`, and `stepToApply: "POST_CHUNKING"`. Lambda input carries `version, knowledgeBaseId, dataSourceId, ingestionJobId, bucketName, priorTask, inputFiles[].{originalFileLocation, fileMetadata, contentBatches[].key}`; batch objects are `{"fileContents":[{"contentBody","contentType","contentMetadata"}]}`. Two modes: with `NONE` your Lambda owns boundaries; with `FIXED_SIZE` Bedrock chunks and hands them back so you can attach **chunk-level metadata**, which *"take precedence and overwrite file-level metadata"* — the cheapest way to carry section headers or ACL tags per chunk. Gotcha: web connectors pass **markdown, not HTML**, to your Lambda.
- **Unverified and decisive: whether the custom-transformation Lambda works on Managed KBs.** It is documented under general KB docs and unmentioned on the managed ingestion page. Test with a `CreateDataSource` call before designing around it — if it is customer-managed-only, Managed KB has no structure-aware chunking escape hatch at all beyond one-file-per-chunk.

## Parsing tiers

`SMART_PARSING` (managed only, $0) vs `BEDROCK_FOUNDATION_MODEL` / `BEDROCK_DATA_AUTOMATION` (customer-managed, billed per token / per page) vs default text extraction (free, *"only parses text in text files"* — AWS itself recommends against it for figures, charts, tables). FM parser families are *"Claude vision models, Nova vision models, LLama 4 vision models"* — **no model IDs are published on that page; do not hardcode one from memory.** BDA is **preview and `us-west-2` only**. Both advanced parsers cap at **1,000 files**, non-adjustable — a pilot, not a corpus — and choosing one applies it to **all** PDFs in the data source including text-only ones you now pay to parse; splitting them means more data sources, and customer-managed has 5. Extracted figures/tables land in an S3 destination set at **KB-creation time**. On Managed KBs, visual/audio/video indexing is **opt-in per modality**; if you did not enable it, your images were never indexed.

## Vector store: the cost floor decides more than the feature list

| Store | Idle floor | Hybrid | Filtering notes |
|---|---|---|---|
| **OpenSearch Serverless** | **~$350.40/mo** (2 OCU × $0.24/OCU-hr × 730; rate read from a worked example, not a rate card) — ~$175.20 with redundancy off; NextGen collections have *"no minimum OCU"* and *"scale to zero after 10 minutes of inactivity"* | Yes | Best-supported: only store with `startsWith`/`listContains`. Index **must** be `faiss` — `nmslib` breaks filtering *and* hybrid, unfixable in place. Custom fields must be `keyword` (or `text` with a `keyword` subfield) or filters fail with an unsearchable *"Rewrite first"* error |
| **Aurora pgvector** | ACU-hours (**unverified**) | Yes ("RDS") | Must pre-create metadata columns + a **GIN index** on the `jsonb` column; **must be in the same AWS account as the KB**. Post-filtering under-returns silently until you `ALTER DATABASE … SET hnsw.iterative_scan = 'relaxed_order'` and `hnsw.max_scan_tuples = 20000` (pgvector ≥0.8.0, new sessions only) |
| **S3 Vectors** | **~$0 idle**; $0.06/GB-mo, $0.20/GB PUT (128 KB min/PUT), queries $2.5/M | No | **1 KB custom metadata, 35 keys/vector**; no `startsWith`/`stringContains`; float only; deleted-vector reclaim *"can take up to a day"*. *"Best suited for infrequent query workloads"* — right for an archive, wrong for a chat product |
| **OpenSearch Managed / Neptune / Pinecone / Redis / MongoDB** | vendor or instance bill (**unverified**) | No, except MongoDB | OpenSearch Managed **must be publicly accessible** (*"domains behind a VPC are not supported"*) — usually a hard disqualifier. Neptune's vector index **can only be created at graph-creation time** |

Consequences worth internalizing: **hybrid search exists on OpenSearch Serverless, Aurora, and MongoDB only** (the API page names only OSS — doc conflict, assume the narrower claim), and it is a **binary switch** — `overrideSearchType ∈ HYBRID|SEMANTIC`, with **no alpha, no RRF k, no fusion weight anywhere** in the config. If you need to tune dense/sparse balance (`retrieval-stack.md` covers when that matters), Bedrock KB cannot and you need your own store. **PDF page numbers exist only on OpenSearch Serverless and Aurora.** Binary vectors only on OpenSearch. Below roughly 70 GB of raw data, a Managed KB at $5/GB-mo is cheaper than the OpenSearch Serverless floor *alone* — and an existing OSS log-analytics collection does **not** amortize it, because vector collections cannot share OCUs with search/time-series collections.

## Metadata filtering, and the silent empty result

Operators: `equals`, `notEquals`, `greaterThan(OrEquals)`, `lessThan(OrEquals)`, `in`/`notIn`, `listContains`, `stringContains`, `startsWith`, `andAll`/`orAll` — `RetrievalFilter` is a **union, exactly one member per object**. `andAll`/`orAll` require **min 2 array members**, cap at **5 filter types per group, 5 groups, one level of nesting**.

**`notEquals` also returns documents where the key is absent.** That is the opposite of SQL, and a tenancy filter written as `notEquals` leaks every unlabelled document. The S3 sidecar is `<sourceFileName>.<ext>.metadata.json` (full name *including* extension), same folder, **≤10 KB**; the simplified `{"metadataAttributes":{"tag":"value"}}` form is legal and equals `includeForEmbedding: false`, while the full form with `includeForEmbedding: true` concatenates `key: value\n\n` **before embedding** — a cheap relevance lever almost nobody uses. Metadata-only changes trigger an optimization that re-reads vectors and **skips the embedding model** (only if no CSV and no custom-transformation Lambda). `implicitFilterConfiguration` (LLM writes the filter; `metadataAttributes` **1–25**, `modelArn` required, Claude models only) exists **only under `vectorSearchConfiguration`** — on Managed KB, natural-language-to-filter is yours to build. **The failure mode: a bad filter returns HTTP 200 with `retrievalResults: []`. There is no "unknown filter key" error.** Diagnose in order: (1) re-run identical query with no filter; (2) read `metadata` on the unfiltered results — it echoes what is actually indexed, and a year stored as `"2018"` will never match `greaterThan: 2018`; (3) confirm the sidecar name/size and that it existed *at sync time*; (4) check operator legality for your store and KB type; (5) check `andAll` arity; (6) if ACL is on, the empty result may be the ACL filter. Hierarchical chunking, an over-tight filter, and an ACL denial produce the **same symptom**.

## Document-level ACLs — filtering, not authorization

AWS says it in a callout: *"ACL-aware filtering, not a security boundary… You must not rely on this feature as a sole access control mechanism without upstream authentication."* `userContext.userId` is an **unauthenticated string you supply**. Any design where a browser or the model can set that field (or a `filter` fragment) is horizontal privilege escalation — construct it server-side from a validated session claim, reject `filter`/`userContext` keys at your edge, and never expose `$.userContext` via AgentCore Gateway `parameterOverrides` (the Gateway *"does not populate userContext from the caller's IAM identity"*, so a prompt injection in a retrieved document could otherwise assert an identity). See `security.md` for the general ACL-aware retrieval model and why post-filtering leaks.

Mechanics that bite: **email is the only identifier** — no alias resolution, no cross-IdP mapping, and a mismatch *"fails silently and the user receives no results from that data source."* Real-time per-document verification exists on SharePoint (`ENTRA_ID_APP_ONLY`), OneDrive (`ENTRA_APP_ID`), Google Drive (`SERVICE_ACCOUNT`), Confluence (`BASIC`) — **S3 and Custom have none**, so their revocation latency equals your sync interval, and `StartIngestionJob` is capped at 0.1 RPS so "sync more often" is not available. IdP credentials cache **up to 1 hour**. Deny overrides allow; the pipeline **fails closed** (so an ACL outage looks like a recall regression); missing ACL metadata means not-ingested, not public; and **partial results are expected** — *"Bedrock Managed Knowledge Base does not backfill"*, so top-k is a ceiling, not a target. The S3 connector's `Type` must be `USER`: **no group support**, every principal is an email; per-document ACLs beat the global file and re-index only that document, while a global-file change requires reindexing the whole prefix. Web Crawler cannot be ACL-aware at all. Ingesting a permissioned repo into a **non-ACL** KB flattens its ACLs to *"anyone with `bedrock:Retrieve`"* — the classic enterprise-search leak, warned about in one line.

## Ingestion, sync, and delete propagation

Sync is incremental (content *or* metadata change → full re-parse/chunk/embed); **there is no full-resync switch** — forcing a rebuild means deleting and recreating the data source. Data-source deletion policy `DELETE` (default) or `RETAIN`; `RETAIN` is what leaves orphaned vectors behind. **Deletes are asynchronous after the API returns**: status walks `INDEXED → DELETING → DELETE_IN_PROGRESS → NOT_FOUND`. A shipped AWS sample polled immediately, saw `INDEXED`, and a Step Functions `addCatch` turned the resulting exception into `SUCCEEDED` — *"sync shows SUCCEEDED… but the target document remains indexed and continues to be referenced in chat responses."* **Poll for `NOT_FOUND`; treat `INDEXED` as retry, not error.** `PARTIALLY_INDEXED` and `METADATA_PARTIALLY_INDEXED` are success-shaped failures — alarm on them, and on `statusReason` alongside `IGNORED`. Assert on `GetIngestionJob.statistics` (`numberOfDocumentsScanned/NewDocumentsIndexed/ModifiedDocumentsIndexed/DocumentsDeleted/DocumentsFailed/DocumentsSkipped/MetadataDocumentsScanned/MetadataDocumentsModified` + `failureReasons[]`), **never on job status alone** — a job that scans zero documents completes `COMPLETE` and looks healthy. `StartIngestionJob` takes a `clientToken` with **minimum length 33** (use a UUID; short tokens 400). `COMPLETE` ≠ queryable: embeddings take *"a few minutes"* to reflect on every store **except Aurora**. AWS publishes **no throughput figure** for large syncs — derive it from a pilot. `ingestion.md` has the idempotency and orphan-chunk invariants that apply regardless of platform.

## Quotas that break projects late

| Quota | Customer-managed | Managed |
|---|---|---|
| `StartIngestionJob` | **0.1 RPS** (one per 10 s), non-adjustable — kills naive S3-event sync; debounce, or use `IngestKnowledgeBaseDocuments` (5 RPS, 25 files, 6 MB) | — (20 RPS, 10 files/request) |
| `Retrieve` | 20 RPS/account | **5 RPS per KB**, 100 RPS/account (⚠ `kb-managed-quotas` says 600 RPM / 25 RPS burst and *adjustable* — the two AWS pages conflict; check Service Quotas in your account) |
| `AgenticRetrieveStream` | n/a | **1 RPS per account** (or 60 RPM — same conflict). Either reading is ~1 QPS account-wide: **agentic retrieval is an internal-tools feature, not a hot path** |
| `Rerank` | 10 RPS | 10 RPS |
| Structural | 100 KBs, **5 DS/KB**, 1 concurrent job/KB, 50 MB/file, 100 GB/job, **1,000 files** for FM *and* BDA parsers | 10 TB/KB, 200 DS/KB, 50 jobs/KB, **30 MB extracted text per file** |

`numberOfResults` is **1–100, default 5**. Bedrock KB agent endpoints exist in **13 Regions**; FIPS in `us-east-1`/`us-west-2` only. **Cross-Region inference profiles share your data across Regions** — and current Claude models are effectively inference-profile-only, so a pinned `foundation-model/...` ARN in a parsing or GraphRAG config is both a residency landmine and a time bomb (a documented case: a parser model hit end-of-life, ingestion 404'd, and the sync *"silently succeeds"*).

## Built-in evaluation, and what it does not measure

`CreateEvaluationJob` with `applicationType: RagEvaluation`, job types **Retrieve only** and **Retrieve and generate**. Metric enums, verbatim: retrieval — `Builtin.ContextRelevance`, `Builtin.ContextCoverage`; generation — `Builtin.Correctness`, `Builtin.Completeness`, `Builtin.Helpfulness`, `Builtin.LogicalCoherence`, `Builtin.Faithfulness`, `Builtin.Harmfulness`, `Builtin.Stereotyping`, `Builtin.Refusal`. **There is no recall@k, no nDCG, no MRR** — `ContextCoverage` is LLM-judged against ground truth, not computed. Rank-aware IR metrics you compute yourself from `Retrieve` output. Ground truth is mandatory; the **JSONL field names are unverified** — get them from `aws bedrock create-evaluation-job --generate-cli-skeleton`, do not guess. The binding quota is **3 metrics per dataset** (the API's `metricNames` allows 25). Costs: algorithmic scores free, judge tokens at on-demand rates, **plus normal KB charges** — an eval over N prompts adds N × $1/1,000 in `Retrieve` fees; human tasks $0.21 each. Usefully, Evaluations accepts *"your own inference response data from an external RAG source"*, so "we're on Bedrock for evals" is **not** an argument for being on Bedrock for retrieval. Judge design, sample sizes, and significance belong to `agent-evals`; golden-set construction traps to `diagnosis.md`.

## Observability: can you see the retrieved chunks afterwards?

**No — not unless you built for it.** CloudWatch (`AWS/Bedrock/KnowledgeBases`: `Invocations`, `ClientErrors`, `ServerErrors`, `Throttles`, `TotalIterationCount`, `RawDataSize`, dimensioned by `Operation` and `KnowledgeBaseId`) gives counts. CloudTrail logs `Retrieve` as a **data event** on `AWS::Bedrock::KnowledgeBase` — off by default, billed, and an audit trail, not a content trail. Managed-KB X-Ray traces are *"emitted only for the `Retrieve` operation"* and cover latency. Ingestion `APPLICATION_LOGS` give per-document `crawl_status`/`sync_status`/`index_status` and `chunk_statistics{created,deleted,failed_to_create,failed_to_delete}` — the right tool for "why is chunk X missing", where the answer is usually a `FAILED` index status. `AgenticRetrieveStream`'s `traceEvent` is the richest retrieval telemetry Bedrock offers (planner subqueries via `attributes.actions[].retrieve.inputQuery.text`, `fullDocumentExpansion`, `retrievalResponse[]` *with chunk text*, `failures[]`, `warnings[]`) — **and it exists only in the live stream. If you do not persist it, it is gone.** The one back door: on the customer-managed `RetrieveAndGenerate` path, model-invocation logging captures the generation prompt with chunks inline — but only on the `bedrock-runtime` endpoint, so a bare `Retrieve` never appears there (**inferred from two AWS statements; verify in-account before relying on it**). Practical minimum: log `(requestId, query, chunk_ids, scores, filter, userId)` yourself on every `Retrieve`. Nothing else will, and it doubles as your eval corpus.

## Cost traps

$5.00/GB **raw** data/month (so the 10 TB cap is also a $50,000/month cap; trend `RawDataSize`) + **$1.00 per 1,000 `Retrieve` calls, unbounded in traffic** — 10M retrievals/month is $10,000/month in API fees with zero tokens included, and at 5 RPS/KB you are sharding before you hit the bill. Agentic is **$4.00/1,000 agentic calls plus $1.00/1,000 underlying `Retrieve` calls**, and it issues more than one by design: set `maxAgentIteration` explicitly and alarm on `TotalIterationCount`, or your unit cost is set by query complexity. **Pagination is billable** — each `nextToken` page is another call, so a "show more sources" UI multiplies your bill. The "$0 parsing / $0 embeddings / $0 reranking" headline covers *managed* models only: semantic chunking, the FM parser, and BDA all bill a foundation model at ingest. AgentCore Gateway adds *"standard Gateway tool invocation charges"* on top. Reranking bills **$2.00/1,000 queries** (Cohere Rerank 3.5) where a query is ≤100 documents at ≤500 tokens (the page says 512 elsewhere — budget 500), so 50 chunks of 1,000 tokens ≈ 100 documents ≈ 1 query and naive `queries × $0.002` estimates are low by ~`avg_tokens/500`. Amazon Rerank 1.0 has **no published standalone price (unverified)** and is unavailable in `us-east-1`. Neptune Analytics graphs **survive KB deletion and keep billing**. Re-embedding is a full re-ingest, not a config change: chunking is immutable, there is no re-embed-in-place, and on Managed KB new document IDs break every stored citation.

## Lock-in: what actually comes back out

**Source files yes, parsed text yes, chunks no, vectors no.** The export loop is documented and almost unknown: `ListKnowledgeBaseDocuments` (control plane, `bedrock-agent`, `maxResults` 1–1000, `nextToken`) → `GetDocumentContent` (data plane, `bedrock-agent-runtime`, `outputFormat: "EXTRACTED"`) → `presignedUrl` that **expires in 5 minutes**, so enumeration and download must interleave. Two services, two IAM namespaces; **whether `identifier.s3.uri` is the string `GetDocumentContent` accepts as `documentId` is unverified** — check on 10 documents before scripting a million. At 5 RPS/KB, 1M documents is ~55.6 hours; write it resumable. This makes Bedrock's lock-in genuinely lower than OpenAI File Search's or Vectara's: migration becomes "re-chunk and re-embed a JSON corpus", not "re-acquire and re-parse a million PDFs". **The exact JSON schema of `EXTRACTED` is unverified** — export one document and read it; whether it carries page numbers or layout decides whether your migration is cheap. Run that export once now, on 50 documents, as a smoke test. What never comes back: embeddings, chunk boundaries, chunk IDs, tokenizer, fusion weights. Store citations as `(your_doc_id, char_span)`, never as a vendor chunk identity, and keep your own canonical document store with your own stable IDs — that one rule dominates every other lock-in consideration.

## The debugging ceiling — and the hybrid escape

Bedrock is unusually good on the first rung: `Retrieve` returns a per-result **`score`**, full `content.text`, a typed `location` union across ten source types, and free-form `metadata`; `generateResponse: false` on `AgenticRetrieveStream` gives retrieval without generation. **But `score` exists only on `Retrieve`** — `RetrieveAndGenerate`'s `citations[].retrievedReferences[]` and `AgenticRetrieveStream`'s results have no score field. The moment you use the convenient endpoint you lose the number you need to debug it.

Five questions you cannot answer at any price, and they are the ones that matter:
1. **"Why was chunk X *not* retrieved?"** No API scores an arbitrary chunk against a query and no API enumerates the index. This is the single most important debugging question in RAG (`diagnosis.md`, Decision 1) and it is unanswerable on a managed index.
2. **"What are the chunk boundaries?"** Not exported — so you cannot tell whether the answer span was split across two chunks, the most common silent failure of fixed-size chunking, which is one of your only two options.
3. **"Is the embedding model the same as last week?"** No version pin on the managed model. A regression with no code change has no attributable cause; your eval suite detects *that*, never *why*.
4. **"What did hybrid fusion do?"** Weights are not exposed. `HYBRID` or `SEMANTIC`, nothing between.
5. **"Is `score` comparable across queries?"** Documented only as *"the relevance of the result to the query"* — no range, no calibration, no stability statement across model updates. Derive thresholds from your golden set and re-derive them every eval run.

**One sentence: on a managed platform you can debug *ranking* but not *indexing* — and most bad RAG is an indexing problem.** The escape, when the leverage ladder in SKILL.md bottoms out at a wall rather than a fix, is always the same shape: **keep managed ingestion, take back the rest.** Buy the parsers (`SMART_PARSING` at $0, or `GetDocumentContent` `EXTRACTED`, or Unstructured); chunk yourself; call `Retrieve` (or your own store) and do reranking and generation in your code. Two supporting primitives make this cheap: the **standalone `Rerank` API** takes ≤1,000 **inline** documents with no KB at all (note `numberOfResults` on the standalone API vs `numberOfRerankedResults`, range 1–100, inside retrieval — same concept, different names, exactly the kind of thing that gets copied wrong; `queries` is *fixed at 1 item*, so no batching), and **Bedrock Evaluations accepts external RAG data**. Always shadow production with a `Retrieve`-only path on the same queries — at $1 per 1,000 calls it is the cheapest observability you will ever buy.

## The rest of the market, and where the line falls

| Platform | Billing shape | The one thing that disqualifies it |
|---|---|---|
| **Vertex AI RAG Engine** | pricing **unverified** — no Google dollar figures in this research | *"Data residency and AXT security controls aren't supported."* GA in 4 regions. Renamed twice in a year |
| **Azure AI Search** | SU/hour or CU-hour + GB/mo; agentic retrieval priced **per token of planner reasoning** (amounts **unverified**, page renders `$-`) | Serverless preview: **1 GB per index**, no SLA, 3 regions, and *"doesn't support migration to or from other pricing tiers"* — you cannot graduate your prototype |
| **OpenAI File Search** | **$0.10/GB/day** (people misread as per-month and under-budget 30×) | Opaque index, embedding model fixed at `text-embedding-3-large` @256 dims. Genuinely good defaults: 800-token chunks/400 overlap, tunable 100–4096, and real hybrid weights (`hybrid_search.embedding_weight`/`text_weight`) that Bedrock does not expose |
| **Ragie** | $0.02–0.05/page ingest, **unlimited retrievals**, $0.002/page-mo | $250/mo per additional connector — connector count is a pricing axis |
| **Vectara** | **$100K–$500K/year**, no self-serve tier at all | Your budget. The longest-standing pure-play abandoned the low end |
| **Unstructured (parse only)** | $0.03/page, **hard cap $3,000/mo up to 1M pages** | Not a retrieval service — which is the point |

**Model two axes, never one: pages ingested (P) and retrievals served (R).** Read-heavy small corpus (20K pages, 10M retrievals/mo): Bedrock ≈ $10,000/mo in call fees and you cannot serve it from one KB anyway — Ragie or self-hosted wins, and the RPS quota loses before the price does. Write-heavy archive (5M pages, 50K retrievals/mo): Bedrock's free parsing + $5/GB-mo is genuinely strong; Ragie is $100K–250K to ingest; Unstructured + your own index is ~$15,000. Steady-state medium: it is close, and the answer is "whichever your team can operate." **Decide per layer, not per system.** Buy parsing and the reranker; own chunking policy, the query path and fusion, citation mapping, and your golden set (`retrieval-stack.md`, `diagnosis.md`). Stay on Managed KB when sustained load is **<~3 RPS per index**, you need document-level ACL filtering with an identity that maps to one email, your corpus is heterogeneous multimodal, you need SharePoint/Confluence/Drive/OneDrive connectors, and retrieval quality is not your differentiator. Roll your own when any of: consumer-facing scale; you need chunking control; retrieval regression gates in CI tighter than eval-job turnaround; a pinned embedding model for year-over-year reproducibility; query batching. The honest case *for* managed is not "easier to start" — it is incremental sync and deletion propagation, re-embedding cutovers, permission-aware retrieval, adversarial PDFs, and backpressure from poison documents. AWS itself publishes sample repos for KB sync *and* drift detection; your hand-rolled version needs an owner. Wire retrieval behind **your own MCP server**, not the vendor's Gateway binding: the connector's contract is two tools with one required argument (`retrievalQuery.text`), so `search(query) -> [{text, score, source_uri, metadata}]` from your own server makes Bedrock, pgvector, and the Gateway three implementations of one interface. Copy the Gateway's *shape* — administrator sets retrieval policy in `parameterValues`, the model supplies only the query, traces stream as MCP `notifications/message` — and be deliberate about adopting its *binding*.

## NEVER — managed-platform landmines

- **NEVER write code against `RetrieveAndGenerate` before confirming your KB type.** WHY: it is unsupported on Managed KBs and the error reads like a validation failure, not a product-tier mismatch — while every sample you copied from assumes it works.
- **NEVER treat KB type, chunking strategy, or embedding-model type as changeable.** WHY: all three are create-time immutable with no migration path, and on Managed KB a rebuild issues new document IDs that break every citation you have stored.
- **NEVER pick a custom embedding model on a Managed KB without pricing the reranker.** WHY: it silently and permanently disables the managed reranker, and 1024-dim float32 is forced, so the cost/latency levers you switched for are gone too.
- **NEVER trust an empty `retrievalResults` array to mean "no matching documents."** WHY: a bad filter key, a type mismatch, an oversized sidecar, an unsupported operator, an ACL denial, and hierarchical parent-replacement all return HTTP 200 with zero results and no error — six causes, one symptom.
- **NEVER use `notEquals` in a tenancy or permission filter.** WHY: it also matches documents where the key is *absent*, so every unlabelled document leaks.
- **NEVER accept `userContext.userId` or a filter fragment from the client, or expose `$.userContext` through Gateway `parameterOverrides`.** WHY: it is an unsigned string AWS explicitly disclaims as authorization; whoever can set it selects their own permissions, and a retrieved document carrying an injection can set it too.
- **NEVER poll document status immediately after a delete and treat `INDEXED` as terminal.** WHY: deletion is async through `DELETING → DELETE_IN_PROGRESS → NOT_FOUND`; a shipped AWS sample reported SUCCEEDED on documents that kept being retrieved.
- **NEVER build event-driven per-document sync on `StartIngestionJob`.** WHY: 0.1 RPS, account-wide, non-adjustable — one sync per 10 seconds. Debounce into a queue or use `IngestKnowledgeBaseDocuments`.
- **NEVER put `AgenticRetrieveStream` on a user-facing hot path.** WHY: ~1 RPS per *account* on either reading of the two conflicting quota pages, plus 5× the price and an iteration multiplier you only bound with `maxAgentIteration`.
- **NEVER assert `len(results) == numberOfResults`.** WHY: hierarchical chunking replaces child chunks with parents, and ACL filtering withholds documents without backfilling — top-k is a ceiling, not a target.
- **NEVER treat the managed index as your system of record.** WHY: embeddings and chunk boundaries are unexportable, so the only rebuildable path runs from your own canonical store — and the `EXTRACTED` export you would rely on has an unverified ID mapping you must test *before* you need it.
- **NEVER ship on a managed platform without your own retrieval log and eval suite.** WHY: nothing in CloudWatch, CloudTrail, or X-Ray records the retrieved chunks, the embedding model is unpinnable and undisclosed, and a silent quality drift with no code change has no other detector.
