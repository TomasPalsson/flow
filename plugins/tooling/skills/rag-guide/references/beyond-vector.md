# Beyond Vector Similarity

Four instruments, each with a narrow correct domain and a wide misuse radius. Confidence tiers as in SKILL.md: plain = primary source; "reported"/"≈" = one credible source; "unverified" = flagged as such by the research.

## 1. Aggregation questions are a category error, not a quality problem

The mechanism SKILL.md only names: **top-k retrieval is a cardinality mismatch.** "How many contracts expire in Q3?" — if k=20 and the truth is 340, the model reports something ≤20 or hedges, confidently either way. "Top 5 by revenue" needs a total order over the *complete* set; retrieval returns a similarity-ordered *sample*, and the two orderings are unrelated. "Trend since 2024" needs a gap-free series; retrieval returns whichever periods were textually salient.

**The sharpest case, and the one to escalate to stakeholders: absence.** "Which customers have NO open tickets?" Retrieval can only return things that exist; absence has no representation in an embedding space. This is provably unanswerable by any retriever, which is what ends the "just make the RAG better" loop.

### Text2SQL, honestly (Aug 2026)

| Benchmark | State | The caveat that matters more than the score |
|---|---|---|
| [BIRD](https://bird-bench.github.io) | Top test EX ≈**81.95** (AskData+GPT-4o); human baseline 92.96 | **The same system scores 67.41 without Oracle Knowledge** — ~14 points of the headline come from hand-written evidence hints nobody supplies in production. That gap is the value of curated schema docs / a semantic layer, quantified. |
| [Spider 2.0](https://spider2-sql.github.io) | Snow (547 tasks) top ≈96.70; **Lite, the same 547 examples, top ≈76.23**; DBT (68 tasks) ≈65.6 | Snow gives a live warehouse to execute against and iterate; Lite doesn't. ~20 points from **execution feedback alone**. Leaderboard entries are self-reported with no exposed contamination controls or submission dates — do not plan capacity against 96.7. |
| Production | Pinterest reported first-shot acceptance rising ~20% → "above 40%" as users learned the system | *Acceptance*, not correctness. A ~40%-first-shot, iterate-to-answer shape is what production looks like. |

**The benchmarks themselves are broken.** A CIDR 2026 paper ("Text-to-SQL Benchmarks are Broken") reports **52.8% annotation error on BIRD and 66.1% on Spider 2.0-Snow**; re-scoring five leading BIRD methods on a corrected set moved relative rankings **−3% to +31%**. BIRD's dev set was also re-cleaned in Nov 2025 — pre/post numbers are not comparable, and an earlier 2023 cleaning moved GPT-4 dev EX 46.35→49.15 with no model change. Read every number in this table as directional.

**Semantic layer vs raw text-to-SQL — the mechanism behind SKILL.md's failure-mode framing.** Generating a metric call against a governed layer is a drastically smaller output space than free SQL: joins, grain, filters and row-level security are pre-resolved, so the model *cannot* get them wrong. [dbt's reproducible benchmark](https://github.com/dbt-labs/dbt-llm-sl-bench) (Apr 2026, ACME Insurance, 15 tables): Claude Sonnet 4.6 90.0% → 98.2%, GPT-5.3-codex 84.1% → 100.0%. Two non-obvious findings inside it: **once a question is in scope, model choice barely matters** (most models hit ~100%) — so the semantic layer's only real gap is a *modeling* gap, closed here by 3 LLM-authored dbt models; and their text-to-SQL arm got the **entire schema in context**, which the authors flag as impractical, meaning the gap is understated for real 1,000–3,000-column warehouses.

- **NEVER let generated SQL execute without dry-run, cost cap, forced LIMIT, statement timeout, and a read-only role.** WHY: on per-byte billing one missing partition filter is a four-figure query, and the dominant error mode of free-form text2SQL is a query that *succeeds and returns wrong numbers* — worse than an exception because nothing surfaces it.
- **Highest-leverage artifact is not the model:** 20–50 verified question→SQL pairs retrieved as few-shot examples plus real column descriptions. This is RAG over SQL, it is cheap, and it reportedly moves accuracy more than a model upgrade. (Vanna's design is this pattern; the package is drifting — `vanna-ai/vanna` last pushed 2026-02-02. `defog-ai/sqlcoder` is dead, last push 2024-05-23.)

### The router, and the minimal architecture

Start with **one router agent choosing between a static RAG tool and a text-to-SQL tool**, hard cap on tool calls, strict stop condition. Resist adding a graph tool and a live-API tool on day one because the taxonomy has four boxes. Then:

1. **Route on capability lookup, not judgment, wherever possible.** "Does a metric named X exist in the registry?" is deterministic and free. "Does this look analytical?" is an LLM call on 100% of traffic with its own error rate.
2. **Give the router `both` and `ambiguous` branches.** "How did churn trend vs what the Q3 deck said?" needs SQL *and* text; a single-label classifier is confidently half-wrong. When both paths are cheap, just run both — cheaper than the turn spent deciding.
3. **Make the vector path able to refuse.** The dangerous outcome is not mis-routing; it is that the retrieval path *answered anyway*. An explicit "this is a counting question" beats a plausible number derived from top-k.
4. **Log the route with the answer.** A wrong route produces a fluent wrong answer, not an error — it is invisible in end-to-end quality metrics, and per-route accuracy is the only signal telling you whether to invest in the classifier or the retrievers.

## 2. GraphRAG: what the controlled study actually found

Status, Aug 2026 (GitHub API, verified): `microsoft/graphrag` v3.1.1 (2026-07-18), 35.5k stars, 47 open issues — alive, but always disclaimed as "not an officially supported Microsoft offering." The [Azure solution accelerator is archived](https://github.com/Azure-Samples/graphrag-accelerator) (2025-05-27), and its own README warned indexing "can be an expensive operation." `HKUDS/LightRAG` (38.8k stars, v1.5.6, pushed daily) has overtaken it — **the market moved toward the cheaper variant, not the more capable one.** `nano-graphrag` (last release Oct 2024) and `fast-graphrag` are effectively stale; `HippoRAG` has exactly one release — cite the idea, don't depend on the package. LazyGraphRAG: still absent from the OSS repo, [Discussion #1490](https://github.com/microsoft/graphrag/discussions/1490) open since Dec 2024.

**The single source worth citing is [arXiv:2502.11371](https://arxiv.org/abs/2502.11371) v3** (Han et al., MSU/Meta/IBM, revised 2026-03-04) — matched preprocessing, 256-token chunks for all arms, cost *and* quality reported, judge position-bias controlled. Three results that no marketing mentions:

- **Graph adds a permanent per-query token tax, not just index capex.** Retrieved input tokens per query: MultiHop-RAG 3,631 → 9,770 (2.7×); ODSum-Story 2,279 → 10,244 (4.5×) — entities + descriptions + relations + community summaries all ship into every prompt, forever. Construction time was 41× (community) to 57× (KG) over plain RAG on the identical corpus. If a comparison you're reading didn't equalize token budget, it is partly measuring context size, not architecture.
- **A graph manufactures apparent evidence, so abstention collapses.** MultiHop-RAG NULL accuracy (questions whose correct answer is "insufficient information"): 91.36 → 81.06 with a 70B reader; **96.01 → 70.43** with an 8B reader. It degrades *monotonically with extractor quality* — the GPT-4o-built graph abstains worse than the GPT-4o-mini-built one in both. Plausible mechanism (the paper reports the effect without diagnosing it, so treat as hypothesis): a richer graph always surfaces *something* related, so the reader never sees an empty context and never has a reason to abstain. Add an agentic loop on top and it compounds — NULL 80.07 → **50.50** while every other category improved.
- **On summarization — the graph's supposed home turf — plain RAG wins on reference-based metrics.** ODSum-story ROUGE-2 F1 9.81 vs 8.64; ODSum-meeting 11.09 vs 9.72. GraphRAG's advantage appears only under LLM-judge "Diversity," and reversing candidate order produced "substantially different, in some cases opposite" judgments. **RAG is preferred on Comprehensiveness once order is controlled** — the reverse of the original paper's headline metric.

The graph's genuine wins in the same tables: Temporal +33 pts (25.73 → 58.49) and Comparison +10. If your users don't ask those shapes, the graph buys nothing and costs everything.

### Cost, with the label attached

The documented anchor is **$33,000 to index one 5GB legal dataset** (early 2024, Graph Praxis "The GraphRAG Cost Cliff") — widely cited, headline verified, technical breakdown paywalled; treat as one credible source. **Everything else is derivation, and here it is transparently:** 10k docs × ~3k tokens → ~25k chunks at 1,200 tokens; extraction + 1 gleaning ≈ 50k calls, entity-description merges ≈ 15k, community reports ≈ 4k → **≈70k calls, ≈220M input / ≈48M output tokens**. Multiply by your blended rate: $1/M ≈ $270, $5/M ≈ $1,340, $15/M ≈ $4,000. Cross-check: Microsoft's own LazyGraphRAG post says vector indexing is 0.1% of full GraphRAG indexing; embedding 30M tokens is well under $1, ×1000 → order $600. Two routes agreeing within an order of magnitude is all the confidence available. **This is a derived estimate, not a measured figure.**

Then the multipliers nobody budgets: **×4 for re-indexing** (your first extraction prompt produces a garbage ontology — everything typed `ORGANIZATION`, or 400 types); wall clock, which kills more projects than dollars (70k calls at 10 concurrent × ~8s ≈ 15 hours; under enterprise TPM caps, days — a 3-day build means one experiment per week, which means you ship whatever the first run produced); and **×tenant count**, because a graph's value *is* the cross-document relationships it materializes, which is exactly the cross-tenant leak. That last one is the most common reason GraphRAG dies in B2B SaaS.

### Screening — the question that should stop most teams

Write down 30 real queries from logs. **If fewer than ~20% require chaining relationships that co-occur in no single chunk, you do not have a graph problem.** Then apply the harder filter: *can you name one query where hop 2's document shares no lexical or semantic overlap with hop 1's?* Most "multi-hop" questions are solvable by iterative/agentic retrieval because the bridge entity appears verbatim in the first passage — the agent just reads it and searches again. A graph only earns its cost when the hops span vocabulary-disjoint documents.

**The exception that flips everything: if the graph already exists, all the cost and entity-resolution arguments evaporate.** Call/import graphs from an AST, foreign keys, citation networks, org charts, BOMs, SNOMED/ICD, git history. Extraction ≈ free, precision ≈ 100%, IDs are canonical, incremental updates are trivial. Use a graph there, enthusiastically. The cost objection is specifically about **LLM-extracted graphs over unstructured text**.

### Entity resolution — the asymmetry is the whole insight

- **Under-merging** (Acme / ACME Holdings Inc. / Acme Corp stay separate) is **silent**: the graph fragments into shards, traversals dead-end, communities are incoherent. You will blame the chunker or the embedding model, because nothing errored.
- **Over-merging** (two different Acmes fuse) is **catastrophic and confident**: every answer about either entity is corrupted, stated with full confidence *and a real citation*. Strictly worse than a hallucination.

So: block first (50k entities = 1.25B pairs; block on normalized-name/phonetic/ANN neighbourhood **and** entity type), waterfall cheapest-first, and **explicitly allow the adjudicator to answer "uncertain"** — most ER prompts fail because a forced binary choice on a coin-flip is exactly how over-merging happens. Tune conservative (a fragmented graph degrades gracefully; a fused graph lies), sweep on a schedule, and **store merge provenance so merges are reversible** — without it the only fix for an over-merge is the full re-index from the cost section. Evaluate ER on its own labelled pair set; ~200 hand-labelled pairs catches a broken threshold.

Non-obvious coupling: **chunk size is an ER parameter, not just a retrieval parameter.** Bigger chunks improve within-chunk coreference and relation recall but put more entities in one extraction call, raising omission and truncation. No setting is good at both — which makes chunk-size advice ported from vanilla RAG actively misleading here.

### Anti-patterns specific to graphs

- **NEVER design a custom ontology up front.** WHY: every schema change forces re-extraction of the whole corpus, converting your largest one-time cost into a recurring one gated on stakeholder consensus. Use 5–8 fixed types plus free-text label fields.
- **NEVER raise gleanings above 1 "for recall."** WHY: each gleaning re-sends the entire prior conversation, so cost scales roughly with the square of turn count while marginal entity yield falls off fast. It is the most expensive knob and the least instrumented.
- **NEVER run community summaries on a corpus that changes daily.** WHY: Leiden partitioning is *global* — one new document can repartition communities and invalidate their LLM-written summaries up the hierarchy. Microsoft's incremental support keys change detection on document **title**, not content hash, so a silent body edit is simply never picked up. Deletion is harder still: entity descriptions are LLM *merges* of many documents, so retracting one means re-summarizing, which makes right-to-erasure a design-time question, not a patch.
- **NEVER call a kNN similarity graph over chunks a knowledge graph.** WHY: no fact extraction means no path answers, no reasoning over structure, no entity aggregation — you have a vector index with graph-shaped vocabulary and you will claim benefits you don't have. Note the deflationary read of most shipped "graph RAG": entity extraction at ingest, inverted index on entities, entity-tagged sparse retrieval merged into the rerank set. If that is your mechanism, run *that*, at ~1/1000 the cost.
- **NEVER adopt a graph database just because you built a graph.** WHY: below ~10⁶ edges at traversal depth ≤2, a recursive CTE or adjacency table in your existing Postgres is faster to operate, easier to back up, and needs no new on-call rotation.
- **NEVER replace source text with extracted artifacts.** WHY: a controlled ablation ([arXiv:2601.00821](https://arxiv.org/abs/2601.00821)) found verbatim chunks beat LLM-extracted structured artifacts by **15.9 pts on LoCoMo (43.9 vs 28.0)** and **22.0 pts on LongMemEval-S (67.4 vs 45.4)**; adding a 1-hop semantic graph did not recover the gap. The diagnosis is lossy compression at extraction time, not structure itself — a *hybrid* of verbatim text plus artifacts held accuracy. Extraction is an index, never a substitute.

## 3. Code retrieval

**Read the popular claim correctly.** Anthropic's stated reason for glob/grep is bypassing "stale indexing and complex syntax trees" ([context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)) — a *maintenance* argument, not a retrieval-quality one, and the same post recommends a **hybrid** (CLAUDE.md pre-loaded, everything else just-in-time). Meanwhile Anthropic ships official **LSP plugins** whose docs say they give Claude "more precise navigation than grep-based search" ([discover-plugins](https://code.claude.com/docs/en/discover-plugins)). Cursor — the vendor most identified with embedding indexes — now also ships "Instant Grep" and a context-isolated Explore subagent *alongside* its index ([docs](https://cursor.com/docs/context/codebase-indexing)). Convergent evolution from both directions; nobody landed on a pure position. The originating evaluation was *reportedly* self-described as "internal vibes, with some internal benchmarks" — **secondary-sourced only; no primary record was locatable, so weight it as an anecdote, not a finding** — and it concerned **code**, in a product with zero-setup/zero-sync constraints, a different objective function from maximizing recall@k. Separately, "Is Grep All You Need?" ([arXiv:2605.15184](https://arxiv.org/abs/2605.15184)) is cited constantly as code evidence and **is not** — it evaluates a 116-question LongMemEval subset (conversational memory). It is, ironically, the strongest evidence for grep over vectors on a solo dev's *markdown notes*.

**The threshold beats the method.** Sourcegraph's CodeScaleBench (1,281 scored runs, 40+ repos, 9 languages) reports adding indexed search tools gives a reward delta of **−0.080 below 400K LOC** and **+0.259 in the 400K–2M band** ([post](https://sourcegraph.com/blog/why-coding-agents-fail-large-codebases)). Vendor-authored, grep-only baseline, no CIs, no independent replication — cite the *sign flip*, not the deltas.

Why code differs, with the consequence attached:

| Mechanism | Consequence |
|---|---|
| The query often *is* an identifier (`RATE_LIMIT_WINDOW_MS`) | Lexical has recall 1.0 by construction; embeddings can only add false neighbors by pulling `getUserById` toward `fetchUserByIdentifier`. Route on query shape. |
| The vocabulary gap runs the *wrong* way | "How do we retry the payments webhook" answered by `for attempt in range(cfg.max_attempts)` inside `PaymentGatewayClient._dispatch` — no shared token. This is where dense retrieval genuinely earns its keep, and agents under-reach for it: 7,993 keyword vs 2,449 semantic vs 57 deep-search calls across all runs. |
| A change needs a **closed set**, not top-k | def + callers + subclasses + tests + mocks. Top-k returns *independent* results; find-references/call-hierarchy returns the closed set. Sourcegraph's partial-completion case: baseline modified 2 of 7 affected files. |
| Every branch is a different corpus | N branches × M worktrees × uncommitted state, and a rebase invalidates content-addressed chunks en masse. Cursor **excludes worktrees and Cloud Agents** from automatic indexing rather than solving it. |
| The unit of an answer is the whole file | Ship real bytes at the edit site (below). |

**Sync, not build, is what kills code indexes.** A full build is a one-time cost you absorb; keeping the index correct across every commit, rebase, and branch switch is permanent, and a stale index is *worse than none* because it returns confidently wrong paths and line numbers. Design consequences: content-address chunks **by blob hash, not (path, line-range)** so a branch switch is O(diff); **index the merge-base, grep the diff**; scope index shards to directories and load on entry (Anthropic's hierarchical CLAUDE.md — parents eager, children lazy on first file read — is exactly this). Planning number: Agent Retrieval Bench measured ~7.9M chunks over 392K files ≈ **20 chunks/file** ([arXiv:2607.24882](https://arxiv.org/abs/2607.24882)). No verified build-time or dollar figures for a 1M-LOC index exist on any provider — measure your own; do not quote one.

**AST chunking: the evidence is thinner than the consensus.** Two targeted arXiv sweeps found **zero clean AST-vs-fixed-size ablations for code retrieval** (verified negative result). What *is* measured: RepoMap-style tree-sitter outlines win "budgeted context yield at 8K tokens" on Agent Retrieval Bench even while Qwen3-Embedding-4B/8B win MRR/Recall@20 — i.e. **when tokens are the binding constraint, structure beats similarity**. Reasoned-from-mechanism, not measured: chunk at function boundary (it is the unit LSP/SCIP already addresses, giving you a join key), always prepend a context header (path + enclosing class + imports — tens of tokens, highest-value chunk-level intervention), split oversized functions at statement boundaries, and don't chunk files under ~1500 tokens at all.

**Specialized code embedders probably don't win.** On the independent Agent Retrieval Bench a *general* multilingual family (Qwen3-Embedding) took both metrics. CORE-Bench ([arXiv:2606.11864](https://arxiv.org/abs/2606.11864)) shows a sharp embedding-model drop moving from classic code search to agentic code retrieval — meaning published code-embedder leaderboards measure docstring→function, which is not the job you have. voyage-code-3 / codestral-embed numbers are all vendor-self-reported on vendor-selected suites and were **not verifiable** (the voyage announcement URL 404s); do not repeat a percentage for either. The bigger verified wins are elsewhere: LLM reranking of candidates **up to +42.0%**, role-aware summaries as the indexed representation **up to +40% Hit@5** at 10.4–20.9× smaller footprint, combined representations **+31.9%** ([arXiv:2607.11046](https://arxiv.org/abs/2607.11046)). And fine-tuning beats model shopping — your git history is issue→PR training data nobody else has.

- **NEVER deliver summaries or skeletons at the edit site.** WHY: pre-registered and failed ([arXiv:2607.09691](https://arxiv.org/abs/2607.09691)) — NL summaries answered **4/45** behavioral questions vs **27/45** for source, and UML skeletons for a file's remainder resolved no more issues than **deleting** that remainder (N=70, McNemar p=0.75). Retrieve on the summary; deliver the source.
- **NEVER compress or truncate retrieved code mid-span.** WHY: the same program of billed runs found aggressive compression cut successful patch application **27/40 → 15/40** by corrupting verbatim edit anchors.
- **NEVER treat token reduction as cost reduction.** WHY: across 2,848 analyzed provider-billed Claude Code runs, prompt-cache traffic was **~87% of cost**; one arm removed 38% of raw tool-output tokens and paid **6.8% more** end-to-end (95% CI +2.8% to +11.3%), with reduction↔cost correlating at **r = 0.15** ([arXiv:2607.12161](https://arxiv.org/abs/2607.12161)).
- **NEVER trust file-level Hit@k as your retrieval metric.** WHY: across 2,500 SWE-bench Verified trajectories, file choice was too coarse to separate success from failure — function selection and completion behavior do ([arXiv:2607.06184](https://arxiv.org/abs/2607.06184)). You can move file Hit@k a lot and resolve rate zero.
- **NEVER believe a single-digit-point SWE-bench delta.** WHY: temperature-0 API inference flipped **~9% of per-instance outcomes between byte-identical runs**. Most published retrieval improvements sit inside that band unless seed-replicated.
- **Calibrate your ambition:** on SWE-bench Verified, no explicit localization resolves 44.7%, predicted localization 48.9/49.1%, **gold modified-file sets 52.4%** ([arXiv:2606.30963](https://arxiv.org/abs/2606.30963)). Perfect file-level retrieval is worth **under 8 points**. If someone claims a retriever will double your resolve rate, this is the number that says it can't.
- **The most underused signal is your test suite.** Existing tests touch **96.98%** of ground-truth modified files; routing issue→test→code beat direct issue→code in 82.4% of cases, +41.57% function-level Recall@1, and dropped into Agentless resolved 17.72% more issues ([arXiv:2607.17286](https://arxiv.org/abs/2607.17286)). Test files are a hand-written, continuously-maintained, human-verified mapping from behavior descriptions to code locations, and almost nobody indexes them as one. Same logic, unquantified: git blame, merged PR review threads (they contain the rejected alternatives), ADRs, incident reports, CI failure logs, CODEOWNERS.

## 4. Agentic retrieval: what the multiplier actually is

Separate what was measured from what was estimated:

| Setting | Multiplier | Evidence tier |
|---|---|---|
| BRIGHT benchmark, agentic vs single-shot | **2.6×** tokens (52.3K vs 20.4K) — bought **5.9×** recall@1 (8.4% → 49.6%) | empirically measured |
| FinanceBench (long docs) | **7.8×** tokens (114.8K) for 92% vs 94% oracle accuracy | empirically measured — and a *bad* trade |
| Agentic vs enhanced non-agentic, general | 3.3× input / 1.9× output / **1.5× wall time** | empirically measured (arXiv:2601.07711) |
| Anthropic single agent vs chat turn / multi-agent vs chat turn | ~4× / **~15×** | vendor-stated ([post](https://www.anthropic.com/engineering/multi-agent-research-system)) |
| Adaptive/Self-RAG/CRAG ladder | ~1.5–2× / ~2–3× / ~3–5× | vendor & practitioner blogs — **directional consensus, not measured** |
| Complex query, repeated rerank rounds | 20–40× | practitioner analysis, unverified |

Marketing clusters at 10×; controlled measurement clusters at 2–4× for most workloads, with genuine 7–8× only on long-document deep-navigation corpora. The BRIGHT/FinanceBench pair is the useful contrast: the *same* multiplier logic is a bargain on a hard reasoning-retrieval corpus and a waste on one already well-structured for direct lookup. Do not extrapolate BRIGHT's 5.9× quality gain as typical — it is a hard benchmark by construction.

**Handle-then-hydrate, past the headline.** SKILL.md gives the 85%-tokens / 49%→74%-accuracy result. The design details that make it work: make **grain a parameter** (snippet vs full chunk vs full document; the `search_tools` analogue offers name / name+description / full schema), **filter before the model sees results** rather than after — a sandbox filter turns 10,000 spreadsheet rows into 5 — and **surface the remaining search/token budget to the model instead of silently truncating**, because a model that doesn't know its budget either stops early assuming it's fine or plans past a cut-off. Tool descriptions are the interface, not documentation: rewriting flawed MCP descriptions reportedly cut task completion time 40%, and the blunt test is that if a human reading the tool list can't tell which tool applies, the agent can't either. Give one well-named entry point per index rather than an omni-search tool — "an agent searching the web for context that only exists in Slack is doomed from the start."

**Stop conditions.** Hard iteration cap — 3 is typically enough, 5 rarely justified further (practitioner consensus, unverified); token budget; early exit when self-evaluation is consistently high after 2 rounds. And design pagination against the **harness's** consecutive-tool-call ceiling, not just the context budget: a flow needing 18 pages dies silently in a harness that kills tool execution at 15 calls, with the model reasoning correctly the whole time.

**When single-pass is still correct:** high-volume simple lookup (the widely-repeated "60–70% of production traffic" figure has no traceable methodology — treat as folklore, but the shape is right), latency-sensitive UX (pipeline ≈500ms–2s vs agentic 5–30s), and any workload needing a forecastable per-query cost ceiling. Also note Self-RAG proper requires a model fine-tuned to emit reflection tokens — prompting for "reflect on relevance" as a separate call is an approximation at 2–3× cost and 1.5–2× latency without the same grounding. Budget it as a heavier lift than "just add a grading step" suggests.
