# The Retrieval Stack

Everything here is conditional. The dominant failure in this layer is not picking a weak component — it is switching a technique **on globally** that was only ever validated on a narrow query slice, then never measuring the slice it hurts.

Confidence marks follow SKILL.md: unmarked = traced to primary source; "reported"/"≈" = single credible source, not reproduced; **unverified** = named as such.

## Query side — the honest ledger

| Technique | Verdict | The gate | The mechanism nobody mentions |
|---|---|---|---|
| **HyDE** | **Conditional** | Register gap between user phrasing and doc phrasing is large **and** the LLM has real parametric knowledge of the domain. Gate on low top-1 similarity or short query length. | Sharp academic-vs-practitioner split: rigorous benchmarks show it **losing to plain BM25/Contriever** on ArguAna, CQADupStack, SciDocs, TREC-Covid, FiQA, DBPedia, while a practitioner sweep found near-uniform enthusiasm and *no* clearly negative report — read that as survivorship bias, not counter-evidence. The under-credited detail: the original paper ([Gao et al., arXiv:2212.10496](https://arxiv.org/abs/2212.10496)) paired HyDE with **Contriever, an *unsupervised* contrastive encoder**, chosen because it tolerates hypothetical-doc noise. Bolting HyDE onto a supervised embedder is a different, unvalidated configuration — plausibly a chunk of the negative reports. Backfires on domains the LLM doesn't know (hallucinated specifics pull the vector off-target) and at large k (noise compounds); SQuAD-style gains are suspected contamination artifacts. Cost: +1 full LLM round-trip (reported 43–60% latency penalty on small models). |
| **Multi-query expansion** | **Conditional** | Short/ambiguous queries only. | Cost scales linearly in paraphrase count for uncertain return; paraphrases drift when the LLM misreads intent. The "+6.7% exact match from 1→2 queries" figure circulates widely but the artifact could not pin it past general query-expansion literature — **treat as unverified**. |
| **RAG-Fusion** | **Conditional — benchmark-strong, production-uncertain** | Only if you have no reranker. | Reported +19% NDCG@10 / +18% MRR on a BEIR/NFCorpus harness for the hybrid+diverse variant ([arXiv:2402.03367](https://arxiv.org/abs/2402.03367) original). But a 2026 production study (arXiv:2603.02153) found the recall gains **largely neutralized after reranking and top-k truncation** — single paper, not corroborated. The BM25+dense fusion half is doing the work; the multi-query-diversification half is what the reranker eats. |
| **Step-back prompting** | **Conditional, genuinely validated** | Multi-hop/knowledge-heavy QA where the detail obscures the concept. | Up to +27pp over base on Knowledge QA, +36% over CoT ([Zheng et al., arXiv:2310.06117](https://arxiv.org/abs/2310.06117)). Sobering detail from the same paper: on TimeQA, **45% of remaining errors were still retrieval failures** — abstraction narrows the gap, it does not close it. Underused relative to its evidence. |
| **Decomposition** | **Conditional — gate behind a classifier** | Classified multi-hop only. Should be the minority path. | Reported +0.250 context_recall as a practitioner benchmark. Decomposing a query that didn't need it produces *more* merged context, which degrades generation — you pay k-inflation for nothing. |
| **Conversational rewriting (CQR)** | **Recommended** — best-evidenced technique here | Every multi-turn system. | Rewrite **only if the turn depends on history**; pass self-contained turns through untouched. This caveat is the most-repeated finding in the CQR literature and the most-skipped in implementations. Beyond pronouns, the failure classes are ellipsis, zero anaphora, topic change, and topic *return*. One ecommerce report claims >60% of follow-ups carry unresolved context (reported, vendor). |

**No log-derived measurement of real multi-hop prevalence exists.** MultiHop-RAG and HotpotQA are synthetically constructed; tuning to them can over-index on a query shape that is rare in your traffic. Sample and annotate your own logs before building a decomposition path.

### The two unglamorous winners

1. **A curated acronym/alias/synonym lexicon.** Static dictionary, zero query-time latency, no LLM call. Palo Alto Networks and Allganize both report production wins (vendor-published, not peer-reviewed); Amazon Kendra ships thesaurus files as a first-class feature, which is the real signal that this is infrastructure rather than a hack. **The non-obvious half:** Allganize's ablation found synonym mapping in the *retriever alone* raised recall but left answer quality lagging — the generator didn't know a synonym had been applied. Inject the mapping into the generation prompt too. Do not quote the 6.7% query-expansion number as evidence for synonyms specifically; it is not that study. Classical IR is explicit that over-expansion *reduces* relevance — expand selectively, not against a giant thesaurus.
2. **A "don't retrieve" branch.** [Zero-RAG (arXiv:2511.00505)](https://arxiv.org/abs/2511.00505) formalizes it: label training queries mastered/unmastered by whether the base model already answers correctly, train a binary router on those labels. Value is dual — compute saved *and* avoiding noisy docs dragging a correct parametric answer off course. **No production %-cost-saved figure exists in any source consulted; expect savings, measure your own, cite nobody's.** Tiny-Critic RAG (arXiv, Mar 2026) reports GPT-4o-mini-level routing accuracy from a LoRA-tuned SLM at ~an order of magnitude lower latency (reported), so this no longer needs a full LLM call. One practitioner reports 1.8s→0.5s moving off an LLM router; another reports **keyword routing beating ML classification** outright — reach for rules first when the signal is a SKU pattern or a ticket ID.

**Route on query × corpus, not query alone.** RAGRouter-Bench (arXiv:2602.00296; 7,727 queries, 4 domains, 5 RAG paradigms) finds which paradigm wins is shaped by the *interaction* — the same query type calls for different routing against a different corpus. A router tuned on one corpus does not transfer.

### Self-query filters — the silent zeroing

An LLM converting "papers by Smith after 2023" into a hard metadata predicate has no signal distinguishing "field not mentioned" from "field deliberately unconstrained." Documented concretely in [LangChain.js issue #2794](https://github.com/langchain-ai/langchainjs/issues/2794): "nextjs jobs" returned **zero results** while "nextjs jobs in 2020" worked — the LLM emitted a `NO_FILTER` sentinel, and the store's exact-match predicate (`WHERE metadata @> filter`) eliminated every candidate *before* similarity ranking ran. It surfaces as "the corpus doesn't have this," not as "the filter broke."

Two distinct bugs needing separate tests: hallucinated filter **values** (wrong year, invented category) and hallucinated filter **presence** (a constraint the user never asked for). Mitigations in effort order: enumerate allowed values per field in the schema description → merge the generated filter with an explicit default rather than letting "unmentioned" mean "match nothing" → verify the store's filter translator actually supports those fields/operators → **zero-result fallback that re-runs pure semantic search with the filter dropped** (catches the value bug only) → post-filter in application code as a degrade-gracefully option that cannot zero the set, at the cost of a lower recall ceiling.

### Query shapes retrieval handles badly — three different diseases

- **Negation/contrastive** ("how to avoid X" vs "how to detect X" embed almost identically). Dense-only reported at Recall@10 ≈ 0.58–0.65 on heterogeneous enterprise corpora vs 0.72–0.85 hybrid. Fix is hybrid, not a better dense encoder.
- **Comparison/table/numeric.** Structure mismatch, reported at 73% of failures in one table-heavy study; a legal audit found dense ranking thematically-related-but-wrong articles above the requested one in 31% of failures. Damning detail: **71% of gold documents appeared in neither dense nor BM25 top-5** — these are not fusion artifacts, they need structure-aware ingestion.
- **Typos.** Subword tokenization does **not** buy dense retrievers free typo robustness — a consistent SIGIR/EMNLP line (Zhuang & Zuccon 2021–2023; Sidiropoulos & Kanoulas 2022, 2024) finds off-the-shelf dense retrievers degrade significantly on misspellings; one typo shifts the token sequence out of the clean-text training distribution. Requires typo-aware training, not a model swap. The widely-repeated claim that **BM25 is *more* brittle to typos than dense is unverified** — no head-to-head paper was found.

## Embeddings

**MTEB rank is a weak predictor of domain fit.** Gemini Embedding ranks #1 on MTEB but **#7** on the legal MLEB benchmark; Voyage 3.5 ranks #23 on MTEB but **#3** on MLEB (reported). Same inversions appear on FinMTEB, ChemTEB, SABER-Math. Build a 50–200 pair in-domain eval from your own corpus and measure Recall@k/nDCG@10 before committing — this costs an afternoon and beats any leaderboard. Also: **MTEB v2 scores are not comparable to v1**, and the English v2 and MMTEB boards are not comparable to each other; anything citing v1-scale numbers is on a retired scale.

**OpenAI has shipped no new embedding generation since `text-embedding-3` in January 2024** (pricing verified live 2026-08-13: `-small` $0.02/M, `-large` $0.13/M; **no batch-discount row exists on that page** — batch-rate claims are unverified). Every other major vendor has shipped one or two generations since. Do not default to OpenAI out of habit. Model-selection detail: `gemini-embedding-001` caps input at **2,048 tokens** and silently truncates rather than erroring; `nomic-embed-text-v2-moe` caps at **512**. Both are easy to miss against 8K–32K norms and produce silent quality loss. Licensing moves the wrong way over time — `jina-embeddings-v5-text` ships CC BY-NC 4.0, *stricter* than v4's Qwen Research License. Check every release independently.

**Instruction prefixes are a silent bug, not a config detail.** E5 (`query:`/`passage:`), Nomic (`search_query:`/`search_document:`), BGE/mxbai (a full instruction sentence). There is no error — just degraded rankings that engineers spend hours attributing to chunking or retrieval logic. Qdrant issue #9024 documents cloud-hosted E5 silently embedding raw text without prefixes. Assert the prefix in the embedding wrapper; make it impossible to omit.

**Matryoshka truncation** retains ~94–98% quality at half dimensions and ~88%+ at a quarter, then falls off a model-dependent knee below ~128 dims (one benchmark: 62.5%–80.4% retention at 64 dims across models — enormous variance). **Always L2-renormalize after manual truncation; it is not optional.** Two edge cases: some vendors *retrain* their short variants rather than truncate, so slicing their 1024-dim output does not reproduce their 256-dim output — check the docs; and non-MRL models truncated arbitrarily lose far more than MRL-trained ones at the same target, so use PCA fitted on a representative sample instead.

**Quantization.** A 33-model study found int8 costs an average of **−1.9 MTEB points for 4× storage savings** — safe as a default, no tuning. Binary averages **−6.87 but ranges −2.01 to −35.79 by model family**; the E5 family alone loses 18–36 points. There is no "binary is fine" — there is only "binary is fine *for this model*, measured." Without a rescoring pass, binary accuracy sits ≈76–91% versus ≈97–99% with a 3× oversampled float rescore, so binary is a **two-stage design** (binary coarse retrieval → float/int8 rescore), never a drop-in. It also works best above ~1024 dims and on roughly zero-centered embeddings — check both. Voyage and Cohere v4 emit `int8`/`binary` natively from the embed API; that model was trained quantization-aware, which is materially different from you quantizing floats afterward. Size it with e.g. `python scripts/rag_calc.py index --vectors 10_000_000 --dims 1536 --quant int8` — and note what that prints: **graph overhead does not shrink when you quantize**, because it is pointer data.

**Migration is a data migration, not a config change.** Two models at the *same* dimensionality are not interchangeable — dimension 347 encodes something different in each space, so a mixed-version index corrupts retrieval **silently, with no error**. Rolling deploys, async re-embed jobs, and vendors swapping the model behind a stable endpoint name all produce this. Prerequisite: keep raw source content outside the vector store forever; vectors are derived data.

| Strategy | Buys you | Costs you |
|---|---|---|
| **Blue-green / shadow index** | zero downtime, trivial rollback (repoint an alias) | 2× storage for the migration window |
| **Dual write** | new index stays fresh across a long backfill | write latency |
| **Dual index serving** | no hard cutover | ~2× serving cost + merge latency |
| **In-place update** | low storage overhead | quality degrades mid-update — and for an *embedding-model* change it is a hard NEVER (see `scale-and-ops.md`): old and new vectors are non-comparable, so there is no moment in the window when search is safe |
| **Lazy background re-embed** | defers bulk compute | mixed-state index, complicated querying |

Backfill must be checkpointed and resumable (`last_processed_id`, rate-limited against the provider). Gate the flip on a golden-query set compared old-vs-new, then ramp 5–10% of traffic rather than 100%. On Postgres: expand/contract via an `embedding_new` column, then `CREATE INDEX CONCURRENTLY` — a plain `CREATE INDEX` write-locks the table. Make reindex an explicit command, never automatic-on-config-change; a typo should not be able to trigger a full-corpus re-embed. **Every tuned similarity threshold dies with the old model** — plan to re-derive them, not port them.

## Fusion

Hybrid is a per-model empirical decision. The mechanism behind the regression SKILL.md flags: when the dense model already captures lexical signal implicitly, BM25 contributes **noise that promotes lexically-similar-but-semantically-irrelevant** documents. Reported numbers, medium confidence (exact paper unconfirmed): GTE-Qwen2 23.3→21.3 and ReasonIR 24.1→21.2 nDCG@10 *down*; BGE 13.7→17.2 and Instructor-L 14.2→19.1 *up*. Optimal weight is often heavily skewed — one physics-domain study found dense=0.9/BM25=0.1 best, meaning a naive α=0.5 lands *below* pure dense (single domain, low-medium confidence).

| Fusion method | Use when | Failure mode |
|---|---|---|
| **RRF** (`1/(rank+k)`) | score scales are incomparable or you don't trust either retriever's calibration | discards magnitude by design — a landslide win and a hair-thin win are identical; **degrades to "no better than the best single list" when the retrievers return near-disjoint sets**, since RRF rewards consensus. Check overlap@k first. |
| **Relative-score fusion** (min-max; Weaviate default since v1.24) | you've verified both score distributions are similarly shaped and want magnitude to matter | silently breaks when they aren't — and BM25 (unbounded IDF sum) vs cosine (bounded) usually aren't |
| **DBSF** (mean/stddev scaling) | same as RSF but with outlier-prone scores | community technique, implemented in Qdrant and LlamaIndex, **not Weaviate** — check availability before designing around it |

**RRF k=60 is a flat optimum from a 2009 pilot study** (MAP barely moved across k∈[20,100]); vendors default to 60 by convention-following, not re-derivation. k=30 beat it on a 2025 patent benchmark (NDCG@100 0.3475, [DAPFAM](https://arxiv.org/pdf/2506.22141)). Sweep it once; don't agonize. The circulating "OpenSearch found RRF 3.86% lower NDCG@10" figure is **unverified** — no primary post was locatable.

Hygiene first: **verify your embeddings are L2-normalized.** Unnormalized outputs make dot-product scores incomparable even *within* one result list, silently corrupting every fusion and threshold decision downstream. And never weighted-sum raw BM25 against raw cosine — normalize or use RRF.

**BM42 is retracted, not merely disappointing.** Qdrant admitted a benchmark bug that understated their own BM25 baseline; independent reproduction (Cohere) found it losing across finance/biomedical/Wikipedia; Qdrant now labels it experimental. Any source citing BM42 as a BM25 replacement without caveat is stale. Separately, if you use SPLADE-style learned sparse: **do not apply BM25 scoring to SPLADE vectors to reuse your inverted-index infra** — SPLADE's regularization optimizes for dot-product specifically, and forcing BM25 scoring measured 0.568→0.455 nDCG@10 on BEIR ([SPLADE dissection](https://arxiv.org/pdf/2605.19628)). Vector-format compatibility is not scoring-function compatibility. SPLADE's 10–300ms cost is the *query* transformer forward pass, constant regardless of corpus size — it does not get worse at scale, and does not get better on a small corpus.

## Reranking

**Cross-encoder is the default second stage for quality** — when you rerank, use one, not an LLM. Feed it 50–100 candidates: Voyage's own data shows NDCG@10 rising 81.58%→83.33% from 10→50 candidates, then a slight dropoff, with diminishing returns past 100 across all models tested. Only go wider if your own eval shows recall@100 meaningfully beats recall@50.

**Whether to rerank *every* query is a separate, latency-driven call.** Reranking is usually the largest controllable latency line in the pipeline, so once quality is acceptable the production pattern is to condition it on low first-stage confidence rather than run it unconditionally — see the ops NEVER list in [`scale-and-ops.md`](scale-and-ops.md). "Cross-encoder by default" answers *which* reranker; it does not mean *always run one*.

**The inversion that surprises people: LLM rerankers get *worse* with more candidates.** Gemini 2.0 Flash reportedly degraded 81.58%→75.97% going 10→200 candidates (low-medium confidence, exact source unconfirmed). More pool is not merely wasted spend — it is worse quality, because noise scales faster than the LLM's robustness to it. Cross-encoders do not share this behavior.

**Architecture beats parameter count.** Qwen3-Reranker-4B (causal LM, yes/no logit scoring) takes >1s/query for 77.67% Hit@1 — worse accuracy *and* 4.5× the latency of a 1.2B SequenceClassification model at 83.00% Hit@1 / 243ms; Jina reranker v3 (0.6B) hits 81.33% at 188ms (reported, single leaderboard-style source). Decoder-style pointwise LLM scoring is structurally slower than encoder-style cross-encoder classification for equal-or-better accuracy. Picking a reranker by parameter count is misleading.

**LLM listwise is a routed escalation tier, never the primary reranker.** Reported cost curves: pointwise LLM reranking ≈10× a dedicated cross-encoder for *lower* accuracy; listwise wins 0.78 vs 0.74 NDCG@10 at **9× cost and 35× latency** ([ZeroEntropy](https://zeroentropy.dev/articles/llm-as-reranker-guide/), vendor-adjacent). Production pattern is cascading: cross-encoder narrows 100→20, LLM listwise runs on those 20 and only for queries flagged as needing multi-hop reasoning. One honest counterpoint: [Fin.ai](https://fin.ai/research/using-llms-as-a-reranker-for-rag-a-practical-guide/) got pointwise LLM reranking under 1s and ~8× cheaper through aggressive engineering — and their own listwise A/B showed **no resolution-rate gain at +40% latency**.

Vendor claims and independent rankings disagree, which is the expected outcome of comparing against different baselines: Voyage claims rerank-2.5 beats Cohere 3.5 by +7.94% across 93 datasets (vendor, vs an *older* competitor model), while an independent ELO snapshot (2026-02-15) puts Zerank-2 1638, Cohere Rerank 4 Pro 1629, Voyage rerank-2.5 1544 ([Agentset](https://agentset.ai/rerankers) — GPT-judged ELO, carrying its own judge biases). Discount both; run your own 50-query comparison.

Order note: **MMR and rerankers solve different problems** (redundancy vs relevance ordering) and whether MMR belongs before or after the reranker is not settled in the literature — treat the ordering as untested for your stack. And MMR shipped with LangChain's default λ, never measured, is the actual cargo cult; MMR itself is legitimate when tuned.

## Scores are not a measurement

Similarity is a **ranking signal, not a calibrated confidence**. It is not comparable across queries, across models, or across corpora — 0.75 from all-MiniLM-L6-v2 and 0.75 from text-embedding-3-large encode different things, because embedding spaces are anisotropic and scores cluster in narrow model-specific bands. A global cutoff is close to a category error, and thresholds are among the first casualties of a model migration.

If your system makes binary decisions off a raw score (auto-approve above X, escalate below Y), it is silently miscalibrated: temperature-scaled softmax over similarities still puts >60% of predictions in the ">0.9 confidence" bin while true accuracy there is ≈85%. Fit **isotonic regression** — it beats Platt scaling under retrieval's typical class imbalance — on a held-out labeled set, **per model and per corpus**.

**Hubness** explains a symptom usually misdiagnosed as "bad embeddings": in high dimensions, points near the data centroid become nearest-neighbor to many unrelated queries, so a handful of chunks get retrieved across wildly different questions and dominate context while being weakly relevant. Retraining a better embedding model does not fix this. Distributional corrections do — CSLS local scaling, query-bank normalization, z-score standardization.

## Storage

**Do you even need a vector DB?** Below **~100K vectors**, brute-force NumPy/FAISS-flat is a legitimate default, not a hack — reported single-query latency at 128-dim float32: 10K → 25.2ms, 100K → 36.7ms, 1M → 391ms, 10M → 4.5s ([softwaredoug, Jul 2026](https://softwaredoug.com/blog/2026/07/29/just-brute-force-embeddings)); these are low-QPS numbers, so concurrency moves the line earlier. One test found ChromaDB's default HNSW returning the *exact same* top-10 as brute force at 100K. Below **~10M**, pgvector, with little debate. **10M–50M**, pgvectorscale (StreamingDiskANN); its headline "28× lower latency than Pinecone / 11.4× better than Qdrant" numbers are **Timescale benchmarking itself against named competitors, with no independent reproduction** — a hypothesis, not a fact. Above **~50M**, dedicated engines earn their operational cost, though one dissenting source puts the honest Postgres ceiling at "low tens of millions." **What actually overrides raw count**: filtering complexity, multi-tenant isolation, sub-10ms p95 at high concurrency, or vector search being the dominant workload rather than one feature. Two traps: DuckDB's own docs **recommend against persistent HNSW in production** (every checkpoint re-serializes the whole index, no incremental persisted updates) — it is only defensible in a rebuild-on-ingest pattern; sqlite-vec is still pre-1.0 with breaking storage-format changes expected.

**Filtered search is the top landmine.** HNSW's graph is built filter-blind. At Qdrant's default m=16, a benchmarked collection averaged ~21 links per node at layer 0 — filter out 96% of points and **fewer than one link per node survives on average**, so traversal strands before reaching true neighbors. Silent: near-empty or wrong results, no error. No vendor publishes a hard cardinality threshold; sources converge qualitatively on **filters leaving under ~5% of the corpus** as the danger zone. Benchmark it against your own filter-field cardinality.

- **Pre-filter** (allow-list then brute force): fast on small filtered sets, degrades linearly as they grow (Weaviate's `flatSearchCutOff` sets the switchover).
- **Post-filter**: you cannot predict survivor count; a restrictive filter risks zero results despite true matches existing. Over-fetching K/s for selectivity s buys latency for a guarantee that is still not exact.
- **Adaptive** is the real answer. [ACORN (SIGMOD 2024, arXiv:2403.04871)](https://arxiv.org/pdf/2403.04871): ACORN-γ expands neighbor lists at *build* time — claimed 2–1,000× throughput at fixed recall, at **8.8–33.1× slower builds**; ACORN-1 is the light variant, checking two-hop neighbors at *search* time only when the filter has stranded traversal. Weaviate made ACORN the **default** filter strategy in v1.34 (Nov 2025), but it requires `indexFilterable`/`indexRangeFilters` on the filtered properties to do anything. Qdrant instead runs a **per-query planner** across four paths (filterable HNSW with index-time extra edges / + ACORN-1 / payload index directly / full scan) — on a 1%-selectivity AND filter, **471 of 500 queries were routed straight to the payload index and only 29 walked the graph**. The routing decision matters more than the algorithm. Milvus and Elasticsearch are configurable but fixed, not selectivity-adaptive at runtime.
- **The filter shape that looks safe and isn't:** a payload value shared by too many points (a whale tenant, a popular category) gets no extra edges *by design*, and an AND across two independently-indexed fields gets no *combined* edges even though each field alone is indexed. Both recover with ACORN-1 explicitly enabled.

**Multi-tenancy is the same problem wearing a different hat.** Metadata filtering as your only tenant mechanism scans the whole namespace regardless of selectivity: Pinecone's own RU pricing shows a **100× delta** between querying a dedicated 1GB tenant namespace (1 RU) and filtering the same data out of a shared 100GB namespace (100 RU); a modeled 100M-vector case at 500 RU/query and 6M queries/month lands near **$72,000/month**. Partition tenant → namespace/shard as the *first* key; metadata filtering only within a tenant. Physical partitioning has its own ceilings — Qdrant Cloud caps collections at 1,000, which is why Tiered Multitenancy (v1.16.0, Nov 2025) exists to promote a hot tenant to a dedicated shard without reindexing. The whale-plus-minnows shape breaks both layers at once: no ACORN edges for the whale's value, and minnows billed for scanning the whale's data.

**HNSW memory:** OpenSearch's canonical form is `1.1 × (4×dim + 8×M)` bytes/vector. **Only M affects memory** — `efConstruction` and `efSearch` are memory-free, trading build time and query latency for recall. Practically: you can always raise `efSearch` to chase a recall problem without a capacity conversation; raising M requires one. Run `python scripts/rag_calc.py index --vectors 10_000_000 --dims 1536 --m 16` rather than reproducing the arithmetic. Starting recipe M=16 / efC=128 / efS=100; 99%+ recall needs M=32+, efC=256+, efS=400+; diminishing returns past M=16 for most workloads, but high-intrinsic-dimensionality data can need M=48–64.

**Deletes degrade the index quietly.** HNSW cannot cheaply remove a node — deleting a sparse upper-layer connector can fragment the graph — so engines tombstone instead. At ~40% deleted, ghost nodes burn traversal CPU and hold RAM for data that will never be returned, and effective recall drops under top-k filtering unless you over-fetch. FAISS's `IndexHNSWFlat` has **no `delete()` at all**. Treat tombstone ratio as a first-class monitored metric, alert above 20–30%, and schedule compaction in low-traffic windows (Weaviate exposes `cleanupIntervalSeconds`, `TOMBSTONE_DELETION_MAX_PER_CYCLE`, `TOMBSTONE_DELETION_CONCURRENCY`). On IVF-family indexes the equivalent silent decay is centroid staleness under streaming ingestion — and if recall has plateaued there, `n_probe` is a **wasted lever**; you are bit-budget-limited and need more PQ bits. A tombstone is also not an erasure: the "Ghost Vectors" paper (arXiv 2606.18497) documents ChromaDB's `delete()` updating a SQLite metadata table while leaving `index.bin` untouched, leaving embeddings reconstructible on disk — see `security.md`.

Finally: **treat VectorDBBench results as vendor-adjacent hypotheses.** It is authored by Zilliz, which ships one of the systems it benchmarks, and it reports recall and QPS separately rather than as a joint Pareto curve — which is exactly the reporting choice that makes cherry-picking easy. Many managed services also don't expose tunable HNSW parameters, so a self-run comparison can under-tune a competitor without technically falsifying anything.
