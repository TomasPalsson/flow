# Pattern forces

The adoption gate, the section list and the NEVER list live in [`code-design-doctrine.md`](code-design-doctrine.md) — **load that first**; this file adds only the by-force lookup layer on top. It is read once, by you — from `flow`, inside Phase 3 with the slice list and the Behavior Inventory in context; from `flow-spec`, before a build plan exists, against a provisional slice list derived from the spec's journeys — and by nobody else.

Claude already knows what an Adapter is. It does not reliably know when one earns its cost: GoF classification runs at **38.8%** best-case, and Singleton and Factory are the two most over-predicted classes because their surface markers are the most salient — which is exactly why they show up in generated code as needless statics and one-product factories. Every row below is therefore indexed by the **force**, and every row is decidable at the moment you fill gate field 5.

**Nothing in this file ships by name.** Column 3 is the only column that reaches code-design.md. Naming a pattern in a generation prompt moved output AWAY from the human reference implementation in **15 of 22** model-task conditions (arXiv:2501.04835, Table II). Be honest about that metric: it measures *similarity to a human reference implementation*, not independent quality. The finding is that saying "use Strategy" made the output **less** pattern-conformant than saying nothing — the name is generative, not constraining. That is the whole reason column 3 exists.

**Three rules on column 3, because it is the only column that ships.** (a) *The language is illustrative.* Detect the project's stack first and write field 5 in it — nine of the ten rows below are declared in a language your build is not using, and translation is the step where a model re-selects the shape: force 3's Go `interface` becomes an ABC or a `Protocol` in Python, which `detection-heuristics.md:61` drops on sight. Translate the MECHANISM (one method, declared in the consumer, strictly smaller than the SDK), never the keyword. (b) *Signatures yes, bodies no* — a type, a name, a signature, plus for forces 2 and 6 only ONE initialiser carrying at most one real member, because in those two rows the value is the mechanism. Never a function body, never an example implementation, never pseudo-code: a slice agent pastes whatever it is handed. (c) *A column-3 entry carrying a runtime value cannot live in a `.d.ts` or a `.pyi`.* Both are declaration-only, and a `.pyi` sitting beside a real module shadows it under `mypy --strict`, so the stub always wins and drift is silent. Force 2's dict and force 6's do-nothing value go in a plain importable module (`contracts.py`, `contracts.ts`) that the slice agents actually `import`.

**The four-way collapse warning.** Strategy, State, Bridge and Adapter are all composition + delegation. A model can justify any of the four for the same code and will pick whichever name it saw most recently — so a name is never evidence that a structure was selected on structural grounds. **ALWAYS require the PROBLEM statement, not the structure, as the justification.** If the strongest defence you can write is "it decouples X from Y", you have described all four and chosen none: go back to gate field 1. Write the problem as a one-line comment above the type so the reviewer can check it against a spec line.

## The ten forces

**The trigger column is a HARD REJECT of its own, and every trigger is a conjunction — each clause must hold TODAY, in the spec and the plan (or, from `flow-spec`, the provisional slice list) already in front of you.** All eight gate fields fill cleanly for a structure whose trigger does not: a dict of functions has no "implementations", so gate field 3 never reads 1 and the gate's only count-based reject never fires on it. Count the members and count the slices BEFORE you write field 5. A slice you split in order to produce the second consumer is not a second consumer, and a member you plan to add in a later feature is not a member.

**Expected hit rate: zero or one row on a typical Medium build.** Three or more rows firing means you are designing the plan rather than the spec — go back and read the triggers as conjunctions. Ten rows sitting in context is a menu, and a model fills a menu.

| Force (the situation) | Detectable trigger | Mechanism + signature (what goes in the doc) | False-positive test (when NOT) |
|---|---|---|---|
| **Value object** — a primitive is carrying a rule, a unit, or an identity the type system is not holding | Two same-base-typed params sit adjacent in one signature and swapping them still typechecks (`transfer(from: string, to: string)`); OR one validity rule is restated in 3+ functions; OR unit ambiguity (money, duration, timezone) | TypeScript: `export type UserId = string & {readonly _brand: 'UserId'}` · `export type Money = {minor: number; currency: Currency}` (integer minor units, currency never implicit) · the only constructor is fallible — `parseUserId(raw: string): Result<UserId, ParseError>` | One field, one module, no invariant, never swapped or compared — a lone display label. `class ProductName(str)` buys nothing and this row's failure mode is 40 single-use wrappers. Wrap on swap-risk, invariant, or unit — never on "it is a domain concept" |
| **Registry as a dict** — behaviour is selected by a value that arrives as DATA | 3+ members selected by a config key, DB column, HTTP field or filename, AND 2+ plan slices each add a member | Python: `# handlers.py — the only file that may hold this dict` · `HANDLERS: dict[EventType, Callable[[Event], Result]] = {EventType.REFUND: handle_refund, ...}` · unknown key raises `UnknownEvent`, never falls back to a default | The selector is a literal written in the code, not a value in the data — then it is a 3-branch `match` and the dict adds a hop with no lookup. Also: one slice owns every member → local, leave it out of the doc and let that agent choose |
| **Adapter / port** — an external interface you do not control is called from 2+ slices | 2+ slices call the same SDK, AND the surface you actually use is strictly smaller than the SDK's | Go, declared in the CONSUMER package, named for what the consumer needs: `type Mailer interface { Send(ctx context.Context, to Address, body Body) error }` — 1 method against an SDK's 40 | Port method count == SDK method count → passthrough wrapper; delete it and call the SDK directly. "We might swap vendors" with no second vendor named in the spec is not a force — gate field 1 rejects it verbatim |
| **Test-data builder** — every slice's tests must construct the same aggregate | An aggregate with 4+ required constructor fields that 2+ slices instantiate in tests | Python: `# tests/builders.py` · `def a_user(**overrides) -> User` · one per aggregate THAT MEETS THIS TRIGGER — never one per aggregate — listed in code-design's Test-seams section | A *production* Builder class: keyword arguments and `dataclasses.replace` / object spread already do it in Python, TypeScript and Kotlin. Also an aggregate only ONE slice constructs in tests → a fixture inside that slice, not a shared builder every other slice's tests then import |
| **Repository** — persistence detail would otherwise leak into 2+ slices | 2+ slices need the SAME non-trivial query, or driver/ORM types would appear in 2+ slices' domain code | Rust: `pub trait OrderStore { fn find_open(&self, c: CustomerId) -> Result<Vec<Order>, StoreError>; }` — methods are the QUERIES the spec names, not CRUD | "We might swap the database" is not a force. One slice, one query → call the driver. A trait with `save`/`find`/`delete`/`list` mirroring the table is the table with extra steps, and it is a shallow module by flow-deepen's depth-ratio rule |
| **Service-layer method** — a unit of work spans more than one entity | A transaction boundary, OR 2+ gateway calls that must succeed together, OR a rule that is no single entity's invariant | TypeScript, one method named for the use case, owning the transaction: `placeOrder(cmd: PlaceOrderCmd): Promise<Result<OrderId, PlaceOrderError>>` | Body would be `return this.repo.find(id)` → delete the method (`detection-heuristics.md:38`, pass-through). One service method per repository method is a layer that introduces no new vocabulary — `detection-heuristics.md:39` |
| **Null object** — absence is a legitimate DOMAIN state | Every call site would otherwise write the same `if x == nil` guard, and the guarded branch is "do nothing, correctly" | Go: `type Metrics interface { Count(name string, n int) }` + `var NoMetrics Metrics = noopMetrics{}` — the do-nothing value is a named member of the type, declared once | Absence means a lookup FAILED (`NullUser`, `NullAccount`, `NullPermissions`) → this converts a loud failure into silent wrong behaviour, which is unrecoverable across slices. Test: *if this value is absent, is the program still correct?* No → return an error |
| **Composite** — the DATA is recursive and callers must treat leaf and container alike | The spec names a tree (folders, rule groups, nested line items) AND 2+ slices walk it | Rust: `pub enum Node { Leaf(Item), Group { children: Vec<Node> } }` · state explicitly which variant owns `add`/`remove` and in which module, or six agents place them in six places | Two fixed levels (order → lines) is nesting, not recursion — that is a `Vec` field. If no slice recurses, the uniform-treatment benefit is zero and you have bought an extra indirection for the reader |
| **Facade** — a naive caller must perform ordered setup it should not know about | 4+ ordered setup steps, AND 2+ slices are that caller | Python: `def open_session(path: Path) -> Session` returning an object with 2-3 verbs; ordering and teardown live inside. Cap the surface at ~7 methods | It gains a method every slice → it is becoming the god object; split it by consumer group before slice 4. One caller → inline the steps in that slice and let the agent read them |
| **Observer / event bus** — the producer genuinely cannot know its consumers | Consumers register at RUNTIME (plugins, user-configured webhooks, subscriptions in the DB) | TypeScript: `type OrderPlacedSubscriber = (e: OrderPlaced) => Promise<void>` passed as an explicit array at construction — never a module-global bus | The consumer set is fixed at design time, which is the case for almost every event-driven design a model proposes. Call them directly in explicit order: you keep the stack trace, the ordering guarantee and the test. A bus also makes `grep OrderPlaced` land on nothing that runs |

## Obsolete by language — GoF entries that patched a hole your language does not have

These exist because C++ and Java 1.x lacked first-class functions, modules-as-values, or pattern matching. In a language that has them, the pattern is ceremony around a language feature. Detect the stack first, then write the right-hand column. (Singleton, Factory Method, Prototype and Iterator are also forbidden outright — their replacements are in the next section, not repeated here.)

| GoF entry | The language hole it patched | Write this instead |
|---|---|---|
| **Strategy** | no first-class functions | A function value. `Callable[[Event], Result]` *is* the pattern — see force 2. An ABC named `XStrategy` is the pattern's C++ scaffolding, not the pattern |
| **Command** | no closures | A closure for scheduling; a plain data record the handler `match`es on when you need undo, replay or persistence. Pick by which of the two the spec asks for |
| **Template Method** | no higher-order functions | A function that takes the varying step as a parameter. Inheritance for one varying line forces every reader into a two-file read to learn what runs |
| **Visitor** | no pattern matching and no double dispatch | `match` on a closed sum type (Rust `enum`, Python 3.10 `match`, TypeScript discriminated union). Adding a variant then fails exhaustiveness at compile time — that compile error is the benefit Visitor was faking by hand |
| **State (class-per-state)** | same | An enum plus the transition table from code-design's state-machine section. Class-per-state scatters the table across N files and no single file answers "what happens next" — expensive for a human with an IDE, far worse for a fresh-context agent |
| **Decorator** | no default arguments or options objects | One class with options — `X(cached=True, retries=3, logger=...)`, per `detection-heuristics.md:40` |
| **Bridge** | no generics | A type parameter. Or, far more often, just the two concrete types — the second dimension of variation named in the gate's field 4 usually does not exist |

## FORBIDDEN BY DEFAULT

Reject in review, no discussion, no gate needed. Write the replacement, never the pattern. [`code-design-doctrine.md`](code-design-doctrine.md)'s gate section abbreviates this list and the next one; **these are the normative copies — where the two differ, this file governs.**

- **Singleton** → a module-level value, or pass it explicitly. The shared-resources table in code-design.md already names who constructs it and who receives it.
- **Factory Method** → a function: `create_x()`.
- **Prototype** → `copy.deepcopy` / object spread / `dataclasses.replace` / `#[derive(Clone)]`.
- **GoF Iterator classes** → implement the language's own iteration protocol and return it.
- **Any ABC, Protocol or interface whose members are one verb and whose implementer is selected at runtime** → the dict of functions in force 2. The ban is STRUCTURAL, not name-shaped: `XStrategy`, `PricingRule`, `Notifier` and `Handler` are one structure, and renaming it is not a fix. One production implementer is already dropped by `detection-heuristics.md:61`, and a test double does not count as the second.
- **A production Builder class** → keyword arguments, `dataclasses.replace`, object spread. Force 4's TEST builder is the only builder that earns a line in the doc. Consequence of missing this one: a production builder fills all eight gate fields without effort, and the aggregate then gets constructed two ways in the same codebase — the builder in slices that inherited it, the constructor in slices that did not.
- **Abstract Factory** → unless you can NAME THE CONCRETE BUG that occurs when a caller mixes variant A's product with variant B's. *"It would be inconsistent"* is not a bug; *"a Postgres cursor handed to the SQLite writer raises at runtime, in production only"* is.
- **Self-registering registries** (`@register` decorators, metaclass registration, import-time side effects) → **one explicit dict literal in one named file.** Consequence: an agent adds `handlers/refund.py`, nothing imports it, no error is raised, every test passes, and the feature does not exist. Silent absence is the worst failure class in this pipeline, because nothing is red and no agent reads all the code. With one dict literal, six agents each add one line to the same file, git surfaces the conflict, and it resolves in seconds.

## NOT A DESIGN-DOC DECISION

**Chain of Responsibility · Proxy · Memento · Mediator · Flyweight · Bridge · Template Method · State · Command · Decorator · Visitor**

Their force is discovered while writing the implementation, and none of them coordinate anything across slices — gate field 2 names fewer than two slices for every one of them. A slice agent may use any of these INSIDE its own slice without asking. Putting one in code-design.md spends an instruction from a per-prompt budget of five on a decision the agent will make better with the code in front of it.

**This list answers "does it go in the doc?" and nothing else.** Six of the eleven — `Bridge · Template Method · State · Command · Decorator · Visitor` — also sit in the obsolete-by-language table above, which answers a different question: what shape the thing takes when it is written. The two never conflict, because permission to use Decorator inside a slice is not permission to write the C++ scaffolding version, and `detection-heuristics.md:40` flags the ceremony version post-merge. Do not resolve the overlap by adding an instruction to code-design.md.

## Already covered — do not invent a new criterion

- **Depth ratio** (Ousterhout; flow-deepen's depth-ratio rule). Depth = benefit hidden ÷ interface complexity imposed on callers. WHY: a registry, port or facade that raises interface complexity without hiding proportional benefit is already banned by that one sentence, and a second threshold is only a second thing to argue with. Filter: run flow-deepen's depth-ratio rule, not a new number — a port whose method count equals the SDK's hides nothing and drops.
- **Decorator trap** (`detection-heuristics.md:40`). WHY: stacked ports and layered adapters are the same defect wearing a different name, and the house banned it before this file existed. Filter: class implements `I`, holds a field of type `I`, method count == `I`'s → `LoggingX` + `CachingX` + `RetryingX` collapse into `X(cached=true, retries=3, logger=...)`.
- **Speculative generality** (Fowler/YAGNI, `detection-heuristics.md:62`). *No current consumer → drop*, unchanged here word for word; only the unit of count moves, from instances in shipped code to named rows in the build plan (or, before a plan exists, the provisional slice list), which are committed rather than anticipated. Filter: cannot point at two consuming slices BY NUMBER → the filter fires and the structure does not go in the doc. A structure that does pass leaves its eight gate fields in `code-design.md`'s Decisions section — that record, not this file, is what a post-merge pass must read before applying flow-deepen's HARD FILTER to a structure the design mandated.
