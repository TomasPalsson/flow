# Code design doctrine

The spec says WHAT and never HOW (`flow-spec/SKILL.md`); slice decomposition lives in `${CLAUDE_PLUGIN_ROOT}/skills/flow/planning.md`; the post-merge smell catalogue lives in `${CLAUDE_PLUGIN_ROOT}/skills/flow-deepen/references/detection-heuristics.md` — **load those for slicing and for deepening**; this file adds only the cross-slice structure layer on top. It is the inverse of `detection-heuristics.md:10-52`'s five smell families: the same five failures, prevented before any code exists rather than detected after the merge — cite that file, never restate it in `code-design.md`. Three boundary rules follow from the spec's own rubric. `code-design.md` is **not a spec** and is never routed to spec-judge (`spec-judge/SKILL.md:3` — *"Do NOT use for design docs, architecture docs, or code reviews — those are not specs"*); an unlabelled design doc scores F on D4 and D7 for purely structural reasons. The technology name that costs the spec 3 points as an implementation leak (`spec-judge/SKILL.md:250-253`) is **relocated** here, into sections 1 and 5 — never relaxed there. And the design may **reference** an NFR (*"NFR-3's 200ms p95 is why this seam exists"*) but never **host** one, because the spec must stand alone (`spec-judge/SKILL.md:396`).

You are the orchestrator. You read this once, at design time: from `flow`, inside Phase 3, after vertical decomposition into slices and the Behavior Inventory exist and before the plan file is written, with the full spec, the slice list and the Behavior Inventory in context, so every slice count below is real; from `flow-spec`, no build plan exists yet, so derive a PROVISIONAL slice list from the spec's journeys (`flow/planning.md` already calls these the natural slices), count fields 2 and 3 against that list, mark every count provisional, and let `flow-to-issues` (or flow Phase 3) revalidate them against the real slices, dropping any structure whose consuming-slice count then falls below 2. **Do NOT re-load it in a later phase and never paste it into a subagent prompt** — its entire output is `code-design.md`, written to `.specs/<NNN>-<slug>/code-design.md` beside the spec, and every prose line in it costs reader context in every slice agent. Solution-first questions are banned in discovery (`question-bank.md:262`) because the *stakeholder* is not equipped to answer them, not because the decision does not need making: you make REST-vs-GraphQL-class decisions here, on your own judgment, and **surface** them (never ask them) at the plan-approval gate. The candidate structures are indexed by force in [`pattern-forces.md`](pattern-forces.md) — load it once, in this pass only, never during `flow`'s Phase 4 (the TDD build) and never inside a slice prompt. On a typical Medium build zero or one of its ten forces fires; three or more firing means you are designing the plan rather than the spec.

**The thesis.** A pattern's value in a fan-out build is not flexibility — it is **nameability**. Adopt a structure when it removes a decision from six prompts; reject it when its payoff is an extension point for a seventh slice that does not exist. What `code-design.md` eliminates is `spec-judge/SKILL.md:43-56`'s **D — Debatable** category (*"A developer reads this and could build 2–3 valid things"*) applied to structure instead of behaviour. **Patterns are top of mind for YOU and structurally invisible to the BUILDER.** The generated `code-design.md` may not contain a GoF pattern name anywhere; it carries the mechanism and the exact signature. `Use Strategy` reliably yields an ABC, two concretes, a factory and a registry. `HANDLERS: dict[EventType, Callable[[Event], Result]]` yields a dict.

> *"If a fresh agent building slice 5 never read this document, which of its decisions would still come out right?"*

The answer is the structural half. Everything else runs at ~67% compliance — budget for the leak rather than wishing it away.

## The three carriers

Every line you write into `code-design.md` sorts into exactly one of these. **If it is none of the three it is decoration — cut it.** In the largest controlled study of agent rule files (679 files, 25,532 rules, >5,000 Claude Code runs): every rule that helped in isolation was a negative constraint, and every rule that hurt was a positive directive.

| Carrier | Compliance | What it looks like |
|---|---|---|
| **(S) Structural** | ~88% | A compile error, a shared type, a physical file location, a lint rule. Survives an agent that never opened the doc. |
| **(L) Literal** | high, conditional | A value the agent copies verbatim. Only works if it lands **in the slice prompt** — a file the agent may skim is not a carrier. |
| **(P) Prohibition** | ~67%, assume 33% leakage | A NEVER that fires at a decision point. Budget **≤5 binding prose constraints per slice prompt**, not per document. |

Anything that could be a compile error, a shared type, a file location or a lint rule **must not be prose**. And the doc has two halves in opposite voices, deliberately: **forbid local ceremony** (over-abstraction lives inside what one agent can see) as prohibitions; **supply global decomposition** (under-structure lives in what no agent can see) as literal values, names and assignments. A single voice gets one of the two backwards. Do **not** shorten the doc "so agents follow it better": file size and cross-file contradiction were measured as *affirmative* nulls (BF10 0.05–0.10) and instruction position showed no detectable effect. Shorten it because it competes for context in six agents at ~15× chat token cost, and because fewer sections mechanically means fewer simultaneous instructions, which *is* a live lever. State the reason correctly or a later agent re-adds pages citing the null.

## Sections of the generated `code-design.md`

Medium emits sections 1–7, **≤70 lines** + the contract file. Large adds 8–11, **≤130 lines**. Wrap 8–11 in `<!-- SIZE: large only -->` / `<!-- END SIZE: large only -->` exactly as `spec-template.md` does. Sections 9, 10 and 11 are conditional — write the condition as a **deletion instruction inside the section** (`Delete this section if no contract type has a ≥3-value status field`), never as a parenthetical `(optional)`: a model fills every heading it is given. Per-section budget: naming table ≤20 · trust boundaries ≤10 · error taxonomy ≤5 · module allow-lists ≤2 lines per module · shared resources ≤8 · deliberately-duplicated ≤8 · decisions ≤6 Y-statements + 6 `Makes hard:` lines · churn ≤10 · state and ladder ≤1 line per row · test seams ≤10. Over the cap, cut naming-table rows first — the contract file already carries every name a compiler sees — and **never** cut sections 5, 6 or 11, which is where an under-specified design hides. **Signatures yes; bodies no**: no pseudo-code and no example body a slice agent could paste.

| # | Section | Notation — emit exactly this shape |
|---|---|---|
| **1** | Contract file + ubiquitous language | Path to a **runtime-importable** contract file (`contracts.ts` / `contracts.py` / `types.rs` / `.proto`) slice agents actually `import` — never `contracts.d.ts` or `contracts.pyi`, because a declaration-only file cannot hold the enum members, the error class or the parse function the rest of this doc mandates, and a `.pyi` beside a real module silently shadows it under `mypy`. Plus a ≤15-row table `Canonical \| identifier \| plural/collection \| defined in \| banned synonyms`; the value-object declarations (branded ids `export type UserId = string & {readonly _brand:'UserId'}`, money as integer minor units + currency, UTC-aware instants) — the only coordination mechanism that works on an agent that never opens the doc; and the async-vs-sync convention for every shared function. Run `tsc --noEmit` / `mypy --strict` / `cargo check` on it before handoff — a table is a request, an import is a constraint. |
| **2** | Type contracts & trust boundaries | Table `Boundary \| untrusted input shape \| parse fn \| failure granularity`, one line each for absent-vs-null, money representation, timestamp representation (UTC-aware instants — naive local in slice 1 and epoch millis in slice 3 both typecheck) and id minting (uuid7 / DB sequence / caller-supplied). Boundaries MUST include the non-obvious ones — DB rows, queue messages, env vars, third-party responses, LLM/tool output. Agents get HTTP handlers right unaided and treat "our own database" as trusted; the schema is older than the code. |
| **3** | Error taxonomy | One closed literal type declaration **in the contract file** + one prose line: *"Adding a variant is a design change — escalate, do not add locally."* State thrown-vs-returned once, and give the ONE mapping from error variant to transport representation (HTTP status + wire body shape, or exit code) — otherwise slice 1 returns `{"error":{...}}`/422 and slice 4 returns `{"detail":...}`/400 and every client breaks per endpoint. |
| **4** | Module boundaries | One line per module: `layer N · may import: <closed list> · exports: … · seam label: <the label the plan's **Seam** field will use>` + *"Anything not listed is a bug."* Emit the enforcement config (`.importlinter` / `.dependency-cruiser.json` / ArchUnit) — that config, not the prose, is what ships the closed-world rule. Sibling independence as a **pattern** (`no src/features/<X>/ may import src/features/<Y>/ for X != Y`), never pairwise — pairwise lists grow quadratically and rot by slice four. |
| **5** | Shared resources & construction | Table `resource \| constructed-by \| passed-how \| received-by` for DB handle, HTTP client, config, cache, clock and logger, plus the config-key namespace (`DB_URL` vs `DATABASE_URL` — one slice otherwise reads `None` in silence), the owner of migration-file numbering, and who may add a dependency. A fresh agent that needs a client and is not told who provides it constructs its own. Do **not** seed a `registry` row: `detection-heuristics.md:62` drops strategy registries by name, a row here presupposes one exists, and a model fills every row it is given — a registry appears only after force 2 passed the gate. |
| **6** | Deliberately duplicated — do NOT consolidate | Bullets, each naming the prohibited consolidation **and what to do instead**; at minimum rule on retry/backoff, date formatting, validation helpers, HTTP-client wrapping and `utils/`. If genuinely none, write `none — justified because <reason>`: an empty section and a complete one are otherwise indistinguishable and both pass every check. Silence is not permission; it is an invitation to invent six incompatible `utils/`. |
| **7** | Decisions | ≤6 Y-statements, one line each: *"In the context of `<component>`, facing `<force, as a checkable fact>`, we chose `<mechanism + signature>` and rejected `<option>`, to achieve `<benefit>`, accepting that `<named cost>`."* Then one `Makes hard:` line per decision naming a concrete future change **and the files it touches**. The `rejected` and `accepting that` slots are structurally empty until filled with something unflattering. This section carries gate fields 1, 5, 6 and 8; fields 2, 3, 4 and 7 are answered during the pass and never written down. |
| **8** | Hidden decisions + churn | Table `decision hidden \| module \| STABLE / CHURNING / PROVISIONAL`; flag every CHURNING element embedded in a STABLE one. **STABLE = changing it invalidates completed slices**, and "rigidity" means only that a STABLE row's name, type and location are fixed for this build. A flagged mismatch is an **input to field 1 of the gate and nothing else** — it is never itself a reason to extract a seam. |
| **9** | State machines | Transition table `current \| event \| next \| guard \| side effect` + an exhaustive `match` over the status type in the contract file, so a missing pair is a compile error rather than a prose rule. One test per row; illegal transitions are visible as absent rows. **Delete this section if no contract type has a ≥3-value status/phase field.** |
| **10** | Cross-slice call ladder | Numbered lines, each an exact signature: `4. OrderService.place(cmd: PlaceCmd) -> Result<OrderId, PlaceError>`. Removes the agent's need to invent a callee name. **Delete this section if no single behaviour spans ≥3 modules.** |
| **11** | Test seams & shared fakes | One named fake per process boundary (fake HTTP server / sqlite / testcontainer / recorded fixtures); the test file location and runner config (`tests/` vs `__tests__/` vs colocated — two trees and the runner silently collects one); and a test-data builder **only** for an aggregate with 4+ required constructor fields that 2+ slices instantiate in tests, never one per aggregate. Two rules: no unit test targets a design-introduced shared helper; tests are named for spec behaviours, not production classes. **Delete this section if no aggregate and no process boundary is shared across slices.** |

`code-design.md` is structured **for copying, not reading**. Components are **cited by** slices, never **ordered against** them — many slices touch one component and one slice touches many; a layer-ordered design doc produces `Slice 1: implement the registry`, which `flow/planning.md`'s Step 1 horizontal-slice ban forbids. The contract file has exactly one owner: you. A slice agent imports from it and never edits it; a type it needs and cannot find is an escalation. The design pass itself cuts one of these blocks per slice, now, in this same pass — later, at the Phase 4 hand-off, `flow/orchestration.md` pastes the already-cut block into the subagent prompt at RED, verbatim and nothing else from this doctrine file:

```
## Contract for this slice — Slice <N>: <title>
CONTRACT   <path to the contract file> — import from it. A type you need that is not there is an escalation, never a local declaration.
NAMES      <the naming-table rows this slice touches, verbatim, banned synonyms included>
MODULE     <path> · layer N · may import: <closed list> · exports: <closed list> · seam: <the plan's seam label>
CALLS      <the exact call-ladder signatures this slice implements or calls>
DUPLICATE  <the section-6 bullets that touch this slice — do not consolidate these>
THE FIVE   (1) NEVER invent an error type, field name or result shape that already exists in the contract — copy the literal declaration. (2) NEVER type a boundary function's parameter as the narrow type; the narrow type appears only as the RETURN of a fallible function. (3) NEVER add a mode, flag, boolean or extra required parameter to a shared abstraction the design handed you — duplicate it inside your slice and say so in your completion note; and before extracting anything, write the signature first, because a flag needed at birth disproves the extraction. (4) NEVER refactor, rename or restructure outside your slice — a change to an unlisted file is a defect. (5) NEVER abbreviate inside an identifier. Spell the word.
```

≤25 lines, and THE FIVE is the entire prose budget: the set is closed and ranked by repair cost × what no compiler catches, and you do not substitute into it. It fixes **NAME, LOCATION and SIGNATURE — never COMPLETENESS**, locks **STRUCTURE — never behaviour coverage**, and supplies **no acceptance criteria** (those come verbatim from the spec, per `flow/planning.md`'s Step 1 acceptance-criteria-verbatim rule). Everything else is a lookup by path: section 9's exhaustiveness ships as the contract file's `match`, section 4's closed world ships as the emitted linter config, and section 11's naming convention is greppable after the fact — none of the three spends a slot. This delivery is not the duplication flow-handoff's *reference, don't copy* rule bans; cheap slice agents demonstrably do not read long docs end to end.

## Pattern adoption gate

Run this before ANY structure enters `code-design.md`. Fill every field or do not adopt. **The output of the gate is field 5 and nothing else** — fields 1, 6 and 8 land in the Decisions section, fields 2, 3, 4 and 7 are answered here and discarded, and none of them ever reach a slice prompt.

```
1. HIDDEN DECISION   This structure hides the decision "____" (one concrete sentence, in domain language).
2. SLICE CONSUMERS   Slices ____ and ____ must know this to write correct code.
3. PRODUCTION COUNT  ____ implementations reachable in production TODAY. Test doubles, mocks, fakes and in-memory stores count as ZERO. If field 5 is a dispatch table rather than an interface: ____ members that exist TODAY, and ____ plan slices that each ADD a member.
4. SPEC WITNESS      The >=2 concrete cases live at spec lines ____ (spec line numbers only — never a plan row; you wrote the plan).
5. MECHANISM         <the exact declaration six agents will read, in this project's language>
6. REJECTED          ____ , rejected because ____ (must cite a force from field 1 or 4).
7. CONFIRMATION      A violation is caught by ____ (name the lint rule, import-boundary test, grep or type error).
8. COST              This makes ____ harder — it would touch ____.
```

**HARD REJECT** — any one of these and the structure does not go in the doc:

- Field 1 is empty, or reads "might vary", "flexibility", "extensibility", "future-proofing", "swappability", "in case we need to change X later" — **or is any paraphrase of those**, which is the failure mode a six-string blocklist cannot catch. The semantic test: field 1 must name a decision the spec has already made **two different ways**, not a thing that could change. *"Hides which storage backend we use"* fails it unless field 4 cites two backends live in production today — that sentence is swappability in domain clothes, and `pattern-forces.md`'s Repository row rejects it verbatim. *"Hides that refund eligibility is computed from the settlement date, not the order date"* passes; *"Handles users"* is not a decision at all.
- Field 2 names **fewer than 2 slices** → local implementation detail. Delete it from the doc and let the slice agent choose. Do not "helpfully" specify it.
- Field 3 is **fewer than 2** — `0`, `N/A`, `not an interface` and an empty cell all count as fewer than 2 → delete the abstraction, depend on the concrete type, test against a real dependency (sqlite, testcontainer, fake HTTP server, recorded fixtures). For a dispatch table the same floor applies to members: fewer than 3 members today, or fewer than 2 plan slices that each add one → write the `if`/`match` inline and let the slice agents extend it. Without this line a one-handler registry fills all eight fields and passes, because a dict has no "implementations".
- Field 4 is in the future tense, or cites no spec line.
- Field 5 contains a GoF pattern **name** instead of a declaration → `Use Strategy` produces an ABC, two concretes, a factory and a registry; `HANDLERS: dict[EventType, Callable[[Event], Result]]` produces a dict. The same reject fires on the name-free restatement: an ABC / Protocol / interface whose implementers are selected at runtime and whose only member is one verb is that dict written the long way — renaming `XStrategy` to `PricingRule` changes nothing. Field 5 is also written in **this project's language**: `pattern-forces.md` column 3 is polyglot by row, and translating its Go interface into Python re-selects the shape and yields the ABC this gate just rejected.
- Field 5's port has the **same method count** as the SDK surface it wraps → passthrough wrapper. Delete it and call the SDK directly.
- Field 5 needs a boolean, enum or mode parameter to serve the slices that exist **today** → the call sites encode different knowledge. Split it, or duplicate.
- Field 6 says "more complex", "less clean" or "not idiomatic" with no named force.
- Field 7 says "code review", "the adversary lens" or "a test", or names no specific lint rule, import-boundary test, grep or type error → the structure is unenforceable, so slice 3 will violate it and nothing will be red.
- Field 8 is empty, or a compliment in disguise ("makes it hard to add unnecessary complexity").

**FORBIDDEN BY DEFAULT** and **NOT A DESIGN-DOC DECISION** — both lists live in [`pattern-forces.md`](pattern-forces.md) (`## FORBIDDEN BY DEFAULT`, `## NOT A DESIGN-DOC DECISION`); run them from there rather than from a second copy that drifts, per flow-handoff's *reference, don't copy* rule. Two entries neither list can express by name, so the gate owns them: a **production** Builder class (keyword arguments, object spread and `dataclasses.replace` already do it — only the *test* builder earns its line, in section 11), and the one-verb runtime-selected interface above. And the second list means only *do not put these in `code-design.md`*: `pattern-forces.md`'s obsolete-by-language table still governs how a slice agent writes them.

**TIEBREAK**, when the gate is genuinely ambiguous: choose the option that is **cheaper to reverse**, not the one that is more elegant. Duplication → abstraction is mechanical, greppable and local; abstraction → duplication is judgment-laden, test-breaking, socially blocked, and needs information the abstraction itself destroyed. Ask *"which of these could I undo in an afternoon?"*

**PREFER DISPATCH THAT GREP FINDS.** Given two correct designs, choose the one where searching for the literal string that arrives in the DATA lands you on the code that runs. A human pays "jump to definition" (~zero); a fresh-context agent pays "read N files to find which one actually runs", and every indirection layer multiplies its search. This outranks conventional elegance. Nothing here is relaxed relative to `detection-heuristics.md`: field 2 **is** `:62`'s *"no current consumer → drop"* with the consumers read off the build plan; field 3 **is** `:61`'s single-implementation filter, hardened against the model manufacturing its own second implementation. Because that claim only holds if the post-merge pass can tell a gated structure from an invented one, section 7 is the durable record — `flow-deepen` must read `code-design.md` before applying its HARD FILTER, or it either churns design-mandated structure or learns to wave the filter through.

## Principle gates — designer-only, never a builder instruction

There is no strong published evidence that SOLID adherence improves maintainability. Every gate below earns its place from an observable failure mode — blast radius, contract drift, call-site type switches — never from the authority of the principle. The folk version of each is **banned by name**; the source version is a pass/fail test you run at a decision point. Emit gates, never properties: a property has no decision point, and gradient-following on a quality property *increases* abstraction, because abstraction scores higher on a model's own surface-quality judgment.

| Folk version — BANNED | Source gate — RUN THIS |
|---|---|
| **"a class should do one thing"** | **Actor test.** Name the single actor (role / team / external system) who would request a change here. Can't name one, or you name two → the boundary is wrong. |
| **"extend, don't modify"** | **Variation ≠ evolution point** (Larman). Build the abstraction only around a variation that exists NOW, witnessed by ≥2 concrete cases named in the spec. |
| **"don't break inheritance"** | **"Expect no more, promise no less"** (Martin) — and thrown errors are part of the return type. |
| **"interfaces should be small"** | **Two named consumer groups using disjoint method subsets.** One consumer → no obligation, regardless of size. |
| **"depend on abstractions, use DI"** | **Ownership test.** The interface file lives in the **consumer's** module, named for what the consumer needs. Sitting beside its only implementation → nothing was inverted; delete it. |

**Free win:** the first two collapse into one operation (Parnas, cited by both Martin and Larman) — **name the design decision this boundary hides.** Can't write the sentence → delete the boundary. That sentence is field 1 of the gate, and it is subject to field 1's semantic reject: a decision the spec already made two ways, not a thing that might change.

## Counting gates — DRY, and Rule of Two Slices

**DRY the DECISIONS, duplicate the CODE.** Two failures wear one name. *Contract divergence* (six error shapes, six id types, six timestamp formats, six module layouts, six naming schemes) is cross-cutting, infectious, not locally fixable, and costs **zero** to prevent because it is a convention → be maximally prescriptive. *Implementation duplication* (six retry loops, six date formatters) is local, greppable and cheap, and preventing it risks the wrong abstraction → be deliberately permissive. The felt problem — "six agents invent six different structures" — is almost entirely the first, and reaching for a shared abstraction to fix it is solving a free problem with an expensive tool. Exactly one DRY test ships to slice agents, the **parameter forecast**, and it ships fused into constraint 3 of THE FIVE because both fire at the same decision point, a flag parameter: before extracting, write the signature; if it already needs a boolean/enum/mode parameter to serve today's call sites, the extraction is disproven — a flag argument present at birth is a certificate of coincidental duplication. The other four tests (provenance, divergence, naming, change-coupling) stay designer-only; they spend instruction budget against a cap of five and need context no slice agent has.

| | Unit counted | Who runs it | When | Threshold |
|---|---|---|---|---|
| **Rule of Three** (Metz) | textual instances in shipped code | flow-deepen, Phase 7 | post-merge | < 3 → wait |
| **Rule of Two Slices** | slices that touch the seam — the slice list from `flow`, or the provisional slice list derived from the spec's journeys from `flow-spec` | you, at design time | pre-code | ≥ 2 → fix it in `code-design.md`; provisional counts are revalidated at `flow-to-issues` (or flow Phase 3) and dropped if they fall below 2 |

Rule of Three still governs code. Rule of Two Slices governs the document. **They never contradict because they never count the same thing.** Exactly one slice touching a seam → keep it out of the doc even at three occurrences inside that slice; that agent sees all three and consolidates itself. Two or more → fix it now, because parallel agents have no "later" in which to consolidate.

## Boundary types — "loose" describes the DECLARED TYPE, never tolerant semantics

Loose means the boundary function's parameter is typed as the genuinely untrusted shape (`str`, `bytes`, `unknown`, `Mapping[str, Any]`), because you cannot honestly claim to know what arrived. The narrow type appears only as the RETURN of a fallible function; probe every check by its return type — `bool`/`void`/`None` is a validator, not a parser. **Semantics stay strict.** RFC 9413 repudiates the robustness principle: tolerated errors entrench as de facto standards, and tolerance conceals problems, making them harder or impossible to fix later. That citation stays here, in the doctrine — a bare RFC number in `code-design.md` is none of the three carriers and costs a line in a file six agents read. What ships instead is the decidable line: **normalize redundancy, reject ambiguity.** Several encodings unambiguously denoting one value → normalize. Two plausible meanings where the code must pick one → fail with a specific error. **Named bans**, because a general rule does not fire at the decision point: coercing `""` → null · mapping an unrecognized enum value to a default · truncating over-long input · inferring date locale · string→number coercion. Every leniency carries an inline note naming the specific producer it exists for and the condition under which it is deleted; an unattributed leniency is a permanent undocumented contract.

Spend nothing on the half the compiler already covers (Java/C# parameter types are invariant, Go and Rust have no variance to exercise, TypeScript method syntax is bivariant by design). Three residues, and only three: **(1) thrown errors are part of the return type** — declare the closed error set once; adding a variant is escalation, never a slice-local decision. **(2) Adding a required parameter to an implementation of a shared interface is precondition strengthening and is forbidden** — it is the single most likely thing a slice agent does when its slice needs one extra input, which is why it is fused into constraint 3 of THE FIVE, and `# type: ignore[override]` is a written confession, every occurrence a review item. **(3) Mechanical detector:** grep `isinstance` / `instanceof` / `typeid` / a type-switch on a shared interface's own types **at a call site**, excluding parsers, deserializers and factories. Every hit is an LSP violation and, per Martin, an OCP violation too. Put it in the slice exit gate — zero judgment required.

## What `clean-code` §5 means here

`clean-code/SKILL.md` runs as a MANDATORY pass in every Refactor phase, and its §5 *"Data Abstraction: Hide the implementation behind interfaces"* reads as a licence to mint one. It is not. **§5's "interfaces" means the PUBLIC SEAM of a module — the small stable surface callers depend on. It does not mean a language `interface` / `Protocol` / ABC keyword.** A language interface with one production implementer is banned by `detection-heuristics.md:61` (one impl, never mocked → drop) and **stays banned during Refactor**. Per feature/execution-prompt.md's Refactor-phase constraint list, a Refactor phase may not change public API surface at all — so `code-design.md` must be inherited at **RED**, where stubs and signatures are written. A doctrine that assumes Refactor cleans up design drift is wrong. Two extraction tests both camps endorse, decidable at the moment of writing: **depth ratio** — reject any extraction whose interface is not strictly less detailed than its implementation (Martin's own rejection criterion; Ousterhout's depth, already the operative rule in flow-deepen's depth-ratio filter). **Entanglement** — if understanding method A requires reading method B, merge them; the trigger is flipping back and forth between two implementations to understand either. Then two rejection checks on any extracted unit: a side effect its name does not disclose, or a precondition established by a caller more than one level away and stated nowhere. **Say nothing about function length, in either direction** — a model has seen far more Clean-Code-derived text than the alternative, so any hedged statement resolves silently toward tiny functions with long names. Silence plus these tests is the only stable position.

## Adversary lens

Run by a **different agent** than the one that wrote the design, over the **design document, the contract file and slice descriptions** — never over slice output, never by the slice agent on itself. Run it after the design pass has cut the per-slice contract blocks (the same pass that writes `code-design.md` also cuts every `## Contract for this slice` block — see above) and before slice 1 starts, so the lens runs over a complete artifact set. It emits **only numbers against thresholds**. Never phrase it as "improve the architecture" or "is this well designed?": that self-check scores 50.3%, materially worse than passive prose at 67.0%, because the more abstract a design looks the higher its surface-quality score to a model. A *binding prose constraint* is one sentence carrying an imperative no compiler, linter or type checker can check. Verdict format: one line per check — `check · value · threshold · PASS/FAIL`; any FAIL is a **prediction of where the six agents will diverge**, so write it down and check it after the build.

| # | Check | Threshold | Fails because |
|---|---|---|---|
| 1 | Contract file typechecks (`tsc --noEmit` / `mypy --strict` / `cargo check`) | exit 0 | Notation whose errors are undetectable is the wrong notation |

## Kill switch and skip rule

> **If the contract file exports zero types, the naming table has zero rows and section 6 is empty, delete `code-design.md` and do not ship it.** It pins nothing; it is an implementation manual, and writing the code directly would have been better. Do NOT use *"zero rejected alternatives and zero `Makes hard:` entries"* as the test — section 7's grammar mandates both slots, so that switch can never fire on a format-conforming doc.

**`code-design.md` is required when two or more slices share a name, id type, error shape, module boundary or shared resource, and skipped otherwise — including on every one-slice build**, where nothing crosses an agent boundary. From `flow-spec`, run this test against the provisional slice list. The trigger is cross-agent surface, never file count and never the size tier: a Small build is usually skipped because it rarely has 2+ slices sharing a seam, not because it is Small. Do not add *"no element would be tagged STABLE"* as a conjunct: a shared closed error type and shared id types are STABLE by that definition on every multi-slice build, so the skip rule would never fire.

## NEVER

Each prohibition names the failure it prevents. The WHY is what makes the rule load-bearing instead of stylistic. The tag names the audience: `[designer]` rules govern what you put in the doc and are pasted nowhere; the five `[→ slice prompt]` rules are THE FIVE, and that set is **closed** — a sixth costs one of the five.

- **NEVER write a GoF pattern name into `code-design.md` or a slice prompt.** `[designer]` Write the mechanism and the exact signature. Consequence: `use Strategy` reliably yields an ABC, two concretes, a factory and a registry, where `HANDLERS: dict[EventType, Callable[[Event], Result]]` yields a dict of functions. Naming the pattern moved output **away** from the human reference implementation in **15 of 22** model-task conditions (arXiv:2501.04835, Table II) — that metric is similarity to a human reference, not independent quality, so the honest claim is that naming the pattern made output *less pattern-conformant*, not that it degraded quality.
- **NEVER write "apply SOLID", "follow DRY", "keep it simple", "clean architecture", or "consider design patterns" as an instruction.** `[designer]` Consequence: quality exhortations in a generation prompt cut Pass@1 up to 39% and raised output variance ~5× (0.48 → 2.48) — which is precisely the cross-agent divergence the design doc exists to prevent. These strings may appear here, as tests you run; never there, as directives. Check 8 greps for them.
- **NEVER put a structure in the doc that fewer than two slices need.** `[designer]` Consequence: it is a local implementation detail, and specifying it steals the slice agent's judgment while spending one of five instruction slots.
- **NEVER count a test double as an implementation.** `[designer]` Consequence: asked "does this interface have more than one implementation?", the model writes `InMemoryFooRepository` and answers yes — every "abstract at 2+ implementations" rule is trivially self-satisfied unless it says production-reachable.
- **NEVER register handlers by decorator, metaclass, or import side effect.** `[designer]` Use one explicit dict literal in one named file. Consequence: an agent adds `handlers/refund.py`, nothing imports it, no error is raised, every test passes, and the feature does not exist — silent absence is the worst failure class in a pipeline where nobody reads all the code.
- **NEVER declare a shared error variant, id type, or field name in more than one place.** `[designer]` Consequence: thrown errors sit outside most type signatures, so six agents produce six error hierarchies and nothing fails until integration — the highest repair cost of any contract.
- **NEVER invent an error type, field name or result shape that already exists in the contract.** `[→ slice prompt]` Copy the literal declaration. Consequence: this is the exact form the ~33% prose leakage takes, and it is the form that costs most to repair, because the divergence is invisible until integration.
- **NEVER type a boundary function's parameter as the narrow type.** `[→ slice prompt]` The narrow type may appear only as the RETURN of a fallible function. Consequence: the parse becomes a no-op lie that passes both the typechecker and review — `handle(req: CreateUserRequest)` when nothing produced a verified value — and every downstream slice re-derives the check its own way. Six agents each writing one local check is shotgun parsing by construction.
- **NEVER add a mode, flag, boolean, or extra required parameter to a shared abstraction the design handed you.** `[→ slice prompt]` Duplicate it inside your slice and say so in your completion note. Consequence: a subagent handed a design doc inherits the felt obligation to preserve an abstraction it did not create, and under fan-out six agents meet the same almost-fitting abstraction in one build window with nobody present to wince at the third; adding a required parameter to a shared implementation is also precondition strengthening.
- **NEVER refactor, rename, or restructure outside your slice.** `[→ slice prompt]` A change to an unlisted file is a defect, not a courtesy. Consequence: this is the canonical individually-helpful rule that turns into "aggressive implementation" — scope creep across files other agents are editing in the same window, and the regressions surface in slices nobody touched.
- **NEVER abbreviate inside an identifier. Spell the word.** `[→ slice prompt]` Consequence: "Abbreviation As Word In Name" is 100% of the largest measured implementation-smell delta (+1006% inconsistent naming), and six agents produce `usrRepo`, `custSvc`, `txnID` and `orderRepository` for one concept — one rule, one grep, the highest yield per instruction slot in this list.
- **NEVER put a mermaid class diagram, ER diagram, or flowchart in `code-design.md`.** `[designer]` Consequence: `*--` vs `o--` and `}o` vs `}|` are one-character semantic flips that always render, no tool in this pipeline catches them, and the diagram is a completion signal that fires before the error table, the ownership table and the import allow-lists ever get written.
- **NEVER leave a placeholder identifier (`ClassA`, `ServiceX`, `<EntityName>`) in the doc.** `[designer]` Consequence: an agent's invented names are generated from the words in its prompt, so a placeholder guarantees it mints the real name itself.
- **NEVER ask the slice agent to verify its own design compliance.** `[designer]` Consequence: LLM self-reflection on compliance scores 50.3% against passive prose at 67.0% — the check makes the outcome worse than doing nothing. This applies to the gate too: eight sentences justifying a structure leave you *more* committed to it, so field 4 must cite the spec, which you did not write.
- **NEVER unit-test a shared helper the design introduced.** `[designer]` Test the concrete behaviour at its call sites. Consequence: tests aimed at an abstraction make it irremovable — inlining it later fails the suite, and whoever proposes the inline becomes the person proposing to cut coverage. This is why section 11's builder is conditional rather than one-per-aggregate.
- **NEVER treat a green suite or a clean merge as design evidence.** `[designer]` Consequence: correct and incorrect solutions had statistically indistinguishable smell density (31.33 vs 32.93), and 600 parallel-generation trials held 5–10% semantic conflict at 100% merge success. The Refactor step needs independent stated criteria or it provably does nothing.
- **NEVER read this list as a licence to specify nothing.** The flip side is equally banned: the failure mode of an anti-abstraction doctrine is not fewer abstractions — it is **under-specified seams**, six agents each inventing their own error shape, id type, naming scheme and module layout. Be **prescriptive about every seam that crosses slices** and **silent about everything inside a slice**. Over-specification and under-specification are one bug (`spec-judge/SKILL.md:37-41`). Consequence: a doc that forbids without supplying moves the divergence somewhere no upper-bound check is looking, which is why check 16 is a floor and not a cap.
