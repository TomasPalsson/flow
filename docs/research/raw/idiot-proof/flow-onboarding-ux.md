# flow's own onboarding UX — an idiot-proofing audit of the product, 7 September 2026

**Angle.** Not "what do other harnesses do" (that is 01/02/07/08) and not "what is buggy"
(that is 09). This is: *a person sits down at a new machine and a new repo with flow. What do
they run, what happens if they skip it, and what fails without telling them?*

**Method / source grade.** Every claim below is PRIMARY: a file in this repo, or a command run
against it on 2026-09-07 in worktree `.claude/worktrees/bridge-cse_01UeHtGEcYPu5vTrSPb3uNPp`
(node v22 on Arch, HOME=/home/tomas). No network fetches — the brief scoped this to the repo.
Where a claim rests on Claude Code platform behaviour rather than flow's own code it is marked
**PLATFORM (SECONDARY, per `docs/research/07-harness-smoothness-2026.md`)** and is not
re-verified here. `UNVERIFIED` marks anything I inferred but did not execute.

---

## 0. BLUF

1. flow's headline promise — "refuses to end the turn while gates are red" — **silently does
   nothing** in any repo whose manifest yields no runnable gates. `check-all` returns no
   ecosystem → `stop-gate.sh` `hook_ok`s. Nothing in `doctor`, `init` or SessionStart says so.
2. `flow doctor` is a *deployment* doctor, not a *repo* doctor. It answers "are my symlinks
   right", never "will the harness actually do anything here".
3. Run inside a git worktree, `doctor` reports **26 pass / 0 fail** while every hook edit in
   that worktree is dead: `hooks-drift` resolves `~/.claude/hooks` to the *main* checkout and
   diffs there. The exact newcomer mistake, reported green.
4. On a genuinely fresh machine `doctor` prints **8 FAILs, none of which say `flow install`** —
   and the four checks that would diagnose "plugin not loaded" silently do not print at all,
   because they early-return when the plugin is absent.
5. `flow tutorial` is written, tested and committed — and **not wired into `bin/flow`**.
   `flow tutorial` → `unknown command`. `flow tutorial --help` → exit 0, top help, no mention.
6. There are four ways to turn enforcement off (`flow off`, `stopGate:false`, `CC_NO_*`,
   platform `disableAllHooks`) with different blast radii, and only one of them is discoverable.
7. `flow off` disables `git-guard.sh` too — the same switch that silences style nagging also
   removes the only barrier against `git reset --hard` and `rm -rf`.
8. `.claude/flow.config.json` has **no schema validation anywhere**. A typo'd key, a wrong enum
   (`stopGate: "off"`), or a wrong type silently reverts to defaults, and `doctor` says PASS.
9. `requireSpec` — the one key that can *deny every edit you make* — is absent from the README
   knob list, absent from the SPEC C4 JSON block, and absent from SessionStart's override notice.
10. Seven `CC_NO_*` / `CC_*` env vars exist. Two (`CC_NO_SPEC_GATE`, `CC_NO_POST_BASH_WRITE`)
    appear in **zero** docs. There is no `flow env`, no `--knobs`, no way to list them.
11. `docs/reference/hooks.md` is generated by truncating each hook to its **first comment line**.
    Nineteen hooks; nineteen one-line stubs. The only real hook docs are SPEC.md and the source.
12. SessionStart's 20-line cap is applied *before* `flow next`, so on any repo with a real
    PROGRESS.md the `Next:` line is dropped. Verified: it is dropped in this repo right now.
13. `flow check` in a repo with a bare `package.json` prints "No supported project file found"
    and exits 1 — the message names the wrong cause (gates absent, not manifest absent).
14. Naming has forked: plugin dir `flow`, gitignored alias `plugins/harness`, generated
    `docs/reference/plugins.md` still says "harness (28 skills)", plugin README titled
    "# harness (plugin)". The alias is on `$PATH` on this machine and `doctor` never checks it.
15. The good news, and the template to copy: `spec-gate.sh`'s deny message names the branch, the
    missing file, the fix, *and both escape hatches by exact name*. Every other block message and
    every doctor FAIL should be written to that standard.

## 1. The first-run walk, executed

### 1a. New machine

```
$ HOME=/tmp/fh2 node plugins/flow/bin/flow doctor
  WARN symlink:workflows: /tmp/fh2/.claude/workflows does not exist and no plugin provides workflows
  FAIL symlink:skills: /tmp/fh2/.claude/skills does not exist
  FAIL symlink:agents: ...            FAIL symlink:commands: ...
  FAIL symlink:scripts: ...           FAIL symlink:hooks: ...
  FAIL symlink:settings.json: ...     FAIL symlink:CLAUDE.md: ...
  FAIL settings:hooks-key: /tmp/fh2/.claude/settings.json is missing, unreadable, or has no "hooks" key
  PASS skill-index-cost: 0 chars ≈ 0 tokens
  WARN local-bin-harness: /tmp/fh2/.local/bin/flow is missing; run flow install
  WARN plugin-list: flow@skills-dir not found in claude plugin list --json
  12 pass, 6 warn, 8 fail    (exit 1)
```

Three failures in one screen:

- **No remediation on the FAILs.** `local-bin-harness` is the *only* line that says
  `run flow install`; the other eight (`bin/flow` ~:264) push a bare `does not exist`.
- **The plugin checks vanish when the plugin is missing.** `plugin-skills-flow`,
  `plugin-hooks-json`, `plugin-double-registration`, `plugin-double-load` are absent above —
  each `return`s without pushing when `~/.claude/skills/flow` is gone (`:779`, `:816`, `:868`,
  `:907`). The diagnostics for "plugin not loaded" are disabled by the plugin not being loaded.
- **`skill-index-cost: 0 chars ≈ 0 tokens` is a PASS.** Zero skills scores green on the metric
  whose purpose is catching a broken index.

`flow install` then refuses without a dotfiles checkout (exit 1; message names all three search
paths and both flags — this one is *good*). But `README.md` also advertises a checkout-free path
(`claude plugin install flow@flow`), and in that mode there is no `flow` binary on `$PATH` at
all: `doctor`, `init`, `next`, `off` and the tutorial are unreachable and nothing says so.
**The two install paths are not the same product and are documented as if they were.**

### 1b. New repo

```
$ mkdir r && cd r && git init && echo '{"name":"x"}' > package.json && git commit ...
$ flow next
Next: /flow <feature> for a feature, or just ask for a one-sentence change
```

`flow next` — the "you never have to remember a rule" command — does **not** notice that
`flow init` has never run here. State (5) in `computeNext` (`bin/flow:1789-1793`) is
"generic dirty/clean fallback"; there is no state for "unmanaged repo".

```
$ flow init
  WROTE REVIEW.md · PROGRESS.md · .claude/flow.config.json
        .github/workflows/gates.yml · .flow/eslint.thresholds.mjs · CLAUDE.md
Spread .flow/eslint.thresholds.mjs into your eslint flat config …
$ flow next
Next: /wrap before leaving, or continue
```

- Six files written; the README's follow-up is `git add REVIEW.md PROGRESS.md
  .claude/flow.config.json` — **three of six**. `CLAUDE.md`, `.flow/`, the CI gate: unmentioned.
- The next `flow next` says `/wrap before leaving` because init dirtied the tree. "Commit what
  init wrote" is not a state the engine models.
- The eslint-threshold spread is a **manual step with no enforcement** — only a later doctor
  WARN (verified: `flow-thresholds-referenced: not referenced by any lint config`). A WARN
  buried in a 30-line report is weak for a step init just requested in prose.

```

✗ No supported project file found (package.json, pyproject.toml, Cargo.toml, go.mod)   (exit 1)
```

`package.json` is right there. `detectGates()` (`skills/shared/scripts/check-all:269-288`)
requires `buildNodeGates()` to return **a non-empty gate map**; a manifest with no
test/lint/typecheck scripts falls through every branch to `{ ecosystem: null }` and `main()`
prints the manifest-missing message. **The error names the wrong cause.**

## 2. The flagship silent degradation

That same `ecosystem: null` is the input to the Stop gate.

```sh
# hooks/stop-gate.sh:398-409  (_sg_run_full_sweep)
_fs_out=$(cd "$dir" && CI=true node "$_check_all" --json 2>/dev/null)
if [ -z "$_fs_out" ]; then
    # check-all exits before printing JSON when no ecosystem is detected.
    FS_NO_ECOSYSTEM=1
    return 0
fi
# …:436-441 (_sg_attempt_full_sweep)
if [ "$FS_NO_ECOSYSTEM" -eq 1 ]; then
    if _sg_manifest_deleted; then … fi
    [ "$_rewrite" = "rewrite_stamp" ] && { date +%s >"$_gates_stamp" …; }
    return 0          # ← turn proceeds
fi
```

So: **in any repo where `check-all` finds no runnable gates, the Stop gate is a no-op, forever,
silently.** That covers a fresh app before scripts exist, a shell-script repo, a docs repo, a
Terraform repo, and a monorepo whose root manifest has no scripts. The README's spine table
promises "refuses to end the turn while red"; in those repos it never can be red.

Two more silent-death paths in the same file: `have jq || hook_ok` (`:332`) — **jq missing ⇒
dead stop gate**, even though `lib/hookout.sh` has a working `python3` fallback for
`hook_field`; and `[ ! -e "$_check_all" ] && return 0` (`:432`) — a broken `CC_SHARED_SCRIPTS`
silently allows. (`stop_hook_active` short-circuit at `:131` is correct per PLATFORM/07 §A.1.)

**None of these conditions is reported anywhere.** There is no `doctor` check named
"can this repo run gates", no SessionStart line, no `flow next` state. This is the single
largest gap between what flow promises and what a newcomer gets.

## 3. The worktree blind spot, reproduced

Run from this worktree, editing `plugins/flow/hooks/*`:

```
$ node plugins/flow/bin/flow doctor
  PASS symlink:hooks: /home/tomas/.claude/hooks -> /home/tomas/Desktop/Projects/flow/plugins/flow/hooks
  PASS hooks-drift: plugins/flow/hooks matches HEAD in /home/tomas/Desktop/Projects/flow
  26 pass, 5 warn, 0 fail
```

`doctorHooksDriftCheck` (`bin/flow:421-452`) realpaths `~/.claude/hooks`, walks up to the
enclosing `.git`, and diffs **there** — the main checkout. It never compares against `cwd`
(`git rev-parse --show-toplevel` returns the worktree; the information is one command away).
You edit `hooks/stop-gate.sh` in a worktree, reload, see no change, and doctor says all is well.

The asymmetry: flow implements exactly this warning — for `/flow` runs, not for itself.
`session-context.sh:96-108` reads `.claude/flow.json` and prints `note: flow worktree mismatch
— this flow lives in <w> (branch <b>); this session is in <top>`. The pattern exists; it was
just never pointed at the harness.

## 4. What a hook block tells you, and whether it is true

| Message (source) | Names the fix? | Correct? |
|---|---|---|
| `spec-gate.sh:170` — "…set `requireSpec:false` in .claude/flow.config.json or `CC_NO_SPEC_GATE=1` for this session." | **Yes — file, key, value, env var** | Yes. **The gold standard; copy this everywhere.** |
| `stop-gate.sh` FS_REASON — "Gate(s) failed: … Do not delete, skip, xfail, or weaken a test…" | No escape hatch named | True, but never mentions `stopGate:false` / `CC_NO_STOP_GATE=1`, so the only visible way out is to weaken a test — the thing it forbids |
| `stop-gate.sh:541` wedge valve — "the same gate blocked this session N times… suggest /lesson" | Yes | Yes |
| `git-guard.sh` coarse deny — lists every denied pattern | Names the patterns, not the override | True. There is no override; `--force-with-lease` is the documented alternative but the message does not say so |
| `size-guard` / `format-lint` feedback | No | Neither mentions `sizeGuard:false`, `CC_MAX_FILE_LINES`, or `ignore` |
| `session-context.sh:15` — "hooks are OFF … no format, size, tamper, spec, stop or git guards" | Yes (`flow on`) | **Yes** — verified: `git-guard.sh:12` does call `hook_skip_if_off`. The message is accurate; the *design* is the problem (§5) |

**Rule to adopt:** every `hook_deny` / `hook_block` / `hook_feedback` reason ends with its own
off-switch, spelled exactly. `lib/hookout.sh` already post-processes every reason through
`_lesson_nudge` — the same seam can append a per-hook `escape:` line mechanically.

## 5. `flow off` is overloaded

`hook_skip_if_off` classification, by reading all 19 hooks:

| Off-able with `flow off` | Always on |
|---|---|
| codebase-map, format-lint, **git-guard**, lesson-nudge, post-bash-write, size-guard, spec-gate, stop-gate, tamper-notice | notify, postcompact-context, pre-compact-backup, rtk-fast, rtk-rewrite, session-context, subagent-log, tool-stamp, turn-stamp, worklog-hook |

`git-guard.sh` is the one hook whose failure mode is **irreversible data loss**, and it sits
with the style nags. `flow off` in a scratch directory — precisely where `rm -rf` and
`git reset --hard` get typed casually — removes it; `docs/reference/hooks.md` lists it as a
"judging hook" alongside `format-lint`. Idiot-proof: two tiers. `flow off` silences the
*judges*; dropping the *safety* guard needs `flow off --unsafe` — or never, since
`--force-with-lease` and `git restore --source` already cover legitimate use.

## 6. Four off-switches, one discoverable

| Switch | Scope | Blast radius | Discoverable from? |
|---|---|---|---|
| `flow off [dir]` | directory + descendants, persistent | 9 hooks incl. git-guard | `flow --help`, README, SessionStart notice |
| `.claude/flow.config.json` `stopGate:false` / `sizeGuard:false` / `formatOnEdit:false` / `requireSpec:false` | repo, persistent, per-hook | one hook each | SPEC C4 + README (partial: `requireSpec` missing) |
| `CC_NO_STOP_GATE` / `CC_NO_SIZE_GUARD` / `CC_NO_SPEC_GATE` / `CC_NO_POST_BASH_WRITE` / `CC_NO_LESSON_NUDGE` = 1 | one session | one hook each | nowhere coherent; two are undocumented entirely |
| `disableAllHooks` in settings, `--safe-mode` / `CLAUDE_CODE_SAFE_MODE=1` | whole session, platform | everything | PLATFORM (SECONDARY, 07 §B); **flow's own docs never mention it exists** |

07 §G item 13 floats retiring `flow off` for `disableAllHooks`. Through this lens the verdict
inverts: keep `flow off` (directory scope is real; `--safe-mode` also kills skills and MCP),
**delete the per-hook `CC_NO_*` layer**, and give the README one line naming `--safe-mode` as
the nuclear option, so nobody invents a fifth mechanism.

## 7. Configuration has no schema

`doctorHarnessJsonOverridesCheck` (`bin/flow:473-478`):

```js
for (const k of Object.keys(C4_DEFAULTS)) {
  if (Object.prototype.hasOwnProperty.call(cfg, k)) { … diffs.push(k) }
}
```

It iterates the **defaults**, not the file. So: `maxFilesLines: 200` (typo) → ignored by every
hook, **PASS**. `codebaseMap: true` → works, but is not in `C4_DEFAULTS`, so never reported as
an override. `stopGate: "off"` → `stop-gate.sh:140` compares only against `"false"`/`"true"`;
anything else falls to scoped — you asked for off, you got on, doctor said **PASS**. Same for
`stopGate: 0` and `sizeGuard: "false"`. No type check anywhere.

Key coverage is inconsistent across the five places a key can be described:

| Key | hooks read it | `C4_DEFAULTS` | SPEC C4 JSON | README knob list | SessionStart override notice |
|---|---|---|---|---|---|
| maxFileLines / maxFuncLines | ✅ | ✅ | ✅ | ✅ | ✅ |
| stopGate / stopGateFullEverySec | ✅ | ✅ | ✅ | ✅ | ✅ |
| sizeGuard / formatOnEdit / ignore | ✅ | ✅ | ✅ | ✅ | ✅ |
| **requireSpec** | ✅ (denies edits!) | ✅ | ❌ | ❌ | ❌ |
| **codebaseMap** | ✅ | ❌ | ❌ (prose only) | ✅ | ❌ |

Setting `requireSpec: true` makes flow deny every source edit in the repo, permanently, with no
session-start notice that it is on. That is the worst-case misuse and it is the least documented.

## 8. The tutorial: promised, built, unreachable

`plugins/flow/bin/lib/tutorial.js` (321 lines) + three lessons + `scripts/tests/test_tutorial.sh`
are committed. Commits `7df4be7` ("Slice 2 — tutorial runner with lessons 1-3") and `7580745`
are on this branch.

```
$ node bin/flow tutorial
flow: unknown command 'tutorial'      (then the top help, exit 1)
$ node bin/flow tutorial --help
<top-level help — no tutorial entry>  exit 0
```

`main()` (`bin/flow:2220-2226`) has no `tutorial` branch; the file's header admits it
("bin/flow's own `tutorial` dispatch (a later slice)"). The `--help` case is worse than the bare
one: `rest.includes('--help')` short-circuits *before* dispatch (`:2207`), so any unknown
subcommand plus `--help` **exits 0 and prints a help page that does not mention it**
(`flow doctr --help` looks fine).

Reached by path (`node bin/lib/tutorial.js`) it delivers a disposable `mkdtemp` git sandbox with
a `flow` shim on a private PATH, three lessons (doctor / init / next), progress in
`~/.claude/flow-tutorial-progress.json`, `--list --reset --lesson N --sandbox`, resume on `q`.
Genuinely good design — the sandbox means a newcomer cannot damage anything. It covers 3 of 8
subcommands and none of the concepts newcomers actually get wrong (worktree, off-switches,
config keys, "why did nothing happen").

`check`, `off`, `on`, `skills-lint` and `tutorial` all fall through to the *top* help; only
`init`, `install`, `next` have real per-command help. So `flow off --help` never explains
`.claude/flow.off`, the `.git/info/exclude` write, or that git-guard goes with it.

## 9. Documentation drift, measured

- `docs/reference/hooks.md` (338 lines) is generated by extracting each hook's **first comment
  line**: nineteen entries reading `git-guard.sh — PreToolUse/Bash hook.` and nothing else. Two
  hand-written subsections (`flow off`, `hook_git_managed`) carry the file's entire information
  content. Real hook behaviour lives only in `docs/SPEC.md` and the source.
- `docs/reference/plugins.md` still lists the core plugin as **"harness (28 skills)"**;
  `plugin.json` says `flow`. The generator walked the gitignored `plugins/harness` alias.
- `README.md`'s spine table lists 12 hooks; `hooks/hooks.json` registers **24 commands** across
  11 events. Missing: `spec-gate` (can deny edits), `tool-stamp`, `lesson-nudge`,
  `post-bash-write`, `worklog-hook` (7 events — a personal integration shipped in the core
  plugin), `rtk-rewrite` (Mac-only), `postcompact-context`.
- `plugins/flow/README.md` is still the **M1 unit report**, titled `# harness (plugin)`, ending
  "do not treat this plugin as installable yet". The plugin's own README says it does not work.
- `~/.claude/skills/harness -> flow` is gitignored (`.gitignore:4`), **not created by
  `flow install`**, and wins on `$PATH` here (`command -v flow` →
  `~/.claude/skills/harness/bin/flow`, ahead of `~/.local/bin/flow`). `doctor`'s
  `local-bin-harness` validates `~/.local/bin/flow` — not the path that actually runs. On a new
  machine the alias will not exist and a profile exporting that bin dir breaks silently.

## 10. SessionStart drops the one line that matters

`hooks/session-context.sh` caps output at 20 lines (`_sc_print`) in this order: repo state (≈7)
→ `head -20 PROGRESS.md` → REVIEW.md note → config overrides → **`flow next` last**. `flow
init`'s own PROGRESS.md template is 19 lines; `doctor` permits 60. Executed against this repo
(`echo '{"session_id":"t1"}' | CLAUDE_PROJECT_DIR=$PWD bash hooks/session-context.sh`): the cap
is reached inside PROGRESS.md and **no `Next:` line is printed**. C23's "print the next command
at session start" is dead in every repo with a PROGRESS.md longer than ~12 lines — i.e. every
repo `flow init` touches. The fix is ordering, not budget: print `Next:` first.
