# Memory of Where Code Lives: Persistent Memory for Reader/Explorer Subagents

## TL;DR

Every current memory system for coding agents — Claude Code's subagent `memory` frontmatter, its auto-memory, Serena's MCP memories, community tools (claude-mem, A-MEM, hmem, darc), and Anthropic's own file-based memory tool — converges on the same shape: small, human-readable Markdown files, an index that's loaded eagerly and detail files loaded lazily, and no built-in mechanism that verifies a stored fact still matches the filesystem. Vendors document the mechanics (what loads, when, how big) in detail; none of the primary docs claim memory is validated against ground truth at read time. The strongest, most consistent warning — from Anthropic's own engineering blog down to individual practitioners — is architectural: treat memory as an index of *where to look*, not a cache of *what you'll find*, because "runtime exploration... bypass[es] the issues of stale indexing" (Anthropic, 2025) while several community builders report memory accumulating stale, unreviewed, unpruned notes that agents then trust over the actual code. The practical policy for a reader/explorer subagent falls out of this: persist entry points, seams, and search recipes (dated); recompute file contents, line numbers, and current signatures every time by reading them.

## Findings

1. **Claude Code subagents get a dedicated, scoped `memory` frontmatter field** — `memory: user | project | local` — added as first-class config, not a bolt-on. `user` scope stores at `~/.claude/agent-memory/<name-of-agent>/`, `project` at `.claude/agent-memory/<name-of-agent>/` (checked into git), `local` at `.claude/agent-memory-local/<name-of-agent>/` (gitignored). Anthropic's own guidance: "`project` is the recommended default scope. It makes subagent knowledge shareable via version control." [PRIMARY, docs.claude.com/code.claude.com, accessed 2026-09-04, undated page — reflects Claude Code ≥2.1.x as of Sep 2026]

2. **What loads and how much**: when `memory` is enabled, the subagent's system prompt automatically includes (a) instructions for reading/writing the memory directory and (b) "the first 200 lines or 25KB of `MEMORY.md`... whichever comes first," with Read/Write/Edit tools auto-granted. Topic files beyond `MEMORY.md` are *not* preloaded — the subagent reads them on demand with its normal file tools. This is an explicit two-tier design: a cheap always-loaded index, and detail fetched just-in-time. [PRIMARY, code.claude.com/docs/en/sub-agents, accessed 2026-09-04]

3. **Claude Code's own auto-memory (separate from subagent memory) times-tamps every write.** When a memory file has YAML frontmatter, Claude Code records a `modified` ISO-8601 timestamp on every write so the fact's age is visible "both to you and to Claude when it reads the memory back" [UNVERIFIED: the memo's original inline quote — "so and to Claude when it reads the memory back" — is garbled and does not match the source's actual wording; corrected quote substituted, see Source check] — direct product support for "date facts." It also enforces size discipline: if `MEMORY.md` nears its 200-line/25KB limit, Claude Code injects a reminder to "keep one line per entry, move detail into topic files, and merge or drop stale entries"; going over the limit doesn't block the write but silently truncates what's loaded next session. [PRIMARY, code.claude.com/docs/en/memory, accessed 2026-09-04, `modified` field requires Claude Code ≥2.1.214]

4. **Auto-memory deliberately excludes anything recomputable**: "Claude skips anything it can derive from the codebase, such as architecture, file paths, or debugging fixes. It also skips anything your CLAUDE.md files already say." The four categories it *does* save are `user` (role/preferences), `feedback` (corrections), `project` (decisions/deadlines not visible in code or git history), and `reference` (external pointers like an issue tracker). This is the clearest first-party statement of the "store facts, not derivable structure" principle. [PRIMARY, code.claude.com/docs/en/memory, accessed 2026-09-04]

5. **Anthropic's context-engineering guidance explicitly frames memory as an anti-staleness tool, not a staleness risk to manage separately**: agents should keep "lightweight identifiers (file paths, queries, web links)" and reload data at runtime, "mirroring human cognition" — we don't memorize corpora, we build "external organization and indexing systems... to retrieve relevant information on demand." It names Claude Code's own CLAUDE.md-plus-grep/glob pattern as the reference implementation: partial upfront context plus autonomous just-in-time exploration, "effectively bypassing the issues of stale indexing" [UNVERIFIED: re-fetch renders this as avoiding "the issues of stale indexing and complex syntax trees" — the general claim holds but this exact clipped phrase could not be confirmed verbatim, see Source check]. This is the single strongest sourced claim underpinning "recompute file locations, persist search strategy." [PRIMARY/vendor, anthropic.com/engineering/effective-context-engineering-for-ai-agents, 2025]

6. **Serena (MCP memory server for coding agents) splits memory into project-scoped (`.serena/memories/`) and global (`~/.serena/memories/global/`) stores**, organizes memories hierarchically (`modules/frontend`-style paths), and gives memories `mem:`-prefixed cross-references that get rewritten automatically on rename (`rename_memory`) — an explicit mechanism against the "stale locations after refactors" failure mode for the memory files themselves (not the code they describe). Config knobs `read_only_memory_patterns` and `ignored_memory_patterns` exist to protect/hide memories from the agent, which is an implicit acknowledgment that unpruned or wrong memories are a real operational problem. Notably, the docs are silent on whether Serena ever re-validates a memory's claims against current file contents — the design philosophy stated is "agents decide *what* to read and *when*," i.e., verification is left entirely to agent judgment, not enforced by the tool. [PRIMARY, oraios.github.io/serena, accessed 2026-09-04]

7. **Community consensus tool design increasingly favors "retrieval of exact evidence" over "summarized memory," precisely because summaries drift.** Darc (grep-like memory search for coding agents) states its philosophy as "Darc does **not** summarize your work, decide what is important, or rewrite agent state" — instead it indexes past session transcripts in SQLite so agents can query "on demand from exact evidence instead of relying only on distilled memory." [SECONDARY/GitHub README via WebFetch summary, github.com/0xjunha/darc, accessed 2026-09-04] This directly opposes tools like claude-mem and A-MEM, which do summarize/compress and store derived facts (claude-mem: SQLite + Chroma vector DB, "compresses it with AI"; A-MEM: Zettelkasten-style graph where the LLM "extracts keywords, context, and tags automatically" and links/evolves memories over time) [SECONDARY, github.com/thedotmack/claude-mem and github.com/DiaaAj/a-mem-mcp, accessed 2026-09-04]. Neither claude-mem's nor A-MEM's README documents a staleness-detection or pruning mechanism — this is a **contested design split** in the ecosystem, not consensus: evidence-retrieval tools (darc) treat compression as the risk; compression tools (claude-mem, A-MEM) treat re-discovery cost as the risk, and none of the READMEs fetched claim to solve both.

8. **Anthropic's own Memory Tool (API-level, file-based `/memories` directory) documents "memory expiration" as an unsolved operational responsibility pushed onto the developer**: "Periodically delete memory files that haven't been accessed in a long time" and "Track memory file sizes and cap how large a file can grow" are listed under Security Considerations — i.e., pruning is explicitly *not* automatic and is the integrator's job. The doc's one anti-staleness mechanism is prompting-based, not structural: developers are told to tell Claude "when editing your memory folder, always try to keep its content up-to-date, coherent and organized... Do not create new files unless necessary" if it "still creates cluttered memory files" — an admission that the default behavior drifts toward clutter without reinforcement. [PRIMARY, platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool, accessed 2026-09-04]

9. **A real-world practitioner account documents the "agent trusts memory over ground truth" failure mode directly** and reports disabling automatic session-transcript memorization after it accumulated wrong information: "if anything is worth being remembered, it will be in code comments, git commit messages, CLAUDE.md or other formal documentation" [UNVERIFIED: this exact sentence, presented in quotation marks, does not appear in the cited article; the closest actual passage is "We don't really write code by hand anymore. In order to make PRs legible, we emphasize good commit messages, good pr messages, and comprehensive documentation." — the underlying claim (human-reviewed artifacts over agent-written notes) is directionally consistent with the article but this is not a verbatim quote; see Source check] — i.e. human-reviewed artifacts, not agent-written notes. The same piece reports that in a weekly human-review process, only ~20% of automatically-proposed memory updates were accepted ("We accept less than 20% of these"), and that in "thousands of sessions" the author had "never seen" an agent autonomously and correctly prune stale memory content on its own ("across literal thousands of sessions, I've never seen it happen even once"). Root causes cited: models are "penalized for assuming that the input data is wrong" during training (so they default to trusting stored context as intentional), and agents treat all prior memory/scratch content "as an expression of intent" even when it was never reviewed. [SECONDARY/opinion, 12gramsofcarbon.com/p/agentics-memorizing-session-transcripts, surfaced via HN comment thread, accessed 2026-09-04 — single practitioner's account, not a controlled study, treat as informed opinion/anecdote rather than measured result]

10. **Vendor-reported (unverified) statistics on real-world staleness**: a commercial "CLAUDE.md automation" product's launch post claims industry data showing "only 5% of repositories had adopted AI configuration files" and that of repos with `AGENTS.md`, "50% were never modified after the initial commit" — cited by the vendor to motivate their automated-rule-maintenance product. This is a **vendor claim with no linked primary study** found in the fetched page; treat the specific percentages as unverified marketing framing, though directionally consistent with independent reports (CodeYam: "we weren't updating them frequently enough to be effective," "outdated information... actively causing confusion"). [VENDOR/SECONDARY, blog.codeyam.com/p/introducing-the-codeyam-cli-with, accessed 2026-09-04]

11. **Regenerate-rather-than-accumulate has a working precedent outside "memory" framing**: aider's repo map is rebuilt fresh on (essentially) every request using a PageRank-style graph-ranking algorithm over file dependency edges, token-budgeted (`--map-tokens`, default 1,000) and dynamically resized based on chat state — it is a computed index, not a stored/accumulated one, and so cannot itself go stale between sessions (though the underlying computation cost is paid every time). No caching/staleness-avoidance tradeoff is discussed in the docs fetched, but the design itself is the pattern: recompute a lightweight structural summary instead of persisting one. [PRIMARY, aider.chat/docs/repomap.html, accessed 2026-09-04]

## Downsides and failure modes

- **Stale locations after refactors**: no primary source for any tool reviewed (Claude Code auto-memory/subagent memory, Serena, claude-mem, A-MEM, hmem, darc) documents automatic detection of "this file path/line/signature I remembered no longer matches the code." Serena mitigates *memory-to-memory* reference rot (via `mem:` link rewriting on `rename_memory`) but this only fixes links between memory notes, not drift between a memory note and the actual source it describes. Anthropic's context-engineering post treats this as solved *by design choice* (just-in-time exploration) rather than something memory tooling detects and corrects.
- **Agent trusting memory over the filesystem**: documented directly in practitioner reporting (Finding 9) as the dominant real-world complaint — agents treat old, possibly-wrong memory content as ground truth rather than re-verifying, partly because RLHF-style training penalizes assuming input is wrong. No vendor doc reviewed instructs subagents to cross-check a stored fact against a fresh read before acting on it; the Claude Code subagent-memory docs' own example prompt ("check your memory for patterns you've seen before") asks the agent to consult memory but not to verify it.
- **Cross-project leakage**: partially engineered around, not eliminated. Claude Code auto-memory is explicitly scoped "per repository, shared across worktrees" and is "machine-local... not shared across machines or cloud environments" [PRIMARY, code.claude.com/docs/en/memory] — a structural leakage guard. Serena splits project vs. global (`~/.serena/memories/global/`) memory, which is itself an admission that a single undifferentiated store would leak facts about one codebase into another's context. No source reviewed reports a *concrete leakage incident*; the guardrails found are preventive design, not postmortems, and a general HN search for "cross-project leakage AI agent memory" returned zero hits, suggesting this is an under-discussed/under-reported risk relative to staleness.
- **Growth without pruning**: the most consistently under-solved problem across every tool. Anthropic's own Memory Tool docs push size-capping and expiration entirely onto the developer ("periodically delete memory files that haven't been accessed") rather than solving it in the tool. Claude Code's `MEMORY.md` has a hard 200-line/25KB *read* budget enforced with an in-band reminder to prune, but content past that limit is simply dropped from context next session — silently truncated, not actively curated. claude-mem and A-MEM READMEs (fetched) contain no pruning/retention policy at all. The 12gramsofcarbon account reports agents essentially never self-prune in practice.
- **Vendor-claim inflation**: CodeYam's specific "5% adoption / 50% never modified" figures are asserted without a citation in the fetched page — plausible directionally given corroborating anecdotes, but should not be repeated as measured fact.

## Concrete setup (exact commands/config from sources)

**Enable subagent persistent memory** (Claude Code, project-scoped, recommended default):
```yaml
---
name: code-reviewer
description: Reviews code for quality and best practices
memory: project
---

You are a code reviewer. As you review code, update your agent memory with
patterns, conventions, and recurring issues you discover.
```
Storage path: `.claude/agent-memory/<name-of-agent>/` (checked into git). Use `memory: user` → `~/.claude/agent-memory/<name>/` for cross-project learnings, or `memory: local` → `.claude/agent-memory-local/<name>/` (gitignored) for project-specific-but-personal notes. Subagent memory requires auto memory to be enabled globally (`autoMemoryEnabled`, on by default) or it silently has no effect. [PRIMARY, code.claude.com/docs/en/sub-agents]

**Instruct the subagent to actually use memory** (put directly in the subagent's markdown body):
```markdown
Update your agent memory as you discover codepaths, patterns, library
locations, and key architectural decisions. This builds up institutional
knowledge across conversations. Write concise notes about what you found
and where.
```
And drive it conversationally: "Review this PR, and check your memory for patterns you've seen before" before starting, "Now that you're done, save what you learned to your memory" after. [PRIMARY, code.claude.com/docs/en/sub-agents]

**Check what actually loaded**: run `/context` in a session to see which CLAUDE.md/memory files loaded; run `/memory` to browse, open, or toggle auto memory; run `/doctor` (Claude Code ≥2.1.206) to get proposed trims of a checked-in CLAUDE.md that strip content Claude can derive from the codebase (directory layouts, dependency lists, architecture overviews) and keep only pitfalls/rationale/non-default conventions. [PRIMARY, code.claude.com/docs/en/memory]

**Redirect auto-memory storage location** (e.g., to keep it out of a synced home dir):
```json
{
  "autoMemoryDirectory": "~/my-custom-memory-dir"
}
```
[PRIMARY, code.claude.com/docs/en/memory]

**Serena project memory tools** (MCP): `write_memory`, `read_memory`, `list_memories` (topic-filterable); CLI maintenance: `serena memories check` (integrity validation), `serena memories auto-prefix-references`. Disable entirely via config: add `no-memories` or `no-onboarding` to `base_modes`. Protect a memory from agent edits with `read_only_memory_patterns`; hide obsolete ones from tool access with `ignored_memory_patterns`. [PRIMARY, oraios.github.io/serena]

**Anthropic Memory Tool (API level)** — minimal request enabling file-based memory:
```json
{
  "model": "claude-opus-5",
  "max_tokens": 2048,
  "messages": [{"role": "user", "content": "Help me respond to this customer service ticket."}],
  "tools": [{"type": "memory_20250818", "name": "memory"}]
}
```
Your application must implement the `/memories` file-op handler (view/create/str_replace/insert/delete/rename) and is responsible for path-traversal protection, size caps, and periodic expiration of unused files — none of this is automatic. [PRIMARY, platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool]

## Policy: what a reader/explorer subagent should remember vs. recompute

Given the above, for a reader/explorer subagent whose job is knowing *where code lives*:

**Remember (persist, dated, in `.claude/agent-memory/<agent>/`, project scope):**
- Entry points: where `main()`/app bootstrap/router root/build entry lives, and why (one line each).
- Seams: module boundaries, plugin registration points, the file that owns a cross-cutting concern (auth, config loading, DB migrations) — the kind of fact that takes real exploration to find and is stable across most refactors.
- Search recipes: "grep for `X` to find all handlers," "the feature-flag registry is wherever `FEATURE_FLAGS` is imported" — a *procedure* for relocating something, not the location itself, so it self-heals when the location moves.
- Known dead ends / traps: "don't trust the `legacy/` dir, it's unused since 2025-11" — negative knowledge that's expensive to rediscover and doesn't drift the same way positive file-path facts do.
- Every entry timestamped (`modified` frontmatter or an explicit date in the line) so a later reader can judge whether to trust or re-verify it, mirroring Claude Code's own `modified`-field practice (Finding 3).

**Recompute every time (never trust the stored copy):**
- Exact file paths, line numbers, and function/class signatures — these are exactly what Anthropic's context-engineering guidance calls out as best fetched "just-in-time" via grep/glob rather than cached, specifically because it "bypass[es] the issues of stale indexing" (Finding 5).
- Current file contents, current dependency graphs, current test status — anything a single `Read`/`Grep`/`Glob` call answers authoritatively and cheaply, per Claude Code auto-memory's own exclusion rule: skip "anything it can derive from the codebase" (Finding 4).
- Anything only useful once (a one-off search result, a specific line of a specific commit) — Darc's "evidence over memory" philosophy (Finding 7) argues these belong in on-demand retrieval, not distilled/pre-chewed memory.

**Before acting on any remembered location fact**, verify it with one cheap read/glob before relying on it for an edit — none of the tools surveyed enforce this automatically (Downsides, "trusting memory"), so it has to be a stated instruction to the subagent, not an assumption about the tooling.

**Prune aggressively, on a schedule, not reactively**: since every tool surveyed either drops old content silently past a size limit (Claude Code's `MEMORY.md`) or pushes expiration onto the integrator with no default (Anthropic Memory Tool), and since practitioner reporting says agents essentially never self-prune (Finding 9), treat memory file review as a periodic human or scripted task — e.g., mirror Serena's `read_only_memory_patterns`/`ignored_memory_patterns` split (curated vs. quarantined) or CodeYam's "continuous auditing that detects when rules become stale as code changes" as the target behavior, even where the tool doesn't do it for you today.
