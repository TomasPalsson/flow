# Static codebase maps vs. live exploration for coding agents

## TL;DR

There are two competing philosophies for giving an agent a mental model of a repo, and every real tool picks one: (1) a small, hand-curated, checked-in file (CLAUDE.md, AGENTS.md, matklad-style ARCHITECTURE.md) that encodes durable "why/where" facts a script can't infer, kept honest by staying short and being reviewed rarely; or (2) a mechanically regenerated structural map (aider's repo map, repomix, gitingest, community "codebase-map" generators) rebuilt from source on every use, which can't go stale but also can't carry curated rationale. Anthropic's own Claude Code documentation — the most authoritative, current, primary source found — explicitly argues *against* using the static file as a full codebase map ("exclude anything Claude can figure out by reading code," "file-by-file descriptions of the codebase") and instead recommends live exploration via subagents for structure, reserving the static file for non-derivable conventions. Concrete size numbers exist (Claude Code: target <200 lines / hard 4 MiB cap; auto-memory index: hard 200-line/25KB cutoff; aider: ~1,000-token default map budget), but no mainstream tool yet has a mature, widely-adopted mechanism for verifying a static map's claims are true — the one example found (a linter that checks every referenced path exists) is a low-traction, likely-unmaintained side project, not a standard. Regeneration strategies in the wild split three ways: every invocation (aider, repomix/gitingest — "it's a build artifact, not documentation"), on git commit hook (a community "codebase-md" tool), and on session start / on-demand via slash command (Claude Code's `/init`, `/doctor`). I could not find or verify a citable public source for "OpenAI's harness-engineering docs/ tree with an index and a doc-gardening agent" or for a distinct "Conductor context files" feature — both are flagged as gaps below rather than guessed at.

## Findings

1. **Anthropic explicitly tells users *not* to make CLAUDE.md a full codebase map.** The official best-practices guidance lists "File-by-file descriptions of the codebase" and "Anything Claude can figure out by reading code" under things to *exclude*, and frames CLAUDE.md as being for "Bash commands Claude can't guess," non-default code-style rules, and project-specific gotchas — i.e., facts live exploration can't recover, not structure it can. [code.claude.com/docs/en/best-practices](https://code.claude.com/docs/en/best-practices) — fetched Sept 2026, PRIMARY, vendor documentation (current).

2. **Claude Code gives hard, numeric size budgets, not just "keep it short."** Guidance: target under 200 lines per CLAUDE.md (longer files "consume more context and reduce adherence"); a checked-in CLAUDE.md over ~4 MiB is skipped entirely; the *auto-memory* index file `MEMORY.md` has a hard read limit of the first 200 lines or 25KB (whichever comes first) — content past that is silently dropped on the next session load, and the harness nudges Claude to shorten the file when it gets close to the limit. [code.claude.com/docs/en/memory](https://code.claude.com/docs/en/memory) — fetched Sept 2026, PRIMARY, vendor documentation (current). This is a **consensus-adjacent, vendor-stated** number — the same "shorter is better for adherence" claim is repeated independently in the best-practices doc's "over-specified CLAUDE.md" failure pattern, i.e., two independent sections of the same vendor's docs converge on it.

3. **Anthropic's own tooling treats a static map as inherently decaying and gives two different fixes: regeneration on demand, and automatic pruning.** `/init` generates a starter CLAUDE.md by having a subagent explore the codebase (and, if a CLAUDE.md already exists, `/init` *suggests improvements rather than overwriting*); a newer interactive flow (`CLAUDE_CODE_NEW_INIT=1`) explores with a subagent, asks follow-up questions, and presents a reviewable proposal before writing. Separately, `/doctor` proposes trims to an existing checked-in CLAUDE.md, specifically cutting "content Claude can derive from the codebase, such as directory layouts, dependency lists, and architecture overviews" while keeping "pitfalls, rationale, and conventions that differ from tool defaults." [code.claude.com/docs/en/memory](https://code.claude.com/docs/en/memory) — fetched Sept 2026, PRIMARY, vendor. Notably, both `/init` and `/doctor` are **on-demand / human- or agent-triggered**, not automatic on every session — Claude Code does not ship an automatic "regenerate CLAUDE.md" hook out of the box.

4. **CLAUDE.md and CLAUDE.local.md are re-read fresh from disk at the start of every session, and the project-root file is explicitly re-read after every `/compact`** — so the "SessionStart" regeneration point already exists as a *load* point in Claude Code's architecture even without a custom hook; a generator script only needs to write the file before that load happens. Nested CLAUDE.md files and path-scoped rules instead reload lazily, when Claude reads a file in that subdirectory. [code.claude.com/docs/en/memory](https://code.claude.com/docs/en/memory) — fetched Sept 2026, PRIMARY, vendor (current).

5. **AGENTS.md is a separate, cross-vendor open convention (not read natively by Claude Code) stewarded by the Agentic AI Foundation under the Linux Foundation**, with no prescribed length, described as "living documentation," and used (per the site's own claim) by over 60,000 open-source projects, with support cited from OpenAI Codex, Amp, Google Jules, Cursor, and Factory. In monorepos, nested AGENTS.md files are recommended, with the closest file to the edited code taking precedence. [agents.md](https://agents.md/) — fetched Sept 2026, PRIMARY, but the adoption/support numbers are **self-reported / vendor-coalition claims**, not independently verified. Claude Code's own docs confirm it reads `CLAUDE.md`, not `AGENTS.md`, and recommend either `@AGENTS.md` import syntax or a symlink (`ln -s AGENTS.md CLAUDE.md`) so both tools share one source rather than maintaining duplicate files. [code.claude.com/docs/en/memory](https://code.claude.com/docs/en/memory) — same fetch, PRIMARY.

6. **matklad's ARCHITECTURE.md argument is an opinionated blog post, not a formal spec, and it explicitly designs the format around staleness by scoping it down, not by updating it often.** Core claims (his own framing, presented as personal judgment rather than measured fact): for 10k–200k LOC projects, the hard part of a contribution isn't writing code (maybe "2x harder" unfamiliar) but figuring out *where* to change it ("10x harder"); the fix is a short, coarse-grained "codemap" of modules and their relationships, naming important files/types but avoiding fine-grained links that will break, so that it only needs a **revisit "a couple of times a year"** rather than continuous synchronization. He cites rust-analyzer's `docs/book/src/contributing/architecture.md` as the model example. [matklad.github.io/2021/02/06/ARCHITECTURE.md.html](https://matklad.github.io/2021/02/06/ARCHITECTURE.md.html) — fetched Sept 2026, PRIMARY, personal-blog OPINION (well-regarded in the Rust/systems community but not a standard). I independently verified the referenced doc is real and currently **517 lines** as of Sept 2026: [github.com/rust-lang/rust-analyzer/blob/master/docs/book/src/contributing/architecture.md](https://github.com/rust-lang/rust-analyzer/blob/master/docs/book/src/contributing/architecture.md) — verified via raw fetch, PRIMARY. Note this is ~2.5x Anthropic's <200-line CLAUDE.md target — the numbers aren't in tension, because the two documents serve different consumers: one is read by humans a few times a year, the other is injected into every LLM context window.

7. **aider's repo map is not a static file at all — it's rebuilt live, budgeted in tokens rather than lines, and ranked algorithmically.** It replaced an original ctags-based system with tree-sitter parsing (via `py-tree-sitter-languages`, avoiding an external binary dependency), extracts symbol/signature information per file, then applies "a graph ranking algorithm, computed on a graph where each source file is a node and edges connect files which have dependencies" (a PageRank-style approach) to select the most important identifiers within a configurable budget — `--map-tokens`, defaulting to roughly 1,000 tokens — and the map's actual size is adjusted dynamically: it shrinks when many files are already in the chat and expands significantly when no files are in context and the model needs broader repo understanding. Docs explicitly acknowledge the tradeoff: the map deliberately includes only "the most important identifiers," not every symbol, so it can miss context on large repos even after ranking. [aider.chat/docs/repomap.html](https://aider.chat/docs/repomap.html) and [aider.chat/2023/10/22/repomap.html](https://aider.chat/2023/10/22/repomap.html) — fetched Sept 2026, PRIMARY (docs + project blog). This is the clearest real-world instance of the "regenerate on every request" strategy in the question.

8. **repomix and gitingest both target the opposite failure mode — an unconstrained full-repo dump blowing the context budget — with different levers.** repomix outputs XML/Markdown/JSON/plain-text bundles and provides: per-file and aggregate token counts (configurable tokenizer, GPT-4o by default), a `--compress` flag using tree-sitter to keep only function/class signatures (vendor claims **~70% token reduction**), a `--token-budget` flag that fails the run with a non-zero exit code if the packed output exceeds a set ceiling (explicitly pitched for CI use), `--split-output` for chunking large outputs, a watch mode (`-w`) that repacks continuously during development, and an MCP server mode so an agent can request a pack/search/read on demand rather than working from a stale static bundle. [github.com/yamadashy/repomix](https://github.com/yamadashy/repomix) and [repomix.com/guide/output](https://repomix.com/guide/output) — fetched Sept 2026, PRIMARY, vendor (compression-ratio number is a **vendor claim**, not independently benchmarked here). gitingest is simpler: it turns a repo (or any GitHub URL, by swapping "hub"→"ingest") into a summary + tree + concatenated file contents, with a tiktoken-based token estimate and a default 50KB per-file inclusion cutoff, but its documentation gives **no explicit guidance on staleness or scheduled regeneration** — like the aider map, it's designed to be run on demand rather than committed as a persisted doc. [github.com/cyclotruc/gitingest](https://github.com/cyclotruc/gitingest), [gitingest.com](https://gitingest.com) — fetched Sept 2026, PRIMARY.

9. **A concrete, if small and unofficial, tool operationalizes each of the two regeneration strategies the question asks about.** `codebase-md`, a community Python CLI, scans a repo once (tree-sitter AST parsing for conventions, dependency-manifest parsing across `package.json`/`requirements.txt`/`pyproject.toml`/`go.mod`/`Cargo.toml`/`Gemfile`, git-hotspot analysis) and writes six overlapping context files in one pass — `CLAUDE.md`, `.cursorrules`, `AGENTS.md`, `codex.md`, `.windsurfrules`, `PROJECT_CONTEXT.md` — and explicitly documents **git post-commit hooks for auto-regeneration on commit** as its staleness fix. [github.com/sauravanand542/codebase-md](https://github.com/sauravanand542/codebase-md) — fetched Sept 2026, PRIMARY, small/community project (surfaced via Hacker News, 1 point, [news.ycombinator.com/item?id=47272113](https://news.ycombinator.com/item?id=47272113)) — treat as illustrative of a pattern, not as an authoritative or widely-adopted standard. Writing six near-duplicate files is also in direct tension with Claude Code's own recommendation (finding 5) to have *one* file import another rather than maintain parallel copies that can drift from each other independently of drifting from the code.

10. **"Lint that every path exists" is a real but immature/low-adoption idea, not a built-in feature of any mainstream tool reviewed.** The one implementation found, `agents-lint`, checks that every filesystem path referenced in AGENTS.md/CLAUDE.md-style files still exists on disk, validates referenced npm scripts against `package.json`, flags deprecated dependencies and outdated framework patterns (e.g., pre-14 Angular `@NgModule` idioms, removed `ReactDOM.render()`), cross-checks multiple context files for conflicting build commands, and computes a 0–100 "freshness" score; it's suggested for a **weekly scheduled GitHub Action** specifically because context can rot from *external* drift (a dependency going deprecated) even when the repo itself hasn't changed, which a commit-hook-triggered regenerator would miss entirely. [github.com/giacomo/agents-lint](https://github.com/giacomo/agents-lint), surfaced via [news.ycombinator.com/item?id=47189911](https://news.ycombinator.com/item?id=47189911) — fetched Sept 2026, PRIMARY but **very low-traction (1 HN point)**, likely experimental/unmaintained — presented as evidence the idea exists and is easy to build, not that it's a mature or adopted practice. No such path-existence check is mentioned anywhere in the Anthropic docs, the AGENTS.md spec, aider's docs, or repomix/gitingest's docs.

11. **Vendor "context system" products (Agent OS, Conductor) claim to solve this but are thin on verifiable regeneration/size specifics in their public docs.** Agent OS (buildermethods.com) is pitched as "a lightweight system for defining and managing your coding standards in AI-powered development," storing everything as markdown under an `agent-os/` directory, with a four-phase workflow (Discover → Inject → Shape → plan-mode refinement); its v3 release mentions "automatic discovery," implying some re-scan capability, but the fetched page does not specify exact file names, target sizes, or an update cadence. [buildermethods.com/agent-os](https://buildermethods.com/agent-os) — fetched Sept 2026, PRIMARY, vendor, **claims not independently verified**. For Conductor, I could not find public documentation describing a distinct "context files" feature at all (the marketing page only describes running parallel agents in isolated git-worktree workspaces) — flagged as a **gap**, not a finding.

## Downsides and failure modes

- **Bloat degrades instruction-following, per the vendor that would most want CLAUDE.md to work well.** Anthropic states directly, in two separate sections of current docs, that longer files "consume more context and reduce adherence," and names "the over-specified CLAUDE.md" as one of a short list of named common failure patterns, where "Claude ignores half of it because important rules get lost in the noise." [code.claude.com/docs/en/best-practices](https://code.claude.com/docs/en/best-practices), [code.claude.com/docs/en/memory](https://code.claude.com/docs/en/memory) — PRIMARY, vendor.
- **Full-repo dumps routinely exceed context budgets**, which is *why* repomix ships `--compress`, `--token-budget`, and `--split-output` rather than just packing everything by default — the existence of these flags is itself evidence from the vendor that unconstrained maps don't scale to real repos. [github.com/yamadashy/repomix](https://github.com/yamadashy/repomix) — PRIMARY.
- **Static maps drift from the code the moment a file moves or a symbol is renamed, and almost nothing checks this automatically.** Only one low-traction community tool (`agents-lint`) does path-existence verification; it isn't part of any core agent product's default workflow. This is a genuine, confirmed gap in current tooling, not just an assumption. [github.com/giacomo/agents-lint](https://github.com/giacomo/agents-lint) — PRIMARY, low-confidence-adoption.
- **Practitioner anecdote (community, not vendor) confirms the failure mode in the wild**: a Hacker News submission titled "Knowl – CLAUDE.md hit 1000 lines, so I built memory that prunes itself" describes exactly the runaway-growth problem Anthropic's own size guidance is meant to prevent. [news.ycombinator.com/item?id=49399942](https://news.ycombinator.com/item?id=49399942) — SECONDARY, anecdotal/one data point, treat as illustrative only.
- **Mechanically-regenerated maps (aider, gitingest, repomix) solve staleness by construction but can't carry curated rationale.** They show *what* exists (symbols, files, dependency edges) but not *why* the architecture is shaped that way — the exact gap matklad's ARCHITECTURE.md is designed to fill and the exact content Anthropic's `/doctor` explicitly preserves ("pitfalls, rationale, and conventions") when trimming everything else. No source reviewed claims a purely mechanical map can replace curated prose; the two approaches are complementary, not substitutes, in every source that discusses both.
- **Duplicated-file generators (codebase-md, Agent OS-style multi-tool output) add a second staleness axis**: files can drift from *each other*, not just from the code, especially since Claude Code's own guidance explicitly favors one canonical file with an import over parallel copies. [code.claude.com/docs/en/memory](https://code.claude.com/docs/en/memory) — PRIMARY.
- **Live exploration isn't free either — it's the reason static maps get proposed in the first place.** Anthropic's own best-practices doc names "the infinite exploration" (Claude reads hundreds of files investigating an unscoped question, filling the context) as a named failure pattern, and its recommended fix is delegating exploration to subagents that run in a separate context window — i.e., the vendor's answer to "map vs. live exploration" is neither a full static map nor unscoped live exploration, but *scoped, subagent-isolated* live exploration plus a short curated file for what exploration can't discover. [code.claude.com/docs/en/best-practices](https://code.claude.com/docs/en/best-practices) — PRIMARY.

## Concrete setup

A solo dev running Claude Code could combine the patterns actually documented across these sources into one lightweight generator:

**1. Generator script — cheap, deterministic, no LLM call.** A shell/Python script (e.g. `scripts/gen-codebase-map.sh`) that:
- Builds a pruned directory tree (`tree -L 3 -I 'node_modules|dist|.git'` or equivalent), consistent with the "coarse codemap, not file-by-file description" guidance from matklad and from Anthropic's exclude-list.
- Extracts exported symbols/entry points using the same class of tool aider uses — tree-sitter or `ctags` — rather than asking a model to read every file, since this is exactly the mechanism aider's repo map and repomix's `--compress` both use to stay cheap and deterministic.
- Detects entry points from known filenames (`main.py`, `index.ts`, `cmd/*/main.go`) and manifest fields (`package.json` `main`/`bin`, `pyproject.toml` `[project.scripts]`), rather than guessing.
- Enforces a **hard line/token cap** on output (mirror Anthropic's <200-line target for anything injected every session, or aider's ~1,000-token default for anything meant to be dynamically sized), truncating deterministically — e.g., keep only the top-N files by import in-degree, aider's own ranking heuristic — rather than growing unbounded.
- Writes the result to `.claude/codebase-map.md`, imported from the project's `CLAUDE.md` via Claude Code's documented `@path` import syntax (`@.claude/codebase-map.md`), and stamps it with the current commit hash and generation timestamp inside an HTML comment — Claude Code strips block-level HTML comments before injecting CLAUDE.md content into context, so the stamp costs no context tokens but is still visible to a human or a lint step reading the raw file. [code.claude.com/docs/en/memory](https://code.claude.com/docs/en/memory) — PRIMARY, confirms both the `@path` import mechanism and the comment-stripping behavior.

**2. Regeneration trigger — SessionStart, with a git-hash short-circuit, not PostToolUse.** Register the script as a `SessionStart` hook. On every session launch it compares the stamped commit hash in `.claude/codebase-map.md` against the current `git rev-parse HEAD`; if unchanged, it exits immediately (a git-hash comparison is sub-100ms, far cheaper than re-parsing the tree), and only regenerates on a mismatch. This mirrors the load point Claude Code already uses for CLAUDE.md itself — fresh from disk at every session start and again after every `/compact` — so the generator only has to win the race to write the file *before* that load happens, not invent a new lifecycle event. `PostToolUse` was considered and rejected for a solo dev: it would fire after every single `Edit`/`Write`, and most individual edits don't change the shape of exports/entry points enough to justify a full regen on every one — that granularity fits repomix's dev-time `--watch` mode better than a context file meant to be injected into every session.

**3. Honesty check — a companion lint step, run separately from generation.** A second script (or a weekly scheduled CI job, following `agents-lint`'s reasoning that context can rot from *external* drift even without local commits) walks every file path named in the generated map and asserts it still resolves with `test -e`; on failure it exits non-zero rather than letting a broken map ship silently. This is deliberately kept separate from the generator itself, on the theory (implicit in every source that discusses trust) that a self-checking generator can't catch its own logic bugs — an independent check is the only way to catch, say, the change-detector missing a case.

**Downside of this design, stated directly**: the map is produced by cheap structural heuristics — export lists and an import graph — not judgment, so it will faithfully report *what* exists but never *why*, inheriting exactly the gap Anthropic's own docs warn against filling with derivable content and the gap matklad designed ARCHITECTURE.md's coarse, curated codemap to cover instead. Worse, the regeneration trigger has a specific, easy-to-miss blind spot: a git-hash short-circuit compares against `HEAD`, so it will happily report "unchanged" during exactly the sessions where staleness matters most — mid-refactor, with uncommitted or staged-but-not-committed changes — because the working tree has moved but the last commit hasn't. None of the sources reviewed (including the one dedicated path-existence linter, which is itself a 1-point, likely-unmaintained side project) has a mature answer to "how do you validate the invalidator" — as of September 2026 that remains a genuinely open, mostly-unsolved problem across the tools surveyed here, not a solved-and-just-not-well-known one.
