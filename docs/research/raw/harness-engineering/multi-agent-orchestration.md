# When Multi-Agent Fan-Out Helps for Coding (2026 Status)

## TL;DR

- Anthropic's own research team said outright, in the post that popularized multi-agent orchestration, that **coding parallelizes worse than research**: "most coding tasks involve fewer truly parallelizable tasks than research," and agents aren't yet good at real-time coordination/delegation. That post is about a *research* product, not a coding one. (PRIMARY, anthropic.com/engineering, Jun 13 2025)
- The famous **~15x token-cost multiplier** is real but is Anthropic's own research-system number, not a general coding-agent number; Claude's own newer guidance (Jan 2026) gives a lower, coding-oriented range of **3–10x**. Treat 15x as "one credible data point for a specific heavy-parallel research workload," not a universal constant. (PRIMARY, both Anthropic properties)
- Cognition (Devin) went from **"Don't Build Multi-Agents"** (Jun 2025, context-fragmentation argument, the Flappy Bird example) to **"Multi-Agents: What's Actually Working"** (Apr 2026): the reversal is narrow — multi-agent works when **writes stay single-threaded** and the extra agents only contribute intelligence (review, consult, coordinate), never independent parallel edits. This is the single most load-bearing conceptual pivot in the whole space. (PRIMARY, cognition.com, both posts by Walden Yan)
- The Bun Zig→Rust rewrite (~$165k API spend, 5.9B input / 690M output tokens, ~64 concurrent Claude instances at peak, 11 days, ~1M LOC, 100% of the existing test suite passing pre-merge) is the flagship "fleet coding works" case — but it worked because of an unusually favorable setup: a pre-existing 1.38M-assertion, language-independent test oracle as an objective referee, git-worktree file-scope isolation, adversarial implementer/reviewer loop, and one deeply-expert human (Jarred Sumner, who co-founded Bun) doing continuous process-level supervision rather than line-by-line review. (PRIMARY: claude.com/blog + simonwillison.net; SECONDARY: developersdigest.tech)
- That same case is contested: Zig's creator Andrew Kelley publicly called the shipped result "unreviewed slop," arguing the huge test suite doesn't substitute for review and that Bun's pre-existing code quality problems (not Zig) were the real issue — a useful counterweight to the "just trust the process" framing. (PRIMARY quote via SECONDARY reporting, The Register, Jul 14 2026)
- Official Claude Code guidance (agent-teams docs) gives a concrete, current decision rule: use a single session or subagents for **sequential tasks, same-file edits, or heavy-dependency work**; use agent teams only when teammates can be genuinely independent (new modules, cross-layer split, competing-hypothesis debugging, multi-angle review). Default team size: **3–5**, sized to 5–6 tasks per teammate; token cost scales roughly linearly with teammate count, with real coordination overhead on top. (PRIMARY, code.claude.com, doc version "as of v2.1.178", accessed Sep 2026)
- Academic work in 2026 backs the "small teams, real interfaces" rule with numbers: an inverted-U in performance vs. agent count, a rule of thumb that if a single agent already clears ~45% success rate, adding coordination *hurts*; a "Ringelmann effect" scaling-law paper showing effective (not nominal) team size plateaus; and a coordination-measurement paper (UCL, Aug 2026) showing failures cluster at **unowned interfaces** ("belonged to neither" agent) rather than from raw message volume. (PRIMARY papers, arXiv, 2026)
- The recurring pattern across every credible 2026 source — Anthropic, Cognition, Claude Code docs, and the academic papers — converges on the same rule: **decompose by who owns which files/interfaces and keep writes single-owner; let review/consultation be the parallel part.** "One strong agent + an adversarial reviewer with a clean, independent context" is the load-bearing pattern that keeps showing up (Cognition's code-review loop finding ~2 bugs/PR with 58% severe; Bun's implementer + 2+ reviewers).

## Findings

1. **Claim:** Anthropic's multi-agent research system outperformed a single agent by 90.2% on an internal research eval, but the same post explicitly flags that coding is a worse fit for this architecture than research.
   **Evidence:** "A multi-agent system with Claude Opus 4 as the lead agent and Claude Sonnet 4 subagents outperformed single-agent Claude Opus 4 by 90.2% on our internal research eval." / "most coding tasks involve fewer truly parallelizable tasks than research, and LLM agents are not yet great at coordinating and delegating to other agents in real time."
   **Source:** https://www.anthropic.com/engineering/multi-agent-research-system (Jun 13, 2025)
   **PRIMARY. Standard/consensus** — this framing (research parallelizes, coding mostly doesn't) is echoed by every later Anthropic and Cognition source found.

2. **Claim:** Multi-agent systems use ~15x more tokens than single-turn chat interactions; token usage alone explains ~80% of the performance variance in Anthropic's internal eval, with number of tool calls and model choice as the other two factors.
   **Evidence:** "Multi-agent systems use about 15× more tokens than chats." Also (via secondary aggregation of the same post): token usage explains 80% of variance.
   **Source:** https://www.anthropic.com/engineering/multi-agent-research-system (Jun 13, 2025)
   **PRIMARY (15x figure and economic-viability framing) / SECONDARY (80%-variance framing, reported by multiple blogs e.g. Codingscape/X and getnadir.com but consistent with the primary post's content).** Standard/consensus as *the* canonical citation, but scoped to Anthropic's own research-agent workload — not validated as a general coding-agent number.

3. **Claim:** Claude's more recent, coding-oriented guidance gives a materially lower multiplier — "3-10x more tokens than single-agent approaches for equivalent tasks" — and states plainly that outside three specific scenarios (context protection, parallelization of independent work, tool/domain specialization), coordination costs exceed the benefit.
   **Evidence:** "Multi-agent implementations typically use 3-10x more tokens than single-agent approaches for equivalent tasks." / "the coordination costs typically exceed the benefits" outside those scenarios. Also gives the key coding-specific decomposition rule: "Dividing by context boundaries means an agent handling a feature should also handle its tests, because it already possesses the necessary context," and warns against problem-centric splits (separate planning/coding/testing agents) because they create "telephone game" coordination losses.
   **Source:** https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them (Jan 23, 2026)
   **PRIMARY. Standard/consensus**, and it explicitly supersedes/refines the older 15x framing for coding contexts — the newer, lower number should be treated as the more relevant one for a solo coder.

4. **Claim:** Cognition's original argument against multi-agent coding: parallel subagents produce **context fragmentation** — because "actions carry implicit decisions, and conflicting decisions carry bad results," and subagents that can't see each other's work produce inconsistent output that a final agent has to reconcile (illustrated with a Flappy Bird clone where one subagent builds a Mario-style background and another builds a mismatched bird).
   **Evidence:** "Subagent 1 and subagent 2 cannot see what the other was doing and so their work ends up being inconsistent with each other." Their recommendation at the time: single-threaded linear agents for most applications, plus context-compression for long histories, with subagents used only for well-scoped question-answering, not parallel work. They also praised Claude Code's design choice: "The designers of Claude Code took a purposefully simple approach."
   **Source:** https://cognition.com/blog/dont-build-multi-agents (Jun 12, 2025, author Walden Yan)
   **PRIMARY. One practitioner's (influential) opinion at the time** — later superseded/refined by the same author, see Finding 5.

5. **Claim:** Ten months later, Cognition published a reversal-with-nuance: multi-agent setups **do** work now, but only in the specific shape where "multiple agents contribute intelligence to a task while writes stay single-threaded" — i.e., parallel agents may read, review, or advise, but only one agent/thread actually mutates the codebase at a time. Three validated patterns: (a) a code-review loop where a review agent with **no shared context** with the coder catches ~2 bugs/PR (58% rated severe) — the clean-context isolation is *why* it works, avoiding "context rot"; (b) a "smart friend" pattern where a weaker primary model consults a stronger one on demand (works only when both are frontier-level; asymmetric gaps are "still an open problem... a training one"); (c) a manager/coordinator pattern with many child agents but single-threaded decisions.
   **Evidence:** "multi-agent systems work best today when writes stay single-threaded and the additional agents contribute intelligence rather than actions." Context: model capability improved ("naturally agentic" models), Devin enterprise usage grew ~8x in six months creating review bottlenecks, and cost pressure pushed toward cheaper multi-agent setups vs. one very expensive frontier call.
   **Source:** https://cognition.com/blog/multi-agents-working (Apr 22, 2026, author Walden Yan)
   **PRIMARY. This explicitly updates/supersedes Finding 4** — treat the "single-threaded writes, parallel intelligence" rule as the current state of Cognition's guidance, not the 2025 blanket "don't."

6. **Claim:** The Bun Zig→Rust migration is the most-cited large-scale "agent fleet did real coding at scale" case study: 5.9B uncached input tokens + 690M output tokens (+72B cached input reads), ~$165,000 at API list pricing, ~1M lines of Rust produced in <2 weeks (11 days), 100% of Bun's existing test suite (1,386,826 assertions across 60,624 tests) passing in CI before merge, with 19 regressions found and fixed post-merge. Peak concurrency was ~64 Claude instances (4 worktrees × 16 agents each), run across ~50 dynamic workflows over the 11 days, using a pre-release Claude model.
   **Evidence:** "5.9 billion uncached input tokens and 690 million output tokens" / "around $165,000 at API pricing" / "At peak, we were running 4 of these workflows at once each in a separate worktree, each with 16 Claudes per workflow. About 64 Claudes at a time."
   **Source:** https://claude.com/blog/ai-code-migration (Jul 16, 2026) and https://simonwillison.net/2026/Jul/8/rewriting-bun-in-rust/ (Jul 8, 2026, corroborating and adding the worktree/agent-count detail); the 64-agent structural detail is best sourced to https://www.developersdigest.tech/blog/bun-rust-rewrite-agent-fleet-case-study (secondary, but directly quotes the primary post).
   **PRIMARY (Anthropic's own case study) + SECONDARY corroboration. Not really contested on the numbers**, though the *quality* of the outcome is contested (see Finding 8).

7. **Claim:** Anthropic's own stated takeaway from the Bun migration is a process/verification rule, not a "more agents = better" rule: "You don't fix the code. You fix the process (loop) that produced the code." The four preconditions the post gives for this kind of large migration to work: the work is genuinely **parallel** (file-scope decomposable), there's **clear and comprehensive context** from the existing implementation, there's a **built-in referee** (an exhaustive, language-independent test suite), and success is **objectively verifiable** (compiles, passes tests, passes CI on all platforms) rather than requiring subjective judgment.
   **Evidence:** implementer + "2 or more adversarial reviewers per implementer," whose "only job: find bugs & reasons why the code does not work"; disagreement between reviewers escalates to a third agent; phased pipeline with machine-checkable exit gates (trial port → mass translation → per-crate `cargo check` → smoke tests → batched test-suite runs); when agents produced bad patterns (e.g. stubbing out failing compiles), the fix was to change the *workflow instructions*, not hand-edit the output — necessary at "695 commits per hour."
   **Source:** https://claude.com/blog/ai-code-migration (Jul 16, 2026); worktree/pipeline mechanics corroborated by https://www.developersdigest.tech/blog/bun-rust-rewrite-agent-fleet-case-study (secondary) and https://simonwillison.net/2026/Jul/8/rewriting-bun-in-rust/ (primary-adjacent, close paraphrase of Sumner's own writeup).
   **PRIMARY. Practitioner-validated, but scoped**: an HN commenter's caveat (relayed in the developersdigest secondary source) that this "wasn't any engineer plus any codebase" — it required an expert (Bun's own co-founder) who already had deep codebase knowledge and inherited an unusually large pre-existing test suite. Treat as **contested-generalizability**: the mechanism (test-oracle + adversarial review + worktree isolation) generalizes; the ease of execution does not.

8. **Claim:** The Bun/Rust output quality is publicly disputed. Zig's creator, Andrew Kelley, called the shipped code "unreviewed slop," argued the huge test suite is not a substitute for code review ("The argument for shipping all the million lines of unreviewed code is that the test suite is good enough to catch everything. It's not sufficient to catch bugs in Zig code but it is sufficient to catch bugs in [a] million lines of unreviewed slop?"), and attributed Bun's underlying bug history to pre-existing engineering practices rather than to Zig or to AI.
   **Evidence:** direct quotes above, from Kelley's own post "My Thoughts on the Bun Rust Rewrite," reported by The Register.
   **Source:** https://www.theregister.com/devops/2026/07/14/zig-creator-calls-buns-claude-rust-rewrite-unreviewed-slop/5270743 (Jul 14, 2026)
   **SECONDARY (Register quoting Kelley's primary post, which was not directly fetched). Contested** — directly counters the "test suite as sufficient referee" claim in Finding 7, and is a genuine, unresolved disagreement in the record, not a fringe take (Kelley is Zig's creator and has direct expertise).

9. **Claim:** Claude Code's official, current documentation (`code.claude.com/docs/en/agent-teams`) gives an explicit, actionable decision rule for coding specifically: agent teams are "most effective" for new/independent modules, cross-layer work split by layer, competing-hypothesis debugging, and multi-angle review — but "for sequential tasks, same-file edits, or work with many dependencies, a single session or subagents are more effective." Recommended default team size is **3–5 teammates**, sized so each teammate gets ~5–6 tasks; "token costs scale linearly" with teammate count and coordination overhead grows on top of that; "diminishing returns" set in beyond some point. The docs explicitly warn: "Two teammates editing the same file leads to overwrites. Break the work so each teammate owns a different set of files."
   **Evidence:** direct quotes above, full page fetched.
   **Source:** https://code.claude.com/docs/en/agent-teams (documented "as of v2.1.178"; accessed Sep 4 2026)
   **PRIMARY. Standard/consensus / official product guidance**, and it is the most directly actionable, current source for a Claude Code user specifically. Agent teams remain **experimental and off by default** (`CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`), with named limitations: no session resumption for in-process teammates, task-status lag, no nested teams, one team per session.

10. **Claim:** Git worktree support for running multiple isolated Claude Code sessions shipped as a stable, non-experimental feature (v2.1.49, Feb 2026 per secondary reporting); by mid-2026 practitioner reports describe teams running 4–8 concurrent worktrees per developer, "bottlenecked on review rather than on Claude." Subagents remain the lighter-weight mechanism (single session, no peer messaging, results summarized back to the caller, lower token cost) vs. agent teams (separate sessions, direct peer messaging, shared task list, higher token cost).
    **Evidence:** official doc distinguishes: "Subagents work within a single session; agent teams coordinate across separate sessions... They can't message each other, share discoveries mid-task, or coordinate without the main agent acting as intermediary" (subagents) vs. teammates that "message each other directly" and share a claimable task list with dependency tracking and file-locking to prevent race conditions on task claims.
    **Source:** https://code.claude.com/docs/en/agent-teams (PRIMARY, official); worktree adoption stats are SECONDARY, from https://www.developersdigest.tech/blog/git-worktrees-claude-code-parallel-agents-guide and similar 2026 "playbook" blog posts — treat the "4-8 worktrees, bottlenecked on review" figure as one practitioner-community claim, not an Anthropic-verified statistic.
    **Mixed: PRIMARY for the mechanism, SECONDARY/unverified for adoption numbers.**

11. **Claim:** Academic 2026 work quantifies "how many agents is too many" for tool-heavy tasks like coding. One synthesis states: if a single agent already achieves >~45% success rate on a task, adding coordination mechanisms yields diminishing or *negative* returns; performance vs. agent count follows an inverted-U shape (early synergy, then coordination overhead dominates); token cost was described as scaling roughly quadratically with naive agent count in some designs.
    **Evidence:** "If a single agent can already achieve a success rate greater than ~45% on a task, adding coordination mechanisms yields diminishing or even negative returns. Tool-heavy tasks like software engineering using 16+ tools suffer disproportionately from coordination overhead."
    **Source:** Aggregated via WebSearch from multiple 2026 arXiv-adjacent sources (search snippet, not independently WebFetched as a single paper) — flagged as **SECONDARY / needs direct-paper verification**; the ~45% threshold in particular could not be traced to one specific named paper within this research pass and should be treated as an approximate, not authoritative, figure.
    **Contested / unverified precision** — directionally consistent with the primary Claude/Cognition guidance above, but this specific number is the weakest-sourced claim in this report.

12. **Claim:** "The Ringelmann Effect in Multi-Agent LLM Systems: A Scaling Law for Effective Team Size" (Bertalanič & Fortuna, arXiv:2606.02646, Jun 3 2026) formalizes the same intuition with a named scaling law: as nominal team size grows, *effective* team size (marginal contribution per added agent) plateaus, directly analogous to the 1913 Ringelmann rope-pulling effect from social psychology. The paper's benchmarks explicitly include coding tasks alongside knowledge tasks (e.g., GPQA-style questions), i.e., the effect is not claimed to be research-only.
    **Evidence:** paper title and abstract-level framing; full derivation (Theorem 1, multiple equations) was present in the fetched PDF but not fully legible/extractable in this pass — the report used the paper's stated framing rather than its exact formula.
    **Source:** https://arxiv.org/pdf/2606.02646 (Jun 3, 2026)
    **PRIMARY (peer-reviewed-adjacent preprint). Standard-forming but new** — this is a formal treatment of a pattern that Anthropic/Cognition/Claude Code docs describe qualitatively ("diminishing returns"); worth flagging as the most rigorous quantitative backing found, but it is a preprint, not yet a broadly cited consensus result.

13. **Claim:** A UCL coordination-measurement study ("When Agents Coordinate," Destefanis & Aste, arXiv:2608.16801, Aug 17 2026) found that (a) inter-agent messaging grows near-quadratically only during an initial "round of introductions" and then flattens hard — "the slope between eight and sixteen is 0.00" — so raw message-volume growth is not actually the bottleneck at scale; (b) task *shape* determines whether dense mesh communication or sparse pipeline communication is optimal, and forcing the wrong coordination policy actively hurts (mandatory shared files cut tokens ~42% on distributed/parallel tasks but *increased* tokens ~17% on sequential pipeline tasks); (c) naming an agent "coordinator" in the prompt alone produces **no** measurable coordination structure or success-rate improvement — coordinator-labeled teams "level at eight agents" just like flat (non-hierarchical) teams; (d) failures concentrate at **unowned interfaces**: one 8-step task "failed every run on a rounding convention that sat between two agents and belonged to neither."
    **Evidence:** direct quotes above; dataset of 1,902 graded runs + 244 "sealed replication" runs released publicly.
    **Source:** https://arxiv.org/html/2608.16801 (Aug 17, 2026)
    **PRIMARY. This is the strongest, most directly-coding-relevant academic evidence found for the "contract/interface ownership matters more than headcount or messaging" decision rule** — it operationalizes what Cognition and Claude Code docs describe informally.

14. **Claim:** OpenAI's Codex cloud product supports genuine parallel task execution — isolated cloud sandboxes per task, with git-worktree support, designed for embarrassingly-parallel/independent work rather than sequential pipelines: "Give longer tasks dedicated environments and let them continue while you work on something else" and "Start work in parallel and return as each task reaches a reviewable result."
    **Evidence:** quotes above from the fetched docs page.
    **Source:** https://learn.chatgpt.com/docs/cloud (redirected from developers.openai.com/codex/cloud; no publish date visible on the page)
    **PRIMARY. Standard/consensus product documentation** — structurally similar to Claude Code's worktree + subagent model: parallelism is offered as an *infrastructure* capability (isolated environments), with the decomposition-quality problem left to the user, same as Claude Code's docs implicitly do.

15. **Claim:** One practitioner synthesis (Addy Osmani, independent, well-known engineering blogger/ex-Google) gives a competing decision rule that leans more pro-fleet than Cognition/Anthropic: "Three focused agents consistently outperform one generalist agent working three times as long," recommends a documented contract-first pattern (a Data-layer agent produces `DATA.md`, a Logic agent produces `LOGIC.md`, an API-routes agent reads both before implementing), argues plan-approval gates and human-curated (never agent-written) `AGENTS.md`/context files are essential, and states "the bottleneck is no longer generation. It's verification."
    **Evidence:** quotes above.
    **Source:** https://addyosmani.com/blog/code-agent-orchestra/ (Mar 26, 2026)
    **PRIMARY (one named practitioner's own post), explicitly labeled here as one practitioner's opinion** — it is the closest thing in this research pass to a direct pro-fleet counter-argument to "one strong agent + reviewer," and it is *not* a controlled study; it should not be read as consensus. Notably, even Osmani's own strongest recommendations (contract docs, plan-approval gates, human-owned context files, verification-as-bottleneck) are about disciplined interface contracts, not raw fleet size — so the practical prescriptions converge with Cognition/Anthropic/Claude Code docs even where the rhetorical framing ("fleets beat one agent") differs.

## Concrete practices / configs (copy-pasteable this week)

- **Default posture for a solo dev in Claude Code:** stay on a single session/subagents for anything touching shared files, sequential logic, or fewer than ~15 independent units of work. Only reach for agent teams when you can name 3+ genuinely independent, file-disjoint pieces of work up front (e.g., "add tests to module A / module B / module C" or "review this PR for security / performance / test-coverage separately"). — per https://code.claude.com/docs/en/agent-teams
- **Enable agent teams** (experimental, off by default) in `settings.json`:
  ```json
  { "env": { "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1" } }
  ```
  Set it to `"0"` (in user `settings.json`) if Claude keeps auto-spawning teammates when you only wanted subagents — a named subagent auto-promotes to a teammate while the flag is on. — same source.
- **Team-size rule of thumb:** start at 3–5 teammates; give each ~5–6 tasks; don't scale up unless the work is provably independent. Two teammates should never own overlapping files. — same source.
- **Decompose by ownership/context, not by pipeline stage.** Give one agent a whole feature (code + its own tests) rather than splitting into a "planner agent / coder agent / tester agent" chain — the latter creates "telephone game" loss. — https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them
- **If you want a review pattern that actually works today:** run the review agent with **no shared context** from the implementer (fresh session, just the diff/PR) — Cognition's data says this "clean context" is *why* the reviewer catches real bugs (~2/PR, 58% rated severe) instead of rubber-stamping. Don't seed the reviewer with the implementer's reasoning trace. — https://cognition.com/blog/multi-agents-working
- **For any large mechanical migration/refactor you want to fan out:** first make sure you actually have (1) an exhaustive, language/framework-independent test suite that can act as an objective referee, (2) work that truly decomposes by file/module with minimal cross-file coupling, (3) a way to auto-verify each unit (compiles, passes tests, passes CI) without a human judgment call per unit. If you're missing any of the three, don't fan out — do it single-threaded. — https://claude.com/blog/ai-code-migration
- **Git worktrees for manual parallel sessions** (no agent-team coordination needed): `git worktree add ../feature-x feature-x-branch`, then run a separate Claude Code session per worktree. This is the simplest, most battle-tested way to get parallelism without any of the coordination-overhead risk of agent teams. — https://code.claude.com/docs/en/agent-teams ("Manual parallel sessions" section) and corroborated by multiple 2026 practitioner "worktree playbook" posts.
- **Never let an agent write your shared context file unattended** (`CLAUDE.md`/`AGENTS.md`) — review every addition yourself; one practitioner report claims machine-generated context-file edits measurably hurt success rates. Treat this as one practitioner's claim (Osmani), not a verified statistic, but the underlying caution (context files are load-bearing and should be human-curated) is broadly echoed. — https://addyosmani.com/blog/code-agent-orchestra/

## Disagreements and open questions

- **Token multiplier: 15x vs 3-10x.** Anthropic's original 15x figure (research system) is frequently cited as if it were a general "multi-agent coding" tax, but Anthropic's own later coding-focused guidance gives 3-10x. A solo developer should budget for the lower, coding-specific range and treat 15x as an upper bound for heavy, independent-parallel-search workloads, not typical feature work.
- **Bun case study: proof-of-concept vs. cautionary tale.** Anthropic/Willison frame it as evidence that "million-line rewrites are newly economical." Andrew Kelley (Zig's creator) frames the same artifact as "unreviewed slop" shipped on the strength of test-suite coverage alone. Both can be true simultaneously (tests passed, but code quality/maintainability is unproven) — this report could not resolve which framing is more predictive of long-term maintenance cost, because that requires time this research pass doesn't have (the rewrite is ~2 months old as of this report).
- **Does "more agents" ever just work for typical feature work?** Osmani's practitioner post is the one source in this pass arguing fleets straightforwardly beat a single agent for general coding, but even his own concrete prescriptions (contract docs, human-gated plan approval, verification-as-bottleneck) match the contract-first / single-owner-write consensus rather than contradicting it — suggesting the "fleets win" framing may be more rhetorical than the underlying practice.
- **The ~45% single-agent-success threshold** (Finding 11) could not be traced to one specific, individually-verified paper in this pass — it came through aggregated search-engine synthesis rather than a directly fetched primary source. Flagged as the weakest-sourced number in this report; would need a follow-up fetch of the specific "Towards a Science of Scaling Agent Systems" (arXiv:2512.08296) or "Too Many Specialists" (arXiv:2605.08540) papers to confirm/attribute it correctly.
- **Team-size numbers vary by source and aren't obviously reconciled:** Claude Code docs say 3-5 teammates as a default; Osmani independently says "3-5 teammates is the sweet spot" (converges); the Ringelmann-effect paper and the "diminishing returns beyond 3 agents" search synthesis suggest an even lower ceiling (2-4) for complex tasks specifically. These are directionally consistent (small teams) but the exact number is not a single agreed constant — it's task-dependent.
- **Not independently verified in this pass:** the exact optimal-team-size formula/thresholds inside the Ringelmann-effect paper (PDF equations were not fully legible via WebFetch's text extraction); Andrew Kelley's full original post (only reached via secondary reporting from The Register, not fetched directly); Sumner's own primary blog post about the Bun rewrite (referenced by Willison and claude.com but its own URL was not independently located/fetched in this pass — the claude.com/blog/ai-code-migration post functioned as the primary source instead).
