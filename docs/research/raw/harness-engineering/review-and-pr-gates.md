# AI-Era Code Review and PR Gating Practices (2026)

## TL;DR

- Anthropic's own Claude Code Review (multi-agent, GitHub-integrated) lifted the share of PRs getting substantive review comments from 16% to 54% internally, with a claimed **<1% false-positive rate** on findings engineers marked wrong — but this is a self-reported vendor number, not an independent audit. (PRIMARY, claude.com/blog/code-review, 2026)
- The dominant new architecture is **generate → find (parallel specialized agents) → verify (reproduce each candidate bug against real code behavior) → dedupe/rank → report**. Both Anthropic's `/code-review`/`ultrareview` and independent tools (CodeRabbit, Greptile) converge on this "verify before surfacing" pattern to cut noise. (PRIMARY + SECONDARY, multiple sources, 2026)
- Independent, apples-to-apples benchmarking of review bots is immature: the one broad benchmark (Martian, ~300K PRs / 17 tools, Jan–Feb 2026) reports CodeRabbit's F1 ≈ 51.2% (precision ≈49.2%, recall ≈53.5%) as the top score — meaning even the "best" tool is right about half the time by its own online-acceptance metric. Its curated offline gold-set was seeded from two competing tools' own bug lists, a disclosed source of bias. (PRIMARY/SECONDARY mixed, coderabbit.ai + codeant.ai, 2026)
- "Review the plan, not the (post-hoc) code" is a **contested but rapidly spreading opinion**, not yet consensus: the argument (Khandelwal/Zencoder, and implicit in Anthropic's own tiered-risk approach) is that by the time a bad agent decision becomes a clean diff, the expensive mistake already happened, so the control point should move to plan/spec/test-contract review before execution. (PRIMARY, zencoder.ai, 2026-07-06; practitioner opinion)
- Independent (fresh-context) review reliably beats same-session self-review: a controlled study (n=360 reviews, 150 seeded errors) found Cross-Context Review scored F1 28.6% vs. same-session self-review, and repeating self-review in the same session did **not** help — the benefit is context separation itself, not a second look. (PRIMARY, arXiv 2603.12123, 2026-03-12)
- PR size is a load-bearing lever: LinearB's 2026 benchmark (8.1M PRs, 4,800 teams) found AI-assisted PRs run ~2.5x larger (400+ vs 157 lines at the 75th percentile), wait ~5x longer for review pickup (16+ hrs vs ~200 min), and have a 30-day merge rate of 32.7% vs 84.5% for unassisted PRs. (SECONDARY reporting of LinearB data via flowverify.co, 2026-08-03)
- Human oversight of agent-authored PRs is measurably thin in the wild: an EASE-2026 academic study of the AIDev dataset found 61.4% of 33,596 agent-authored PRs had **no recorded review activity at all**, and of the reviewed remainder, 58.8% were reviewed only by another agent, 10.1% by a human only, and 31.1% by both. (PRIMARY, arXiv 2605.02273, 2026-05-04)
- Evidence-in-the-PR-body has become an explicit norm for agent-authored changes: GitHub's own guidance tells reviewers to require "tests that fail on pre-change behavior," and leading agents (Devin, Cursor's cloud agents, GitHub Copilot coding agent) now attach screenshots/video/logs generated by re-running the app in a sandbox — the stated principle is that evidence must come from harness re-execution, never the agent's own unverified claim. (PRIMARY + SECONDARY, github.blog, 2026-05-07; propelcode.ai, 2026)

## Findings

1. **Claude Code's `/code-review` and `/ultrareview` are two tiers of the same find-then-verify pipeline.** `/code-review` runs locally/in a background subagent (seconds to minutes, effort levels low→max trade coverage for confidence, low/medium report only high-confidence findings), while `/code-review ultra` (alias `/ultrareview`) launches a larger agent fleet in an Anthropic cloud sandbox (5–10 min, $5–25/run after 3 free Pro/Max runs) where "every reported finding is independently reproduced and verified." Both can `--fix` the working tree or `--comment`/`--post` findings to a GitHub PR.
   Source: https://code.claude.com/docs/en/code-review and https://code.claude.com/docs/en/ultrareview (2026, docs current as of fetch). PRIMARY. Standard/documented product behavior, not opinion.

2. **Anthropic's hosted "Code Review" GitHub-App product (distinct from the local `/code-review` command) runs a fleet of specialized agents in parallel, each hunting a different issue class, then a dedicated verification step "checks candidates against actual code behavior to filter out false positives," before dedup/rank/post as inline PR comments.** Findings are tagged 🔴 Important / 🟡 Nit / 🟣 Pre-existing, never block merge (check run is always "neutral" conclusion — CI-gating is left to the team to wire up via a machine-readable severity comment), and cost $15–25/review, ~20 min average.
   Source: https://code.claude.com/docs/en/code-review (2026). PRIMARY. Standard practice as designed by the vendor.

3. **Anthropic reports (self-reported, internal dogfooding) that deploying Code Review raised the share of PRs receiving substantive review comments from 16% to 54%,** with large PRs (1,000+ lines) generating findings 84% of the time (avg. 7.5 issues) vs. 31% of small PRs (<50 lines, avg. 0.5 issues), and a claimed **false-positive rate under 1%** based on engineer thumbs-down reactions.
   Source: https://claude.com/blog/code-review (2026). PRIMARY (vendor's own numbers) — treat the <1% FP figure with caution: it's derived from voluntary 👎 reactions post-merge, not an independent audit, and Anthropic's own docs note reactions are collected only "after the PR merges" and don't trigger re-review. One practitioner's/vendor's measurement, not independently replicated.

4. **A controlled academic study directly tested self-review vs. independent review architectures for LLM-generated artifacts.** "Cross-Context Review" (Song, arXiv 2603.12123, 2026-03-12) ran 360 reviews across 30 artifacts with 150 deliberately seeded errors, comparing same-session self-review (SR), repeated same-session review (SR2), context-aware subagent review (SA), and cross-context review (CCR — separate session, no access to the original production conversation). CCR won with F1 = 28.6%; critically, SR2 (reviewing twice in the same session) did **not** beat SR once, showing the gain comes from context separation, not extra passes.
   Source: https://arxiv.org/abs/2603.12123 (2026-03-12). PRIMARY. This is close to consensus among practitioners citing it (see also finding 5), though the absolute F1 (28.6%) is itself low, meaning even the best-tested method still misses/mislabels a majority of seeded errors — a caveat several summaries omit.

5. **Independently, practitioner writing converges on the same "blind sub-agent" pattern**: spawn reviewer/critic agents with fresh, isolated context (not inherited conversation history) to avoid anchoring bias, because "every answer is anchored by assumptions from earlier turns" when agents inherit history. Recommended uses: cold-read documentation review, "blind builder" agents given only public APIs to reveal real UX confusion, and fresh-eyes PR review with domain-specialized agents rather than a single long-session opinion.
   Source: https://www.solberg.is/blind-sub-agents (Jökull Sólberg, 2026-08-17). PRIMARY but this is **one practitioner's opinion/blog post**, not a study — treat as consensus-adjacent (it matches the CCR paper's finding) but not itself measured.

6. **"Review the plan, not the code" is an emerging, contested reframing, argued most explicitly by Neeraj Khandelwal (Zencoder newsletter).** Thesis: "by the time a bad agent plan becomes a clean-looking diff, the expensive mistake has already happened" — a diff can be syntactically fine and still be "strategically wrong" (patches a symptom, skips an architectural boundary, adds a test that blesses the wrong behavior, picks a migration path that creates on-call pain). Proposed gate artifact: task interpretation, affected-files/risk map, test plan + rollback path, and reasons alternate approaches were rejected — reviewed *before* code is written. Cites Cognition's Devin "Security Swarm" finding 36/50 real GHSA CVEs (incl. 3 no other tool caught) as evidence that workflow-level QA (exploit reproduction + patch as one loop) beats post-write scanning.
   Source: https://zencoder.ai/newsletter/plan-review-new-linter-ai-generated-code (2026-07-06). PRIMARY for the argument; the Devin CVE figure is SECONDARY (Zencoder reporting Cognition's own claim, unverified independently in this research pass). **Contested**: this displaces rather than supplements code review in the author's framing, and it is a minority/emerging position — mainstream 2026 tooling (Claude Code Review, GitHub, CodeRabbit) still centers on post-diff review, with plan-review treated as a complement (e.g., Anthropic's plan-approval-for-low-risk-launch step) rather than a replacement.

7. **Independent benchmarking of code-review bots exists but is early, sparse on public numbers, and methodologically contested.** The most cited 2026 attempt is Martian's benchmark (self-described as built by ex-DeepMind/Anthropic/Meta researchers): ~300K real PRs analyzed online (Jan–Feb 2026) using "did the developer change the code after this comment?" as the true-positive signal, plus a 50-PR offline "gold set" from Sentry/Grafana/Cal.com/Discourse/Keycloak. CodeRabbit topped the online leaderboard (F1 ≈51.2%, precision ≈49.2%, recall ≈53.5%, ~15pp higher recall than the next tool); CodeAnt AI ranked #3 (F1 51.7%, precision 52.2%, recall 51.1% — note CodeAnt's own number is *higher* than CodeRabbit's despite ranking #3, suggesting different snapshots/versions were compared across the two secondary write-ups). Martian's own writeup discloses the offline gold set was partly seeded from Augment's and Greptile's own bug datasets — a disclosed source of bias toward those tools, and the offline results "diverged significantly" from the online ones.
   Source: https://www.coderabbit.ai/blog/coderabbit-tops-martian-code-review-benchmark and https://www.codeant.ai/blogs/ai-code-review-benchmark-results-from-200-000-real-pull-requests (both 2026, citing the March 2026 Martian benchmark). SECONDARY (both are vendors reporting a third party's benchmark in the light most favorable to themselves) — **contested reliability**: no neutral primary writeup from Martian itself was directly fetched in this pass, and the two vendor summaries disagree on ranking despite citing the same benchmark.

8. **A separate, no-vendor-conflict-of-interest earlier-generation figure**: CR-Bench (Pereira, Sinha, Ghosh, Dutta; arXiv 2603.11078, 2026-03-13) is an academic benchmark for AI code review agents using precision/recall/F1 against real-world detected issues; full numeric tool-by-tool results were not extractable from the fetch (PDF content only partially parsed) — flagged as a gap.
   Source: https://arxiv.org/pdf/2603.11078 (2026-03-13). PRIMARY but incomplete extraction — GAP, see below.

9. **Earlier/independent measurements cited in secondary sources (not independently re-verified here) claim**: Greptile produced 11 false positives vs. CodeRabbit's 2 across 50 real OSS PRs (Sentry/Cal.com/Grafana) in a benchmark description found via search snippets only (not fetched as a primary page in this pass — GAP); "64% of AI review comments address style rather than logic bugs... only 14% catching real bugs" attributed to "CR-Bench (2026)" in a secondary aggregator (augmentcode.com-style comparison page) — also not independently fetched/verified. GitHub Copilot: one academic-style secondary summary cites a 15–25% false-positive rate and, separately, a claim Copilot "identified zero security vulnerabilities" in a 117-file study despite known vulnerabilities present, alongside a conflicting claim elsewhere of 70–80% known-vulnerability-signature detection — these two Copilot security numbers are **directly contradictory** and neither was traced to a fetchable primary paper in this pass.
   Sources: search-snippet level only (SECONDARY, unverified) — see Gaps section. Flag as **contested/unverified**, not to be treated as established fact.

10. **GitHub's own data (PRIMARY, official blog) on Copilot code review at scale**: 60 million reviews since April 2025 launch (10x growth), >12,000 orgs auto-reviewing every PR, Copilot now involved in "more than one in five code reviews on GitHub" (as of Jan 2026 per a separate GitHub Blog post), 71% of reviews surface actionable feedback (29% surface nothing), 5.1 comments/review average, +8.1pp positive-feedback improvement after moving to an agentic architecture and +6pp more with a stronger reasoning model, and GitHub accepted a 16% latency increase in exchange for the quality gain. No head-to-head comparison to human review accuracy is given.
   Source: https://github.blog/ai-and-ml/github-copilot/60-million-copilot-code-reviews-and-counting/ (2026-03-05). PRIMARY, vendor-reported (GitHub is grading its own product) — standard practice to cite but treat acceptance/positive-feedback metrics as a proxy, not a ground-truth bug-catch rate.

11. **PR size limits are one of the highest-leverage interventions found in large-scale telemetry.** LinearB's 2026 benchmark (8.1M PRs / 4,800 teams, cited via a secondary aggregator) found: AI-assisted PRs run ~400+ lines at the 75th percentile vs. 157 for unassisted PRs; reviewer pickup time balloons from ~200 minutes to 16+ hours; 30-day merge completion drops from 84.5% (unassisted) to 32.7% (AI-assisted); refactoring rate at the 75th percentile falls from ~37% to "near zero" for AI-assisted PRs. Separately, Faros AI data (22,000 developers, same secondary source) shows median code-review time up 441.5%, time-to-first-review up 156.6%, code churn up 861%, and production-incident-to-PR ratio up 242.7%, alongside developer throughput up 33.7%.
   Source: https://www.flowverify.co/blog/ai-code-review-bottleneck-2026-data (2026-08-03), reporting LinearB and Faros AI data. SECONDARY (this research pass fetched the aggregator, not LinearB's or Faros's own report directly — GAP: primary LinearB/Faros reports not independently located/fetched). Directionally this matches multiple other sources (GitHub's own post on agent PRs, the AIDev academic study) so treat the *direction* as consensus, the *exact numbers* as single-sourced/unverified.

12. **A concrete, enforceable PR-size discipline recommendation**: "teams with enforced PR size limits under 100 lines (75th percentile benchmark) see pickup times 60–70% shorter than teams without size enforcement," and the single highest-leverage intervention identified is instructing agents (via system prompt/harness config) to break large tasks into small PR batches — improving pickup time, acceptance rate, and cycle time simultaneously. A companion capacity rule of thumb: a human reviewer can do ~200–400 lines of *meaningful* review per hour.
   Source: search-result synthesis attributed to a "2026 numbers" aggregator (huuhka.net / codacy.com / github.blog family — not independently re-fetched as a single primary page in this pass). SECONDARY, **treat as practitioner consensus/rule-of-thumb**, not a controlled experiment.

13. **GitHub's own reviewer guidance for agent-authored PRs (PRIMARY, github.blog, Andrea Griffiths, 2026-05-07)** codifies a **10-minute timed review protocol**: scan & classify (1–2 min) → CI-change audit first (2–3 min, because agents may quietly weaken tests/lint/coverage thresholds) → search for duplicated utilities (3–5 min, because models re-implement existing helpers under new names) → trace one critical path end-to-end (5–8 min) → check security boundaries/permission scoping on any LLM-calling workflow (8–9 min) → require evidence — "tests that fail on pre-change behavior" (9–10 min). Named failure modes: **CI gaming** (agents removing/weakening tests), **code-reuse blindness** (duplicate logic under new names), **hallucinated correctness** (compiles + passes tests but fails on real edge cases — off-by-one pagination, missing permission checks, races), **agentic ghosting** (large unstructured PRs correlate with the agent abandoning the task mid-way), and **untrusted input flowing into LLM-calling workflows** (PR bodies/commit messages interpolated into prompts, or model output executed as shell commands). Explicit **PR-rejection criteria**: request a smaller PR if it touches 5+ unrelated files, its purpose isn't a one-sentence description, it has no implementation plan or an empty body, or it only touches test files while CI is red.
   Source: https://github.blog/ai-and-ml/generative-ai/agent-pull-requests-are-everywhere-heres-how-to-review-them/ (2026-05-07). PRIMARY. This reads as GitHub's attempt to set a *standard*, and it's consistent with Anthropic's REVIEW.md guidance (finding 14) and the plan-review argument (finding 6), so treat the checklist shape as emerging consensus even though the exact minute-by-minute timing is one org's prescription.

14. **Anthropic's `REVIEW.md` mechanism operationalizes "raise the evidence bar" and noise control as repo-level config** (distinct from `CLAUDE.md`, which is general project context read as nit-level signal). Documented tunable levers: redefine what counts as 🔴 Important per-repo; cap nit volume (e.g., "report at most five nits, mention the rest as a count"); skip rules for generated code/lockfiles/vendored deps/machine-authored branches; require file:line evidence citations for "behavior claims" ("cuts false positives that would otherwise cost the author a round trip"); convergence rules for re-review (suppress new nits after the first pass, Important-only thereafter); and a mandated one-line tally at the top of the review summary (e.g., "2 factual, 4 style").
   Source: https://code.claude.com/docs/en/code-review (2026). PRIMARY, documented product feature — standard/prescriptive by the vendor, directly copy-pasteable (see Concrete practices below).

15. **Human oversight in the wild is thinner than review-count metrics suggest.** The EASE-2026 paper "These Aren't the Reviews You're Looking For" (Duma, Wróblewski, Bobińska, Winiarska, Przymus; Nicolaus Copernicus University; arXiv 2605.02273, submitted 2026-05-04) mined the AIDev dataset and found 61.38% of 33,596 agent-authored PRs carry **no recorded review activity**; among the reviewed remainder, 58.77% were reviewed only by another agent, 10.14% only by a human, 31.09% by both — and where humans are present, involvement is frequently expressed as "agent steering" (telling the agent what to redo) rather than standalone independent evaluation. The authors explicitly warn this "raises challenges for interpreting review metrics as indicators of human oversight" — i.e., a PR marked "reviewed" is not evidence a human actually evaluated it.
   Source: https://arxiv.org/abs/2605.02273 (2026-05-04). PRIMARY, peer-reviewed (EASE 2026 accepted). This is close to consensus-establishing empirical evidence — the strongest data point in this report for "what's actually happening" vs. "what vendors recommend."

16. **Anthropic's stated internal human-oversight model (its own SDLC, not general guidance) tiers codebases by risk**, with some low-risk changes eligible for a form of self-approval once automated security assessment clears them, while "truly critical" or regulated-system code requires substantive human review; a risk-weighted *sample* of automatically-approved changes still gets human review; new automated reviewer agents start in "shadow mode," posting comments for human approval until trust is earned; and incident-response automated fixes require a separate agent-human reviewer pairing before deploying. The piece frames the shift explicitly as: human attention moves from "reviewing code and bug reports" to "monitoring loops" (overseeing the automation itself, not reading every line).
   Source: https://claude.com/blog/how-anthropic-secures-its-ai-native-software-development-lifecycle (2026, exact date not confirmed in fetch — GAP). PRIMARY (Anthropic describing its own practice) — **one organization's practice**, presented by Anthropic as their approach, not an industry standard, though it is influential given Anthropic's position building the tools discussed elsewhere in this report.

17. **Evidence-artifact norms for PR bodies**: the emerging standard (per GitHub's checklist in finding 13, and corroborated by secondary trend-pieces) is that agent-authored PRs should carry re-executed evidence — test output that demonstrably fails on pre-change code and passes after, plus for anything with a runtime/UI surface, screenshots or short recordings from an actual run (Cursor's cloud agents run the app in a VM and attach video/screenshots/logs; Devin returns a "chaptered test video with pass/fail assertions" plus labeled screenshots delivered to Slack; GitHub's own Copilot coding agent uses a Playwright-driven browser to post screenshots into the PR it opens). The stated design principle across these tools is that evidence must be **the output of harness re-execution**, never the agent's own unverified claim or a hand-picked screenshot.
   Source: https://github.blog/ai-and-ml/generative-ai/agent-pull-requests-are-everywhere-heres-how-to-review-them/ (2026-05-07, PRIMARY) plus https://www.propelcode.ai/blog/artifact-first-coding-agents-files-vs-chat-memory (2026, SECONDARY trend summary — not independently fetched in full in this pass, described via search synthesis only; treat the Cursor/Devin/Copilot specifics as SECONDARY/unverified-in-depth here). Consensus on the *principle* (re-executed evidence, not agent self-report); the specific vendor feature claims are secondary and not independently confirmed against each vendor's own docs in this pass.

## Concrete practices / configs (copy-pasteable this week)

- **Turn on Anthropic's local review before every push**: run `/code-review` (alias of `/review`) on your branch diff; use `/code-review high` or `/code-review ultra` before merging anything substantial. Effort levels `low`/`medium` = fewer, high-confidence findings (good for a fast pre-commit habit); `high`→`max` = broader coverage, more false positives possible; `ultra` = cloud multi-agent verify pipeline, $5–25/run after 3 free runs on Pro/Max, ~5–10 min. `/code-review --fix` applies findings directly; `/code-review --comment` posts inline PR comments; `ultra --post` posts a single plain (non-approving) GitHub comment from your account.
  Source: https://code.claude.com/docs/en/code-review, https://code.claude.com/docs/en/ultrareview (2026).

- **Add a `REVIEW.md` at repo root** (separate from `CLAUDE.md`) to tune Anthropic's Code Review / `/code-review`'s noise level. Minimal template, adapted from Anthropic's own example:
  ```markdown
  # Review instructions

  ## What Important means here
  Reserve Important for findings that break behavior, leak data, or block
  a rollback. Style/naming/refactor suggestions are Nit at most.

  ## Cap the nits
  Report at most five Nits per review. If you found more, say "plus N
  similar items" instead of posting them inline.

  ## Do not report
  - Anything CI already enforces: lint, formatting, type errors
  - Generated files and any lockfile
  - Test-only code that intentionally violates production rules

  ## Verification bar
  Behavior claims need a file:line citation in the source, not an
  inference from naming.

  ## Re-review convergence
  After the first review, suppress new nits and post Important findings only.
  ```
  Source: https://code.claude.com/docs/en/code-review (2026).

- **Enforce a PR size cap for agent-generated diffs.** Multiple independent data points converge: target well under 100 lines at the 75th percentile (60–70% shorter pickup time per one 2026 aggregate); reject/split any PR touching 5+ unrelated files, lacking a one-sentence purpose, or shipping with an empty body/no plan (GitHub's own rejection criteria). Practically: tell your agent's system prompt/harness to scope work into small, single-purpose PR batches rather than one large sweep.
  Source: https://github.blog/ai-and-ml/generative-ai/agent-pull-requests-are-everywhere-heres-how-to-review-them/ (2026-05-07); flowverify.co aggregation of LinearB data (2026-08-03).

- **Run a timed 10-minute checklist on every agent PR before merging** (adapt GitHub's protocol): 1) scan/classify scope, 2) diff the CI config first (did the agent weaken tests/lint/coverage?), 3) grep for near-duplicate helpers the agent may have reinvented, 4) trace one critical path input→transform→output by hand, 5) for anything invoking an LLM, check permission scoping and that PR bodies/commit messages/model output aren't interpolated into prompts or executed as shell commands unsanitized, 6) require evidence — a test that provably failed before the change and passes after.
  Source: https://github.blog/ai-and-ml/generative-ai/agent-pull-requests-are-everywhere-heres-how-to-review-them/ (2026-05-07).

- **Require re-executed evidence in the PR body, not agent self-report**: test output pasted from an actual run (not paraphrased), and for anything with a UI/runtime surface, a screenshot or short recording taken by re-running the harness, not hand-picked by the agent.
  Source: https://github.blog/ai-and-ml/generative-ai/agent-pull-requests-are-everywhere-heres-how-to-review-them/ (2026-05-07).

- **Prefer independent/fresh-context review over same-session self-review** for anything that matters: dispatch a review in a *new* session/subagent with no access to the original build conversation (a "blind" review), rather than asking the same session that wrote the code to re-check itself. Repeating the check in the same session is measured to add ~nothing; the separate-context step is what helps.
  Source: https://arxiv.org/abs/2603.12123 (2026-03-12); https://www.solberg.is/blind-sub-agents (2026-08-17).

- **For solo/small-team use, a practical stack** consistent with the sources above: `/code-review` on every commit locally (cheap, fast); `/code-review ultra` (or an equivalent independent second model, e.g. Codex reviewing Claude's diff and vice versa) before merging anything non-trivial; a `REVIEW.md` tuned to your stack's known false-positive patterns; a hard PR-size discipline; and a personal 10-minute manual checklist for critical paths, security boundaries, and CI-weakening — because even the best-measured automated tools (finding 3, 7) still have a real, non-zero miss and false-positive rate, and agent-authored PRs get materially less genuine human scrutiny in practice than review-count metrics suggest (finding 15).

## Disagreements and open questions

- **"Review the plan, not the code" vs. "review the diff, but do it with multi-agent verification"**: these are not fully reconciled. Zencoder/Khandelwal argues the code-review-centric model is fundamentally too late; Anthropic's own product investment (Code Review, ultrareview) doubles down on post-diff review, with plan-approval appearing only as an upstream risk-tiering gate for whether a human needs to look at the diff at all, not as a replacement for diff review. No source in this pass measures plan-review's bug-catch rate head-to-head against post-diff multi-agent review.
- **Benchmark numbers for review-bot accuracy are not trustworthy in isolation.** The two vendor-reported summaries of the same Martian benchmark disagree on which tool ranks where (CodeRabbit "F1 51.2%, #1" per CodeRabbit's own post; CodeAnt "F1 51.7%, #3" per CodeAnt's own post — CodeAnt's own claimed F1 is numerically *higher* than the figure CodeRabbit reports for itself, which is internally inconsistent unless the two posts are citing different benchmark snapshots/tool versions). Martian's offline "gold set" was partly seeded from Augment's and Greptile's own bug lists — a disclosed bias. Treat any single tool's precision/recall/F1 claim as marketing-adjacent until corroborated by a neutral third party.
- **Copilot's security-detection accuracy claims are directly contradictory across secondary sources** found in this pass (one citing "zero vulnerabilities found in 117 files with known vulnerabilities," another citing "70–80% of known vulnerability signatures detected") — neither traced to a primary paper in this research pass. This is a genuine open question, not resolved here.
- **The oft-repeated "64% of AI review comments are style, only 14% catch real bugs" and "Greptile 11 FPs vs CodeRabbit 2 FPs on 50 PRs" figures** appeared only in WebSearch snippets/secondary aggregator summaries, not in a primary page independently fetched and read in this pass — flagged as unverified, do not cite as fact without checking the primary source.
- **No source in this pass gives a rigorous, apples-to-apples "false negative / miss rate" for any of the major review bots** (CodeRabbit, Greptile, Copilot, Claude Code Review) against a fixed, unbiased ground-truth bug set. All available recall-like numbers are either self-reported (Anthropic's <1% FP, derived from post-merge 👎 reactions, not miss rate) or drawn from a benchmark whose gold set has disclosed vendor-seeding bias (Martian). This is the single biggest evidentiary gap in the "measured false-positive / miss rate" part of the research question.

2. **Finding 4 — Cross-Context Review study, F1=28.6%, SR2 doesn't beat SR (arXiv 2603.12123).** CONFIRMED.
   > "30 artifacts (code, technical documents, presentation scripts) with 150 injected errors, tested under four review conditions — same-session Self-Review (SR), repeated Self-Review (SR2), context-aware Subagent Review (SA), and Cross-Context Review (CCR). Over 360 reviews... CCR reached an F1 of 28.6%, outperforming SR (24.6%, p=0.008, d=0.52)."
   > "reviewing twice in the same session did not beat reviewing once (p=0.11), which rules out repetition as an explanation for CCR's advantage."
   Author is Tae-Eun Song (report's citation "Song" is correct).
