# Context Engineering for Coding Agents — 2026 State

## TL;DR

- **Keep CLAUDE.md under 200 lines** (Anthropic's own docs, current guidance) — "Size: target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence." Practitioner blogs converge on the same range (HumanLayer: <300 lines, "shorter is better"; their own root file is <60 lines).
- **Instruction-following degrades with instruction count, not just token count.** IFScale (arXiv 2507.11538, Jul 2025) found even the best frontier models hit only **68% accuracy at 500 simultaneous instructions**, with three degradation archetypes (threshold/cliff, linear decay, exponential decay) and a peak "primacy" bias toward early instructions concentrated around 150–200 instructions.
- **Context rot is real and starts well before the context window fills.** Chroma's 18-model study (Jul 2025) showed non-uniform degradation as input grows — "a model with a 200K token window can exhibit significant degradation at 50K tokens" (secondary characterization; Chroma's own report frames it as degradation appearing "even on simple tasks" well below the nominal limit).
- **Skills/progressive disclosure is now Anthropic's official mechanism** for keeping bulk knowledge out of context until needed: SKILL.md kept under ~500 lines, skill listing (name+description) costs ~1% of the context window by default, description+trigger text capped at 1,536 characters, and after compaction each invoked skill is re-injected capped at 5,000 tokens (25,000 tokens combined budget).
- **Compaction is a real API primitive now**, not just a Claude Code trick: default trigger at 150,000 input tokens (configurable, minimum 50,000), and it deliberately discards raw tool output/reasoning in favor of a structured summary — which is exactly why "instructions from early in the conversation can get lost" per Anthropic's own docs.
- **Subagents are the sanctioned way to protect the main context window**: Anthropic's Sonnet 4.5 cookbook post says a subagent "might explore extensively, using tens of thousands of tokens or more, but returns only a condensed, distilled summary of its work (often 1,000-2,000 tokens)." Claude Code's own docs give a worked example: 6,100 tokens read by a subagent, 420 tokens returned to the parent.
- **"Frequent Intentional Compaction" (HumanLayer/Dex Horthy)** is the leading practitioner pattern for solo/small-team use: deliberately compact context every 10–15 exchanges into structured artifacts (progress files, plan files), targeting **40–60% context utilization**, rather than letting auto-compaction fire under pressure.
- **Auto memory (Claude Code's built-in long-term memory) is capped hard**: only the first 200 lines or 25KB of MEMORY.md load per session; anything beyond that is silently dropped on load (Claude gets an error nudging it to trim, but the file itself isn't truncated on disk).

## Findings

1. **Claude.md size target: under 200 lines, official Anthropic guidance.**
   Claude Code's memory docs state: "**Size**: target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence." Files over 200 lines "consume more context and may reduce adherence"; files over 4 MiB are skipped entirely. "Shorter files produce better adherence."
   Source: https://code.claude.com/docs/en/memory (fetched 2026-09-04, undated but current docs). PRIMARY. Consensus/standard guidance.

2. **HumanLayer's own root CLAUDE.md is under 60 lines; recommends <300 lines as an outer bound.**
   "At HumanLayer, our root `CLAUDE.md` file is *less than sixty lines*." General guidance: "< 300 lines is best, and shorter is even better." Content should cover WHAT (stack/structure), WHY (purpose), HOW (build/test/verify); explicitly excludes code-style rules (use linters) and one-off task instructions.
   Source: https://www.humanlayer.dev/blog/writing-a-good-claude-md, author "Kyle", dated November 25, 2025. PRIMARY (author's own practice). One practitioner's opinion, but converges with Anthropic's number.

3. **Claude Code's system prompt itself already consumes a meaningful share of "instruction budget."**
   Per the HumanLayer post: "Claude Code's system prompt contains ~50 individual instructions," and "Frontier thinking LLMs can follow ~150-200 instructions with reasonable consistency" — meaning the system prompt alone eats roughly a third of that budget before a user's CLAUDE.md is even loaded. Smaller/non-frontier models "exhibit an exponential decay in instruction-following performance" well before that count.
   Source: same as #2. SECONDARY synthesis of the IFScale numbers, applied to Claude Code specifically — one practitioner's extrapolation, not an Anthropic-verified claim.

4. **IFScale: frontier models top out at 68% accuracy under 500 simultaneous instructions.**
   IFScale (arXiv:2507.11538, "How Many Instructions Can LLMs Follow at Once?", Daniel Jaroslawicz et al.) tested 20 models across 7 providers on a synthetic task requiring inclusion of N keywords (10 to 500, in a business-report-writing task). Abstract-level finding: "even the best frontier models only achieve 68% accuracy at the max density of 500 instructions." Three degradation patterns were identified, correlated with model size/reasoning capability, plus "bias towards earlier instructions" and distinct categories of omission vs. modification errors.
   Source: https://arxiv.org/abs/2507.11538 (abstract, fetched directly) — PRIMARY. Published July 16, 2025. Standard/consensus finding within its own benchmark; the underlying benchmark itself has not (as far as this research found) been independently replicated by a second lab, so treat the exact numbers as PRIMARY-but-single-source.

5. **IFScale's three degradation archetypes, with approximate thresholds.**
   Via a synthesis site quoting the paper's language (not independently re-verified against the raw PDF text, since the PDF extraction failed): (a) **Threshold decay** (e.g. Gemini 2.5 Pro, o3) — "maintain near-perfect accuracy up to a critical density (N_threshold ≈ 150–200). Beyond this point, performance drops precipitously." (b) **Linear decay** (e.g. GPT-4.1, Claude Sonnet 4) — "accuracy declines steadily with a roughly constant slope as N increases." (c) **Exponential decay** (e.g. Claude 3.5 Haiku, Llama-4-Scout) — steep losses at low instruction density, floor accuracy "≈7–15%" as N grows. Peak primacy effect (bias toward earlier instructions) is "consistently observed between 150 and 200 instructions." Latency for reasoning models blows up "from ≈12.4s at 10 instructions to >430s at 250 instructions."
   Source: https://www.emergentmind.com/topics/ifscale-benchmark (fetched 2026-09-04). SECONDARY (third-party synthesis quoting the paper) — flagged because direct PDF text extraction was not achievable in this session; treat exact thresholds as indicative, not verbatim-verified.

6. **Chroma "Context Rot": all 18 tested frontier models degrade as input length grows, non-uniformly.**
   Chroma tested 18 models (Claude Opus 4/Sonnet 4/3.7/3.5/Haiku 3.5; OpenAI o3, GPT-4.1 family, GPT-4o, GPT-4 Turbo, GPT-3.5 Turbo; Gemini 2.5 Pro/Flash, 2.0 Flash; Qwen3 8B/32B/235B). Core finding: "model performance varies significantly as input length changes, even on simple tasks" and "models do not use their context uniformly." Specific sub-experiments: needle-question similarity (lower semantic similarity between the needle and the question degrades faster with length); distractors ("even a single distractor reduces performance relative to the baseline... adding four distractors compounds this degradation further"); haystack structure (counterintuitively, "models perform worse when the haystack preserves a logical flow of ideas" vs. shuffled/incoherent text); LongMemEval shows "significantly higher performance on focused prompts compared to full prompts"; a repeated-word replication task shows consistent accuracy degradation with length, plus measurable model refusal rates (Claude Opus 4: 2.89%, GPT-4.1: 2.55%, overall 0.035% across 194,480 calls, GPT-3.5 Turbo excluded due to a 60.29% content-filter refusal rate on that task).
   Source: https://www.trychroma.com/research/context-rot, published July 14, 2025. PRIMARY. Standard/consensus within the field — widely cited by Anthropic and others as the reference context-rot study. Note: the commonly repeated claim that "a 200K window can show real degradation by 50K tokens" is a SECONDARY paraphrase seen in commentary (e.g. Inkeep, Morph); Chroma's own page frames the result qualitatively ("varies significantly," task-dependent) rather than naming a single universal 50K threshold — treat any single crossover number as an approximation, not Chroma's own headline stat.

7. **Anthropic's official context-engineering framing: "attention budget," "right altitude," minimal-but-sufficient prompts.**
   Anthropic's engineering blog (Sept 29, 2025, alongside the Sonnet 4.5 launch) frames context engineering as the successor discipline to prompt engineering: "LLMs have an 'attention budget' that they draw on when parsing large volumes of context," and context rot means "as the number of tokens in the context window increases, the model's ability to accurately recall information from that context decreases." Prompting guidance: aim for "the minimal set of information that fully outlines your expected behavior" while noting "minimal does not necessarily mean short; you still need to give the agent sufficient information" — the "right altitude" is between brittle hardcoded if-else prompts and vague generalities.
   Source: https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents, published 2025-09-29. PRIMARY. This is Anthropic's own standard guidance (supersedes older, thinner "prompt engineering" framing).

8. **Anthropic's compaction guidance and its acknowledged failure mode.**
   Same Anthropic post: compaction is "taking a conversation nearing the context window limit, summarizing its contents, and reinitiating a new context window with the summary." Claude Code's implementation "preserves architectural decisions, unresolved bugs, and implementation details while discarding redundant tool outputs." Tuning approach: "start by maximizing recall... then iterate to improve precision." Explicit failure mode: "overly aggressive compaction can result in the loss of subtle but critical context whose importance only becomes apparent later." Tool-result clearing is called out as "one of the safest lightest touch forms of compaction" — a lower-risk alternative to full summarization.
   Source: same as #7. PRIMARY. Standard guidance, actively superseding the earlier "just let auto-compact handle it" assumption implicit in Claude Code's initial UX.

9. **Compaction as an API primitive: 150,000-token default trigger, 50,000-token floor.**
   Anthropic's platform docs describe compaction as a first-class API feature (not just a Claude Code UI trick): it detects when input tokens reach a trigger threshold, generates a summary, creates a `compaction` block, and continues; on the next request, "the API automatically drops all content blocks prior to the `compaction` block." Default trigger: `{"trigger": {"type": "input_tokens", "value": 150000}}`; the `value` "must be at least 50,000 tokens" — no documented upper bound. On Claude Fable 5.1/Mythos 5.1, "thinking blocks from before a `compaction` block aren't carried forward, so the summary is all the model has of that earlier work" — a specific model-version failure mode. Compaction "requires an additional sampling step," which adds to billed usage; cost tracking must sum `usage.iterations` rather than a single `usage.input_tokens`/`output_tokens` pair.
   Source: https://platform.claude.com/docs/en/build-with-claude/compaction (fetched 2026-09-04, current docs). PRIMARY. Standard/current API behavior.

10. **What survives compaction in Claude Code, concretely.**
    Per the interactive context-window docs: on `/compact`, Claude Code re-loads the startup content (system prompt, CLAUDE.md, memory, MCP tools) automatically, generates a "structured summary" retaining "your requests and intent, key technical concepts, files examined or modified with important code snippets, errors and how they were fixed, pending tasks, and current work" — but "full tool outputs and intermediate reasoning are gone." It also "re-reads the files modified most recently" (up to five) and "re-injects the skills you invoked," each capped at 5,000 tokens with a 25,000-token combined skill budget; but the **skill-description listing itself does not reload** after compaction — only skills actually invoked survive. Project-root CLAUDE.md "survives compaction" by being re-read from disk; nested/path-scoped CLAUDE.md and rules only reload when a matching file is touched again — meaning an instruction given only in conversation, or a not-yet-triggered nested rule, is exactly what gets lost.
    Source: https://code.claude.com/docs/en/context-window and https://code.claude.com/docs/en/memory (both fetched 2026-09-04). PRIMARY.

11. **Illustrative startup token costs (Claude Code's own numbers, marked "illustrative").**
    Claude Code's interactive context-window explainer gives example (not universal) token costs for what loads before a user types anything: system prompt ≈4,200 tokens; auto memory (MEMORY.md) ≈680 tokens; environment info ≈280 tokens; MCP tool names (deferred) ≈120 tokens; skill descriptions ≈450 tokens; user-level `~/.claude/CLAUDE.md` ≈320 tokens; project CLAUDE.md ≈1,800 tokens — against a 200,000-token window in this example. The page explicitly labels these "illustrative... actual values vary with your CLAUDE.md size, MCP servers, and file lengths."
    Source: https://code.claude.com/docs/en/context-window (fetched 2026-09-04). PRIMARY, but self-flagged as illustrative, not a universal budget.

12. **Subagents: real, documented context-isolation numbers.**
    Anthropic's context-engineering post: a subagent "might explore extensively, using tens of thousands of tokens or more, but returns only a condensed, distilled summary of its work (often 1,000-2,000 tokens)," recommended for "complex research and analysis where parallel exploration pays dividends." Claude Code's own docs give a concrete worked example in the interactive walkthrough: a subagent reads 6,100 tokens across three files and returns a 420-token summary to the parent — "That's the context savings." Claude Code's sub-agents doc: "Use subagents when: the task produces verbose output you don't need in your main context" (tests, docs fetches, log processing named explicitly). Subagent descriptions themselves have a budget: "When the combined descriptions of your subagents... exceed 15,000 tokens, Claude Code shows a warning at startup."
    Sources: https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents (2025-09-29) and https://code.claude.com/docs/en/sub-agents, https://code.claude.com/docs/en/context-window (fetched 2026-09-04). PRIMARY. Consensus.

13. **Subagent and its own memory system also has the 200-line/25KB cap.**
    "The subagent's system prompt also includes the first 200 lines or 25KB of `MEMORY.md` in the memory directory, whichever comes first" — same limit as the main session's auto memory, but subagents get their own separate memory directory (scoped `user`, `project`, or `local`) and do **not** inherit the main session's auto memory unless the subagent is a "fork" of the current conversation.
    Source: https://code.claude.com/docs/en/sub-agents and https://code.claude.com/docs/en/memory (fetched 2026-09-04). PRIMARY.

14. **Auto memory (MEMORY.md): hard 200-line/25KB read cap, four note types, silent truncation risk.**
    Claude Code's auto memory writes four kinds of notes (`user`, `feedback`, `project`, `reference`) into a per-project directory (`~/.claude/projects/<project>/memory/`), indexed by `MEMORY.md`. "The first 200 lines of `MEMORY.md`, or the first 25KB, whichever comes first, are loaded at the start of every conversation. Content beyond that threshold is not loaded at session start." When Claude writes past the limit, Claude Code returns an error prompting a rewrite/trim rather than silently truncating on disk, but anything still over the limit at the next session start is simply not loaded. Detail is meant to live in separate per-topic files (not loaded at startup; read on demand). Auto memory is machine-local, shared across worktrees of the same repo, and is not shared across machines.
    Source: https://code.claude.com/docs/en/memory (fetched 2026-09-04). PRIMARY.

15. **Progressive disclosure via Agent Skills — official Anthropic mechanism, released as an open standard.**
    Anthropic's own framing: "Claude scans available skills to find relevant matches. When one matches, it loads only the minimal information and files needed—keeping Claude fast while accessing specialized expertise." Skills are "composable" (stack together), "portable" (same format across Claude apps/Code/API). This directly operationalizes progressive disclosure as a system-design pattern (metadata always visible → full SKILL.md body loaded on trigger → linked reference files loaded only as needed).
    Source: https://claude.com/blog/skills, published October 16, 2025 (redirected from anthropic.com/news/skills). PRIMARY. Standard/current guidance — this is the mechanism Anthropic now recommends over stuffing everything into CLAUDE.md.

16. **Concrete Agent Skills budget numbers (Claude Code implementation).**
    Recommended: "Keep `SKILL.md` under 500 lines. Move detailed reference material to separate files." The `description` (+ optional `when_to_use`) frontmatter is "truncated at 1,536 characters in the skill listing to reduce context usage." The skill-name-and-description listing Claude sees at startup is bounded to "1% of the model's context window" by default (configurable via `skillListingBudgetFraction`); when it overflows, least-used skills' descriptions get dropped first. After `/compact`, "Claude Code re-attaches the most recent invocation of each skill after the summary, keeping the first 5,000 tokens of each. Re-attached skills share a combined budget of 25,000 tokens," dropping older invoked skills first if many were used in one session.
    Source: https://code.claude.com/docs/en/skills (fetched 2026-09-04). PRIMARY. Standard/current.

17. **HumanLayer's "Frequent Intentional Compaction" (FIC): the leading practitioner pattern for solo/small-team context management.**
    Core prescription: "keeping utilization in the 40%-60% range (depends on complexity of the problem)." Rather than letting context fill to the auto-compaction threshold, the workflow deliberately compacts progress into structured artifacts at regular intervals — "after 10–15 exchanges, you pause and ask your AI to summarize progress." The overall workflow is Research → Plan → Implement: research produces a written understanding of the codebase and relevant files; plan is an explicit, editable file listing exact steps and files to touch; implementation steps through the plan phase by phase, and "for complex work... compact the current status back into the original plan file" as a running handoff/checkpoint document. Subagents are framed explicitly as a context-control primitive, not a "multi-agent personas" gimmick: "Subagents are not about playing house... Subagents are about context control," used mainly for "finding/searching/summarizing" with a fresh window. The post argues human review effort should concentrate upstream: "A bad line of code is... a bad line of code. But a bad line of a plan could lead to hundreds of bad lines of code," so review research and plans hardest, code less so.
    Source: https://github.com/humanlayer/advanced-context-engineering-for-coding-agents/blob/main/ace-fca.md, author Dex Horthy (HumanLayer), 2025 (see also https://www.humanlayer.dev/blog/advanced-context-engineering). PRIMARY. One practitioner's methodology — widely cited but not an Anthropic-endorsed standard; presented and tested on large (300k LOC Rust) codebases at HumanLayer specifically.

18. **FIC's reported outcomes (practitioner-reported, not independently verified).**
    Cited results: a 300k-LOC Rust codebase bug fix shipped as a single PR approved the next day; a 35k-LOC feature took 7 hours total (3 research/planning + 4 implementation); an intern went from 2 PRs on day one to 10 PRs by day eight using this workflow; team spend was reported around $12k/month on Claude Opus.
    Source: same as #17. PRIMARY (self-reported by the practitioner/company) but unverified by a third party — treat as anecdotal evidence of the pattern's effectiveness, not a controlled study.

19. **12-Factor Agents, Factor 3 ("Own your context window"): custom, dense context formats beat default message arrays.**
    "You don't necessarily need to use standard message-based formats for conveying context to an LLM." The framing of what belongs in context: "the prompt and instructions you give to the model," "any documents or external data you retrieve (e.g. RAG)," "any past state, tool calls, results, or other history," "any past messages or events from related but separate histories/conversations (Memory)," and "instructions about what sorts of structured data to output." Recommends custom, XML-like tagging (e.g. `<slack_message>`, `<list_git_tags_result>`) collapsed into as few messages as practical (even a single user message) for token- and attention-efficiency, plus explicit error-hiding once resolved: "consider hiding errors and failed calls from context window once they are resolved."
    Source: https://github.com/humanlayer/12-factor-agents/blob/main/content/factor-03-own-your-context-window.md, author Dex Horthy/HumanLayer, no specific date in-page (repo is widely dated to ~2025). PRIMARY. One practitioner's opinion/framework — contested in the sense that it directly argues against defaulting to standard chat-message-array context, which most frameworks (including Claude Code itself) do use by default.

20. **When to `/clear` vs. continue: no hard rule from Anthropic, but a clear qualitative signal.**
    Anthropic's own docs frame this operationally rather than with a fixed token number: "As you work, context fills up. Claude compacts automatically, but instructions from early in the conversation can get lost. Put persistent rules in CLAUDE.md, and run `/context` to see what's using space." The guidance to switch to a fresh session (`/clear`) rather than compact is implicit in "sessions are independent... each new session starts with a fresh context window" and in third-party guidance (secondary) that frames `/clear` as appropriate "when switching to unrelated work" since old conversation "crowds out the files you need next and costs tokens on every message," whereas `/compact` (or FIC-style manual compaction into a plan/handoff file) is for continuing the *same* task past the token ceiling.
    Sources: https://code.claude.com/docs/en/how-claude-code-works (PRIMARY, fetched 2026-09-04) for the compaction-loses-early-instructions point; the `/clear`-for-unrelated-work framing is SECONDARY (seen via search-result synthesis of Claude Code docs commentary, not independently re-verified verbatim on an official page in this session).

20b. **Session handoff documents: a recognized third-party pattern, not (yet) an Anthropic primitive.**
    Multiple independent "session-handoff" skills/tools (e.g. softaworks/agent-toolkit's `session-handoff` skill) exist specifically to solve "the long-running agent context exhaustion problem by preserving complete context, decisions, and state across sessions" as a structured Markdown+JSON file capturing file lists, decisions, next steps, and open questions, triggered by context nearing capacity, milestone completion, or session end, and loaded back in at the start of a fresh session so "the agent [becomes] immediately oriented without any re-explaining." This is structurally the same idea as HumanLayer's "compact the current status back into the original plan file" (#17) and is the same shape as this repo's own memory/auto-memory system (#14), just implemented as a community skill rather than a first-party Claude Code feature.
    Source: https://github.com/softaworks/agent-toolkit/tree/main/skills/session-handoff (fetched via search synthesis; not independently WebFetched in full in this session — treat description as SECONDARY, sourced from the tool's own README/SKILL.md as summarized by search). Standard/consensus pattern across the ecosystem, but not an official Anthropic feature name.

## Concrete practices / configs (copy-pasteable this week)

- **CLAUDE.md**: keep it under 200 lines (Anthropic's number) or aim even lower (~60–300, per HumanLayer). Structure with markdown headers/bullets. Write concrete, verifiable rules ("Use 2-space indentation," "Run `npm test` before committing") instead of vague ones ("format code nicely") — Claude Code's own docs give this exact contrast as the debugging heuristic when instructions aren't followed.
- **Move anything procedural or topic-specific out of CLAUDE.md** into `.claude/rules/*.md` (optionally path-scoped via YAML frontmatter `paths:`) so it only loads when relevant files are touched, or into a `skills/<name>/SKILL.md` (kept under 500 lines) for multi-step procedures Claude should pull in only when needed. Use block-level HTML comments (`<!-- ... -->`) in CLAUDE.md for human-only notes — they're stripped before hitting context, at zero token cost.
- **AGENTS.md interop**: if you already maintain `AGENTS.md`, don't duplicate it — put `@AGENTS.md` as the first line of `CLAUDE.md` (or symlink `CLAUDE.md -> AGENTS.md` on Linux/macOS) and append any Claude-specific instructions below the import.
- **Run `/init`** to auto-generate a starting CLAUDE.md from codebase analysis, and periodically run **`/doctor`** to get a proposed trim of a checked-in CLAUDE.md (it keeps pitfalls/rationale/non-default conventions, cuts things Claude can derive from the code itself, like directory layout).
- **Adopt Frequent Intentional Compaction**: don't wait for auto-compact. Every 10–15 exchanges (or before starting a big new subtask), have Claude write/update a plan or progress file on disk, and manually `/compact` (optionally with a focus string, e.g. `/compact focus on the API changes`) rather than letting context silently degrade toward the trigger. Target roughly 40–60% context utilization as a rule of thumb, not 90%+.
- **Use `/context` regularly** to see what's actually consuming space (system prompt, CLAUDE.md, memory, skills, MCP tools, conversation) before deciding whether to `/compact` or `/clear`.
- **Prefer subagents for anything that generates a lot of read/search output you don't need verbatim** (running tests, fetching docs, log analysis, broad codebase research) — they keep tens of thousands of tokens of exploration out of your main window and hand back a ~1–2K-token summary. Don't use them as "personas" — use them specifically for context isolation.
- **Use `/clear` when switching to genuinely unrelated work**, and continuation (`/compact` or a fresh session seeded from a handoff/plan file) when staying on the same task but past a comfortable context size.
- **Let auto memory do its job, but keep MEMORY.md terse**: only its first 200 lines / 25KB load per session — put detail in separate topic files Claude reads on demand, and treat `MEMORY.md` itself as an index, not a knowledge base.
- **For long multi-session work, write an explicit handoff/plan file on disk** (decisions made, files touched, open questions, next steps) rather than relying on conversation history or auto-compaction to preserve it — this is the practice common to FIC's "plan file," community "session-handoff" skills, and Claude Code's own auto-memory `project`-type notes.
- **If you author skills**: put the single most important use case first in the `description`/`when_to_use` frontmatter (truncated at 1,536 characters in the listing), keep SKILL.md itself under 500 lines, and push reference material to separate files loaded only on demand — this is literally what makes progressive disclosure work instead of becoming "CLAUDE.md but hidden."

## Disagreements and open questions

- **Exact CLAUDE.md line-count ceiling isn't uniform.** Anthropic's own docs say "under 200 lines"; HumanLayer says "<300 is best, shorter is even better" with their own file at <60 lines. These aren't contradictory so much as differently conservative — no source argues for a *larger* number, so this is closer to a converging consensus than a real disagreement, but the exact number is not standardized.
- **The Chroma "50K tokens on a 200K window" degradation-onset figure is widely repeated as if it were Chroma's headline number, but Chroma's own page states the effect is task- and model-dependent rather than naming one universal crossover point.** Treat specific "degradation starts at X tokens" claims from secondary sources with caution; the primary finding is qualitative non-uniformity, not a single threshold.
- **IFScale's exact per-pattern threshold numbers (N≈150–200 for threshold decay, 7–15% floor for exponential decay, etc.) could not be independently verified against the raw PDF text in this session** — PDF extraction returned only structural/binary content, not the prose. The numbers reported here (via emergentmind.com's synthesis) are internally consistent with the confirmed abstract-level finding (68% at N=500) but should be treated as SECONDARY until checked against the actual paper text or HTML rendering.
- **12-Factor Agents' "own your context window" advice (custom XML-tag formats collapsed into fewer messages) is a specific, opinionated stance that cuts against how most agent harnesses — including Claude Code itself — actually structure context (as a message array with per-tool-call blocks).** This is a real disagreement in practice: HumanLayer's own framework argues for owning your format; Anthropic's shipped product uses the standard format and instead optimizes what enters it (compaction, skills, subagents). Not a resolved question — more a build-your-own-harness vs. use-Claude-Code's-defaults tradeoff.
- **No official Anthropic guidance found that names "session handoff documents" as a first-party pattern or feature** — it exists as a converging community practice (skills, blog posts) and is functionally reinvented by Claude Code's own project-scoped auto-memory notes and by HumanLayer's plan-file compaction. Whether Anthropic will formalize this (e.g. a dedicated command) is an open question, not something this research could confirm or deny.
- **"12-factor agents" publish date could not be pinned down precisely** — the repository is heavily cited throughout 2025–2026 but no single canonical "published on X date" was found on the fetched page itself.
