# The Harness Engineering Canon: What the Foundational Texts Actually Prescribe

## TL;DR

- **"Harness engineering" as a named discipline is ~7 months old.** Mitchell Hashimoto coined the phrase on his personal blog Feb 5, 2026 ("anytime you find an agent makes a mistake, you take the time to engineer a solution such that the agent never makes that mistake again"); OpenAI's Codex team post six days later (Feb 11, 2026) and Martin Fowler's April 2026 article cemented "Agent = Model + Harness" as the field's working formula. (mitchellh.com/writing/my-ai-adoption-journey; openai.com/index/harness-engineering/; martinfowler.com/articles/harness-engineering.html)
- **OpenAI's core move: stop writing a giant AGENTS.md, write a small map instead.** They tried "one big AGENTS.md," it rotted, they replaced it with a ~100-line AGENTS.md that acts as a table of contents pointing into a structured `docs/` tree (design-docs/, exec-plans/, product-specs/, references/, generated/) — mechanically enforced by linters and CI, with a recurring "doc-gardening" agent that deletes stale docs. (openai.com/index/harness-engineering/, Feb 11 2026)
- **Anthropic's long-running-agent pattern (Nov 2025): initializer agent + incremental agent, driven by a `feature-list.json` and a `claude-progress.txt`.** One agent scaffolds once; every subsequent session reads the progress file, picks exactly one unfinished feature, and is explicitly forbidden from deleting or editing tests to fake completion. (anthropic.com/engineering/effective-harnesses-for-long-running-agents, Nov 26 2025)
- **Anthropic's follow-up (Mar 2026) reverses part of its own Nov 2025 advice as models improved**: the three-agent planner/generator/evaluator split and "context resets" existed specifically to fight Sonnet 4.5's "context anxiety"; with Opus 4.5+ the anxiety mostly disappeared and the harness's own "sprint" construct became removable. Anthropic's stated principle: "every component in a harness encodes an assumption about what the model can't do on its own" — so harnesses should shrink as models get better, not just grow. (anthropic.com/engineering/harness-design-long-running-apps, Mar 24 2026)
- **Every text that touches self-review says the same thing: don't let the model grade its own work.** Anthropic's harness posts, Claude Code's current best-practices page, and OpenAI's Codex pipeline all converge on a fresh-context / separate-agent reviewer — but they gate it differently (see Disagreements).
- **Tool design and context management are the same problem at two scales.** "Writing tools for agents" (Sep 2025) and "Effective context engineering" (Sep 2025) both reduce to: treat tokens as a scarce, non-linear resource, prefer fewer/higher-signal tools and just-in-time retrieval over dumping everything into context up front.
- **Claude Code's own current best-practices page (fetched live, 2026) is the most operational document of the set** — it converts the abstract harness principles into literal keybindings, hooks, `/goal` conditions, Stop-hook gating (with an 8-consecutive-block override so an unattended run can't deadlock forever), and a documented failure-pattern table.
- **The term is contested, not consensus.** A May 2026 critique (Stuart Miller) argues "harness engineering" repackages platform engineering / SRE / control-plane design with no fundamentally new problem; it also reports (secondhand) a real terminological split — HumanLayer treats harness engineering as a subset of context engineering, LangChain treats it as the thing that supersedes context engineering.

## Findings

1. **Claim:** Mitchell Hashimoto coined "harness engineering" on Feb 5, 2026, defining it as: whenever an agent makes a mistake, engineer a permanent fix into its environment so that specific mistake becomes structurally impossible to repeat — implemented either as documentation ("implicit prompting," e.g. one line added to AGENTS.md per bad behavior observed) or as programmed tools (scripts, verification utilities).
   **Evidence/quote:** "anytime you find an agent makes a mistake, you take the time to engineer a solution such that the agent never makes that mistake again." / "Each line in that file is based on a bad agent behavior, and it almost completely resolved them all."
   **Source:** https://mitchellh.com/writing/my-ai-adoption-journey — Feb 5, 2026 — **PRIMARY** — one practitioner's account, now widely cited as the term's origin (standard/consensus that this is the coinage; the content itself is one practitioner's opinion/method).

2. **Claim:** OpenAI's Codex team ran a 5-month, ~1M-line, zero-manually-written-code internal product build (Mar–Aug 2025, first commit "late August 2025," post published Feb 11, 2026) with a 3→7 engineer team, averaging 3.5 merged PRs/engineer/day, and throughput *increasing* as headcount grew.
   **Evidence/quote:** "0 lines of manually-written code... Humans steer. Agents execute." / "roughly 1,500 pull requests have been opened and merged with a small team of just three engineers driving Codex."
   **Source:** https://openai.com/index/harness-engineering/ — Feb 11, 2026, by Ryan Lopopolo (contributions from Victor Zhu, Zach Brock) — **PRIMARY** — one team's reported result, not independently verified; consensus among secondary coverage (InfoQ, Ken Huang, SaaSCity) that this is the anchoring case study for the discipline.

3. **Claim:** OpenAI explicitly tried and rejected a single large AGENTS.md ("one big AGENTS.md approach... It failed in predictable ways") because context is scarce, "too much guidance becomes non-guidance," a monolithic file "rots instantly," and it's not mechanically verifiable. Their fix: a ~100-line AGENTS.md as a *table of contents*, with the real knowledge base in a structured, linted `docs/` directory (design-docs/, exec-plans/{active,completed}, product-specs/, references/, generated/, plus ARCHITECTURE.md, DESIGN.md, QUALITY_SCORE.md, SECURITY.md, RELIABILITY.md).
   **Evidence/quote:** "instead of treating AGENTS.md as the encyclopedia, we treat it as the table of contents." / "Dedicated linters and CI jobs validate that the knowledge base is up to date, cross-linked, and structured correctly. A recurring 'doc-gardening' agent scans for stale or obsolete documentation... and opens fix-up pull requests."
   **Source:** https://openai.com/index/harness-engineering/ — Feb 11, 2026 — **PRIMARY**. **Consensus-adjacent**: this specific "small map + linted knowledge base, prune the manual" pattern is echoed independently by Claude Code's own best-practices page (finding 9) and by Anthropic's long-running-agents post (finding 5), so treat the *general* prescription ("don't let the instructions file become an encyclopedia") as cross-vendor consensus, even though the concrete directory layout is OpenAI's own design choice.

4. **Claim:** OpenAI enforces architecture mechanically, not by prose convention: each business domain has a fixed, one-directional dependency order (Types → Config → Repo → Service → Runtime → UI), cross-cutting concerns must enter through a single "Providers" interface, and violations are caught by custom linters (themselves written by Codex) and structural tests whose error messages are written to "inject remediation instructions into agent context."
   **Evidence/quote:** "The agent doesn't need more instructions. It needs a world where the right thing to do is obvious and the wrong thing is hard." [paraphrase reported by secondary sources — see caveat below] / directly quoted from the primary source instead: "By enforcing invariants, not micromanaging implementations, we let agents ship fast without undermining the foundation." / "we statically enforce structured logging, naming conventions for schemas and types, file size limits, and platform-specific reliability requirements with custom lints. Because the lints are custom, we write the error messages to inject remediation instructions into agent context."
   **Source:** https://openai.com/index/harness-engineering/ — Feb 11, 2026 — **PRIMARY**. Note: the "make it hard to do wrong" one-liner appears verbatim in several secondary write-ups (saascity.io, alphasignalai) attributed to this post; my own full-text fetch of the primary source did not contain that exact sentence — the closest primary-source equivalents are the "invariants, not micromanaging" and layered-architecture quotes above. Treat the exact phrase as **SECONDARY** (possibly a paraphrase that propagated as if verbatim) until confirmed against the primary text; the underlying mechanism (mechanical enforcement > prose rules) is **PRIMARY** and solidly sourced.

5. **Claim:** Anthropic's Nov 2025 pattern for long-running coding agents: an **initializer agent** runs once, expands the user's prompt into a structured `feature-list.json` (each feature initially marked `passes: false`) and writes an `init.sh`; a **coding agent** then runs repeated sessions, each of which must: run `pwd`, read git log + `claude-progress.txt` for context, pick exactly one incomplete feature, run `init.sh`, sanity-test, then work — leaving the repo in a mergeable state ("no major bugs, the code is orderly and well-documented") and committing with descriptive messages. Editing or deleting tests to fake a pass is explicitly forbidden.
   **Evidence/quote:** "an initializer agent that sets up the environment on the first run, and a coding agent that is tasked with making incremental progress" / "It is unacceptable to remove or edit tests because this could lead to missing or buggy functionality." / "Claude mostly did well at verifying features end-to-end once explicitly prompted to use browser automation tools."
   **Source:** https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents — Nov 26, 2025 — **PRIMARY**. Anthropic's own framing, presented as a validated pattern from their research — **one practitioner's (Anthropic's) prescription**, not yet cross-validated by OpenAI's post (which uses a different pattern: exec-plans/active + exec-plans/completed as first-class checked-in artifacts, not a single feature-list.json).

6. **Claim:** Anthropic's Mar 2026 follow-up ("Harness design for long-running application development") replaces the single coding-agent loop with a three-agent architecture — **planner** (expands a brief prompt into a full spec, stays ambitious on scope, avoids over-specifying implementation), **generator** (implements incrementally, self-evaluates before handoff), **evaluator** (drives the running app like a user, grades against explicit criteria, files bugs) — because letting the generator grade its own work fails: "[generators] respond by confidently praising the work — even when, to a human observer, the quality is obviously mediocre." The post also names "context anxiety" — models that fear hitting the context limit and wrap up prematurely — as a specific failure mode that compaction alone didn't fix for Sonnet 4.5, requiring hard context resets with structured file-based handoffs; this need "largely" disappeared with Opus 4.5+.
   **Evidence/quote:** "every component in a harness encodes an assumption about what the model can't do on its own, and those assumptions are worth stress testing" — used to justify removing the "sprint" construct once Opus 4.6 improved planning/long-context/debugging.
   **Source:** https://www.anthropic.com/engineering/harness-design-long-running-apps — Mar 24, 2026, Prithvi Rajasekaran (Anthropic Labs) — **PRIMARY**. This is Anthropic revising its own Nov 2025 guidance in public — an explicit case of "prefer the newest guidance; note when older guidance was superseded" per this research's own instructions: the single-progress-file pattern from finding 5 is presented in the Mar 2026 post as the *original*, now-partially-superseded harness, not the current recommendation for capable models.

7. **Claim ("Building effective agents," the foundational architecture piece, predates the "harness engineering" term by over a year):** Anthropic defines **workflows** ("systems where LLMs and tools are orchestrated through predefined code paths") vs. **agents** ("systems where LLMs dynamically direct their own processes and tool usage"), and recommends starting with the simplest possible solution, escalating to agents only for open-ended problems where the number of steps can't be predicted and a fixed path can't be hardcoded. It names five composable workflow patterns (prompt chaining, routing, parallelization — sectioning/voting, orchestrator-workers, evaluator-optimizer) and three cross-cutting principles: simplicity, transparency (show the agent's planning steps explicitly), and ACI — agent-computer interface — design, argued to deserve as much engineering investment as human-computer interfaces.
   **Evidence/quote:** "Maintain simplicity in your agent's design." / "Prioritize transparency by explicitly showing the agent's planning steps." / "[invest] just as much effort in creating good agent-computer interfaces (ACI)" as human ones.
   **Source:** https://www.anthropic.com/engineering/building-effective-agents — Dec 19, 2024, Erik Schluntz and Barry Zhang — **PRIMARY**. **Standard/consensus**: this piece predates "harness engineering" as a term but its ACI concept is the direct conceptual ancestor of the 2026 harness-engineering wave; virtually every later text (OpenAI's, Anthropic's own, Fowler's) restates some version of "invest engineering effort in the interface, not just the model."

8. **Claim ("Effective context engineering for AI agents"):** Context is a finite resource with *diminishing, non-linear* returns — n tokens create n² pairwise attention relationships, so agents don't just run out of context, their attention degrades as context fills. Prescriptions: write system prompts at "the right altitude" (not brittle if-else, not vague generalities) — "the smallest possible set of high-signal tokens that maximize the likelihood of some desired outcome"; keep tool sets minimal and unambiguous; use a small number of diverse, canonical few-shot examples rather than exhaustive edge-case enumeration; for long-horizon tasks use **compaction** (summarize history near the context limit, preserving architectural decisions/unresolved bugs/implementation details, discarding redundant tool output — "start by maximizing recall, then improve precision"), **structured note-taking** (persist notes outside the context window, e.g. a to-do/progress file), and **sub-agent architectures** (specialized agents with clean context windows returning condensed 1,000–2,000 token summaries to a coordinating agent) as three concrete long-horizon techniques; and prefer **just-in-time retrieval** (agents hold lightweight references — file paths, stored queries, links — and load data at runtime) with a **hybrid** fallback (load some context eagerly for speed, explore the rest autonomously) over front-loading everything.
   **Evidence/quote:** "context must be treated as a finite resource with diminishing marginal returns." / "Examples are the 'pictures' worth a thousand words."
   **Source:** https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents — Sep 29, 2025, Prithvi Rajasekaran, Ethan Dixon, Carly Ryan, Jeremy Hadfield — **PRIMARY**. **Standard/consensus** among Anthropic's own later posts: compaction and structured note-taking reappear as load-bearing mechanisms in both the Nov 2025 and Mar 2026 harness posts (progress files, context resets), and sub-agent-with-clean-context reappears verbatim as a Claude Code best practice (finding 9).

9. **Claim ("Writing tools for agents"):** Fewer, more powerful, consolidated tools outperform one-tool-per-API-endpoint (e.g. replace `list_users`+`list_events`+`create_event` with a single `schedule_event`); tools should be namespaced (prefix- or suffix-based, e.g. `asana_search`) to reduce ambiguity; responses should favor human-readable, semantically meaningful fields over raw technical identifiers (name/image_url/file_type over uuid/mime_type), optionally via a `response_format` enum (their own example: "detailed" = 206 tokens vs. "concise" = 72 tokens for the same query); default to pagination/filtering/truncation with actionable truncation messages ("Try using filters or pagination for narrower searches"); errors should steer, not just report ("Parameter `user` must be numeric ID... Try searching first" rather than a raw stack trace); and tool quality should be driven by evaluations built on realistic multi-step tasks with verifiable outcomes, reading raw transcripts (not just aggregate scores) because "what agents omit in their feedback and responses can often be more important than what they include." Claude Code itself caps individual tool responses at 25,000 tokens by default.
   **Evidence/quote:** "More tools don't always lead to better outcomes." / "Small refinements to tool descriptions can yield dramatic improvements."
   **Source:** https://www.anthropic.com/engineering/writing-tools-for-agents — Sep 11, 2025, Ken Aizawa with 15 named contributors — **PRIMARY**. **Standard/consensus**: this is Anthropic's most cited tool-design reference and is echoed by third-party ADRs and MCP server design guides (e.g. the vishnu2kmohan mcp-server-langgraph ADR found in search), suggesting broad industry adoption of the consolidation/namespacing/token-efficiency prescriptions specifically.

10. **Claim (Claude Code current best-practices page, fetched live Sept 2026):** The single overriding constraint the whole page is organized around is context-window degradation ("Claude's context window fills up fast, and performance degrades as it fills"). Concrete, load-bearing prescriptions:
    - **Give Claude a check it can run** (test, build, linter, screenshot diff) — "Claude stops when the work looks done. Without a check it can run, 'looks done' is the only signal available." Four escalating gate mechanisms are named explicitly: ask-in-prompt; a `/goal` condition re-checked by a separate evaluator after every turn; a Stop hook that blocks the turn deterministically as a script gate — **but Claude Code itself overrides the hook and force-ends the turn after 8 consecutive blocks**, an explicit anti-deadlock design choice; or a fresh-context verification subagent/dynamic workflow ("so the agent doing the work isn't the one grading it").
    - **Explore → Plan → Implement → Commit** as the default four-phase workflow, using Plan Mode (`Shift+Tab`) to separate research from execution; explicitly *not* recommended for small, one-sentence-describable diffs ("If you could describe the diff in one sentence, skip the plan").
    - **CLAUDE.md discipline**: keep it short, human-readable, reviewed like code; litmus test per line — "Would removing this cause Claude to make mistakes? If not, cut it."; an explicit include/exclude table (include: bash commands Claude can't guess, non-default code style, testing instructions, repo etiquette, architectural decisions, environment quirks, non-obvious gotchas; exclude: anything inferable from code, standard conventions, detailed API docs — link instead, frequently-changing info, tutorials, "self-evident practices like 'write clean code'"); domain knowledge that's only *sometimes* relevant belongs in **Skills**, not CLAUDE.md, because skills load on demand.
    - **Hooks are for zero-exception rules** ("Unlike CLAUDE.md instructions which are advisory, hooks are deterministic and guarantee the action happens").
    - **Subagents for investigation and adversarial review**: delegate research to keep the main context clean; before calling work done, "have a subagent review the diff in a fresh context and report gaps" — but explicitly warn against over-trusting that reviewer: "A reviewer prompted to find gaps will usually report some, even when the work is sound... Tell the reviewer to flag only gaps that affect correctness or the stated requirements."
    - **A named table of five failure patterns** with fixes: the kitchen-sink session (fix: `/clear` between tasks), correcting-over-and-over (fix: after two failed corrections, `/clear` and rewrite the prompt), the over-specified CLAUDE.md (fix: ruthlessly prune, convert rules to hooks), the trust-then-verify gap (fix: always require evidence — "If you can't verify it, don't ship it"), infinite exploration (fix: scope narrowly or delegate to subagents).
    - **Automation/scale layer**: non-interactive mode (`claude -p`) for CI/hooks/scripts; parallel sessions via worktrees, cross-session messaging, the desktop app, cloud sessions, or experimental "agent teams"; fan-out via `/batch` (5–30 subagents, each its own worktree + PR) or a manual `for file in ...; do claude -p ...; done` loop with `--allowedTools` scoping; "auto mode" as the default starting permission mode on paid plans, where a separate classifier model reviews actions instead of the user and blocks only what looks risky (scope escalation, unknown infrastructure, hostile-content-driven actions), falling back gracefully rather than halting a non-interactive run.
    **Source:** https://code.claude.com/docs/en/best-practices — live/current, fetched Sept 4, 2026 — **PRIMARY**. This is Anthropic's current operational distillation of the same ideas in findings 5, 6, 8, 9 into a single actionable page; it is the most concrete, copy-pasteable of all the texts reviewed. **Standard/consensus** in the sense that it's Anthropic's own official, currently-maintained guidance (supersedes any older Claude Code best-practices content this research did not separately check).

11. **Claim:** Martin Fowler's April 2026 article formalizes "Agent = Model + Harness" and decomposes the harness into **feedforward controls** ("Guides" — anticipate and steer behavior before it acts) and **feedback controls** ("Sensors" — observe after the agent acts and help it self-correct), each split into **computational** (deterministic — tests, linters, type checkers; fast/cheap) vs. **inferential** (AI-based semantic judgment; slower, non-deterministic, more expensive) execution. He proposes three regulation categories — maintainability harness (most mature), architecture-fitness harness (performance/observability), behaviour harness (functional correctness — his weakest/least mature category) — and explicitly flags a limitation neither computational nor inferential controls catch reliably: misdiagnosis of issues and overengineering/unnecessary features. He also warns against over-trusting AI-generated test suites as a verification source. **[UNVERIFIED: MISATTRIBUTED — the article's byline is Birgitta Böckeler, not Martin Fowler; Fowler did not author this piece (it merely runs on his site, which is a multi-author blog). Additionally, the article does not originate "Agent = Model + Harness" — it explicitly credits that formula to a linked LangChain blog post ("The term harness has emerged as a shorthand... [Agent = Model + Harness](https://blog.langchain.com/the-anatomy-of-an-agent-harness/)"), so treating it as Fowler's/this article's own formalization overstates its originality. See Source check section below.]**
   **Evidence/quote:** "Agent = Model + Harness." / "A good harness should not necessarily aim to fully eliminate human input, but to direct it to where our input is most important."
   **Source:** https://martinfowler.com/articles/harness-engineering.html — Apr 2, 2026 — **PRIMARY** (Fowler's own framework, drawing on but not identical to OpenAI's and Stripe's documented practices). **One practitioner's opinion/framework** — influential (Fowler is a widely-cited industry voice) but not an Anthropic/OpenAI position; presented as complementary synthesis rather than a competing claim.

12. **Claim:** Lilian Weng's July 2026 post defines a harness as "the system surrounding a base model that orchestrates execution and decides how the model thinks and plans, calls tools and acts, perceives and manages context, stores artifacts, and evaluates results," drawing an explicit OS-kernel analogy (harness as the layer between raw model "processes" and real-world resources). Concrete prescriptions: durable artifact storage on the **file system**, not the context window (logs, diffs, trajectories persisted so long-horizon agents don't lose state); **explicit, inspectable parallelism** — subagents/background jobs should be traceable via files and logs rather than living only in transient chat context; standardized tool interfaces across agent products; and — her most distinctive claim — harness components themselves can become **optimization targets for evolutionary search**, i.e. automatically searching over harness code/config rather than only hand-engineering it.
   **Evidence/quote:** "the layer between the raw model and the real-world context seems to be as important as the model's raw intelligence."
   **Source:** https://lilianweng.github.io/posts/2026-07-04-harness/ — Jul 4, 2026 — **PRIMARY**. One (highly credentialed, ex-OpenAI) practitioner's synthesis; she reports convergent patterns across "Claude Code, Codex, OpenCode, and Cursor-style agents" as evidence of emerging cross-vendor consensus on file-based memory and standardized tool interfaces, but does not adjudicate any of the specific vendor disagreements below.

13. **Claim:** The discipline's newest visible extension (Aug 19, 2026) is OpenAI turning the harness into a *product surface*: "Codex as a platform: build on the open agent harness," opening Codex's own harness for third parties to build on.
   **Source:** referenced via https://kenhuangus.substack.com/p/from-software-engineering-to-harness, which cites developers.openai.com/blog/codex-as-a-platform — **SECONDARY** (the substack article quotes and links the original OpenAI developer post; I was not able to independently fetch developers.openai.com/blog/codex-as-a-platform in this session, so treat the existence and Aug 19, 2026 date as secondary-sourced, not independently confirmed against the primary page).

14. **Claim (contested):** A May 8, 2026 critique argues "harness engineering" is not conceptually new — it repackages platform engineering, middleware design, SRE, service-oriented architecture, and control-plane design under a new name, with one legitimate but "slightly, not fundamentally" different wrinkle: LLMs are stochastic where traditional software is deterministic. The same piece reports a live terminological turf dispute: HumanLayer frames harness engineering as a *subset* of context engineering, while LangChain frames it as the thing that *supersedes* context engineering.
   **Evidence/quote:** "The 'thing' being described is not new. It is not even slightly new." / "Wrapping something stochastic in a disciplined environment is a slightly different design problem... Slightly. Not fundamentally."
   **Source:** https://haverin.substack.com/p/what-is-harness-engineering-ai-hype — May 8, 2026, Stuart Miller — **SECONDARY/opinion** — explicitly **contested**: this view is a direct rebuttal to the framing in findings 1, 2, 11, 12, and represents one critic's position, not something Anthropic, OpenAI, Hashimoto, Fowler, or Weng have responded to in the material fetched for this report.

15. **Claim:** Independent search coverage (not separately primary-fetched here) reports the discipline is still young enough that practitioners openly disagree on its boundaries — "the term is about five months old, half the people using it mean different things by it" — alongside a counter-argument that a "decent model with a great harness beats a great model with a bad harness," used to justify continued investment in harness work rather than waiting for the next model generation to subsume it.
   **Source:** search-engine synthesis over multiple results (winter/@WinterArc2125 on X, addyosmani.com/blog/agent-harness-engineering, hyperdev.matsuoka.com) — **SECONDARY**, not independently fetched/verified page-by-page; flagged as a gap (see below).

## Concrete practices / configs (copy-pasteable this week)

**1. `docs/` knowledge-base layout (OpenAI, Feb 2026) — replace a bloated instructions file with a small map + linted tree:**
```
AGENTS.md              # ~100 lines, table of contents only, not the encyclopedia
ARCHITECTURE.md
docs/
├── design-docs/
│   ├── index.md
│   ├── core-beliefs.md
│   └── ...
├── exec-plans/
│   ├── active/
│   ├── completed/
│   └── tech-debt-tracker.md
├── generated/
│   └── db-schema.md
├── product-specs/
│   ├── index.md
│   └── ...
├── references/         # vendored llms.txt-style reference docs
│   └── ...
├── DESIGN.md
├── FRONTEND.md
├── PLANS.md
├── QUALITY_SCORE.md
├── RELIABILITY.md
└── SECURITY.md
```
Pair it with: (a) a linter/CI check that the docs tree is cross-linked and not stale, (b) a recurring "doc-gardening" agent job that scans for docs that no longer match code behavior and opens fix-up PRs. This is the practical form of "garbage collection of docs."

**2. Long-running-agent progress artifacts (Anthropic, Nov 2025):**
- `feature-list.json` — every feature starts `"passes": false`; agents may only flip it after end-to-end verification (browser automation if it's a UI feature); explicitly forbidden to edit/delete tests to force a pass.
- `claude-progress.txt` — freeform log of what each session did, read at the start of every new session alongside `git log`.
- `init.sh` — the one command every session runs to boot the dev environment.
- Session boot checklist: `pwd` → read git log + progress file → pick one incomplete feature → `init.sh` → smoke-test → work → leave the tree mergeable.

**3. CLAUDE.md/AGENTS.md hygiene test (Claude Code best practices, current):** for every line, ask "would removing this cause Claude to make mistakes?" — if not, cut it. Include: non-guessable bash commands, non-default style rules, test-runner preferences, repo etiquette (branch/PR conventions), project-specific architecture decisions, environment quirks, non-obvious gotchas. Exclude: anything inferable from the code, standard-language conventions, API docs (link instead), fast-changing info, tutorials, "write clean code"-style platitudes. Move anything only *sometimes* relevant into a Skill instead so it doesn't load every session.

**4. Verification gate, four strengths, pick per situation (Claude Code best practices):**
- Weakest: ask Claude to run the check and iterate, in the same prompt.
- Medium: a `/goal` condition, re-evaluated by a separate evaluator every turn.
- Strong: a Stop hook that runs your check as a script and blocks the turn from ending until it passes (Claude Code force-overrides after 8 consecutive blocks so unattended runs can't wedge forever).
- Orthogonal/strongest for correctness: a fresh-context verification subagent or workflow that never saw the implementer's reasoning — prompt template given verbatim on the page: *"Use a subagent to review the [X] diff against PLAN.md. Check that every requirement is implemented, the listed edge cases have tests, and nothing outside the task's scope changed. Report gaps, not style preferences."*

**5. Tool-design checklist (Anthropic, "Writing tools for agents," Sep 2025):**
- Consolidate: one `schedule_event` tool beats three (`list_users`, `list_events`, `create_event`).
- Namespace: prefix or suffix tools by service/resource (`asana_search`, `asana_projects_search`).
- Return human-readable fields (`name`, `file_type`) over raw IDs/MIME types when the agent is reasoning directly from the result.
- Offer a `response_format` enum ("concise" vs. "detailed") when some callers need IDs for chaining and others just need to reason.
- Truncate with actionable guidance, not silent cutoff: *"Returned first 50 results. Refine query using filters to reduce token usage."*
- Errors should steer: *"Parameter `user` must be numeric ID (e.g., `user_id=12345`), not username. Try searching first."*
- Claude Code's own default: cap individual tool responses at 25,000 tokens.

**6. Golden-principles / entropy control (OpenAI, Feb 2026):** encode 2–3 opinionated, mechanical "golden principles" (their examples: prefer shared utility packages over hand-rolled helpers; validate data at boundaries instead of probing shapes "YOLO-style"), then run a recurring background-agent sweep that scans for deviations, updates quality grades, and opens small (<1-minute-review) auto-mergeable refactor PRs — explicitly framed as garbage collection: "pay down debt continuously in small increments" rather than in periodic manual cleanup sprints.

**7. Hook idea (Claude Code):** *"Write a hook that runs eslint after every file edit."* / *"Write a hook that blocks writes to the migrations folder."* — use hooks specifically for zero-exception rules; CLAUDE.md stays advisory.

**8. Subagent definition file (Claude Code, `.claude/agents/security-reviewer.md`):**
```markdown
---
name: security-reviewer
description: Reviews code for security vulnerabilities
tools: Read, Grep, Glob, Bash
model: opus
---
You are a senior security engineer. Review code for:
- Injection vulnerabilities (SQL, XSS, command injection)
- Authentication and authorization flaws
- Secrets or credentials in code
- Insecure data handling
Provide specific line references and suggested fixes.
```

## Disagreements and open questions

1. **How hard should the merge gate be?** OpenAI (Feb 2026) deliberately runs with *minimal* blocking merge gates and short-lived PRs — "test flakes are often addressed with follow-up runs rather than blocking progress indefinitely" — because at their throughput "corrections are cheap, and waiting is expensive," and they say this explicitly "would be irresponsible in a low-throughput environment." Claude Code's current best-practices page leans the opposite direction by default: "If you can't verify it, don't ship it," with an explicit named failure pattern ("the trust-then-verify gap") to guard against exactly the plausible-looking-but-wrong output that loose gating risks. Neither text says the other is wrong; they're optimizing for different regimes (OpenAI: many agents, high throughput, cheap corrections; Anthropic's Claude Code guidance: general-purpose default for a single developer). A solo developer copying OpenAI's looser-gate philosophy without OpenAI's volume of redundant agent review may be importing a mismatched assumption.

2. **Does the harness shrink or grow over time?** Anthropic's Mar 2026 post treats harness complexity as a scaffold that should be actively *removed* as models improve ("every component... encodes an assumption about what the model can't do on its own" — they deleted the "sprint" construct once Opus 4.6 no longer needed it). OpenAI's Feb 2026 post describes a harness that keeps *accumulating* structure (more linters, more layered enforcement, a permanent doc-gardening/golden-principles process) as agent throughput rises — though note their "garbage collection" is about removing *drift/slop* in the generated code, not about removing harness scaffolding itself. This is a real difference in what "mature harness engineering" converges toward — pruned-down control surface vs. permanently-running control surface — and none of the fetched texts reconcile it directly.

3. **Self-review is universally distrusted, but the fix differs.** Anthropic's Mar 2026 post and Claude Code's best-practices page both independently prescribe a *separate*, fresh-context evaluator because self-graded work over-praises itself. OpenAI's pipeline instead has the same agent review its own changes locally *first*, then request additional agent reviews locally and in the cloud in an iterative "Ralph Wiggum Loop" until "all agent reviewers are satisfied" — a multi-agent peer-review loop rather than a single fresh-context adversarial pass, and it isn't clear from the primary text whether OpenAI's local self-review step is trusted as a real gate or just a cheap pre-filter before the agent-to-agent review that matters.

4. **Is "harness engineering" actually new?** Standard/consensus position (Hashimoto, OpenAI, Fowler, Weng, all fetched primary sources): yes, distinct enough to name, because the target system is stochastic rather than deterministic, which changes what "the interface" needs to do (steer probability mass, not just expose an API). **Contested position** (Miller, May 2026, secondary/opinion, not rebutted by any primary source found): the discipline is old wine (platform engineering / SRE / control planes) in a new bottle, and the stochastic-vs-deterministic distinction is real but "not fundamental." This is presented in the source material as an open, live disagreement, not a settled one.

5. **Scope disagreement, reported secondhand only:** per Miller's article, HumanLayer treats harness engineering as a subset of context engineering; LangChain treats it as superseding context engineering. I could not independently fetch primary statements from either HumanLayer or LangChain in this session to confirm this framing firsthand — **flag as unresolved / secondary-only**.

6. **Gap:** I was unable to fetch developers.openai.com/blog/codex-as-a-platform (Aug 19, 2026) directly — its existence and content come only from a secondary substack summary. If "Codex as a platform" meaningfully redefines OpenAI's Feb 2026 harness-engineering prescriptions (rather than just productizing them), that would need direct verification.

7. **Gap:** The exact phrase "make it hard to do wrong" is attributed to OpenAI's Feb 2026 post by multiple secondary sources (saascity.io, alphasignalai substack) but does not appear verbatim in the full primary text I fetched and read line-by-line. It may be a paraphrase of "The agent doesn't need more instructions. It needs a world where the right thing to do is obvious and the wrong thing is hard" as reported by SaaSCity/other summaries, or may come from a different, later revision of the page, or may be conflated from a different source. Treat any quotation of that exact phrase as unverified against the primary source as of this fetch.

8. **Gap:** I did not independently verify the GitHub `ai-boost/awesome-harness-engineering` list's contents, nor Anthropic's `anthropics/cwc-long-running-agents` reference repo — both surfaced in search as artifacts of the discipline's tooling ecosystem but weren't fetched/read.
