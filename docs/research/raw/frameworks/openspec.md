# openspec

## What it is

`@fission-ai/openspec` (Fission-AI/OpenSpec, npm-published CLI, no marketplace listing found in-repo) is a spec-driven-development framework that pairs a deterministic Node/TypeScript CLI (`openspec`) with generated slash-command/skill files for 30+ AI coding tools. It keeps a change's proposal, spec deltas (ADDED/MODIFIED/REMOVED/RENAMED), design and tasks as plain markdown under `openspec/`, validates and merges them with real parsers (not the model), then archives the change directory and folds its deltas into `openspec/specs/` as the durable source of truth.

Repo: `https://github.com/Fission-AI/OpenSpec` (clone: `/tmp/.../scratchpad/repos/OpenSpec`, depth 1). Stars: not visible from a local clone (git provides no star count; not fetched). Last commit in the clone: `Thu Sep 3 00:00:56 2026 +0000` (`git log -1 --format=%cd`), package.json version `1.12.0`.

Note: this is a much larger/later-stage codebase than the "classic" OpenSpec README suggests — it has grown a "stores"/"workspace"/"initiatives" layer (multi-repo registries, artifact graphs, schema plugins) on top of the original propose→apply→archive loop. The repo also dogfoods itself: `openspec/changes/archive/` contains ~90 [CORRECTED: exactly 83, per `ls -d openspec/changes/archive/*/ | wc -l`] archived OpenSpec changes documenting the tool's own development history.

## Workflow it implements

Two halves, explicitly documented in `docs/how-commands-work.md`:

- **CLI (terminal, deterministic engine)**: `openspec init|list|show|validate|status|instructions|new change|archive|doctor|context|schemas|view|store|config|completion`. "The CLI is the **engine**. It knows the rules: what a change folder looks like, which artifacts depend on which, how to merge a delta spec into your source of truth. It's the same everywhere." (`docs/how-commands-work.md`)
- **Slash commands / skills (chat half, per-tool generated)**: `/opsx:propose`, `/opsx:apply`, `/opsx:archive`, etc. — "the **steering wheel**... every AI tool has a slightly different one." Generated by `openspec init` from one shared template into 31 [CORRECTED: 30 — `ls src/core/command-generation/adapters/*.ts` minus `index.ts`, and `registry.ts`'s static initializer registers exactly 30 adapters] tool-specific adapters (`src/core/command-generation/adapters/*.ts`, e.g. `claude.ts` → `.claude/commands/opsx/<id>.md`).

Sequence as implemented (default `spec-driven` schema, driven by `schemas/spec-driven/schema.yaml`):

1. `openspec new change "<name>"` — scaffolds a change dir with `.openspec.yaml` (schema pointer / `skip_specs` marker).
2. Loop over artifacts in dependency order using `openspec status --change "<name>" --json` (returns each artifact's `status: done|skipped|ready|blocked` and its `requires` edges) and `openspec instructions <artifact-id> --change "<name>" --json` (returns `context`, `rules`, `template`, `instruction`, `resolvedOutputPath`) — the agent writes `proposal.md` → `specs/<capability>/spec.md` (delta) → `design.md` (conditional) → `tasks.md`.
3. `openspec validate` (or `--json`) — deterministic parse + Zod schema + delta-specific rules (below).
4. Implementation: agent works through `tasks.md` checkboxes (`apply.instruction` in schema.yaml: "Read context files, work through pending tasks, mark complete as you go.").
5. `openspec archive <name>` — deterministically merges every delta spec into `openspec/specs/**/spec.md` (RENAMED → REMOVED → MODIFIED → ADDED order) via `src/core/specs-apply.ts`, moves the change directory to `openspec/changes/archive/YYYY-MM-DD-<name>/`, and reports `archivedAs`, `specsUpdated`, per-capability `warnings` (e.g. capability retirement when a delta removes a capability's last requirement).

A parallel "experimental" skill path (`skills/openspec-archive-change/SKILL.md`) instead has the *agent* diff delta specs against main specs and delegates the actual merge to an "agent-driven intelligent merge" workflow (`openspec-sync-specs`) before doing a plain `mv` — i.e. for that skill, the merge that the CLI does deterministically is redone by the model. This is flagged as a weakness below.

## Artifacts it produces

All under `openspec/` (or a registered "store" root). Filenames and schema come from `schemas/spec-driven/schema.yaml`, whose per-artifact `template` field points at `schemas/spec-driven/templates/*.md`:

- **`openspec/changes/<name>/proposal.md`** — template headings: `## Why`, `## What Changes`, `## Capabilities` (`### New Capabilities`, `### Modified Capabilities`), `## Impact`.
- **`openspec/changes/<name>/specs/<capability-path>/spec.md`** — delta spec. Template:
  ```
  ## Purpose
  ## ADDED Requirements
  ### Requirement: <!-- requirement name -->
  #### Scenario: <!-- scenario name -->
  - **WHEN** <!-- condition -->
  - **THEN** <!-- expected outcome -->
  ```
  Full delta grammar (from `schema.yaml`'s `specs` instruction): `## ADDED Requirements`, `## MODIFIED Requirements` (must carry the full updated requirement block, not a diff), `## REMOVED Requirements` (must include `**Reason**` and `**Migration**`), `## RENAMED Requirements` (`FROM:`/`TO:` pairs). Requirement header is always `### Requirement: <name>`; scenario header must be exactly `#### Scenario: <name>` (4 hashtags — "Using 3 hashtags or bullets will fail silently").
- **`openspec/changes/<name>/design.md`** (conditional) — `## Context`, `## Goals / Non-Goals`, `## Decisions`, `## Risks / Trade-offs`.
- **`openspec/changes/<name>/tasks.md`** — `## <n>. <Task Group Name>` with `- [ ] <n>.<m> <task>` checkboxes; the apply phase parses this checkbox format to track progress ("Tasks not using `- [ ]` won't be tracked").
- **`openspec/changes/<name>/.openspec.yaml`** — per-change metadata: schema name, `skip_specs: true` marker (see below), `retire_capabilities: true` marker.
- **`openspec/specs/<capability-path>/spec.md`** — the merged, canonical main spec (source of truth after archive); same `## Purpose` / `### Requirement:` grammar as the delta, but with no ADDED/MODIFIED/REMOVED sections — full content only.
- **`openspec/changes/archive/YYYY-MM-DD-<name>/`** — the archived change, same internal structure, timestamped and immutable.

## Deterministic vs prompt

| Mechanism | Enforced by script/CLI | Asked of the model in prose |
|---|---|---|
| Delta section/requirement parsing (`### Requirement:`, `#### Scenario:`, fenced-code-awareness) | `src/core/parsers/requirement-blocks.ts` (`REQUIREMENT_HEADER_REGEX = /^###\s*Requirement:\s*(.+)\s*$/i`), `code-fence.ts` masks fenced examples so a `#### Scenario:` inside a code block isn't counted | — |
| Every ADDED/MODIFIED requirement has ≥1 scenario; no duplicate names within a section; no name in two sections (ADDED+REMOVED, MODIFIED+RENAMED-FROM, etc.) | `src/core/validation/validator.ts::validateChangeDeltaSpecs` (~330 lines of cross-section conflict checks) | — |
| SHALL/MUST keyword present in requirement body | Checked by `containsShallOrMust` — **ERROR** if requirement text missing entirely, but only **WARNING** ("RFC 2119 best practice") if body omits SHALL/MUST | Author is *told* via schema.yaml instruction text to prefer SHALL/MUST; not blocking |
| A MODIFIED block must not silently drop a scenario the main spec still has | `findScenarioLossIssues` in `validator.ts`, reused verbatim by `archive` so validate can only report what archive would refuse | — |
| Merge order and application of RENAMED → REMOVED → MODIFIED → ADDED into the main spec | `src/core/specs-apply.ts::buildUpdatedSpec` (hard-coded operation order, near-miss header suggestions, duplicate/target-exists errors) | — (the classic `openspec archive` path never asks the model to do this) |
| Zero-delta change must declare `skip_specs: true` or `validate` rejects it | `Validator` + Zod `ChangeSchema` (`CHANGE_NO_DELTAS` message), `readSkipSpecsMarker` in `.openspec.yaml` | schema.yaml prose: "Do not invent a requirement just to satisfy validation" |
| Capability retirement (deleting a spec whose last requirement was removed) | `isRetirableSpec` — re-runs the Validator on the rebuilt spec and only retires if the *sole* remaining error is "no requirements" | Requires `retire_capabilities: true` opt-in marker (a deliberate human/agent decision, not inferred) |
| Task-list progress tracking | `resolveTaskFilesForChange` + checkbox regex parsing in `task-progress.ts`; `findTaskNumberingIssues` (ambiguous numbering) | Task *content/quality* (small enough steps, verification clause) is prose guidance only |
| Which artifact to write next / dependency graph | `openspec status --json` computed from `schema.yaml`'s `requires:` edges — code walks the graph, not the model | — |
| Whether to write `design.md` at all | Not code-gated — schema.yaml instruction lists conditions ("cross-cutting change... new architectural pattern...") entirely in prose | Fully model judgment |
| Whether an ambiguity is "material" enough to ask the user before scaffolding | No code check | Entirely prose ("If the request contains ambiguity that would materially affect scope...") |
| Planning-only boundary (propose must not start implementation) | No code enforcement — nothing stops the agent from editing code mid-skill | Prose only: "Do not edit project code... stop... wait for a new user request" — an explicit *ceremony* the model is trusted to honor |
| JSON envelope shape / exit codes for every subcommand | Fixed contract in `docs/agent-contract.md`, matching code (verified against `src/` per the doc's own "capstone audit" note) | — |

## Mechanisms worth stealing

1. **One YAML (`schema.yaml`) drives both the dependency graph AND the per-artifact prose instructions.** `schemas/spec-driven/schema.yaml` — each artifact entry has `id`, `generates`, `template`, `instruction` (prose for the model), and `requires` (edges the CLI's `status`/`instructions` commands walk in code). A single change to this file updates both what `openspec status --json` reports as buildable-next and what the model is told to write. For a solo-dev dotfiles harness: instead of duplicating "what order do I write files in" across multiple SKILL.md files, put the artifact graph + per-artifact prose in one machine-readable file and have a tiny script compute "ready/blocked" rather than trusting the model to remember order.

2. **A real delta grammar with a deterministic merge order, not "let the model apply the diff."** `src/core/specs-apply.ts::buildUpdatedSpec` — applies `RENAMED → REMOVED → MODIFIED → ADDED` in that fixed order every time, with duplicate/target-exists/near-miss-header errors thrown as hard failures. Quote: comment at line ~386, `// Apply operations in order: RENAMED → REMOVED → MODIFIED → ADDED`. For any harness that lets an agent "update a living doc" (a personal wiki, a running project journal, a decision log): have the agent emit an ADDED/MODIFIED/REMOVED delta block against a known grammar, and merge it with a small deterministic script instead of asking the model to hand-edit the master file — removes an entire class of "silently dropped my other section" bugs.

3. **Every CLI surface has one documented JSON envelope, with a frozen diagnostic-code catalog.** `docs/agent-contract.md` — one `StoreDiagnostic` shape (`severity/code/message/target/fix`) reused everywhere, one predictable null-shape on failure, `--json` guarantees exactly one stdout document. Explicitly re-verified against source ("capstone audit") and lists its own known inconsistencies rather than hiding them. For a dotfiles CLI tool (e.g. `new-project`, `aws-profile`) meant to be agent-driven: define one small diagnostic envelope up front and document exit-code/stdout contract in a single file agents can be pointed at, instead of ad hoc `console.log`/exit codes per script.

4. **Zero-delta changes require an explicit opt-out marker, never inferred.** `.openspec.yaml`'s `skip_specs: true`, checked by both the Zod schema and `validateChangeDeltaSpecs`, with the model explicitly told "Do not invent a requirement just to satisfy validation" (`schema.yaml`). This stops the classic "model writes a fake trivial requirement so validation passes" failure mode by giving it a legitimate, auditable way to say "no spec-level behavior changed here." Directly reusable in any TDD/spec harness gate: an explicit `skip: <reason>` marker beats a model gaming a check it can't otherwise pass.

5. **One template pipeline, 31 [CORRECTED: 30 — see count above] tool-specific adapters.** `src/core/command-generation/adapters/*.ts` (`claude.ts`, `cursor.ts`, `cline.ts`, `factory.ts`, `devin.ts` [CORRECTED: the original list named "windsurf" as an adapter, but there is no `windsurf.ts` — `config.ts` line 101 aliases `windsurf: 'devin'`, i.e. Windsurf was rebranded/merged into the Devin Desktop adapter], `github-copilot`, `oh-my-pi`, ...) each implement `getFilePath`/`formatFile` against one shared `CommandContent` type; `openspec init` picks the tools the user selected and writes each one's native command/skill file format. For a personal dotfiles repo already juggling Claude/Cursor/other assistants, this is the pattern for "write the workflow once, generate the per-tool command file" instead of hand-maintaining N near-duplicate command files.

6. **"Context" (required, must-apply, conflict-reported) vs "operation guidance" (optional, advisory, explainable-skip) as two distinct prompt-input channels**, both explicitly separated from "controlling inputs" (explicit user choices, resolved paths, CLI contracts). Seen in `skills/openspec-archive-change/SKILL.md`: "Treat `context` as a required prompt-level input... Treat `operationGuidance` as optional additive advice... If context conflicts with one of those controlling inputs, report the conflict and preserve the controlling value." This is a reusable vocabulary for any agent skill that accepts both project facts and optional style hints — gives the model an explicit conflict-resolution order instead of blending everything into one undifferentiated prompt blob.

7. **Structural validation caps ceremony with severity tiers (ERROR/WARNING/INFO), not just pass/fail.** `ValidationReport.summary.errors/warnings/info`, strict mode toggling whether warnings also fail (`this.strictMode ? errors===0 && warnings===0 : errors===0`). Lets a harness be strict in CI and lenient during drafting without two separate rule sets — same rules, different threshold.

8. **Advisory "would archive refuse this" dry run reused from the real archive code**, not a re-implementation. `findArchiveBlockers` in `validator.ts` literally calls `buildUpdatedSpec(update, changeName, {silent:true})` and discards the result — so `openspec validate` can warn about a future archive failure using the exact same code path archive itself uses, guaranteeing they never drift out of sync. Directly applicable pattern: when you have a "preview" and a "commit" operation, make preview literally call commit's function in dry-run mode rather than parallel logic.

## Weaknesses / ceremony cost

- **A single `/opsx:propose` (skill: `skills/openspec-propose/SKILL.md`, 1817 words) plus the `schema.yaml` instructions it fetches per artifact (1547 words) plus 4 templates (332 words) is roughly 3700 words (~4800-5000 tokens) of prompt text loaded across one full propose-to-tasks pass** before any actual project code is read. `openspec-onboard/SKILL.md` alone is 560 lines / the largest single skill file in the repo; `openspec-bulk-archive-change/SKILL.md` is 682-line-equivalent (338 lines but dense); total skill prose across all 12 skills is 2586 lines.
- **Gate count for one change**: create → (4 artifact-instruction round trips, each its own CLI call + write + re-check via `status --json`) → validate → implement → archive-time status/task/sync checks (3 more prompts: artifact completion, task completion, delta-sync state) → mv. A solo dev doing something small pays the same ceremony as a team change.
- **Things the model can silently skip**: the "planning boundary" in `openspec-propose` ("Do not edit project code... stop... wait for a new user request") is pure prose — nothing in the CLI stops an agent from writing code in the same turn. Likewise "material ambiguity" triage before scaffolding is entirely judgment-based with no code check.
- **Duplicated merge logic for one path**: `openspec archive` (CLI) does the RENAMED→REMOVED→MODIFIED→ADDED merge deterministically in `specs-apply.ts`, but the "experimental workflow" `openspec-archive-change` SKILL explicitly redoes that same merge via an "agent-driven intelligent merge" (`openspec-sync-specs`) instead of shelling out to the CLI's own archive — a maintenance and correctness risk (two merge implementations, one deterministic and one prompted, that must stay behaviorally equivalent).
- **Significant scope creep beyond the original propose/spec/archive loop.** The current repo has grown a large "stores" (multi-repo registry), "initiatives", "artifact-graph", and "workset" layer (`src/commands/store.ts`, `src/commands/workset.ts`, `src/core/store/*`, `src/core/artifact-graph/*`, `openspec/initiatives/context-store-and-initiatives/` with 19+ work-items) — a lot of surface area for what a solo dev likely wants (a lightweight spec-delta + archive loop). `docs/agent-contract.md` itself documents 8 "Known inconsistencies" it hasn't yet fixed (mixed snake_case/camelCase, inconsistent envelope fields), a sign of an API that outgrew its original design.
- **929 [CORRECTED: 939, per `wc -l src/core/validation/validator.ts`]-line validator + 1108-line specs-apply.ts + 2129-line archive.ts** is a lot of code to reproduce faithfully if borrowing "the mechanism" rather than the whole dependency; a minimal clone would need to cherry-pick the delta-parsing regexes and merge-order logic, not the store/workspace machinery around it.

## Plugin/packaging structure

- Installs as a normal npm package: `"bin": {"openspec": "./bin/openspec.js"}`, published as `@fission-ai/openspec` (package.json, `"version": "1.12.0"`). No Claude-plugin marketplace `plugin.json` in the repo — this is a standalone CLI, not a Claude Code plugin.
- `bin/openspec.js` is a 4 [CORRECTED: `wc -l` reports 5 physical lines (shebang, blank, import, blank, call); the two lines of actual logic are quoted correctly] -line shim: `import { runCli } from '../dist/cli/index.js'; runCli();` — real logic compiled from TS.
- `openspec init` is the installer: it writes tool-native command/skill files via the 31 [CORRECTED: 30] adapters in `src/core/command-generation/adapters/` (Claude Code → `.claude/commands/opsx/<id>.md` with YAML frontmatter `name/description/allowed-tools/category/tags`; other tools get their own path/format per adapter, e.g. `.../opsx-<id>.*` for Cursor/Devin/Trae, `.amazonq/prompts/opsx-<id>.md` for Amazon Q). Also generates the `skills/openspec-*/SKILL.md` files with `allowed-tools: Bash(openspec:*)` frontmatter (Claude-Code Agent-Skill format) — so it registers itself both as slash-commands and as Skills depending on target tool capability, driven by `src/core/shared/skill-generation.ts` / `skill-templates.ts`.
- No runtime hooks (no PreToolUse/PostToolUse hook registration found) — the CLI relies purely on the agent choosing to invoke `openspec ...` Bash commands per the skill's `allowed-tools: Bash(openspec:*)` scoping; enforcement is entirely "the skill tells the model to shell out," not a harness-level hook.
- Publishing/telemetry: `src/telemetry/` (PostHog per an archived change `2026-01-09-add-posthog-analytics`), `scripts/generate-skillssh.mjs` (generates install-script assets), `.changeset/` for release versioning, `.github/workflows/release-prepare.yml`.

## Verdict: adopt / borrow parts / ignore

**Borrow parts, ignore the whole.** The full OpenSpec CLI (stores, workspaces, initiatives, artifact-graph, 31 [CORRECTED: 30] tool adapters) is far more product than a solo dev's dotfiles harness needs, and its own docs admit unresolved API inconsistencies from rapid growth. But three specific mechanisms are worth lifting directly into a lighter, personal spec/change harness:

1. The **ADDED/MODIFIED/REMOVED/RENAMED delta grammar + fixed merge order**, reimplemented in ~150-300 lines rather than pulled in as a dependency — this is the actual load-bearing idea and it's small enough to own.
2. The **schema.yaml pattern** (one file = artifact graph + per-artifact prose instructions, machine-walkable) instead of duplicating ordering logic across skill/command files.
3. The **required-context vs advisory-guidance vocabulary** and the **dry-run-reuses-commit-code** pattern (`findArchiveBlockers` calling the real merge function in `silent: true` mode) — both are cheap, high-value conventions for any future skill/hook design, independent of OpenSpec itself.

Ignore the stores/workspace/initiative layer, the 31-adapter [CORRECTED: 30-adapter] generator, and the telemetry — none of that pulls weight for a single-user, single-tool (Claude Code) setup.

## Second-reader additions

Three deterministic mechanisms in `src/core/archive.ts` that the first pass didn't surface — all guard the exact moment a spec-driven harness is most exposed: the archive step is writing files that are the project's durable source of truth, potentially concurrently with another process or with attacker/user-controlled directory names.

1. **Terminal-escape-safe rendering of untrusted names, with a "can't quote it safely → don't pretend to" fallback instead of a broken command.** A change directory name is just a directory name — nothing stops it from containing a raw CR, LF, or ESC byte. `describeChangeName` (`src/core/archive.ts:266-272`) strips control characters before a name is interpolated into a human-readable message:
   ```ts
   function describeChangeName(name: string): string {
     return name.replace(/[\u0000-\u001f\u007f]/g, '?');
   }
   ```
   with the comment explaining why this matters: "a raw CR or LF would let a change directory forge its own `Fix:` line... An ESC could redraw the terminal." A sibling function, `quoteForShell` (`src/core/archive.ts:257-260`), only emits a pasteable double-quoted command when the value has a portable spelling across bash/zsh/PowerShell/cmd.exe; otherwise it returns `undefined` and the caller (`quoteChangeName`) substitutes the literal placeholder `<change-name>` rather than emit a copy-pasteable command that could execute something the user didn't intend. Worth stealing for any CLI/skill that echoes agent- or user-supplied strings (file names, branch names, freeform IDs) back into terminal text or into a "run this to fix it" suggestion — sanitize on the way to the terminal, and degrade to a placeholder rather than silently emit an unsafe or wrong copy-paste command.

2. **Rollback that re-reads and byte-compares before restoring, so a concurrent edit aborts the rollback instead of being silently clobbered.** `captureSpecSnapshots`/`restoreSpecSnapshots` (`src/core/archive.ts:848-995`) snapshot each spec file's content before archive mutates it, but on rollback they don't blindly restore the snapshot — they first re-read the current file and compare it byte-for-byte against what archive itself last wrote (`expectedContent`) or against the original snapshot; a mismatch throws `Archive rollback would overwrite a concurrent change at ${target}` instead of overwriting. Comments explicitly flag this as an intentional deviation from CodeQL's `js/file-system-race` lint ("re-check this content before restoring, so a mid-run change aborts instead of clobbering"). Directly applicable to any harness that does a multi-file write-then-maybe-rollback (e.g. merging deltas into several spec files, or a multi-file codemod): don't restore-on-failure blindly — re-read and compare before you overwrite, so a rollback triggered by one failure can't silently destroy an unrelated edit that landed mid-operation.

3. **An exclusive-create lock file with an ownership proof, not just a "does the destination exist" check, to stop two concurrent `archive` runs from racing.** `claimArchiveDestination` (`src/core/archive.ts:622-651`) opens `.openspec-archive.lock` with the `wx` flag (fails if the file already exists — atomic create), writes `{pid, nonce: randomUUID()}` into it, and syncs. `releaseArchiveClaim` (`src/core/archive.ts:596-620`) doesn't just delete the lock file on completion — it re-`lstat`s the file, reads its contents, `lstat`s again, and only unlinks if the device/inode identity and file contents still match what this process wrote (bracketing the read between two stats, with a comment: "This is a concurrent-change detector, not an fd-less race to 'fix'"). A stale lock surfaces a specific, actionable error ("remove the stale claim at ... and rerun") rather than hanging or silently double-archiving. Reusable pattern for any CLI script that mutates a shared destination and might be invoked twice at once (e.g. a personal automation triggered by both a cron job and a manual run): an atomic-create lock file carrying an identity token, checked on release rather than blindly deleted, beats a plain existence check or an flock the script forgets to release cleanly.
