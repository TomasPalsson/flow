# anthropic-official-plugins

## What it is
Anthropic's own first-party plugin marketplace for Claude Code: a curated set of `.claude-plugin`-shaped bundles (commands + agents + skills + hooks) covering feature development, code/PR review, security guidance, hook-generation, LSPs, and plugin authoring itself. Two repos matter: `anthropics/claude-plugins-official` (the full marketplace: ~39 first-party plugins under `plugins/`, ~15 more vendored directly into `external_plugins/`, and 238 further vendor plugins referenced only as pinned `git-subdir`/`url` entries in `marketplace.json` with no local files in the repo at all [CORRECTED: see Plugin/packaging structure section — "40+ vendored `external_plugins/*`" undercounted and mislocated the pinned vendor plugins]) and `anthropics/claude-code` (the CLI itself, which bundles a *subset* of the same plugins — feature-dev, code-review, commit-commands, pr-review-toolkit, hookify, security-guidance, frontend-design, plugin-dev, ralph-wiggum — directly in `plugins/`, plus one raw hook example under `examples/hooks/`).
Repos: `https://github.com/anthropics/claude-plugins-official`, `https://github.com/anthropics/claude-code`. Stars not shown in a shallow clone. Last commit (git log -1 --format=%cd): claude-plugins-official = `Fri Sep 4 00:14:13 2026 +0100` (merge "bump/carta-crm"); claude-code = `Thu Sep 3 23:48:05 2026 +0000` (chore: changelog).

## Workflow it implements
Each plugin is an independent, single-purpose workflow — there is no cross-plugin orchestrator. The three worth tracing end-to-end:

**feature-dev** (`plugins/feature-dev/commands/feature-dev.md`, 125 lines, no includes) — a strict 7-phase state machine run entirely in the main agent's own prompt:
1. Discovery — TodoWrite the phases, ask what/why if unclear, confirm understanding.
2. Codebase Exploration — launch 2-3 `code-explorer` subagents in parallel, each targeting a different angle (similar features / architecture / UX / testing), each told to return "5-10 key files"; main agent then **reads those files itself** before proceeding.
3. Clarifying Questions — explicitly flagged "CRITICAL...DO NOT SKIP"; present all questions as a list; wait for answers; if user says "whatever you think", give a recommendation and demand explicit confirmation.
4. Architecture Design — 2-3 `code-architect` subagents in parallel with three different mandates (minimal-change / clean-architecture / pragmatic); main agent picks one, presents trade-offs, **asks user to choose**.
5. Implementation — hard gate: "DO NOT START WITHOUT USER APPROVAL".
6. Quality Review — 3 `code-reviewer` subagents in parallel, each with a different lens (simplicity/DRY, bugs, conventions); consolidate; ask user fix-now/later/proceed.
7. Summary — mark todos complete, report what/why/files/next-steps.

**code-review** (`plugins/code-review/commands/code-review.md`, 92 lines) — a PR-review pipeline, not interactive: (1) Haiku agent gate-checks eligibility (closed/draft/trivial/already-reviewed); (2) Haiku agent lists relevant `CLAUDE.md` paths; (3) Haiku agent summarizes the PR; (4) **5 parallel Sonnet review agents**, each with a distinct lens (CLAUDE.md compliance, shallow bug scan, git-blame history, prior-PR comment precedent, in-code comment compliance) that each return `(issue, reason-flagged)`; (5) for **every individual issue found**, a separate parallel Haiku agent re-scores it 0-100 confidence against an explicit rubric; (6) filter to score ≥ 80, abort silently if none survive; (7) re-run the eligibility gate from step 1 (PR may have changed state mid-review); (8) post one `gh pr comment` in a fixed template.

**ralph-loop** (`plugins/ralph-loop/`) — turns the Stop hook into a while-loop: `/ralph-loop <prompt> [--max-iterations N] [--completion-promise TEXT]` runs `scripts/setup-ralph-loop.sh` which writes `.claude/ralph-loop.local.md` (YAML frontmatter: `iteration`, `session_id`, `max_iterations`, `completion_promise`, `started_at`, then the raw prompt body). On every attempted Stop, `hooks/stop-hook.sh` fires, reads that state file, checks `session_id` so a Stop hook in an unrelated session for the same project doesn't hijack the loop, validates `iteration`/`max_iterations` are numeric (self-heals by deleting a corrupted state file rather than looping forever), reads the transcript JSONL, greps the last 100 assistant-role lines, `jq`-extracts the final `text` block, checks it for a `<promise>EXACT TEXT</promise>` match against the configured completion promise using literal string comparison (explicitly not `==` glob matching), and if not matched, increments the iteration counter and returns `{"decision":"block","reason":"<original prompt>","systemMessage":"🔄 Ralph iteration N | ..."}` — Claude Code re-feeds the *same original prompt* as the next turn's input. Exits cleanly (deleting state) on promise match or max-iterations reached.

## Artifacts it produces
- **feature-dev**: no persisted artifact beyond the todo list and the final chat summary (files modified, decisions, next steps) — everything lives in conversation.
- **ralph-loop**: `.claude/ralph-loop.local.md` — schema:
  ```
  ---
  active: true
  iteration: <int>
  session_id: <uuid>
  max_iterations: <int, 0=unlimited>
  completion_promise: "<text>" | null
  started_at: "<ISO8601>"
  ---

  <original prompt text, verbatim>
  ```
- **hookify**: per-rule files `.claude/hookify.{rule-name}.local.md` in the *project's* `.claude/`, not the plugin's. Schema (from `plugins/hookify/commands/hookify.md`):
  ```
  ---
  name: {rule-name}
  enabled: true
  event: {bash|file|stop|prompt|all}
  pattern: {regex}
  action: {warn|block}
  ---

  {message shown to Claude when triggered}
  ```
  or a multi-condition form with `conditions: [{field, operator, pattern}, ...]` instead of a single `pattern`.
- **code-review**: no local artifact — output is a single `gh pr comment`, format enforced verbatim in the command prompt (heading "### Code review", numbered issue list each with a CLAUDE.md quote + a full-SHA GitHub permalink `#L<start>-L<end>`, closing `🤖 Generated with [Claude Code]` + 👍/👎 react-to-rate line).
- **security-guidance**: session state under a plugin-managed state file (`hooks/session_state.py`) tracking a git baseline SHA (via `git stash create`) so the Stop-hook LLM review only ever diffs code changed *this session*.

Do not output false promises to escape the loop" but nothing verifies truth [CORRECTED: the original quote spliced two files together — "do not lie to exit" is not in `commands/ralph-loop.md`; it's verbatim from the `SYSTEM_MSG` string in `hooks/stop-hook.sh` line 174 ("...ONLY when statement is TRUE - do not lie to exit!"). Confirmed both files independently; each expresses the same honor-system idea but neither contains the other's exact wording.] |
| Max-iteration cutoff | Hard-coded arithmetic in `stop-hook.sh` (`ITERATION -ge MAX_ITERATIONS`) | none — fully deterministic |
| Session isolation of the loop | `stop-hook.sh` compares `session_id` from state file vs `HOOK_INPUT.session_id` | none |
| Hook rule matching (hookify) | `core/rule_engine.py` — regex/`lru_cache`-compiled patterns, structured `conditions` evaluator, `PreToolUse`→`permissionDecision:"deny"` JSON | Which rules to *create* (pattern, action, message) is entirely prompt-driven via `commands/hookify.md` + `AskUserQuestion`; no validation that the generated regex is safe/correct beyond "test it after creating" |

| Git baseline for security diff | `git stash create` snapshot captured at `UserPromptSubmit`, diffed at `Stop`, deterministic shell/git plumbing (`hooks/gitutil.py`, `hooks/diffstate.py`) | none |
| Feature-dev phase gates ("wait for user approval", "ask questions") | none — no hook enforces these; it's all in the 125-line command prompt | 100% prose discipline; a model that ignores "DO NOT START WITHOUT USER APPROVAL" faces no technical block |

## Mechanisms worth stealing

1. **Stop-hook while-loop with a literal completion-promise tag, session-scoped, self-healing on corrupt state** — `plugins/ralph-loop/hooks/stop-hook.sh`. Solves "how do I let an agent keep working past what would normally be a Stop without a human in the loop, but still have a hard, checkable exit condition." Quoted snippet:
   ```bash
   PROMISE_TEXT=$(echo "$LAST_OUTPUT" | perl -0777 -pe 's/.*?<promise>(.*?)<\/promise>.*/$1/s; s/^\s+|\s+$//g; s/\s+/ /g')
   if [[ -n "$PROMISE_TEXT" ]] && [[ "$PROMISE_TEXT" = "$COMPLETION_PROMISE" ]]; then
     echo "✅ Ralph loop: Detected <promise>$COMPLETION_PROMISE</promise>"; rm "$RALPH_STATE_FILE"; exit 0
   fi
   ```
   Fit for a solo-dev global dotfiles harness: a project-scoped `.claude/*.local.md` state file + one small Stop hook is the whole mechanism — no daemon, no external process. Directly reusable for any "run until X is verifiably true" personal automation (e.g. a nightly `/loop`-style task that shouldn't stop until tests are green), and the session-id guard is the one subtlety worth copying verbatim since a solo dev often has multiple terminal tabs open on the same repo.

2. **Confidence-scored, double-checked finding filter with an explicit numeric rubric given verbatim to the grading agent** — `plugins/code-review/commands/code-review.md` steps 4-6. Solves false-positive fatigue in any LLM-review pipeline: generate issues cheaply/broadly, then re-score each one independently with a *separate* agent call and a fixed 0/25/50/75/100 anchor table, keep only ≥80. Quoted: `"Filter out any issues with a score less than 80. If there are no issues that meet this criteria, do not proceed."` Fits a personal review/skill-judge harness (already partially present as `skill-judge`, `code-review` skills in this user's own toolset) — the useful bit to lift is the *explicit anchor definitions*, not just "ask for a confidence score," since vague confidence scores are known to cluster near the top.

3. **Multiple independently-biased reviewer agents in parallel, each given a different lens, rather than one generalist reviewer** — same file, 5 agents (CLAUDE.md compliance / shallow bug scan / git-blame history / prior-PR precedent / code-comment compliance) plus `feature-dev`'s 3-lens reviewer trio (simplicity, bugs, conventions) and 3-lens architect trio (minimal / clean / pragmatic). Fits: any solo-dev review or design skill that currently runs a single subagent could split into 2-3 differently-instructed passes for near-zero added latency (parallel) and materially different blind spots covered.

4. **`asyncRewake` background hook that resumes the agent later with findings instead of blocking synchronously** — `plugins/security-guidance/hooks/hooks.json`, applied to `Stop`, and to `Bash` matched against `git commit`/`git push`/`gt create`/`gt submit`. Quoted:
   ```json
   { "if": "Bash(git commit:*)", "asyncRewake": true,
     "rewakeMessage": "Background security review of commit — address or acknowledge the findings below...",
     "rewakeSummary": "Commit security review found issues" }
   ```
   Solves "I want an LLM-graded check (slow, costs tokens) on every commit/push without making every commit wait on it." Directly useful for a solo-dev harness: e.g. a background secret-scan or lint-quality pass keyed off `git commit`/`git push` in this dotfiles repo's own hook config, using the same `if:`-matcher + `asyncRewake` primitive already in the installed Claude Code CLI.

5. **Git-diff baseline via `git stash create` snapshot, re-armed each turn, so a Stop-hook LLM review only ever sees code changed *this session*** — `plugins/security-guidance/hooks/security_reminder_hook.py` (see module docstring "How the git baseline works"). Solves the generic problem of "run an expensive check only on the delta, not the whole repo, without requiring a commit." `git stash create` produces a commit-object SHA representing the working tree without actually stashing anything — a reusable trick for any hook that wants a diffable snapshot of uncommitted state.

6. **Rule files as user-editable markdown-with-YAML-frontmatter, hot-reloaded, no restart** — `plugins/hookify/` end to end (`commands/hookify.md`, `core/config_loader.py`, `core/rule_engine.py`). Solves "let a non-programmer-facing config format drive hook behavior, and let the *agent itself* author new rules conversationally from an actual conflict that just happened." Quoted trigger design in `commands/hookify.md`: rules are generated by first launching a `conversation-analyzer` subagent that scans the last 10-30 user messages for "frustration signals" (explicit "don't do X," corrections/reversions, "why did you do X?", repeated issues) and returns `{category, tool, pattern, context, severity}` — i.e. hooks are mined from lived friction, not designed up front. Very on-theme for this user's own `hookify`-adjacent instinct (`update-config` skill) — the "mine hooks from conversation frustration" idea is the standout piece to borrow even without the full rule-engine machinery. [CORRECTED: minor — the actual Task-tool call in `commands/hookify.md` line 33 hard-codes `"subagent_type": "general-purpose"` with the analysis prompt inlined, rather than invoking the dedicated `agents/conversation-analyzer.md` agent by name (as `feature-dev`'s command does for `code-explorer`/`code-architect`/`code-reviewer`). The named agent file exists and documents the same behavior, but the command doesn't appear to route through it — a real, if cosmetic, inconsistency in the plugin itself, not a misreading by the first reader.]

7. **Structured agent-return contract: "return the 5-10 files that matter" as an explicit instruction to every exploration subagent, with the parent required to read them before continuing** — `feature-dev/commands/feature-dev.md` Phase 2 + `feature-dev/agents/code-explorer.md` ("List of files that you think are absolutely essential..."). Solves subagent-summary information loss: a subagent's prose summary is lossy, but a file list is cheap for the parent to re-read directly. Trivial, high-leverage pattern for any exploratory-subagent workflow in a personal harness.

8. **Exit-code-2 semantics as the load-bearing hook contract, documented once and reused everywhere** — `examples/hooks/bash_command_validator_example.py` in `claude-code`: `sys.exit(2)` after printing to stderr blocks the tool call *and shows stderr to Claude* (vs exit 1, which shows the user but not Claude). This 83-line file [CORRECTED: report said 84 lines; `wc -l` on the clone gives 83] is the *only* hook example shipped in the `claude-code` repo itself (not the plugins marketplace) and every other hook script in the marketplace (hookify's 4 hook scripts, security-guidance's dispatcher) follows the same "always exit 0 unless deliberately blocking" discipline to avoid ever accidentally breaking a session on a hook bug — worth copying the defensive pattern (`try/except` around all hook logic, default to allow) verbatim into any custom hook in this dotfiles repo.

## Weaknesses / ceremony cost
- **feature-dev**: 7 mandatory phases, minimum 2 rounds of "wait for explicit user approval," a minimum of 8 subagent launches (2-3 explorers + 2-3 architects + 3 reviewers) for even a trivial feature — no scaling-down path in the prompt itself (a one-line feature gets the same ceremony as a large one; the model is trusted to use judgment but nothing in the file says "skip phases for small changes"). The whole thing is prose-only: nothing stops a model from skipping straight to Phase 5 if it decides to; the "CRITICAL: DO NOT SKIP" language is the entire enforcement mechanism.
- **code-review**: up to 5 + 1(N issues) + 3 = potentially 10+ agent calls (mostly cheap Haiku, but 5 are Sonnet) for a single PR comment; if the PR closes or gets marked draft *between* step 1 and step 8, the double eligibility-check (step 7) is the only safeguard — a race window still exists between step 7 and the final `gh pr comment` in step 8.
- **ralph-loop**: the `--help` text says "No manual stop - Ralph runs infinitely by default!" unless `--max-iterations` or `--completion-promise` was set at launch [CORRECTED: this is true of the loop's own built-in exit conditions, but the plugin ships a separate `/cancel-ralph` command (`commands/cancel-ralph.md`) that deletes `.claude/ralph-loop.local.md` on request, giving a documented, non-destructive manual stop that does not require killing the process — the original bullet's "apart from killing the process" overstated the risk]. The completion-promise mechanism has no truth-verification — it's pure prompt-injected honor system ("do not lie to exit"), so a model under enough iteration pressure can simply assert the promise falsely with zero technical barrier.
- **hookify**: generated regex patterns are never validated for correctness/safety before being written — the doc's own troubleshooting section says "Test pattern with: `python3 -c "import re; print(re.search(...))"`" as something the *user* should do manually, not something the tool does automatically. `event: stop` rules can `action: block`, effectively letting a hand-authored, un-reviewed regex hold a session hostage.
- **security-guidance**: heaviest plugin by far (7,778 lines across `hooks/`), with an `ANTHROPIC_API_KEY`/OAuth-token dependency for its LLM-review layer and a documented history of internal CLI quirks it has to work around (`hooks/security_reminder_hook.py` comments reference a specific bug `#2159` around `asyncRewake` JSON validation dropping `rewakeSummary`) — i.e. its author needed intimate knowledge of Claude Code internals to make the mechanism reliable, which is a high floor for anyone trying to replicate it.
- Nothing in any plugin enforces that subagents *actually* used the tools they were given (e.g. `code-explorer` could hallucinate a file list without reading it) — the framework leans entirely on model competence for the "trace through the code comprehensively" instructions; no completion/verification hook checks subagent tool-call counts.

## Verdict: adopt / borrow parts / ignore
**Borrow parts, don't adopt wholesale.** The two genuinely portable, low-ceremony mechanisms are (a) the Stop-hook completion-promise loop (`ralph-loop/hooks/stop-hook.sh`) and (b) the `asyncRewake`-backed background review hook keyed on `git commit`/`git push` (`security-guidance/hooks/hooks.json`) — both are small, self-contained shell/JSON, require no external API dependency beyond what a hook script chooses to call, and map cleanly onto a solo-dev's own dotfiles-managed `.claude/hooks/`. The confidence-scored double-check filter (code-review) and the frustration-mined hook generation (hookify) are worth stealing as *prompt patterns* inside this user's existing `code-review`/`update-config` skills rather than as installed plugins. Ignore feature-dev's full 7-phase machinery as a drop-in — it's pure-prose ceremony with real per-invocation cost (minimum ~8 subagent launches) and no scale-down logic, and this user's own `flow`/`feature` skills already cover the same ground with tighter gating. Ignore security-guidance wholesale as a dependency (7.7k lines, needs `ANTHROPIC_API_KEY`, tracks internal CLI bug numbers to stay correct) but its `git stash create`-as-diff-baseline trick is worth lifting standalone.

## Second-reader additions

The first reader's four traced plugins (feature-dev, code-review, ralph-loop, security-guidance) don't cover `claude-security` — a fifth, entirely separate first-party plugin in `claude-plugins-official/plugins/claude-security/` (8 agents, a `workflows/scan.js` Workflow-tool pipeline, and a `scripts/lib/` Python package) that runs a multi-phase adversarial security scan and emits SARIF. Two of its mechanisms, plus one from `plugin-dev`, are worth adding:

1. **Deterministic secret redaction at the output layer, independent of what the model wrote** — `plugins/claude-security/scripts/lib/secret.py`. Every finding the LLM scanner produces carries a `snippet` field, but before any finding reaches the SARIF/JSONL artifacts, `withheld()` blanks the snippet for any finding whose CWE rolls up to CWE-798 (Use of Hard-coded Credentials):
   ```python
   def withheld(finding: Record) -> Record:
       """`finding` as the products carry it: a hard-coded credential's snippet is empty."""
       return {**finding, "snippet": ""} if is_credential(finding) else finding
   ```
   This solves a problem none of the other four plugins address: an LLM-graded security scanner's own output is a plausible secret-leak vector (the model quotes the credential it found, verbatim, into a report that then gets committed/uploaded/posted). The redaction is pure code, keyed off a CWE taxonomy rollup, not a prompt instruction telling the model "don't include the secret" — the finding's file/line/symbol still locate the code, only the quoted text is stripped. Directly reusable for any personal secret-scanning hook: never trust the model to self-censor a leak it just found, strip it in code after the fact based on a rule table, not a plea.

2. **SARIF as the artifact format, with a version-pinned, hash-based finding-id so re-scans don't create duplicate CI alerts** — `plugins/claude-security/scripts/lib/sarif.py`. Contrasts directly with the report's `code-review` plugin, whose only artifact is a freeform `gh pr comment` (re-generated from scratch, no stable identity across runs). Here, `TOOL_NAME`/`ID_VERSION` are pinned constants with an explicit comment — "The driver name GitHub keys alert identity on; renaming it orphans every open alert" — and each finding gets a deterministic hash-based id (`ID_PREFIX = "claude-security-plugin"`, `ID_VERSION = "v3"`) so the same real bug found on scan N and scan N+1 maps to the same GitHub code-scanning alert instead of opening a duplicate. Worth stealing the general shape — if a personal review harness ever wants findings to survive re-runs (dedupe, track "still open" vs "fixed"), the finding needs a stable id computed from its own content, not from run order.

3. **A real JSON-schema-shaped validator script for hook configs, shipped as a skill script rather than left to the model** — `plugins/plugin-dev/skills/hook-development/scripts/validate-hook-schema.sh` (159 lines; sibling scripts `validate-agent.sh` and `validate-settings.sh` do the same for agent frontmatter and `settings.json`). It's a plain bash+`jq` script — checks JSON syntax, root structure, hook-type validity, matcher patterns, timeout ranges — invoked by the `plugin-validator` agent via `Bash`, not asked of the model as a "please double check" instruction. This directly answers a gap the first reader flagged as a hookify weakness ("generated regex patterns are never validated for correctness/safety before being written... something the *user* should do manually, not something the tool does automatically"): the same marketplace already ships exactly this kind of deterministic validator, just in `plugin-dev`, not wired into `hookify`'s own rule-authoring flow. Worth noting as the fix for that specific weakness, and worth stealing standalone for any personal harness that hand-authors hook/agent config and wants a pre-flight check that isn't "ask the model to review its own regex."
