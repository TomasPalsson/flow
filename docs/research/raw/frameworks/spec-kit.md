# spec-kit

## What it is (3 lines)
`specify-cli` (repo: `github/spec-kit`) is a Python CLI that bootstraps a "Spec-Driven Development" (SDD) workflow into any repo: it scaffolds `.specify/` with templates and bash/powershell/python helper scripts, then installs a set of `/speckit.*` commands (specify → clarify → plan → tasks → analyze → implement, plus checklist/constitution/taskstoissues/converge) rendered natively for 41 different coding agents [CORRECTED: was "51" — `src/specify_cli/integrations/` contains 41 agent subpackages (42 entries registered in `integrations/__init__.py`'s `INTEGRATION_REGISTRY`, including a non-agent `generic` fallback); the project's own `docs/index.md` says "38 integrations" and `README.md` says "30+" — no source in the repo supports "51"] (Claude Code, Copilot, Gemini, Cursor, etc.). It has grown from a template repo into a small platform: extensions (hookable command packs), presets (template-composition packs), a community preset marketplace, and a declarative `workflow.yml` orchestration engine with human-approval gates.

## Workflow it implements (actual sequence, as implemented)
1. `specify init` (Python CLI) — scaffolds `.specify/{memory,templates,extensions,presets}` and installs per-agent command files (e.g. `.claude/skills/speckit-*/SKILL.md` for Claude).
2. `/speckit.constitution` — writes `.specify/memory/constitution.md` (project principles), consulted by every later command.
3. `/speckit.specify "<description>"` — runs `before_specify` hooks (git extension creates/switches branch), computes a numbered feature dir under `specs/` via `create-new-feature.sh`, copies the resolved `spec-template.md` into `spec.md`, fills it from the description, self-validates against a generated `checklists/requirements.md`, asks up to 3 `[NEEDS CLARIFICATION]` questions only if unavoidable, persists `.specify/feature.json`.
4. `/speckit.clarify` (optional but recommended before plan) — asks up to 5 targeted questions one at a time (multiple-choice tables with a recommended option, or ≤5-word short answers), writes each accepted answer into a `## Clarifications` section and the relevant spec section immediately, re-validates the requirements checklist.
5. `/speckit.plan` — runs `check-prerequisites.sh`, fills `plan-template.md`'s Technical Context / Constitution Check, produces `research.md` (Phase 0, resolves all NEEDS CLARIFICATION), then `data-model.md` + `contracts/` + `quickstart.md` (Phase 1), re-checks the constitution gate post-design.
6. `/speckit.tasks` — generates `tasks.md`, organized by user story (not by layer), each line forced into the exact format `- [ ] [TaskID] [P?] [Story?] Description with file path`.
7. `/speckit.checklist` — generates a *custom* requirements-quality checklist (explicitly "unit tests for English", not test-writing) for a domain the user names (e.g. security, UX).
8. `/speckit.analyze` — **read-only** cross-artifact consistency pass over spec.md/plan.md/tasks.md/constitution.md: duplication, ambiguity, underspecification, constitution violations, coverage gaps, inconsistency; emits a severity-tagged Markdown report and asks before suggesting fixes.
9. `/speckit.implement` — executes `tasks.md` phase by phase.
10. `/speckit.taskstoissues` / `/speckit.converge` — optional GitHub issue sync / convergence pass.
Every command's `before_*`/`after_*` boundary can trigger extension hooks (e.g. the bundled `git` extension auto-commits after each step) declared in `.specify/extensions.yml` — no core code changes needed to add a hook.
All of this can also be driven non-interactively via `workflows/speckit/workflow.yml`, a declarative YAML pipeline (`specify → gate → plan → gate → tasks → implement`) with `type: gate` approve/reject steps.

|---|---|---|---|
| `spec.md` | `specs/<NNN-slug>/` | specify | `templates/spec-template.md`: `# Feature Specification: [FEATURE NAME]`, `## User Scenarios & Testing`, `## Requirements`, `### Functional Requirements`, `## Success Criteria`, `## Assumptions` |
| `checklists/requirements.md` | same feature dir | specify (created) / clarify (re-validated) | ad-hoc: `# Specification Quality Checklist: [FEATURE NAME]` → `## Content Quality`, `## Requirement Completeness`, `## Feature Readiness` |
| `plan.md` | feature dir | plan | `templates/plan-template.md`: `## Summary`, `## Technical Context`, `## Constitution Check`, `## Project Structure`, `## Complexity Tracking` |

| `tasks.md` | feature dir | tasks | `templates/tasks-template.md`: `## Format: [ID] [P?] [Story] Description`, `## Phase 1: Setup`, `## Phase 2: Foundational`, `## Phase 3: User Story 1 …`, `## Dependencies & Execution Order` |

| `.specify/feature.json` | repo root | specify (and any command via `_persist_feature_json`) | `{"feature_directory": "specs/003-user-auth"}` — the cross-session "current feature" pointer |

## Deterministic vs prompt
| Mechanism | Enforced by script/hook/CLI | Asked of the model in prose |
|---|---|---|
| Feature number / branch name generation, collision handling, 244-byte GitHub truncation | `scripts/bash/create-new-feature.sh` (pure bash, byte-identical PowerShell/Python twins) | — |
| Repo/feature-dir resolution (`.specify` marker walk, `SPECIFY_FEATURE_DIRECTORY` priority, `feature.json` persistence) | `common.sh: get_repo_root / get_feature_paths / _persist_feature_json` | — |
| Template lookup & composition (override → preset → extension → core; replace/prepend/append/wrap) | `common.sh: resolve_template / resolve_template_content` | — |
| Prerequisite gating (`plan.md` must exist before tasks, `tasks.md` before implement) | `scripts/bash/check-prerequisites.sh` (`--require-spec`, `--require-tasks`) | — |
| JSON escaping / safe path quoting for agent consumption | `common.sh: json_escape`, `printf '%q'` | — |
| Whether a hook actually *runs* | nothing — only "emit `EXECUTE_COMMAND:` and then actually invoke it" | 100% prose instruction in every command template's "Mandatory Post-Execution Hooks" section |
| What counts as `[NEEDS CLARIFICATION]`, capped at 3 (specify) / 5 (clarify) | count cap is stated as a rule, not code-checked | model judges "significantly impacts scope", picks by impact×uncertainty heuristic |
| Spec quality checklist pass/fail | no independent checker — model re-reads its own spec | model self-grades against the checklist it just wrote |
| `analyze` severity (CRITICAL/HIGH/MEDIUM/LOW) and 50-finding cap | cap is a stated instruction | entirely model heuristic, no rubric enforcement |
| Task line format `- [ ] [TaskID] [P?] [Story?] Description` | shown as a "Format" rule with ✅/❌ examples | not parsed/validated by any script — purely convention |
| Workflow-engine gates (`type: gate`, approve/reject) | enforced by the Workflow engine when run via `workflow.yml` | only exists when a user opts into the declarative workflow path; the default `/speckit.*` slash-command path has no such enforcement |

## Mechanisms worth stealing
1. **Deterministic feature-numbering/branch-naming script** — solves "let the LLM invent a slug and hope it doesn't collide or exceed platform limits." `scripts/bash/create-new-feature.sh`. Quote: `clean_branch_name()` uses `LC_ALL=C` specifically "so a name of '-n'/'-e'/'-E' is text, not options" and `fit_branch_name()` truncates to GitHub's 244-byte limit. Fit for a solo-dev harness: any skill that creates work-item directories/branches should shell out to a tiny deterministic script like this instead of asking the model to compute numbering — removes an entire class of "the model picked spec-042 but spec-017 already exists" bugs.

2. **Priority-stacked template resolution with composition strategies** — solves "how do user overrides/presets layer on top of built-in templates without forking them." `scripts/bash/common.sh: resolve_template_content()`. Quote: priority is "1. `.specify/templates/overrides/` 2. `.specify/presets/<preset-id>/templates/` … 3. `.specify/extensions/<ext-id>/templates/` … 4. `.specify/templates/` (core)" and each layer declares `strategy: replace|prepend|append|wrap` (wrap using a literal `{CORE_TEMPLATE}` placeholder). Fit: a dotfiles skill library could resolve a global "spec template" the same way — repo-local override > user preset > shipped default — instead of every skill hardcoding its own template text.

3. **Cross-session "current feature" state file** — solves "the model forgets which feature it's working on between commands/sessions." `.specify/feature.json` written by `_persist_feature_json`, read with priority `SPECIFY_FEATURE_DIRECTORY env > feature.json > error`. Fit: any multi-step Claude workflow skill (e.g. `flow`) could persist a small `.specify`-style state file so a resumed session knows which artifact directory is "current" without re-deriving it from git branch or conversation memory.

4. **Declarative hook manifest instead of code hooks** — solves "how do you let a plugin (git auto-commit, custom lint gate) run before/after any core step without editing the core prompt." `extensions/git/extension.yml`. Quote:
   ```yaml
   hooks:
     before_specify:
       command: speckit.git.feature
       optional: false
     after_specify:
       command: speckit.git.commit
       optional: true
       prompt: "Commit specification changes?"
   ```
   The command templates all read this file at fixed checkpoints and either auto-run mandatory hooks (`EXECUTE_COMMAND:`) or offer optional ones. Fit: a personal skill system could let e.g. a `worklog` or `git` skill register itself against `before_*/after_*` of `flow`/`feature`/`fix` without touching those skills' files — good pattern, though see the weakness below about it being unenforced in the prompt-only path.

5. **Checklist-as-"unit-tests-for-requirements" framing** — solves "checklists silently drift into re-testing the implementation instead of testing the spec's own clarity." `templates/commands/checklist.md`. Quote: "**NOT for verification/testing**: ❌ NOT 'Verify the button clicks correctly' … **FOR requirements quality validation**: ✅ 'Is "prominent display" quantified with specific sizing/positioning?'" plus an explicit checkbox-ownership rule: "`[x]` does NOT mean implementation work is complete… This command generates or appends checklist items; it MUST NOT mark generated items `[x]`." Fit: directly reusable prose for any spec/plan-writing skill (`flow-spec`, `spec-judge`) to stop the common failure mode of a self-graded, rubber-stamped spec checklist.

6. **Bounded, prioritized clarification loop** — solves unbounded "20 questions" ping-pong. `templates/commands/clarify.md`. Quote: "Maximum of 5 total questions across the whole session… If more than 5 categories remain unresolved, select the top 5 by (Impact * Uncertainty) heuristic," one question at a time, always with a stated `**Recommended:**` default so the user can just say "yes." Fit: any interactive planning skill (grill-me, flow-spec) benefits from an explicit numeric cap plus an impact-ranking rule instead of "ask clarifying questions as needed."

7. **Read-only cross-artifact consistency pass, run before implementation, never before** — solves "specs and tasks silently drift apart" without ever letting a fix-it pass mutate files unasked. `templates/commands/analyze.md`. Quote: "**STRICTLY READ-ONLY**: Do **not** modify any files. Output a structured analysis report. Offer an optional remediation plan (user must explicitly approve before any follow-up editing commands would be invoked manually)." Fit: `/flow` or `/audit`-style skills could add an equivalent "diff the plan against the code, report only" gate before a build phase, with the same severity table (CRITICAL/HIGH/MEDIUM/LOW) and finding cap (50) to keep output token-bounded.

8. **One template body, N native renderings** — solves supporting many agents without N copies of the prompt. `src/specify_cli/integrations/base.py` (`MarkdownIntegration`, `TomlIntegration`, `SkillsIntegration`) plus e.g. `src/specify_cli/integrations/claude/__init__.py`, which post-processes the *same* `templates/commands/*.md` body into a Claude Skill by injecting `user-invocable`, `disable-model-invocation: false`, and an `argument-hint` line. Less relevant for a single-agent (Claude-only) dotfiles setup, but the *pattern* — one canonical prompt source + a thin per-target formatter — is reusable if this dotfiles repo ever needs to ship the same skill body to both Claude Code and some other surface.

## Weaknesses / ceremony cost
- **Prompt weight per command**: `templates/commands/*.md` totals 2,437 lines across 10 files; a single `/speckit.specify` invocation loads ~346 lines, `/speckit.checklist` ~379, `/speckit.tasks` ~219 — and every one of them repeats the *same* ~35-40 line "check `.specify/extensions.yml`, parse hooks, filter `enabled: false`, emit optional/mandatory hook block" boilerplate verbatim (specify.md lines 21-54 and 236-268 vs. clarify.md lines 21-54 and 241-273 are near character-for-character duplicates) — real, uncollapsed ceremony cost, not shared via include.
- **Hook execution is unenforced in the default path**: nothing stops the model from emitting the `EXECUTE_COMMAND:` block and then not actually invoking it — the instruction itself says "Emitting the block alone does not run the hook," which is a tell that this has happened before. Only the separate `workflow.yml` + Workflow-engine path has real gate enforcement (`type: gate`, `on_reject: abort`).
- **Self-graded quality gates**: the spec-quality checklist (specify/clarify) and the `analyze` severity assignment are both scored by the same model that authored the artifact, with no independent check — a rubber-stamp failure mode the checklist's own "unit tests for English" framing is designed to reduce but cannot structurally prevent.
- **Large surface for what is fundamentally file scaffolding + prompts**: 131 Python files / ~56k LOC (`src/specify_cli`) [CORRECTED: was "306 Python files" — 131 is the actual count inside `src/specify_cli` (verified via `find src/specify_cli -name "*.py" | wc -l`); 306-307 is instead the whole-repo count *including* `tests/` (307 files, ~169.8k LOC total) — the original stat mixed a whole-repo file count with a `src/specify_cli`-scoped LOC count], 41 agent integrations [CORRECTED: was "51", see above], a preset marketplace (`presets/catalog.json` + `catalog.community.json` with third-party download URLs), an extension registry, and a bundler subsystem — heavy to adopt wholesale for a single user on a single agent.
- **Bounded-question ceremony can under-cover**: the clarify loop hard-caps at 5 questions total ever, deferring "if quota reached with unresolved high-impact categories remaining, explicitly flag them under Deferred" — a deliberate cost/thoroughness tradeoff, not a defect, but worth naming as ceremony that can silently leave gaps on a genuinely complex feature.

## Plugin/packaging structure
- Ships as the `specify-cli` PyPI package (`pyproject.toml`, hatchling build), installed via `uv tool install`, `pipx install`, or run ephemerally with `uvx`; `specify self upgrade` self-updates and auto-detects which installer was used.
- `specify init <project>` scaffolds `.specify/{memory,templates,extensions,presets}` into a target repo and, per chosen agent(s), renders `templates/commands/*.md` into that agent's native command format — for Claude Code specifically, into `.claude/skills/speckit-<name>/SKILL.md` (not raw slash commands) with injected frontmatter (`user-invocable`, `disable-model-invocation: false`, `argument-hint`).
- Core templates/scripts are force-included into the wheel (`[tool.hatch.build.targets.wheel.force-include]`) so `specify init` works fully offline/air-gapped.
- **Extensions** (`extensions/<id>/extension.yml`) declare `hooks.before_*`/`after_*` against the fixed lifecycle points of the 9 core commands, plus optional new commands/config — the bundled `git` extension is the only first-party one shipped in `extensions/`.
- **Presets** (`presets/<id>/preset.yml`) declare template-composition layers (`provides.templates: [{type, name, file, strategy}]`) and are discovered via `.registry` (priority-ordered) or a JSON marketplace catalog (`presets/catalog.json` for bundled, `presets/catalog.community.json` for third-party, each entry with a `download_url` to a GitHub release zip).
- **Workflows** (`workflows/speckit/workflow.yml`) are a separate declarative orchestration layer read by a "Workflow" engine — `schema_version`, `requires.speckit_version` compatibility gate, `steps` of `command`/`gate` type — that actually enforces approve/reject, unlike the prose-only hook path.

## Second-reader additions

Three mechanisms the first pass didn't cite, found while verifying the claims above:

1. **Enforced cross-language script parity via test suite, not just a comment** — the first reader's mechanism #1 asserts the bash/PowerShell/Python scripts are "byte-identical twins" but only cites a comment in `create-new-feature.sh` as evidence. The repo actually *tests* this: `tests/test_create_new_feature_python_parity.py`, `tests/test_check_prerequisites_python_parity.py`, `tests/test_resolve_template_python_parity.py`, `tests/test_setup_plan_python_parity.py`, `tests/test_setup_tasks_python_parity.py`, `tests/extensions/git/test_git_extension_python_parity.py`, and `tests/extensions/test_update_agent_context_python_parity.py` each shell out to the bash script and the Python port (and, where PowerShell is available, the `.ps1` twin via `HAS_POWERSHELL`) with identical inputs and assert identical stdout/exit codes (see `tests/parity_helpers.py`: `bash_cmd`, `ps_cmd`, `py_cmd`, `run`). Fit: if a dotfiles skill ever needs a script ported to a second shell/runtime for portability, this pattern — one parity test file per script, running all variants against the same fixture repo — is a directly reusable way to make "byte-identical" a checked property instead of a comment's promise.

2. **Sandboxed expression evaluator for `workflow.yml` templating, not a real Jinja2/eval** — `src/specify_cli/workflows/expressions.py`. Quote: `"""Sandboxed expression evaluator for workflow templates. Provides a safe Jinja2 subset for evaluating expressions in workflow YAML. Templates cannot perform file I/O, import modules, or run arbitrary code — the evaluator only walks the namespace and applies a fixed set of filters."""` — it hand-rolls `{{ inputs.spec | default(...) }}`-style interpolation with a closed allowlist of five filters (`_REGISTERED_FILTERS = ("default", "join", "map", "contains", "from_json")`), explicitly to avoid handing a real template engine (with its `eval`-adjacent surface) untrusted YAML written by whoever authored the workflow. Fit: any dotfiles mechanism that lets users write their own small templated config (a custom prompt snippet, a hook argument) should reach for a closed-filter interpolator like this rather than Python's `eval`/`format_map`/a full Jinja2 environment.

3. **Contract-tested manifest schema instead of best-effort YAML parsing** — `src/specify_cli/bundler/models/manifest.py`'s `BundleManifest.from_dict()` / `.structural_errors()`, exercised by `tests/contract/test_manifest_schema.py` (which the module docstring says "Mirrors `contracts/bundle-manifest.schema.md`"). It catches cases a naive "read the YAML" approach misses — e.g. `test_explicit_null_bundle_field_is_reported_as_missing` guards against a null YAML field silently becoming the four-character string `"None"` in the packaged bundle rather than tripping a required-field check. Fit: any skill that reads user-authored YAML/JSON config (extension manifests, preset files) benefits from a small typed loader with an explicit "collect structural errors" pass and a contract test file that pins it to a written schema doc, instead of trusting `yaml.safe_load()` output directly.

## Verdict: adopt / borrow parts / ignore
**Borrow parts.** For a solo-dev global dotfiles/Claude-Code harness, the whole 41-integration [CORRECTED: was "51-integration"] / preset-marketplace / bundler apparatus is the wrong shape to adopt wholesale — it's built for an OSS tool serving many teams and many agents, and most of its ~56k LOC exists to solve "render this prompt for 41 different CLIs [CORRECTED: was "51 different CLIs"]," which doesn't apply here. What's genuinely worth lifting: (1) the deterministic bash scripts for numbering/state/prerequisite-gating (`create-new-feature.sh`, `common.sh`'s `get_feature_paths`, `check-prerequisites.sh`) as a template for keeping anything numeric or path-derived out of the model's hands; (2) the template-composition priority stack for a global-override-vs-repo-local template story; (3) the "checklist is a unit test for English, not for code" framing and the bounded/prioritized clarification-question protocol, both directly reusable prose for `flow-spec`/`grill-me`/`spec-judge`; and (4) the read-only, capped, severity-tagged consistency-analysis pattern (`analyze`) as a template for a pre-build "does the plan still match the code" gate. Skip the hook-execution-by-prose-instruction mechanism as-is (its own docs admit "emitting the block alone does not run the hook") — if hooks are wanted, wire them as real Claude Code `settings.json` hooks/scripts rather than trusting the model to self-invoke `EXECUTE_COMMAND:`.
