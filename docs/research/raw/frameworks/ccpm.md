# ccpm

## What it is (3 lines)
CCPM ("Claude Code Project Manager", by automazeio) is a spec-driven delivery workflow that turns an idea into a PRD, the PRD into a technical epic, the epic into numbered task files, and the tasks into GitHub Issues that parallel sub-agents execute inside git worktrees, with all state and progress living in flat markdown files + GitHub issue comments rather than in chat history. As of this clone (2026-09-04, HEAD dated **Wed Mar 18 12:15:22 2026 +0000**) the project has been **rewritten from a Claude-Code-specific `.claude/commands/pm/*` slash-command plugin into a harness-agnostic Agent Skill** (the [agentskills.io](https://agentskills.io) standard) — the old `.claude/commands/`, `.claude/agents/`, `rules/`, and `.claude/context/` directories the task brief expected **no longer exist in the repo**; everything now lives under `skill/ccpm/`. Star count not statically visible (dynamic shields.io badge, not fetched).

Repo: https://github.com/automazeio/ccpm (single repo, no sub-repos). License: MIT.

## Workflow it implements (as actually implemented today)
Entry point is `skill/ccpm/SKILL.md` (82 lines), a router with a YAML `description` frontmatter (used by the harness to decide when to activate the skill) that points to five on-demand reference docs, read only when relevant:

1. **Plan** (`references/plan.md`) — guided-brainstorm PRD writing → `.claude/prds/<name>.md`; then "parse the PRD" → technical epic at `.claude/epics/<name>/epic.md`.
2. **Structure** (`references/structure.md`) — decompose epic into numbered task files `001.md, 002.md, …` with `depends_on` / `parallel` / `conflicts_with` metadata; batches into parallel `Task` sub-agent calls once ≥5 tasks.
3. **Sync** (`references/sync.md`) — push epic+tasks to GitHub as issues (`gh issue create`), rename task files to the real issue numbers, create an `epic/<name>` worktree, post progress-update comments, close issues, merge epics back to main, or file a linked bug against a completed issue.
4. **Execute** (`references/execute.md`) — analyze an issue into parallel work streams, launch one `Task` sub-agent per stream in the shared worktree, track via per-stream progress files, coordinate via git commits (`git pull --rebase` before touching shared files).
5. **Track** (`references/track.md`) — status/standup/next/blocked/search/validate, entirely via bash scripts, no LLM reasoning.

`references/conventions.md` (165 lines) is the shared rulebook (paths, frontmatter schemas, GitHub-op safety check, git/worktree conventions) that SKILL.md says to read "before doing anything."

## Artifacts it produces
All under `.claude/` in the *target* project (not in ccpm's own repo):
```
.claude/
├── prds/<feature-name>.md
├── epics/
│   ├── <feature-name>/
│   │   ├── epic.md
│   │   ├── <N>.md                  # 001.md before sync, renamed to <issue#>.md after
│   │   ├── <N>-analysis.md
│   │   ├── github-mapping.md
│   │   ├── execution-status.md
│   │   └── updates/<issue_N>/{stream-A.md, progress.md, execution.md}
│   └── archived/<feature-name>/
└── context/
```
Template headings quoted verbatim from `skill/ccpm/references/plan.md`:
- PRD body: `## Executive Summary`, `## Problem Statement`, `## User Stories`, `## Functional Requirements`, `## Non-Functional Requirements`, `## Success Criteria`, `## Constraints & Assumptions`, `## Out of Scope`, `## Dependencies`
- Epic body (`references/plan.md`): `## Overview`, `## Architecture Decisions`, `## Technical Approach` (`### Frontend Components`, `### Backend Services`, `### Infrastructure`), `## Implementation Strategy`, `## Task Breakdown Preview`, `## Dependencies`, `## Success Criteria (Technical)`, `## Estimated Effort`
- Task body (`references/structure.md`): `## Description`, `## Acceptance Criteria`, `## Technical Details`, `## Dependencies`, `## Effort Estimate`, `## Definition of Done`
- Progress comment posted to GitHub (`references/sync.md`): `## 🔄 Progress Update - <date>` with `### ✅ Completed Work`, `### 🔄 In Progress`, `### 📝 Technical Notes`, `### 📊 Acceptance Criteria Status`, `### 🚀 Next Steps`, `### ⚠️ Blockers`, footer `*Progress: N% | Synced at <timestamp>*`
- Frontmatter schemas (exact, from `conventions.md`): PRD has `name/description/status/created`; Epic adds `progress/prd/github`; Task adds `github/depends_on/parallel/conflicts_with`; Progress file has `issue/started/last_sync/completion`.

## Mechanisms worth stealing

1. **Thin skill router + lazy-loaded reference docs** — SKILL.md is only 82 lines and never loads all phase docs at once; each phase file (`plan.md` 106, `structure.md` 106, `sync.md` 296, `execute.md` 212, `track.md` 163 lines) is read only when that phase triggers. Path: `skill/ccpm/SKILL.md`. Snippet: `"Before doing anything, read references/conventions.md for path standards..."` / [CORRECTED: the source uses markdown bold, not quoted key-value pairs — verbatim it reads] `**When**: An epic exists and needs to be decomposed into concrete tasks.` / `**Read**: \`references/structure.md\``. **Fit for dotfiles harness**: this is exactly the pattern to use for any multi-phase personal skill (e.g. a `worklog` or `flow` skill) — keep a small always-loaded index and defer detail docs, instead of one giant SKILL.md, to keep context-window cost proportional to what's actually being done.

2. **"Script-First Rule" as an explicit table mapping intents to scripts** — `skill/ccpm/SKILL.md` lines 47-66 is a markdown table: `| Project status | bash references/scripts/status.sh |` etc., with the closing instruction "Use the LLM for work that requires reasoning... Use script for anything that reads and reports without needing reasoning." **Fit**: adopt verbatim as a design rule for any personal automation skill — a small table that tells the model exactly which read-only queries must shell out instead of being "helpfully" reasoned about, cutting both token cost and hallucination risk on things like `git log`, file counts, or status summaries.

3. **Dependency-graph-as-frontmatter, read by grep, not a database** — `depends_on: []` / `parallel: true` / `conflicts_with: []` fields in every task file, resolved purely with `grep "^depends_on:" file | sed ...` in `next.sh` and `blocked.sh` (`skill/ccpm/references/scripts/next.sh` lines 20-27). **Fit**: for a solo-dev todo/queue system, storing dependency edges directly in each markdown file's frontmatter (rather than a separate graph file or DB) means `grep`/`ripgrep` alone can answer "what's unblocked" — no extra tooling, works offline, diffable in git.

4. **Repo-safety guard rail against writing to the template/upstream repo** — repeated verbatim in `skill/ccpm/references/conventions.md` lines 109-118 and `sync.md` lines 7-19: `if [[ "$remote_url" == *"automazeio/ccpm"* ]]; then echo "❌ Cannot write to the CCPM template repository." ...; exit 1; fi`. **Fit**: generalize into any skill that can create GitHub issues/PRs from a cloned template — check `git remote get-url origin` against a known "never touch this" pattern (e.g. the dotfiles' own upstream, or any repo not owned by the user) before doing any write, and hardcode it as a copy-pasted guard at every write call site rather than trusting one central check.

5. **Sync markers to prevent duplicate progress comments** — `sync.md` line 152-155: `Add sync marker to local files to prevent duplicate comments: <!-- SYNCED: <datetime> -->`, combined with a preflight check ("Check `last_sync` in progress.md — if synced <5 minutes ago, confirm before proceeding"). **Fit**: cheap idempotency technique for any skill that posts to an external system (Slack, GitHub, a doc) repeatedly across agent runs — a timestamped HTML-comment marker plus a "too-recent" guard avoids spam without needing external dedup state.

6. **Task file renaming as the sync-completion signal** — `sync.md` step 3: local task files are created as `001.md, 002.md, …` and only renamed to `<real_github_issue_number>.md` after `gh issue create` succeeds, with all `depends_on`/`conflicts_with` arrays rewritten from sequential numbers to real issue numbers at the same time (`sed -i.bak "s/\b001\b/<new_num_1>/g"`). **Fit**: a filename-as-state pattern — whether a task file is "synced" is visible from `ls` alone, no frontmatter parse needed; worth reusing for any local-draft → remote-id workflow (e.g. draft PRs, draft calendar events) to avoid a separate "synced: true/false" field that can drift from reality.

7. **Per-stream progress files as the parallel-agent coordination surface** — `execute.md` has each dispatched sub-agent write to its own `updates/<N>/stream-<X>.md`, with an `execution.md` file tracking Active/Queued/Completed streams centrally (lines 144-155). Coordination rule: `"Before modifying a shared file, check git status <file> — if another agent has it modified, wait and pull first."` **Fit**: for a personal multi-agent build pipeline (this dotfiles repo already has `flow`/`ultracode`), the pattern of "one status file per parallel worker + one roll-up file the orchestrator reads" is a lightweight alternative to a message bus, and it survives context loss (a new session can re-read the files to resume orchestration).

8. **`≤10 tasks per epic` / batch-size-by-scale heuristics stated as hard numeric limits, not vague guidance** — `plan.md` line 96 `"Aim for ≤10 tasks total — prefer simplicity over completeness."`; `structure.md` lines 28-31 gives exact thresholds: "Small (<5 tasks): create sequentially. Medium (5–10): batch into 2–3 groups... Large (>10): ...max 5 concurrent." **Fit**: worth stealing the *style* — replace fuzzy "break it down reasonably" instructions in any planning skill with concrete numeric bands, since models follow numeric thresholds far more reliably than qualitative judgment calls.

## Weaknesses / ceremony cost
- **Lines loaded per invocation**: a full PRD→epic flow loads SKILL.md (82) + conventions.md (165) + plan.md (106) ≈ **353 lines**; a sync operation loads SKILL.md + conventions.md + sync.md (296) ≈ **543 lines**; execute loads ≈ **460 lines**. Not huge, but conventions.md is re-read on every phase regardless of relevance (it mixes PRD frontmatter schema with git/worktree rules even for a pure `status` query, though the Script-First Rule mostly routes status queries away from any doc read at all).
- **Gates that are pure prose, easy to silently skip**: the repo-safety check (never write to the ccpm template repo) is not a hook — it's a bash snippet the model is instructed to run "before any GitHub write operation." Nothing prevents the model from calling `gh issue create` directly without running the check first. Same for the sync-marker/duplicate-comment guard, the `--force`-never rule, and the "check git status before touching a shared file" coordination rule in `execute.md` — all rely entirely on the model choosing to comply mid-task, with no lint/hook backstop.
- **`init.sh` is stale relative to the new Skill architecture**: it still creates `.claude/rules`, `.claude/agents`, `.claude/scripts/pm` directories and prints `"Create your first PRD: /pm:prd-new <feature-name>"` and `"View help: /pm:help"` — slash-command syntax from the old plugin generation that no longer exists in this skill-based repo. Running `init.sh` on a fresh project would scaffold directories the current skill files never reference (`.claude/rules`, `.claude/agents`), and its suggested next-step commands don't correspond to anything the skill actually recognizes.
- **No automatic progress-% recalculation**: `conventions.md` gives the shell formula for epic progress but nothing runs it automatically on task close — `sync.md`'s "Closing an Issue" section just says "5. Recalculate and update epic progress" as a manual prose step.
- **Sub-agent dispatch is entirely prompt-based YAML, not a real scheduler**: the `Task:` blocks describing parallel streams in `structure.md`/`execute.md` are illustrative prompt templates, not code — there's no dependency-aware scheduler that actually launches agents as prerequisites complete; the model is asked to "launch them as their dependencies complete" and "check if blocked issues are now unblocked" as ongoing manual judgment across a session.
- **Conflict resolution is "agents report and pause"** (`execute.md` line 209) — no merge/lock mechanism, purely a documented convention that concurrent agents avoid stepping on each other's files.

## Plugin/packaging structure
No `plugin.json`, no marketplace entry, no npm package. Per README: *"CCPM is a standard Agent Skill. Point your harness at `skill/ccpm/` — that's it."* Install is a **symlink or copy**:
- Factory/Droid: `ln -s /path/to/ccpm/skill/ccpm ~/.factory/skills/ccpm`
- Claude Code: `ln -s /path/to/ccpm/skill/ccpm .claude/skills/ccpm`
- Any other agentskills.io-compatible harness: point at `skill/ccpm/` directly.

The only "installer" with actual logic is `skill/ccpm/references/scripts/init.sh`, which is not auto-run on install — it's invoked manually per-project to check/install `gh` CLI, run `gh auth login`, install the `yahsan2/gh-sub-issue` gh extension, scaffold `.claude/{prds,epics,rules,agents,scripts/pm}`, create GitHub `epic`/`task` labels (colors `#0E8A16`/`#1D76DB`), and write a starter `CLAUDE.md` if missing. No hooks are registered anywhere in the repo (no `hooks/`, no `settings.json` hook config) — all "enforcement" is either a bash script the model chooses to invoke or a prose rule.

## Verdict: adopt / borrow parts / ignore
**Borrow parts.** Don't adopt CCPM wholesale — it targets teams using GitHub Issues as a shared work queue across humans+agents, and a chunk of its ceremony (epic sub-issues, `gh-sub-issue` extension, multi-agent worktree coordination) is overkill for a solo dev's dotfiles harness. But three things are directly worth lifting into this repo's own skills (e.g. `flow`, `worklog`, `feature`):
1. The **thin-router-plus-lazy-reference-docs** structure (mechanism #1) — this repo's larger skills could shed load-time bloat the same way.
2. The **Script-First Rule table** (mechanism #2) — a concrete pattern to apply anywhere a skill currently has the model "reason" its way through a status/listing query that a 10-line bash script could answer deterministically and faster.
3. **Frontmatter-as-dependency-graph + filename-as-sync-state** (mechanisms #3 and #6) — cheap, git-diffable state tracking with no extra database, directly applicable to any local task/queue system in `bin/.local/bin/` or a personal skill.
Ignore: the parallel multi-agent worktree orchestration machinery and GitHub-Issues-as-source-of-truth model — not a fit for a single-developer dotfiles context where there's no team to hand off to and no need for issue-comment audit trails.

## Second-reader additions

1. **Bug-reporting workflow uses GitHub's own auto-link syntax as the traceability mechanism, not custom state** — `skill/ccpm/references/sync.md` lines 221-296 (the whole "Reporting a Bug Against a Completed Issue" section — this is literally the change in the repo's HEAD commit, `7d7e462 "feat: add bug reporting workflow (closes #654)"`, which the first-reader pass never mentions). It reads the original issue for context (`gh issue view <original_N> --json title,body,labels`), writes a local task file with a new `bug_for: <original_N>` frontmatter field (not present anywhere in `conventions.md`'s documented Task schema — an undocumented field), then creates the GitHub issue with a body that "should open with `Fixes / follow-up to #<original_N>` so GitHub auto-links them" (line 289). **Why it's worth stealing**: it gets a bidirectional issue link for free from GitHub's own markdown-parsing convention instead of maintaining a custom cross-reference field or a second database — the cheapest possible way to keep a bug traceable to the work that surfaced it.

2. **`validate.sh` carries the exact same architectural staleness bug the first reader flagged only in `init.sh`** — `skill/ccpm/references/scripts/validate.sh` line 19 checks `[ -d ".claude/rules" ] && echo "✅ Rules directory exists" || echo "⚠️ Rules directory missing"`, and line 93 tells the user to run `/pm:clean` on failure — both are leftovers from the pre-Skill `.claude/commands` plugin architecture: `.claude/rules` is never created or read by any current-architecture reference doc, and `/pm:clean` is old slash-command syntax with no equivalent anywhere in this skill. Every fresh-project run of `validate.sh` will therefore print a spurious "⚠️ Rules directory missing" warning and, on any real warning, point the user at a command that doesn't exist. This deepens the report's existing "init.sh is stale" weakness into a pattern: at least three of the fourteen scripts/docs (`init.sh`, `help.sh`, `validate.sh`) still carry dead references to the retired plugin surface.

3. **Circular-dependency detection is asserted in prose but implemented nowhere** — `skill/ccpm/references/structure.md` line 105: `"Circular dependencies are an error — check before finalizing."` No script actually walks the `depends_on` graph for cycles: `validate.sh` (the only script that inspects `depends_on` for correctness) only checks that referenced task files *exist* (lines 42-61), never whether following the edges loops back on itself, and `next.sh`/`blocked.sh` only read one level of `depends_on` per task, never chase the chain. A task set with `001.md depends_on [002]` and `002.md depends_on [001]` would pass `validate.sh` cleanly and simply never appear in `next.sh`'s output, with no diagnostic pointing at why. This is a gap in the same family as the report's other "prose rule with no backstop" findings (repo-safety check, `--force` ban, sync-marker dedup) but wasn't called out — it's arguably the most consequential one, since a cycle silently deadlocks the whole task queue rather than just risking a policy violation.
