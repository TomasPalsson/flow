# superpowers

## What it is

`obra/superpowers` (author Jesse Vincent) is a Claude Code plugin: a library of ~15 Markdown "skills" plus a SessionStart hook, shell scripts, and prompt templates that impose a specific software-development methodology (brainstorm → spec → plan → TDD → subagent-per-task execution → review → finish) on every coding task the agent does. It installs as a Claude Code plugin (also ported to Cursor, Codex, Gemini, Antigravity, Devin, Kimi, OpenCode, Pi, Hermes). No GitHub star count shown in the local clone. Last commit: `Wed Aug 12 09:53:21 2026 -0700` (`git log -1 --format=%cd` in `/tmp/.../scratchpad/repos/superpowers`).

## Workflow it implements

1. **SessionStart hook** (`hooks/session-start`) fires on `startup|clear|compact` and injects the *entire* `skills/using-superpowers/SKILL.md` (63 lines / 485 words) into context as `<EXTREMELY_IMPORTANT>` — a hardcoded rule that skill-checking must happen before any response, including clarifying questions.
2. **using-superpowers** (the injected skill) tells the model: if any skill might apply, invoking it is mandatory, not optional; process skills (brainstorming, systematic-debugging) take priority over implementation skills; lists 11 "Red Flag" rationalizations to preempt ("this is just a simple question", "I need more context first", etc.).
3. **brainstorming** — classifies every request into Spike / Bounded / Architectural (heavier path wins ties; can only escalate mid-task, never downgrade). A `<HARD-GATE>` blocks any code/implementation action until the human explicitly approves the stated intent, on every path. Architectural path: explore → offer visual companion just-in-time → clarifying Qs one at a time → propose 2-3 approaches → present design in sections with approval per section → write spec to `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md` → self-review (placeholder/consistency/scope/ambiguity scan) → user reviews the file → hand off to writing-plans (and ONLY writing-plans).
4. **writing-plans** — turns the spec into `docs/superpowers/plans/YYYY-MM-DD-<feature-name>.md`, a task-by-task plan written for "an engineer with zero context and questionable taste." Fixed header format, per-task Files/Interfaces/numbered checkbox steps (write failing test → verify fail → minimal impl → verify pass → commit), a "No Placeholders" ban list, and a self-review pass. Ends by offering a choice: subagent-driven-development (same session, fresh subagent/task) vs executing-plans (separate session, inline batch execution).
5. **subagent-driven-development** (568 lines, the core engine) — for each task: dispatch an isolated implementer subagent with only a task brief (never the whole plan or session history) → implementer self-reviews, commits, reports one of 4 statuses (DONE / DONE_WITH_CONCERNS / BLOCKED / NEEDS_CONTEXT) → controller generates a diff "review package" and dispatches a fresh task-reviewer subagent that returns spec-compliance + quality verdicts → a bounded fix loop (max 5 rounds: rounds 1-3 resume the same implementer, rounds 4-5 escalate to a fresh implementer on a more capable model) with scoped re-reviews → a "breaker" that forces the controller to adjudicate (fix / park-with-ruling) once the loop caps out, never silently discard → progress tracked in a per-plan ledger file (`.superpowers/sdd/<plan-slug>/progress.md`) that survives context compaction → after all tasks, one final whole-branch review on the most capable model, one fix wave, one scoped re-review → workspace deleted, decisions summarized as "Rulings I made" → hands off to finishing-a-development-branch.
6. **finishing-a-development-branch** — verify full test suite green, detect worktree vs normal repo, present a fixed menu of integration options (merge/PR/etc.), execute choice, clean up.
7. Cross-cutting skills invoked throughout: **test-driven-development** (Iron Law: no production code without a failing test first — "delete means delete" if code was written before the test), **systematic-debugging** (Iron Law: no fixes without root-cause investigation; 4 phases: root-cause → pattern analysis → hypothesis/test → implementation; escalates to "question the architecture" after 3 failed fixes), **verification-before-completion** (Iron Law: no completion claim without fresh command output in the same message — bans "should pass"/"looks correct" language), **requesting-code-review** (templated reviewer dispatch, Critical/Important/Minor severity buckets), **using-git-worktrees** (detect existing isolation → prefer native worktree tool → git fallback → verify `.gitignore` → baseline test run).

## Artifacts it produces

- **Design spec**: `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md` (architectural path only), committed to git, reviewed by the user before planning starts.
- **Implementation plan**: `docs/superpowers/plans/YYYY-MM-DD-<feature-name>.md`. Mandatory header:
  ```markdown
  # [Feature Name] Implementation Plan

  > **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

  **Goal:** [One sentence describing what this builds]
  **Architecture:** [2-3 sentences about approach]
  **Tech Stack:** [Key technologies/libraries]
  **Spec:** [path to the spec/design doc this plan implements ...]

  ## Global Constraints
  [project-wide requirements copied verbatim from the spec]
  ---
  ```
  Each task then follows:
  ```markdown
  ### Task N: [Component Name]
  **Files:** Create/Modify/Test: exact paths
  **Interfaces:** Consumes / Produces (exact signatures for the next task's implementer)
  - [ ] **Step 1: Write the failing test**
  - [ ] **Step 2: Run test to verify it fails**
  - [ ] **Step 3: Write minimal implementation**
  - [ ] **Step 4: Run test to verify it passes**
  - [ ] **Step 5: Commit**
  ```
- **Per-plan workspace** (git-ignored, deterministic path): `.superpowers/sdd/<plan-basename>/` — created by `skills/subagent-driven-development/scripts/sdd-workspace`. Holds `progress.md` (the ledger, first line `# SDD ledger — plan: <plan file path>`), `task-N-brief.md` (from `scripts/task-brief`), `task-N-report.md` (implementer writes here), `review-<base7>..<head7>.diff` (from `scripts/review-package`). Deleted once the final review is clean — "the git history is the record now."
- **Review verdicts**: fixed template in `skills/requesting-code-review/code-reviewer.md` — sections `### Strengths / ### Issues (#### Critical / #### Important / #### Minor) / ### Recommendations / ### Assessment (Ready to merge? Yes|No|With fixes)`.
- **Ledger ruling lines**: `Ruling: <what you decided> — <why> — <what it costs if wrong>`, `Task <N>: complete (commits <a7>..<b7>, review clean)`, `Task <N>: fix round <R>/5 (...)`, `Task <N>: parked — <finding> — Ruling: <why the code stands>`.

## Deterministic vs prompt

| Mechanism | Enforced by script/hook/CLI | Asked of the model in prose |
|---|---|---|
| Injecting the master skill-usage rule every session | `hooks/session-start` (bash, SessionStart hook, `hooks/hooks.json`) — deterministic | — |
| Where a plan's scratch artifacts live (one dir per plan) | `scripts/sdd-workspace` (bash: `mkdir -p`, writes `.gitignore`) | — |
| Extracting one task's text from the plan file | `scripts/task-brief` (awk fence-aware scan for `# Task N` heading) | — |
| Building the reviewer's diff package (commits/stat/diff) | `scripts/review-package` (`git log`/`git diff --stat`/`git diff -U10` to a file) | — |
| Whether BASE is correct (never `HEAD~1`) | scripts require explicit BASE arg + `git rev-parse --verify` | Controller is *told* in prose never to use `HEAD~1` — not code-enforced |
| Whether a skill actually gets invoked when relevant | — | 100% prose ("Red Flags" table, `<EXTREMELY-IMPORTANT>` tags, "not negotiable") — no hook blocks a response that skips a skill |
| Brainstorming approval gate before implementation | — | Prose `<HARD-GATE>`; nothing technical prevents the model from writing code anyway |
| TDD "write test first" | — | Prose Iron Law + "delete means delete"; no pre-commit hook checks test-before-code ordering |
| Fix-loop round cap (5) and escalation to fresh implementer | — | Prose process description; controller counts rounds itself in the ledger, nothing enforces the count |
| Model selection per role (cheap/standard/most-capable) | — | Prose "Model Selection" section; dispatch calls are manual, no wrapper forces a model param |
| Verification-before-completion ("run it fresh, in this message") | — | Prose Iron Law + rationalization table; nothing checks that a command was actually run before the claim |
| Ledger bookkeeping / ruling capture | — | Prose instruction ("a silent discard is forbidden"); no code parses/validates the ledger |
| Worktree isolation | Falls back to `git worktree add` / `git check-ignore` (bash) if no native tool | Prose decides *whether* to ask for consent and which directory to prefer |

Net: the plugin's only genuinely deterministic pieces are the SessionStart injection and three small bash/awk scripts that manage file paths and diffs. Every actual behavioral rule (gates, review loops, TDD order, verification, model choice, ledger discipline) is enforced purely through prompt engineering — repetition, named "Iron Laws," pre-empted rationalization tables, and severe/urgent language (`<EXTREMELY_IMPORTANT>`, `<HARD-GATE>`).

## Mechanisms worth stealing

1. **SessionStart skill-index injection** — `hooks/session-start` + `hooks/hooks.json` (`SessionStart` matcher `startup|clear|compact`). Problem solved: agents forget which conventions/skills exist once context resets; this guarantees a compact "how to use skills" primer is present at the start of every fresh session without the user having to say anything. Snippet: `session_context="<EXTREMELY_IMPORTANT>\nYou have superpowers.\n\n**Below is the full content of your 'superpowers:using-superpowers' skill...**\n\n${using_superpowers_escaped}\n</EXTREMELY_IMPORTANT>"`. For a solo dev's dotfiles harness: a personal SessionStart hook that injects a short "how I like changes made" or "check CLAUDE.md/these 3 skills before touching X" primer — cheap (63 lines here), high leverage, and doesn't require re-explaining preferences every session.

2. **Deterministic diff/brief packaging via tiny scripts, not prose** — `skills/subagent-driven-development/scripts/{sdd-workspace,task-brief,review-package}`. Problem solved: LLM controllers routinely get the base commit wrong (`HEAD~1` truncates multi-commit tasks), paste huge diffs into their own context, or drift on where scratch files live. `review-package` script: `git log --oneline "${base}..${head}"`, `git diff --stat`, `git diff -U10`, all written to a uniquely named file so "The output never enters your own context." For a dotfiles harness: any workflow that dispatches subagents/reviewers should hand off a *file path* built by a real script, not ask the model to remember to run the right git command with the right range.

3. **Per-plan git-ignored workspace with a resumable ledger** — `scripts/sdd-workspace` creates `.superpowers/sdd/<plan-basename>/`, self-writes its own `.gitignore`, and the SKILL.md instructs: "the ledger is your recovery map... after compaction, trust the ledger and `git log` over your own recollection." Problem solved: context compaction/loss causes a controller to redo already-completed work — "the single most expensive failure observed." For a solo dotfiles harness: any long-running multi-step agent task benefits from a durable, path-namespaced progress file that's checked at start and trusted over conversational memory.

4. **Bounded fix-loop with a hard escalation ladder and a mandatory adjudication step ("the breaker")** — `skills/subagent-driven-development/SKILL.md` §"The fix loop": rounds 1-3 resume the same implementer, rounds 4-5 dispatch a fresh implementer on a stronger model, and at round 5 the controller must explicitly adjudicate every open finding (fix, or park with a written ruling) rather than loop forever or silently drop findings. "A loop that survives three resumes usually means the implementer cannot see its own problem — fresh eyes and a capability bump in one move." Worth stealing as a *pattern*: any self-correcting agent loop should have (a) a finite round cap, (b) an explicit escalation trigger partway through, and (c) a terminal state that forces a recorded decision instead of infinite retries or quiet abandonment.

5. **Task brief isolation — a subagent never sees the whole plan** — "Never make a subagent read the whole plan file" (`SKILL.md` line ~262); `task-brief` extracts just one `### Task N` section. Problem solved: pasting accumulated history into every dispatch (one real session hit "42k chars of which 99% was pasted history") bloats cost and lets a subagent drift on scope. For a personal harness dispatching subagents (e.g. via `Bash`/`SendMessage` to other Claude sessions), always hand a scoped, single-purpose brief file rather than the full task/spec/conversation.

6. **Fixed severity-bucketed review template with an explicit merge verdict** — `skills/requesting-code-review/code-reviewer.md`: `### Strengths / #### Critical (Must Fix) / #### Important (Should Fix) / #### Minor (Nice to Have) / ### Assessment: Ready to merge? [Yes|No|With fixes]`. Problem solved: unstructured review prose is hard to act on programmatically or triage quickly. Directly reusable as a prompt template for any `/code-review`-style skill in a dotfiles CLAUDE.md or slash-command.

7. **Rationalization tables ("Red Flags" / "Common Rationalizations")** appearing in nearly every skill (e.g. `using-superpowers/SKILL.md` lines 37-50, `systematic-debugging/SKILL.md` "Red Flags — STOP and Follow Process," `verification-before-completion/SKILL.md` "Rationalization Prevention"). Problem solved: models rationalize skipping process under time pressure ("just this once," "I'm confident," "should work now"); naming the exact excuse in advance and pairing it with the counter-reality is a cheap, durable prompt-engineering pattern. Directly portable to any personal CLAUDE.md rule the user wants strictly followed (e.g. "always commit only what was asked").

8. **"Iron Law" framing + one-line falsifiable gate function** — `systematic-debugging` and `verification-before-completion` both open with a boxed one-liner (`NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST`, `NO COMPLETION CLAIMS WITHOUT FRESH VERIFICATION EVIDENCE`) followed by a concrete "Gate Function" (`IDENTIFY → RUN → READ → VERIFY → ONLY THEN claim`). This is a reusable prose-only pattern for a personal harness: define the non-negotiable rule as one falsifiable sentence, then give the exact 4-5 step procedure that operationalizes it, rather than a vague admonition.

## Weaknesses / ceremony cost

- **Lines loaded per session automatically:** 63 lines / 485 words of `using-superpowers/SKILL.md` injected at every `startup|clear|compact` (small, cheap). But once any skill is actually invoked, the cost balloons: `subagent-driven-development/SKILL.md` alone is 568 lines; `writing-skills/SKILL.md` 679 lines; `test-driven-development` 320; `systematic-debugging` 283; `brainstorming` 250 — a single architectural task can pull 1,000+ lines of skill prose into context across brainstorming → writing-plans → subagent-driven-development, on top of every task-brief, review-package, and report file generated along the way.
- **Number of gates:** brainstorming's `<HARD-GATE>` (human approval before any implementation, on every path including "bounded"), spec self-review, user-reviews-spec gate, plan self-review, per-task spec+quality review, up-to-5-round fix loop with re-review each round, a breaker adjudication, a final whole-branch review, then finishing-a-development-branch's own test-verification + menu gate. For a solo dev doing small changes this is heavy ceremony — the skill's own "bounded" path exists specifically to cut spec/plan overhead for small tasks, and even that still requires a human "yes" before any code.
- **Everything the model can silently skip:** because virtually every rule above is prose-only (see the Deterministic-vs-prompt table), nothing structurally stops an agent from: skipping the `using-superpowers` skill-check discipline after the initial injection scrolls out of the effective context window; writing code before a failing test (TDD Iron Law); claiming "tests pass" without literally re-running them in the same message; silently discarding a Minor/Important review finding instead of logging it to the ledger; using `HEAD~1` instead of the recorded BASE; omitting the `model:` field on a subagent dispatch (which "silently defeats" the whole cost-tiering scheme, per its own SKILL.md); or a subagent spawning its own reviewer/helper despite being told repeatedly not to (the skill explicitly calls this out as an observed real-world failure — "It's a duplicate seat reviewing the same diff"). The framework is aware of most of these failure modes (it documents them as anti-patterns/rationalizations) but has no code-level enforcement for any of them beyond the three small path-management scripts.
- **Compaction fragility acknowledged but only partially mitigated:** the ledger is explicitly designed around "conversation memory does not survive compaction," and the docs cite re-dispatching whole completed task sequences as "the single most expensive failure observed" — i.e., the framework itself documents that its core state (todos, session narrative) is not durable, and papers over it with a ledger file that the controller must remember to read and trust, which is again a prose-only obligation.

## Plugin/packaging structure

- Primary manifest: `.claude-plugin/plugin.json` — `{name: "superpowers", version: "6.3.0", author: Jesse Vincent, keywords: [skills, tdd, debugging, collaboration, best-practices, workflows]}`.
- Marketplace listing: `.claude-plugin/marketplace.json` (`superpowers-dev` marketplace, one plugin entry, `source: "./"`), matching the README's install commands (`/plugin marketplace add obra/superpowers-marketplace`, `/plugin install superpowers@superpowers-marketplace`, or the official Anthropic marketplace `superpowers@claude-plugins-official`).
- Hook registration: `hooks/hooks.json` registers a single `SessionStart` hook (`matcher: "startup|clear|compact"`) that runs `"${CLAUDE_PLUGIN_ROOT}/hooks/run-hook.cmd" session-start` via bash. `hooks/session-start` is a portable bash script that detects the calling harness (`CURSOR_PLUGIN_ROOT`, `CLAUDE_PLUGIN_ROOT`, `COPILOT_CLI`) and emits the harness-appropriate JSON field name (`additional_context` / `hookSpecificOutput.additionalContext` / `additionalContext`) — one script, three output dialects.
- Skills ship as plain directories under `skills/<name>/SKILL.md` (+ optional `scripts/`, reference `.md` files, prompt templates) discovered by the harness's native Skill mechanism — no separate skill-registration manifest.
- Multi-harness packaging: separate plugin manifests per target — `.codex-plugin/plugin.json`, `.cursor-plugin/plugin.json`, `.devin-plugin/plugin.json`, `.kimi-plugin/plugin.json`, `.hermes-plugin/plugin.yaml` (+ `__init__.py`), `.pi/extensions/superpowers.ts`, `.opencode/plugins/superpowers.js`, `gemini-extension.json`/`GEMINI.md` — plus sync/packaging scripts (`scripts/sync-to-codex-plugin.sh`, `scripts/package-codex-plugin.sh`, `scripts/bump-version.sh`) and a matching `tests/<harness>/` suite per target, showing this is actively maintained as a genuinely cross-agent-runtime product, not just a Claude Code plugin.
- No npm package; distribution is git-clone-and-register-marketplace, or per-harness native extension mechanisms.

## Second-reader additions

1. **Repo self-testing with ShellCheck + a real assertion suite** — `scripts/lint-shell.sh` runs `shellcheck` (`--severity=warning --external-sources --source-path=SCRIPTDIR`, plus a `--strict` set of extra checks: `check-extra-masked-returns,check-set-e-suppressed,quote-safe-variables,deprecate-which,avoid-nullary-conditions`) over changed/tracked shell scripts, and `tests/shell-lint/test-lint-shell.sh` (179 lines) exercises that linter itself with `pass`/`fail`/`assert_contains`/`assert_not_contains` helpers against synthetic git repos and stub tools. There's a matching `tests/` suite per mechanism (`tests/hooks/test-session-start.sh`, `tests/systematic-debugging/test-find-polluter.sh`, `tests/version-bump/`, `tests/codex-plugin-sync/`, `tests/writing-skills/`). The report's "Net:" line (only the SessionStart hook + 3 scripts are deterministic) is accurate for what governs the *user's coding task at runtime* — but for the plugin's own development this is a fourth category of genuinely deterministic enforcement (CI-grade lint + test assertions on the plugin's bash) that's worth stealing on its own: a dotfiles repo's own scripts (`easycommit`, `new-project`, `aws-profile`, `run-maintenance`, `goto`) could get the same `shellcheck`-plus-assertion-tests treatment instead of relying on manual review.

2. **`receiving-code-review` skill — a banned-phrase list for sycophancy, not just for the model giving reviews but for receiving them** (`skills/receiving-code-review/SKILL.md`, 205 lines, not cited anywhere in the main report): a `## Forbidden Responses` section literally bans `"You're absolutely right!"`, `"Great point!"` / `"Excellent feedback!"`, and `"Let me implement that now"` (before verification), replacing them with a `READ → UNDERSTAND → VERIFY → EVALUATE → RESPOND → IMPLEMENT` pattern that explicitly permits "reasoned pushback" against a reviewer's suggestion. Problem solved: models default to performative agreement with any feedback (including a human's), which both wastes a turn and can implement bad suggestions uncritically. Directly portable to a personal CLAUDE.md rule for how the agent should respond to the *user's* corrections, not only to a peer reviewer's.

3. **`dispatching-parallel-agents` skill — an explicit decision graph for parallel vs. sequential subagent dispatch, separate from `subagent-driven-development`'s single-task-at-a-time model** (`skills/dispatching-parallel-agents/SKILL.md`, 167 lines, not cited in the main report). A `dot`-diagram decision tree (`Multiple failures?` → `Are they independent?` → `Can they work in parallel?`) gates when to fan out, and the mechanical trigger for parallelism is concrete and copy-pasteable: "Issue all three subagent dispatches in the same response — they run in parallel... Multiple dispatch calls in one response = parallel execution. One per response = sequential." `subagent-driven-development` by contrast is deliberately sequential (one task, one implementer, one reviewer at a time) — this is a genuinely different, complementary pattern for independent/parallelizable work (e.g., N unrelated failing test files) that a dotfiles harness dispatching multiple Claude sessions could reuse verbatim as the trigger rule for "when do I fan out vs. go one at a time."

## Verdict: adopt / borrow parts / ignore

**Borrow parts, don't adopt wholesale.** For a solo dev's personal dotfiles harness, the full ceremony (spec files, plan files, per-task subagent dispatch with 5-round fix loops, ledgers, ...) is built for a team/enterprise-scale "junior engineer with poor taste" mental model and is overkill for one person iterating on their own tools — the repo's own README pitches it as "a complete software development methodology," and its weight shows in the gate count above.

What *is* directly worth adopting into this dotfiles repo's Claude Code config:
- The **SessionStart hook pattern** (`hooks/hooks.json` + a small bash script) to inject a short, stable primer at session start — this repo already has `claude/.claude/CLAUDE.md` but no SessionStart hook; a compact injected reminder (not the full ceremony) is cheap and effective.
- The **deterministic-scripts-over-prose** pattern (`sdd-workspace`, `task-brief`, `review-package`) for anything that dispatches subagents from this environment: build a tiny script that packages a diff/context to a file path rather than trusting the model to run the right git range every time.
- The **code-reviewer prompt template** (Strengths/Critical/Important/Minor/Assessment) is a good drop-in for a personal `/review` or `/code-review` skill.
- The **rationalization-table / Iron-Law framing** as a prose technique for any rule the user wants strictly enforced (e.g., in this repo's existing skills like `impeccable` or a future `dotfiles-reviewer` agent).

What to skip: the full spec→plan→subagent-driven-development pipeline with its many hard gates, ledger discipline, and 5-round fix loops — that's disproportionate ceremony for personal dotfiles/tooling work, and (per the Weaknesses section) its enforcement is almost entirely prose-based prompt engineering rather than anything structurally guaranteed, so adopting it wholesale buys process weight without buying reliability guarantees.
