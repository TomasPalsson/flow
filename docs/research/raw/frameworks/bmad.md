# bmad

## What it is

BMAD-METHOD (bmad-code-org/BMAD-METHOD, v6.12.0) is a multi-agent AI-development framework packaged as a Claude Code plugin: it ships a set of named personas (Analyst, PM, Architect, UX, Amelia the dev) plus a chain of skills for planning (PRD, architecture, epics/stories), building (spec → implement → review → present), and shipping (retrospective, sprint status, code review). The v6 rewrite abandoned the old monolithic-persona-file style (still present as deprecated "v6-shims") for a **Claude Code Skills** architecture: every capability is a `SKILL.md` plus small step-files, rendered per-project through a Python templating/merge layer.

## Workflow it implements (actual sequence, as coded)

Top-level plugin registers 5 agents + ~19 plan/ship skills + 8 core skills (`.claude-plugin/plugin.json`). The core implementation loop (`bmad-agent-dev` → `bmad-build`) is:

1. **Agent activation** (`src/bmm-skills/agents/bmad-agent-dev/SKILL.md`, 76 lines): resolve a layered TOML persona block via `resolve_customization.py`, adopt persona, load config, greet, present a menu (`BD`=build, `QA`, `CR`=code-review, `SP`=sprint-planning, `ER`=retrospective).
2. **`bmad-build` dispatch** (`SKILL.md`, 13 lines): runs `render_skill.py --project-root … --skill …` once, which resolves `customize.toml` overrides and rewrites `[[bmad-snapshot:*.md]]` includes into an immutable, hash-verified per-project snapshot, then prints the single instruction to follow `workflow.md`.
3. **`workflow.md`** (84 lines) — activation hooks, "READY FOR DEVELOPMENT" and "SCOPE" standards (900–1600 token spec target), step-file architecture rules ("NEVER load multiple step files simultaneously"), then jumps to `step-01-clarify-and-route.md`.
4. **Step 1 — Clarify & route** (100 lines): resolve existing workflow state (explicit arg → recent conversation → scan artifacts+ask), VCS sanity check (dirty tree/branch mismatch → HALT), multi-goal split check, set `spec_file`.
5. **Step 2 — Plan** (62 lines): investigate codebase (delegate deep search to subagents), classify Intent gaps / Irreversibles / Footprint; trivial change → `route:'oneshot'` (skip most sections) else write a full spec from `spec-template.md`; self-review against the READY standard; **CHECKPOINT 1**: token-count gate + Open-Questions gate, HALT for human "Approve and continue / Approve and stop / Review spec".
6. **Step 3 — Implement** (51 lines): capture `baseline_commit`, dispatch a context-free implementation subagent with only the spec (`implementation_handoff` from `customize.toml`), then re-derive a unified diff and verify every task/AC and every I/O-matrix row against it (not against the subagent's self-report).
7. **Step 4 — Review** (85 lines): stage the diff once; launch **N review layers in parallel as context-free subagents** (Blind Hunter, Edge Case Hunter, Verification Gap Reviewer by default); classify every finding into `high/medium/low/false/maybe-false`, group by shared root cause, route to `intent_gap` (loop to step-02) / `bad_spec` (loop to step-03) / `patch` (auto-fix, re-engage the same implementation subagent) / `defer` (append to `deferred-work.md`); cascading loopback capped at 5 iterations then HALT.
8. **Step 5 — Present** (43 lines): mark spec `done`, sync `sprint-status.yaml`, commit locally (never push), print a 1–2 sentence summary, offer PR/next-step.
9. **`step-oneshot.md`** (107 lines) is a fast-path collapsing implement+review+present for small changes routed at step 2.

Parallel skills follow the identical step-file + `[[bmad-snapshot:]]` + `customize.toml` pattern: `bmad-create-epics-and-stories` (4 steps, 1096 lines total, generates `epics.md` from PRD/architecture/UX), `bmad-sprint-planning` (delegates state math to a 697-line Python script, `sprint_plan.py`, with a 524-line pytest suite), `bmad-review` (a generic multi-lens reviewer reused by both `bmad-build` and `bmad-code-review`), `bmad-party-mode` (multi-agent roundtable).

## Deterministic vs prompt

| Mechanism | Enforced by script/CLI | Asked of the model in prose |
|---|---|---|
| TOML layer merge (base→team→user) | `src/scripts/config_utils.py` + `resolve_customization.py` (Python, `tomllib`) | fallback path: SKILL.md tells the model to "resolve yourself" by reading the 3 files in order if the script fails |
| Skill snapshot rendering (`[[bmad-snapshot:]]` includes, `{workflow.*}` substitution) | `render_skill.py` (401 lines; SHA-256 hash-verified snapshot) | — |
| Sprint status parsing/generation, drift detection, atomic write | `sprint_plan.py` (697 lines + regex `EPIC_RE`/`STORY_RE`; atomic temp-file+fsync+os.replace) | which files count as "epics" (explicitly carved out as model judgment in the script's own docstring) |
| Diff staging for review | "use the repository's version-control tooling ... write a unified diff" | model executes the VCS command itself — no wrapper script |
| Finding verdict (`high/medium/low/false/maybe-false`) and routing (`patch/defer/intent_gap/bad_spec`) | none — pure prose rubric in `step-04-review.md` | entirely the model's judgment call, self-graded |
| "Return ONLY your findings, don't spawn subagents, don't call tools" (reviewer isolation) | none — a sandboxing *request*, not an enforced boundary | prose instruction only |
| Token-count gate (900–1600), multi-goal split gate | none | model estimates and self-reports; "Neither limit is a gate... both are proposals with user override" |
| HALT/checkpoint gates (VCS dirty tree, open questions, review-loop iteration cap of 5) | loop-count check is explicit ("read `review_loop_iteration`... If it exceeds 5, HALT") | everything else is the model choosing to stop and ask |

## Mechanisms worth stealing

1. **Layered, deterministically-merged customization (`customize.toml` → `_bmad/custom/*.toml` → `*.user.toml`)** — solves "how do I let a team and an individual both override a shared workflow without forking it." `src/scripts/resolve_customization.py`, `src/bmm-skills/agents/bmad-agent-dev/customize.toml`. Quoted merge rule: *"Scalars override, tables deep-merge, arrays of tables keyed by `code` or `id` replace matching entries and append new entries, and all other arrays append."* — For a solo-dev dotfiles harness: a single `~/.claude/skills/<skill>/customize.toml` with an optional per-project override file gives per-repo behavior (e.g. different review strictness) without editing the shared skill.

2. **Just-in-time step-file loading with a single "current step" rule** — solves prompt bloat: a 5-step workflow never puts more than ~50–100 lines of instruction in front of the model at once instead of one 1000+ line persona file (the deprecated `bmad-create-story` v6-shim is exactly that anti-pattern, 440 lines of nested `<step>/<action>/<check>` XML in one file). `src/bmm-skills/ship/bmad-build/workflow.md`: *"Micro-file Design: Each step is self-contained and followed exactly... NEVER load multiple step files simultaneously."* Directly portable to any multi-step Claude Code skill: split a long SKILL.md into `step-NN-*.md` and have each end with "Read fully and follow `step-N+1.md`".

3. **Context-free adversarial review subagents with a structured verdict/routing rubric** — solves reviewer sycophancy and self-grading: each reviewer sees only the diff (no conversation history), and a separate triage pass re-verifies every claim before it counts. `src/bmm-skills/ship/bmad-build/step-04-review.md`: *"Disregard any severity a reviewing subagent assigned — they lack the context to grade"* and the `false`/`maybe-false`/`high/medium/low` rubric with `patch/defer/intent_gap/bad_spec` routing. Fits a solo-dev harness as a generic `/review-diff` skill: spin up 2–3 fresh-context subagent reviews of a diff, then a triage pass that must re-locate each claim in the code before accepting it.

4. **The spec as a single mutable state machine with a frozen human-approved core** — solves "the plan drifts from what was approved." `<frozen-after-approval reason="human-owned intent — do not modify unless human renegotiates">` around `## Intent` in `spec-template.md`; every later step (`step-03`, `step-04`) explicitly checks "Content inside `<frozen-after-approval>`... is read-only." Directly reusable pattern for any spec-driven coding skill, independent of BMAD.

5. **Cached, purpose-distilled context files with explicit invalidation** — solves re-reading the whole PRD/architecture on every story. [CORRECTED: the validity-check quote is misattributed in the original — it is not in `compile-epic-context.md`, it's the caller's cache-check in `src/bmm-skills/ship/bmad-build/step-01-clarify-and-route.md:57`] *"A file is **valid** when it exists, is non-empty, starts with `# Epic <N> Context:` (with the correct epic number), and no file in `{{.planning_artifacts}}` is newer."* The "describe by purpose, not by source" rule is correctly attributed to `compile-epic-context.md:51` and quoted accurately: *"Describe by purpose, not by source. 6. **Offloading state bookkeeping to a tested script instead of LLM prose** — `sprint_plan.py` (697 lines) + `test_sprint_plan.py` (524 lines) does epic/story parsing, status merging, and atomic YAML writes deterministically; the model's only judgment call is "which files are epics" (explicitly called out in the script's own docstring). This is the clearest deterministic/prompt split in the repo and the strongest argument for writing small Python/Node helpers for anything state-shaped (status enums, ordering, file writes) rather than asking the model to "read the full file and update the key."

## Weaknesses / ceremony cost

- **Duplicated logic between `step-04-review.md` and `step-oneshot.md`**: the verdict rubric, grouping rule, and routing categories (`patch/HALT/defer` vs `patch/defer/intent_gap/bad_spec`) are re-explained almost verbatim in both files (85 + the tail ~80 lines of a 107-line file) instead of one shared step — a maintenance seam where the two can drift (oneshot's routing is already a simplified 3-way vs the dispatch route's 4-way).
- **Legacy `v6-shims/` directory** (`src/bmm-skills/v6-shims/`, `src/core-skills/v6-shims/`) ships old-style, XML-tag-heavy, emoji-laden verbose workflows (`bmad-create-story`, `bmad-dev-story`, `bmad-document-project`, etc.) purely for backward-compat name resolution — e.g. `bmad-create-story/SKILL.md` is a [CORRECTED: 436-line, not 440-line] single-file with `<action>`/`<check>` nesting and instructions like *"EXHAUSTIVE ANALYSIS REQUIRED... do NOT be lazy or skim! This is the most important function in the entire development process!"* — the kind of prose-as-enforcement ceremony the v6 rewrite otherwise eliminated. Two parallel implementations of "create a story" now ship in the same plugin.
- **Gate density**: a full `bmad-build` dispatch run has at minimum: VCS dirty-tree HALT, multi-goal-split HALT, token-count gate, Open-Questions HALT, CHECKPOINT 1 (3-way human choice), a review-loopback cap (5 iterations) — six distinct places a human decision can block a fully automated run. None are optional in the `dispatch` route; only `route:'oneshot'` (small changes) skips most of them.
- **Reviewer isolation is a prompt, not a sandbox**: *"Do not invoke any skill, and do not spawn subagents of your own... do not route them through any findings-reporting tool the host may offer"* is pure instruction to the subagent — nothing in the harness actually prevents a reviewer subagent from calling a tool or another skill.
- **Runtime dependency weight**: nearly every mechanism (`resolve_customization.py`, `render_skill.py`, `sprint_plan.py`) requires `uv` + Python 3.11 (`tomllib`) present in the *target* project, not just where BMAD is installed — a Node/Rust-only repo now needs a Python toolchain solely to run BMAD's own bookkeeping scripts.
- **Installer/packaging is large**: `tools/installer/` is ~16,000 lines of JS across module resolution, IDE integration, channel/version resolution, manifest generation — substantial infrastructure to adopt just to get the skill files onto disk.

## Plugin/packaging structure

- Installs as a **Claude Code plugin** via `.claude-plugin/plugin.json`: one plugin (`bmad-method-analyze-plan-build`, v6.12.0) whose `skills` array lists ~27 skill directory paths (5 `bmm-skills/agents/*`, 14 `bmm-skills/plan|ship/*`, 8 `core-skills/*`) — each path is a folder containing `SKILL.md` (+ `customize.toml`, `references/`, `scripts/`, `assets/`, `review-prompts/`).
- A separate `bmad-modules.yaml` at repo root is the installer's **module registry** (`marketplace-plugin`, `default_channel: stable|next`, `deprecated`/`deprecation-message`, `post-install-message`, `aliases`) — decoupled from the plugin manifest, used by `tools/installer/modules/official-modules.js` (2289 lines) for a picker UI across multiple modules (bmm, other domains not explored here).
- `tools/installer/` (Node.js, ~16k lines) is the actual CLI: `bmad-cli.js` entry point, `core/installer.js` (1823 lines) does the file copy/manifest work, `ide/_config-driven.js` + `ide/manager.js` + `ide/platform-codes.yaml` (363 lines) handle per-IDE integration (Claude Code, Cursor, etc.), `core/manifest.js`/`manifest-generator.js` track installed-file provenance for clean upgrades/uninstalls.
- No git hooks or CI hooks are registered by the framework itself into the *consumer* repo; `.husky/` in the BMAD repo is for BMAD's own dev workflow, not something it installs downstream. Runtime "hooks" are purely the skill-internal `activation_steps_prepend/append` lists in each `customize.toml`.

## Second-reader additions

1. **Loopback re-verification skip via a "carried" verdict** — solves reviewer cost blowup on multi-round loopbacks: once a finding has been triaged, a later review pass in the same loop doesn't re-verify it from scratch. `src/bmm-skills/ship/bmad-build/step-04-review.md:33`: *"If `## Review Triage Log` already has rows — a loopback or a resumed review — check each finding against them first. Same location and same claim as a logged row, and the code there still reads as the row describes: keep the row's verdict and route, write the row again with `carried` in front of the evidence, skip verification, and never patch or defer it again."* Cheap, generalizable pattern for any iterative-review skill: persist a triage log, and treat an unchanged finding as settled rather than re-litigating it every loop.

2. **Evidence-gathering and state-mutation deliberately split across a human-confirmation boundary, inside one script call** — `src/bmm-skills/ship/bmad-retrospective/SKILL.md:94`, describing the `sprint_status.py update --set-action-status` call: *"Where the Phase 4 follow-through has evidence a *previous* epic's action item landed, offer `--set-action-status` and pass only the transitions the user confirms — the evidence justifies proposing a transition, and only the user's confirmation justifies writing it; a headless run records the transitions it would have proposed and does not pass the flag at all."* This is a sharper version of BMAD's general human-gate pattern: the model is trusted to *detect* evidence automatically, but the mutating flag is only ever passed with a per-item user-approved subset — headless mode makes this concrete by recording what it *would* have proposed rather than writing anything. Worth stealing for any skill that both infers status and persists it: separate "what did I notice" (auto) from "what do I write" (gated), and make headless mode a no-write dry-run of the same detection, not a silent auto-approve.

3. **Capability-probed mode selection with silent, single-tier degradation** — `src/core-skills/bmad-party-mode/SKILL.md:43`: *"One mode is active at a time; if its mechanism isn't available in your harness, fall back to `session` without comment."* (`party_mode` picks among `session`/`auto`/`subagent`/`agent-team`, the last two needing real subagent/persistent-team support the host may lack.) Rather than erroring or asking the user to pick a supported mode, the skill always has a zero-dependency floor mode (`session`, "voice every persona inline") that every fancier mode degrades to. Generalizes past party-mode: any skill offering an enhanced-but-optional execution mode (parallel subagents, a specific tool, a host capability) should define the plain fallback in the same file and drop to it quietly rather than failing or nagging.

## Verdict: adopt / borrow parts / ignore

**Borrow parts.** Ignore the installer, the module marketplace, the multi-IDE abstraction layer, and the legacy v6-shims — none of that earns its complexity for a solo-dev dotfiles harness. Adopt, as standalone patterns re-implemented directly in the dotfiles skill set (no BMAD dependency, no `uv`/Python requirement unless already present):

- the step-file-per-turn loading discipline (mechanism 2) — cheapest win, directly cuts prompt tokens per invocation;
- the frozen-intent spec block (mechanism 4) and its self-review checklist ("READY FOR DEVELOPMENT" standard) as a template for any `/feature`- or `/fix`-style skill;
- context-free multi-lens review with re-verification triage (mechanisms 3 and 7) — this is BMAD's most defensible IP and generalizes to any code-review skill;
- offloading state bookkeeping to a small tested script rather than prose (mechanism 6) whenever a skill needs to track status across turns.

Skip the TOML customization-layer machinery (mechanism 1) unless dotfiles skills need per-project overrides distinct from per-user ones — for a single user across their own repos, a simpler single-file config likely suffices and the three-layer merge would be unused ceremony.
