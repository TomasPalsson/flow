## 5. Duplicates what the developer already has

1. **`verifier` substantially overlaps `adversary`'s existing "deterministic sweep."** `agents/adversary.md` step 3 already does: re-run the oracle command itself, count tests executed vs. baseline, grep for `skip`/`xfail`/weakened assertions, and its "Blinding rules" already say to *disregard* the implementer's "tests pass" claims and judge only command output. That is close to the entire job description given to the new `verifier` agent ("re-runs the evidence behind status claims... returns CONFIRMED/UNSUPPORTED"). `developer.md`'s Output contract already requires "actual output (trimmed, not paraphrased)" and forbids fabrication. The synthesis never checks the existing agent files before proposing `verifier` as "the single highest-value addition" — the genuinely new territory is narrower than claimed: catching claims made in the *main* session outside a diff-review pipeline (post-compaction, mid-conversation "tests pass" assertions), not claims inside `/flow`/`ultracode`, which already have this discipline.
2. **`flow`'s own review step (steps/05-verify.md §5.3) already names a "verifier" role** — "scanner ≠ fixer ≠ verifier" is a stated invariant with a separate scorer applying anchors to adversary findings. Introducing a *subagent* also named `verifier` with a different scope (claim-checking, not finding-rescoring) creates a name collision the synthesis doesn't flag: dispatching `agentType: 'verifier'` inside a `/flow` or `/ultracode` Workflow call would be ambiguous against the pipeline's own internal use of the word.
3. **`repro` overlaps `fix`'s existing mandate.** `skills/fix/SKILL.md` already states "NEVER fix without reproducing," drives reproducibility as Step 0/1 of its own workflow, and its description explicitly says it "drives reproducibility... performs root cause analysis." The synthesis justifies `repro` purely from keyword-frequency data (90 hits on "fix") without checking that the `fix` skill already implements reproduction inline — the real, uncredited case for `repro` is context-isolation (keeping log/stack noise out of the main session), not new capability, and the Build list doesn't note that `fix`'s SKILL.md would need editing to actually delegate to `repro` for this to take effect.
4. **`hooks/subagent-log.sh` (`SubagentStop`, log `last_assistant_message`) has no acknowledged relationship to `worklog`**, which the stale `settings.json.bak` shows was previously wired to `PostToolUse`/`Stop`/`SubagentStop`/`SessionEnd`/`UserPromptSubmit` via `worklog hook-run` on a different machine (Mac path `/Users/tomas/...`). The synthesis never checks for a prior/parallel logging mechanism before proposing a new one; if `worklog` is still in use cross-machine, the two could double-log the same events.
