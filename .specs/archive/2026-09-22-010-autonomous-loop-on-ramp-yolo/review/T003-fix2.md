# Fix brief — T003, round 2

Commit 23466c5 closed seven of nine findings with receipts. A fresh verifier reproduced two
Fatals and three Significants that remain or that the fix itself introduced. Same three files,
same rules as `.specs/010-autonomous-loop-on-ramp-yolo/review/T003-brief.md`. One commit.

## Fatal

N1. **Ctrl-C during the control now arms the loop.** `negcontrol.js:86-93`.
    Receipt: SIGINT to the CLI mid-control → exit 0, contract written, "ARMED". Two SIGINTs, same.
    Cause: the handlers are registered only around the after-run, and that whole window is one
    blocking `spawnSync`. Node cannot run a JS signal callback while the loop is blocked; when
    `spawnSync` returns, the `finally` restores and `removeListener` runs synchronously, so the
    queued callback never fires — `process.exit(130)` provably never ran. The handlers are dead
    code AND they suppress Node's default termination. At 8b58659 Ctrl-C killed the process; now
    it is swallowed. This is strictly worse than before the fix.
    Fix direction: the handler sets a flag only. After the `finally` has restored, if a signal was
    seen, print the reason and exit 130 (SIGINT) / 143 (SIGTERM) WITHOUT arming. `runNegControl`
    must never return a verdict `init.js` will arm on after a signal.
    Acceptance: Ctrl-C mid-control exits non-zero and no `loop.md` exists.

N2. **F1a is still open for the case the brief named.** `negcontrol.js:50-52`.
    Receipt: `--verify 'mktemp -u; true' --allow-green` → rc=0 ARMED, 6 runs out of 6. The mktemp
    suffix is 10 mixed-case alphanumerics; `normalizeOutput` only eats `[0-9]+`, so the letters
    always differ → `outputChanged` → arm. The `ponytail:` comment at :48-49 names this gap, but
    the round-1 brief listed a mktemp path as a reproduced failure to CLOSE, so a comment is not
    an acceptable disposition.
    Fix direction: stop hand-rolling normalization. `verify.js`'s `signatureOf` already masks
    volatile tokens for exactly this purpose — reuse it and compare `(rc-class, sig)`. verify.js
    is on `negcontrol.js`'s import allow-list, so this is reuse, not duplication. That also
    dissolves N5 below.
    Acceptance: `mktemp -u; true` returns rc 4 across ~10 consecutive runs.

## Significant

N3. **The dirty check refuses on any untracked file, so the gate cannot run in this repo.**
    `negcontrol.js:37-42`. `init.js:250` runs the verifier once BEFORE the gate at :256, so a
    verifier that writes `build.log` makes the tree dirty before preflight even looks → rc=3
    "the working tree is dirty". A stray `stray.tmp` does it too; the flow repo has six such
    entries right now.
    RULING (recorded in NOTES.md): the dirty preflight is scoped to the TARGET PATH only. The
    break writes one file and the restore is `git checkout -- <that file>`; unrelated tree dirt
    is none of this check's business, and refusing on it makes the safety net unrunnable. Keep
    F3's protection exactly — uncommitted work IN THE TARGET still refuses at exit 3 — and drop
    the whole-tree condition.
    Acceptance: an unrelated untracked file present → the control still runs; uncommitted work in
    the target → still rc 3 with the bytes intact.

N4. **Errors after preflight are reported as exit 3.** `init.js:106-109`. The catch wraps all of
    `runNegControl`. A verifier that deletes the target on its second call gives exit=3, stderr
    `ENOENT: no such file or directory, open '.../app.txt'`, and `git status` shows ` D app.txt`.
    Exit 3 means "input could not be composed, nothing was touched" — here a tracked file is gone,
    and the raw Node message is the very thing F4 complained about.
    Fix direction: tag the preflight's error (e.g. `err.preflight = true`) and map only that to
    exit 3. Anything else is an internal failure with its own code and its own one-line reason.

N5. **Digit normalization added a false-refusal class.** `negcontrol.js:50-52`, `:112`. With the
    same rc on both runs, a numeric-only output difference is invisible:
    `echo "bytes: $(wc -c < app.txt)"; exit 1` → rc=4 refused, and `"0 tests failed"` vs
    `"3 tests failed"` → rc=4 refused. Both armed at 8b58659. It fails closed so it is not worse
    than the original bug, but it defeats the stated purpose of comparing output at all.
    This should fall out of N2's `signatureOf` fix. Confirm it does.
