## What the control is
Before arming an unattended loop, break one tracked file (truncate it), re-run the verifier, and
refuse to arm unless the verifier's result changed. The tree must be byte-identical afterwards on
EVERY path — pass, refuse, error, timeout, Ctrl-C, killed. A loop that arms on a verifier that
cannot fail is the thing this whole feature exists to prevent.

## What the three rounds tried, and why each failed — do not repeat these
1. Process-level `process.on('SIGINT'|'SIGTERM')` handlers that restore and exit. DEAD CODE: Node
   cannot run a JS signal callback while `spawnSync` blocks the thread, and after it returns the
   queued callback never fires. Worse, registering a handler suppresses Node's default termination.
2. An async watchdog shell beside Node polling `kill -0 $PPID`. It OUTLIVED the CLI and reverted the
   operator's next edit to the target a second after exit (5/5). Never run anything concurrently.
3. Hand-written masking regexes on verifier output. Each fixed one direction and broke the other.
   Replaced by the noise measurement above. Do not add a regex.
4. Round 3's synchronous shell — right shape, four bugs, below.

## The four bugs to fix (reproduced by a fresh verifier against d3e3057)

F1 FATAL — the executable bit is lost. negcontrol.js:58-59 restores via temp file + `mv`, which
   creates a new inode with default mode. Commit an executable `run.sh`, `--verify 'test -s run.sh'
   --allow-green` → rc 0 ARMED, mode 100755 → 100644, ` M run.sh`. Node's second restore writes into
   the mv'd inode and keeps 0644. `restored` compares bytes only, so this is silent, on every run.
   Direction: restore IN PLACE (`cat backup > target` keeps inode and mode) and have `restored` check
   mode as well as bytes. Consider backing up the working-tree bytes before the break (e.g. `cp` to a
   `mktemp` file OUTSIDE the repo) and restoring from that instead of `git cat-file`: no git in the
   restore at all, and it also fixes the Improvable below (LFS/CRLF files restored as raw blob bytes).

F2 FATAL (regression) — `--verify-timeout` is not enforced on the broken run. negcontrol.js:63's
   `trap 'exit 143' TERM` makes the shell defer spawnSync's timeout SIGTERM until the foreground
   verifier finishes by itself. Broken-run `sleep 15` with `--verify-timeout 1` took 15.1s (1.1s at
   59ddc8d). A verifier that hangs on the broken tree hangs init forever — breaks spec §5's
   2 × verifyTimeout bound. Direction: a shell only runs a trap between foreground commands, but
   `wait` IS interruptible — run the verifier as `cmd & wait $!`, and in the trap kill the verifier
   (and its group), restore, exit.

W1 FATAL — Ctrl-C leaves the target broken when the CLI returns. A group SIGINT mid-control kills
   Node at once (default disposition); the target is EMPTY when the CLI returns; the wrapper restores
   only when its verifier exits, over whatever the operator wrote meanwhile (0ms write clobbered; a
   jest-style 1.5s graceful shutdown clobbered a write made 0.5s after return). Same root cause for a
   PID-only `kill -TERM <node pid>` from an agent harness or a Python subprocess timeout — delay is
   unbounded because nothing times out the orphaned wrapper.
   Direction: Node must not die before the shell has restored. Ignore SIGINT/SIGTERM in Node for the
   duration of the `spawnSync` ONLY (registering a no-op listener prevents default death — the exact
   property that made attempt 1 harmful is the one you want here), remove the listeners right after.
   The shell receives a group SIGINT too; with F2's `wait` pattern it restores promptly and exits 130,
   and Node reads that from spawnSync's status/signal and exits 130 WITHOUT arming.
   For a PID-only signal to Node: the shell is unaffected and finishes normally, so the tree is safe.
   Preferred: Node then exits 143 without arming. If you prove Node cannot learn of that signal
   synchronously within these three files, arming after it is an ACCEPTABLE documented residual —
   say so in the report; the orchestrator will record a Ruling. SIGKILL is a documented residual.

F3 SIGNIFICANT — Node's second restore can mask a changed tree. It writes `original`, read AFTER the
   before-run (negcontrol.js:128); a before-run that edits the target leaves edits in place while
   `restored` reports true. Direction: capture the target's bytes AND mode at the very start of the
   control, before any verifier run — that is the state FR-05 promises to return to.
